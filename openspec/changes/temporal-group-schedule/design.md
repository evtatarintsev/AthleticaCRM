## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь только то, что нужно для объяснения подхода.

Текущее состояние, формирующее решения:

- `schedule_slots` уже имеет первичный ключ `id UUID DEFAULT uuidv7()`, но `DbGroup.save()` делает `DELETE FROM schedule_slots WHERE group_id = ...` и вставляет слоты заново. Идентификатор пересоздаётся при каждом сохранении группы, поэтому ссылаться на него нельзя.
- Поэтому занятие ссылается на слот суррогатно: `origin_day_of_week TEXT` + `origin_start_time TIME` + `origin_date DATE` и частичный уникальный индекс `uq_sessions_generated`. Несовпадение типов (`schedule_slots.day_of_week` — PG-enum, `sessions.origin_day_of_week` — `TEXT`) — прямой след этого обхода.
- `generateSessions` — цикл по дням на Kotlin с отдельным `INSERT` на итерацию, вызывается из четырёх мест с разными границами.
- PostgreSQL 18 в проде (`postgres:18-alpine3.23`) и в тестах (TestContainers `postgres:18`). `CREATE EXTENSION` в миграциях уже применяется (`pg_trgm` в `0062`).
- Проект не в проде. Совместимость данных и API не требуется.

## Goals / Non-Goals

**Goals:**

- Один механизм материализации занятий вместо четырёх, с одним владельцем инварианта.
- Инварианты расписания держит схема БД, а не дисциплина вызывающего кода.
- Сверка расписания и занятий — множественные операции в SQL, а не цикл по датам в приложении.
- Забыть фильтр по времени при чтении расписания должно быть невозможно по конструкции типа, а не по невнимательности.

**Non-Goals:**

- Материализованные (событийные) проекции. Чтение остаётся синхронным SQL по таблицам записи, как и в остальном проекте.
- Обобщённая темпоральность как инфраструктура. Период действия вводится только для слотов расписания; тарифы, состав тренеров и филиал остаются как есть.
- Bitemporal-модель (отдельно «когда действовало» и «когда мы об этом узнали»). Хранится только период действия.

## Decisions

### Слот — версия правила с полуоткрытым периодом

Слот перестаёт быть редактируемой строкой и становится версией: изменение закрывает текущую версию и открывает новую. Период хранится как `daterange` и трактуется как `[from, to)` — `to` есть первый день, когда версия уже не действует.

Полуоткрытый интервал выбран потому, что «поменять с 1 марта» записывается одной и той же датой в обе версии: `S1.to = '2026-03-01'`, `S2.from = '2026-03-01'`. Ни зазора, ни пересечения, ни арифметики ±1 дня. Классические ошибки в темпоральных данных берутся из закрытых интервалов, где «последний день действия» и «первый день новой версии» — разные значения, которые надо согласовывать вручную.

`daterange` вместо двух колонок `valid_from`/`valid_to` — потому что конвенцию полуоткрытости тогда держит тип, а не договорённость, и потому что он даёт операторы `@>` и `&&`, без которых следующее решение невозможно.

Рассмотрено и отклонено: **версионирование расписания целиком** (таблица версий, слоты принадлежат версии). Концептуально аккуратнее — «расписание на неделю» есть единая вещь из единого языка. Но каждая версия дублирует неизменившиеся слоты, а занятие вынуждено ссылаться на пару «версия + слот внутри неё», то есть композитный ключ возвращается. Слот с собственным периодом даёт занятию односоставную ссылку и позволяет менять один слот, не трогая остальные.

### Пересечение версий делает непредставимым БД

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE schedule_slots ADD CONSTRAINT no_overlapping_slot_versions
    EXCLUDE USING gist (
        group_id    WITH =,
        day_of_week WITH =,
        start_time  WITH =,
        validity    WITH &&
    );
```

Две версии одного слота, действующие одновременно, — главная опасность версионирования, и она молчаливая: расписание начинает показывать дубли, а сверка материализует два занятия на одну дату. Exclusion constraint делает это состояние физически невозможным.

Это тот же приём, что предписан в CLAUDE.md для smart constructor, применённый к схеме: инвариант проверяется при записи, а не в каждом callsite.

Рассмотрено и отклонено: **проверка пересечений в коде перед вставкой**. Требует либо блокировки, либо гонки между проверкой и вставкой, и повторяется в каждом новом пути записи.

Чего этот constraint сознательно **не** ловит:

- Два слота с разным временем начала в один день — это законно, группа может заниматься в понедельник дважды.
- Пересечение занятий по часам в одном зале (двойное бронирование) — самостоятельный бизнес-инвариант, вынесен из скоупа.
- Дубли внутри одного входного набора слотов — приходят одним запросом до вставки, проверяются валидацией запроса.

### Стабильный `SlotId` и разделение identity / attributes

Занятие ссылается на версию слота: `sessions.origin_slot_id`. Три колонки `origin_*` схлопываются в две, уникальность генерации становится `(origin_slot_id, origin_date)`.

Отсюда поля сгенерированного занятия делятся на два класса, и это разделение определяет всю логику сверки:

```
  IDENTITY -- какое это занятие
      origin_slot_id, origin_date
      изменилось -> набор занятий другой -> удалить и создать

  ATTRIBUTES -- как оно выглядит
      start_time, end_time, hall_id, состав тренеров
      изменилось -> набор тот же -> обновить на месте
```

Со стабильным `SlotId` время начала переезжает из identity в attributes: сдвиг занятия с 10:00 на 11:00 обновляет существующие занятия, а не пересоздаёт их. При суррогатном ключе это было невозможно, потому что время начала было частью ключа.

Побочно исчезает залипание отменённых занятий: новая версия слота получает новый `SlotId`, поэтому ключ не переиспользуется и «удалили слот, вернули обратно» работает.

### Расписание отделяется от группы

`Group.schedule: List<ScheduleSlot>` означает неявное «сейчас», а с периодами списка слотов без указания даты не существует. `Group` теряет поле расписания, `DbGroup.save()` перестаёт трогать `schedule_slots` — сегодня переименование группы стирает и пересоздаёт её расписание, что с историей означало бы её уничтожение.

Интерфейс расписания не содержит метода, возвращающего слоты без момента времени:

```kotlin
interface GroupSchedule {
    /** Слоты группы, действующие на [date]. */
    suspend fun slotsOn(groupId: GroupId, date: LocalDate): List<ScheduleSlot>

    /** Слоты, период действия которых пересекает [from]..[to]. */
    suspend fun slotsDuring(groupId: GroupId, from: LocalDate, to: LocalDate): List<ScheduleSlot>

    /** Устанавливает расписание группы начиная с [effectiveFrom]. */
    suspend fun setFrom(groupId: GroupId, effectiveFrom: LocalDate, slots: List<NewSlot>)
}
```

Это главная защита от типовой ошибки темпоральных данных — забытого фильтра по времени. Фильтр нельзя пропустить, потому что его нечем пропустить.

Период — value-тип со smart constructor по образцу `CustomFieldKey` из CLAUDE.md: приватный конструктор, фабрика, возвращающая `Either<DomainError, Validity>`, инвариант `to == null || to > from`. Состояние `to <= from` не создаётся ни в коде, ни через десериализацию; тот же инвариант дублируется `CHECK` в схеме.

Побочно `POST /groups/edit` перестаёт принимать расписание. Баг молчаливой смены расписания не чинится — он исчезает вместе с полем, которого больше нет.

### «С даты D и навсегда»

Установка расписания с даты D заменяет всё, что действует начиная с D, включая ранее запланированные изменения. Версии, начинающиеся в D или позже, удаляются; версии, пересекающие D, обрезаются до D.

Рассмотрено и отклонено: **«с D до следующего запланированного изменения»**. Темпорально аккуратнее, но для человека это сюрприз — заданное расписание само откатится в дату, о которой он забыл. Выбранное правило соответствует тому, что человек имеет в виду, говоря «теперь будет так». Ответственность за предупреждение переносится в UI: при наличии более позднего запланированного изменения интерфейс сообщает, что оно будет отменено.

Рассмотрено и отклонено: **ограничение «не более одного отложенного изменения»**. Проще в реализации, но создаёт искусственное состояние, которое надо объяснять пользователю и снимать позже.

Удаление ещё не вступившей в силу версии — единственный случай, когда слот вообще удаляется. Если её даты уже попали в горизонт и по ним есть ручные правки, сработает `RESTRICT` и потребуется явное открепление занятий от слота. Это редкий угол, а не основной поток.

### `ON DELETE RESTRICT` для ссылки занятия на слот

```sql
origin_slot_id UUID REFERENCES schedule_slots (id) ON DELETE RESTRICT
```

Рассмотрено и отклонено: **`ON DELETE CASCADE`**. Удаление слота унесло бы вместе с ним всю историю занятий этого слота — включая проведённые полгода назад и посещаемость, когда она появится. Чтобы этого не происходило, перед каждым удалением пришлось бы открепить всю историю, после чего каскаду нечего удалять. Получается referential action, который при исправной работе кода не срабатывает никогда, а если сработал — произошла катастрофа.

Рассмотрено и отклонено: **`ON DELETE SET NULL`**. Молча разрешает состояние «слот удалён, нетронутые занятия остались сиротами». Прецедент в этой же таблице уже есть: `sessions.group_id REFERENCES groups (id) ON DELETE SET NULL`, при том что `toSessionRow()` читает `group_id` как ненулевой. Не стреляет только потому, что удаления групп в приложении нет.

`RESTRICT` превращает обе ошибки из состояния данных в исключение: забыл удалить нетронутые или открепить остальные — транзакция падает на FK. Порядок операций при удалении версии слота:

```sql
DELETE FROM sessions WHERE origin_slot_id = :slot AND <нетронутое>;
UPDATE sessions SET origin_slot_id = NULL WHERE origin_slot_id = :slot;
DELETE FROM schedule_slots WHERE id = :slot;
```

### Колонка `is_manual` удаляется

`is_manual` записывается ровно в одном месте — `DbSessions.new`, как `originDayOfWeek == null` — и никогда не обновляется. Это денормализованная копия «происхождение пустое», то есть два поля, обязанных согласовываться по договорённости. После введения `origin_slot_id` признак выводится как `origin_slot_id IS NULL`, и рассинхрон становится невозможен.

Занятие из удалённой версии слота и занятие, созданное вручную, после открепления неразличимы по поведению: не управляются правилом, сверка их не трогает, редактируются свободно. Два состояния с одинаковым поведением сводятся к одному; происхождение при необходимости восстанавливается по журналу аудита.

`is_rescheduled` из той же семьи денормализаций, но выводить его в SQL неудобно, а предстоящий переход от строкового `status` к состояниям перетасует эти признаки целиком. Оставлен как есть, зафиксирован как отдельный долг.

### Сверка синхронна и множественна

Сверка выполняется в транзакции изменения, а не через outbox. Событие обязано быть асинхронным, иначе outbox не нужен, а значит между «расписание сохранено» и «занятия соответствуют расписанию» всегда есть окно, в которое попадает ответ на тот же запрос. Прямой вызов этого окна не создаёт, а инвариант становится проверяемым в тесте сразу после коммита.

Удаляются `GroupCreated`, `GroupScheduleChanged` и оба обработчика. Сама шина `domain/events/` остаётся — она используется messaging.

Вся сверка — четыре множественные операции, и ни одной из них не нужен цикл по группам: таблица слотов теперь содержит всё, включая период действия, поэтому «какие занятия должны существовать» полностью выразимо в SQL.

```sql
-- 1. создать недостающие
INSERT INTO sessions (id, org_id, group_id, date, start_time, end_time, hall_id,
                      origin_slot_id, origin_date)
SELECT uuidv7(), ss.org_id, ss.group_id, d::date, ss.start_time, ss.end_time, ss.hall_id,
       ss.id, d::date
  FROM schedule_slots ss
  CROSS JOIN LATERAL generate_series(
        GREATEST(:today, lower(ss.validity)),
        LEAST(:horizon, COALESCE(upper(ss.validity) - 1, :horizon)),
        interval '1 day') AS d
 WHERE ss.org_id = :orgId
   AND isodow_of(ss.day_of_week) = extract(isodow FROM d)
    ON CONFLICT (origin_slot_id, origin_date) DO NOTHING;

-- 2. подтянуть атрибуты у нетронутых
UPDATE sessions s
   SET start_time = ss.start_time, end_time = ss.end_time, hall_id = ss.hall_id
  FROM schedule_slots ss
 WHERE s.origin_slot_id = ss.id AND s.date >= :today AND <нетронутое>
   AND (s.start_time, s.end_time, s.hall_id)
       IS DISTINCT FROM (ss.start_time, ss.end_time, ss.hall_id);

-- 3. убрать нетронутые, вышедшие за период своего слота
DELETE FROM sessions s USING schedule_slots ss
 WHERE s.origin_slot_id = ss.id AND s.date >= :today AND <нетронутое>
   AND NOT (ss.validity @> s.origin_date);

-- 4. синхронизировать состав тренеров у нетронутых
```

Случаи «слот удалён из расписания» и «дата вышла за период слота» слились в шаг 3 — отдельной ветки удаления больше нет. Диапазон `generate_series` вырождается в пустой сам собой, если период слота не пересекает окно, поэтому «слот ещё не начал действовать» и «слот уже закончился» не требуют отдельных условий.

Предикат нетронутости:

```
origin_slot_id IS NOT NULL
AND status = 'scheduled'
AND is_rescheduled = false
AND is_employee_assignment_overridden = false
AND notes IS NULL
```

Ежедневная сверка по всей организации — те же четыре операции, а не `группы × слоты × 90` round-trip'ов, как сегодня.

`day_of_week` остаётся PG-enum; для сопоставления с `extract(isodow FROM d)` вводится `IMMUTABLE`-функция `isodow_of(day_of_week) RETURNS int`. Альтернатива — перевести колонку в `smallint` 1–7 — отклонена: enum читаем в SQL и защищает от значений вне диапазона, а `IMMUTABLE`-функция пригодна для индекса.

### Горизонт зажат внутри сверки

Горизонт — 3 месяца, вычисляется от сегодняшнего дня внутри самой сверки. Никакой вызывающий код не передаёт границу материализации: параметр `to` у сверки отсутствует как таковой. Это закрывает исходную уязвимость у источника, а не только на входе конкретного роута.

Отдельно ограничивается и запрос чтения: `SessionListRequest.from/to` становятся обязательными, длина периода ограничена сверху.

### Размещение кода

```
  ДО                                          ПОСЛЕ

  usecases/sessions/                          domain/groups/
    generateSessions()        ---+              GroupSchedule    интерфейс
    updateGroupSchedule()     ---+              DbGroupSchedule  реализация
    updateGroupEmployees()    ---+              ScheduleSlot     сущность с SlotId
    sessionList()             --------+         Validity         value-тип
                                      |
  domain/sessions/Sessions.kt         |       domain/sessions/
    futureScheduledBySlot()   ---+    |         ScheduleSync     интерфейс, один метод
    syncFutureEmployeesFrom() ---+    |         DbScheduleSync   реализация, 4 SQL
                                      |         Sessions         new/list/listAll/byId
  Application.kt                      |
    generateSessionsDaily()   ---+    +-----> read/sessions/
                                                SessionListView  проекция
```

Оба удаляемых метода `Sessions` — симптом отсутствующего объекта: они существовали только потому, что логика сверки жила снаружи и была вынуждена дотягиваться внутрь репозитория. Их SQL переезжает в `DbScheduleSync` приватными запросами.

`ScheduleSync` имеет один публичный метод и три вызова: создание группы, изменение группы, ежедневный тик. Четыре пути материализации схлопываются в одну операцию с тремя триггерами. Одна точка входа, вызываемая после любой мутации группы, снимает целый класс ошибок «забыли синхронизировать» — именно точечность породила баг `POST /groups/edit`.

`sessionList` перестаёт быть usecase: он ничего не меняет, поэтому по правилам CLAUDE.md переезжает в `read/` проекцией.

## Risks / Trade-offs

**Темпоральные данные ошибаются молча.** Не падают, а показывают не то расписание. → Закрывается конструкцией, а не дисциплиной: `daterange` держит полуоткрытость, exclusion constraint — непересечение версий, интерфейс без метода «все слоты» — обязательность момента времени, `Validity` со smart constructor — корректность периода.

**Граничные даты конструкцией не закрыть.** → Обязательные тесты: смена ровно на дату занятия, смена между занятиями, закрытие расписания в ноль, отложенное изменение внутри горизонта и за ним, возобновление после перерыва, слот с периодом целиком в прошлом и целиком за горизонтом.

**Тестов на генерацию занятий сегодня ноль.** Изменение приземляется на пустое покрытие, регрессию сравнивать не с чем. → Тесты на сверку пишутся до правки существующего поведения, а не после.

**Две проекции чтения достают слоты без фильтра по дате.** `DbGroupListView` и `DbGroupDetailView` собирают слоты подзапросом по `group_id`; после введения периодов они молча начнут показывать все версии сразу. Защита интерфейсом на SQL в проекциях не распространяется. → Правятся явно, каждая покрывается тестом с группой, у которой есть закрытая версия слота.

**Соблазн распространить паттерн.** Тот же аргумент немедленно применим к составу тренеров, тарифам и филиалу. → Признак того, что паттерн верен, но брать всё сразу нельзя; вынесено в Non-Goals.

**Объём.** Изменение крупнее исходной задачи «убрать генерацию из чтения»: темпоральная схема, отделение расписания от группы, новый endpoint, правка проекций, удаление мёртвого кода. → Разделить на два изменения технически можно, но первое пришлось бы делать поверх суррогатной идентичности слота и затем переделывать под `SlotId`. Дешевле одним заходом.

**Пересечение с активным изменением `add-schedule-week-view`.** Оно явно отложило вынос генерации из чтения и ограничило период запроса 62 днями, а также трогает выборку занятий по филиалу. → Порядок слияния согласуется до начала реализации; при слиянии `add-schedule-week-view` первым его ограничение периода сохраняется, а материализация в границах запроса снимается этим изменением.

**`RESTRICT` требует явных шагов при удалении версии слота.** Забытый шаг роняет транзакцию. → Это осознанный размен: громкая ошибка вместо молчаливой потери данных или молчаливого мусора. Путь единственный и покрывается тестом.

## Migration Plan

Проект не в проде, поэтому миграция данных — формальность, а не этап.

1. Миграция Liquibase: `btree_gist`, функция `isodow_of`, `schedule_slots.validity` с заполнением `daterange(<прошлая дата>, NULL)` для существующих строк, exclusion constraint.
2. Миграция Liquibase: `sessions.origin_slot_id` с заполнением по совпадению `(group_id, origin_day_of_week, origin_start_time)`; занятия без совпадения остаются с `NULL`; перестройка уникального индекса на `(origin_slot_id, origin_date)`; удаление `origin_day_of_week`, `origin_start_time`, `is_manual`.
3. Замена `sessions.group_id ON DELETE SET NULL` на `ON DELETE RESTRICT` заодно — колонка читается как ненулевая, текущее поведение сломало бы чтение.

Откат — возврат коммита вместе с down-миграциями changeset'ов. Внешних потребителей API нет.

## Open Questions

- **Связывать ли версии одного слота явной ссылкой.** Для сверки и для занятий она не нужна: каждое занятие указывает на конкретную версию. Понадобиться может интерфейсу, если он захочет показывать «история этого слота» одной лентой вместо набора независимых записей. Добавляется отдельной колонкой без изменения остального.
- **Как подписывать запланированное изменение на карточке группы.** Что именно показывать — дату, дельту слотов или и то и другое — вопрос интерфейса, не меняющий контракт: сведения о будущих версиях проекция отдаёт в любом случае.
