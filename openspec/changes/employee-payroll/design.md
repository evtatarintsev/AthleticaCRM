## Context

Факты, от которых считается зарплата, уже есть в master:

- `attendance-journal`: занятие закрывается («проведено») только с заполненным журналом. Отметка
  принимает значения «пришёл» или «не пришёл». Метки — справочник организации («опоздал»,
  «болеет», «пробное» и т. п.). Отметку закрытого занятия можно править, проведённое занятие нельзя
  отменить.
- `membership-debits`: за «пришёл» списывается одно занятие с подобранного абонемента, за
  «не пришёл» не списывается. Посещение без списания — неоплаченное занятие, его можно позже
  погасить.
- `session_employees`: фактический состав тренеров занятия, включая ручную замену.
  `group_employees`: тренеры группы.
- Абонемент хранит `price` и `sessions_total` (`null` — безлимит).

Ни кассы, ни учёта расходов школы в продукте нет. `orgbalance` — баланс организации у сервиса, а
не касса школы.

Подход выбран после разбора МойКласс и AlfaCRM. У них есть ставка педагога с вариантами для
групп, оплата за время или посещения, прогрессия по числу учеников, процент от доходности занятия,
ведомость с зарплатным балансом, начисления, премии, штрафы и выдачи. Самая частая ошибка
пользователей там — шкала с дырой, когда занятие получает 0 ₽ без предупреждения.

## Goals / Non-Goals

**Goals:**

- Управляющий настраивает ставку за минуту. Типичная школа меняет 2–3 числа и не открывает особые
  случаи.
- Каждая сумма объяснима: строка ведомости показывает, по какой версии ставки и из каких чисел она
  получилась.
- Утверждённая ведомость не меняется от поздних правок посещаемости и ставок.
- Расчёт тестируется без БД.

**Non-Goals:**

- Налоги, взносы, МРОТ, формы занятости и выгрузка в бухгалтерию.
- Касса и расходы школы: выплата не создаёт расхода, потому что модуля расходов нет.
- Процент от продаж абонементов, KPI, бонус за конверсию пробных. Это ставки администраторов и
  менеджеров, отдельный change.
- Смены администраторов и план-график. Оклад начисляется за месяц без учёта смен.
- Компенсация за позднюю отмену занятия. Отменённое занятие не оплачивается.
- Деление процента между несколькими тренерами занятия. Каждый тренер получает по своей ставке.
- Прогноз заработка по будущим занятиям и автоматические корректировки за утверждённые периоды.
  Это этап 2, когда появится опыт эксплуатации.

## Decisions

### Ставка — пресет над общей моделью

Пользователь выбирает один из четырёх способов, а не собирает формулу из компонентов:

| Способ | Формула за занятие |
|---|---|
| За занятие | `S` |
| За занятие и учеников | `S + P × n`, затем гарантия |
| Процент от стоимости посещений | `p% × Σ стоимость посещений`, затем гарантия |
| Оклад | за месяц, не за занятие |

Здесь `n` — учтённые ученики занятия. В домене это одна модель: `PayTerms` из базовой суммы за
занятие, части за учеников (`StudentPart`: нет / за каждого / шкала), процента, гарантии и особых
случаев. Пресет — способ заполнить и показать эту модель. Свободные формулы и произвольный набор
компонентов отклонены: их нельзя объяснить в расшифровке и нельзя проверить на полноту при
сохранении.

`StudentPart` — sealed-тип:

- `None`;
- `PerStudent(rate)`;
- `TierPerStudent(tiers)`: всё занятие по ставке ступени, в которую попало `n`;
- `TierFixed(tiers)`: сумма за занятие по ступени.

Ступени — smart constructor `Tiers`. Первая ступень начинается с 1, следующая продолжает
предыдущую без разрывов, последняя не имеет верхней границы. Шкалу с дырой невозможно создать, а не
только проверить в UI. Занятие с `n = 0` шкалой не оценивается, для него действует правило пустого
занятия.

### Кто считается учеником

Учтённый ученик — участник проведённого занятия с отметкой «пришёл». Особые случаи ставки
уточняют это правило:

- **Метки.** Для метки отметки «пришёл» задаётся: «как обычный ученик» (по умолчанию), «не
  учитывать» или «своя цена за ученика». Пробные и бесплатные посещения организация обозначает
  метками. Отдельного понятия «пробное занятие» не вводим. Если у отметки несколько меток с разными
  правилами, побеждает самое ограничивающее: «не учитывать», затем «своя цена», затем «как
  обычный».
- **Неоплаченные посещения** (без списания на момент расчёта): «учитывать» (по умолчанию) или «не
  учитывать». Погашение долга после утверждения ведомости её не меняет.
- **Пустое занятие** (учтённых учеников 0): «платить базовую сумму» (по умолчанию), «не платить»
  или «своя сумма». Гарантия к пустому занятию не применяется.

Отметка «не пришёл» не учитывается никогда. В модели списаний пропуск не списывается, поэтому
вариант МойКласс «пропуск со списанием считать посещением» у нас не имеет смысла.

### Стоимость посещения для процентной ставки

Стоимость посещения равна стоимости одного занятия абонемента, с которого оно списано:

- абонемент с числом занятий: `price / sessions_total`;
- безлимит: `price / расчётное число занятий`. Расчётное число задаётся в тарифе, копируется в
  абонемент при выдаче и в абонементе правится;
- неоплаченное посещение стоит 0 ₽.

`price` абонемента — фактическая цена выдачи, то есть уже со скидкой. Пересчёт по фактическому
числу посещений безлимита отклонён: он меняет суммы задним числом в уже утверждённых месяцах.
Безлимит без расчётного числа даёт посещению стоимость 0 ₽, и ведомость показывает это
предупреждением.

### Варианты для групп

У ставки есть основные условия и необязательные варианты. Вариант — набор групп и свои условия
(`PayTerms`). Занятие группы из варианта оплачивается по варианту, остальные — по основным
условиям. Группа входит не более чем в один вариант ставки. Поэтому для любого занятия ровно один
набор условий, и не нужен приоритет совпадений, как в AlfaCRM, или запрет на непокрытые группы,
как в МойКласс.

### Версии и назначение

Ставка — агрегат `PayRate` с версиями. Версия хранит условия и дату начала действия. Изменение
ставки создаёт новую версию, старые не редактируются. Сотруднику назначается не более одной ставки
на дату. Назначение тоже версионируется датой начала. Для занятия берутся назначение и версия
ставки, действующие на дату занятия. Так же устроено расписание (`0064-temporal-schedule-slots`).

Оклад начисляется пропорционально календарным дням месяца, в которые действовали назначение и
версия.

### Ведомость

Агрегат `PayrollStatement` — одна ведомость на организацию и месяц (уникальность в БД).
Пересечений периодов и двойного начисления, возможного в МойКласс, нет по построению.

Решение «одна ведомость на организацию с фильтром по филиалу, а не ведомость на филиал» принято
потому, что тренер может вести занятия в разных филиалах. При ведомости на филиал его заработок и
аванс разъехались бы на две ведомости. Филиал занятия известен по группе, поэтому фильтр и итоги по
филиалу остаются доступны.

Состав ведомости:

- **Строки начислений** (авто): одна строка на пару «занятие × тренер» и одна строка оклада на
  сотрудника. Строка хранит снимок: id версии ставки, применённые условия, `n`, суммы по частям,
  итог, флаги («гарантия», «пустое занятие», «стоимость безлимита неизвестна»).
- **Ручные правки**: новая сумма и обязательная причина, ключ — пара «занятие × тренер».
- **Корректировки**: премия или штраф, сумма, обязательный комментарий.
- **Выплаты**: дата, сумма, способ (наличные или перевод), комментарий.

Статусы: «черновик» → «утверждена» → (возврат) «черновик».

- **Пересчёт черновика** удаляет и заново строит только авто-строки. Правки, корректировки и
  выплаты сохраняются. Правка, у которой пропала пара «занятие × тренер», остаётся в ведомости
  помеченной «не применена».
- **Утверждение** фиксирует строки. Пересчёт, правки и корректировки после него недоступны.
- **Возврат в черновик** требует `CAN_MANAGE_PAYROLL` и пишется в аудит.
- **Выплаты** доступны в любом статусе, чтобы аванс выдавался до утверждения.

Предупреждения ведомости вычисляются при чтении, а не хранятся:

- незакрытые прошедшие занятия месяца;
- тренеры проведённых занятий без назначенной ставки;
- безлимиты без расчётного числа;
- для утверждённой ведомости — занятия, у которых после утверждения изменились отметки или состав
  тренеров.

### Расчёт

`PayrollCalculation` — чистая функция:

```
(facts: PeriodFacts, rates: RateVersionsByEmployee) -> List<AccrualLine>
```

Факты собирает `read/payroll/PayrollFactsView` одним SQL на период: проведённые занятия, тренеры,
отметки «пришёл» с метками, списание и стоимость посещения. Проекция не импортирует `domain/`.
Ставки читает `PayRates`. Предпросмотр ставки при сохранении вызывает ту же функцию с черновой
версией на фактах прошлого месяца. Расчёт покрывается таблицей unit-тестов без БД, DB-тесты
проверяют только сбор фактов.

Деньги — только `Money` в валюте организации. Округление до минорной единицы выполняется один раз,
на итоге строки. Процент считается от суммы стоимостей посещений занятия, а не по каждому
посещению.

### Права и видимость

- `CAN_MANAGE_PAYROLL`: ставки, назначения, ведомости, правки, корректировки, утверждение, возврат,
  выплаты.
- `CAN_VIEW_PAYROLL`: чтение ставок и всех ведомостей без изменения.
- Без этих прав сотрудник видит только свои строки, корректировки и выплаты в любой ведомости,
  вместе с её статусом. Чужие суммы ему не отдаются.

## Risks / Trade-offs

- **Правка посещаемости после утверждения не попадает в зарплату автоматически.** Это осознанно:
  утверждённая ведомость неизменна. Риск снижают предупреждение в утверждённой ведомости и
  корректировка в следующей. Автоматический перенос разницы — этап 2.
- **Безлимит без расчётного числа даёт 0 ₽ в процентной ставке.** Риск снижает предупреждение.
  Для тарифов-безлимитов поле становится обязательным при создании и правке. Уже выданные
  абонементы заполняются из тарифа миграцией, если тариф указан.
- **Несколько тренеров на занятии получают каждый полную ставку.** Для процентной ставки это
  переплата, если школа ожидает деления. Деление — отдельное решение, когда появится запрос.
- **Пересчёт черновика после смены ставки меняет суммы без явного действия.** Это поведение
  черновика по определению. Предпросмотр при сохранении ставки показывает разницу заранее.
