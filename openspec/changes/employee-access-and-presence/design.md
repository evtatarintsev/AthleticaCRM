# Design

## Context

- `employees.is_active` ставится `false` при создании и `true` в `invite()` (`send-access`)
  вместе с `user_id`. Флаг проверяется при входе и refresh (`DbAuth`), в `UserProfile`,
  `DueMemberships`, `DbEmployees.activeIdsWithAccessTo`, `OrgSearch`.
- `contextFromRequest` на каждом запросе загружает сотрудника (`employees.byId`) в своей
  транзакции, но флаг не проверяет: отключённый сотрудник работает до истечения access-токена
  (15 минут). Ошибка в `contextFromRequest` сейчас превращается в исключение — HTTP 500.
- Веб при редактировании шлёт `allBranchesAccess: employee.allBranchesAccess`
  (`EmployeeSheet.tsx`), так что у сотрудника с флагом `true` выбранные филиалы игнорируются;
  это прямо закреплено в спеке — меняем её (см. delta `web-client/employees`).
- Права на управление сотрудниками в системе нет: редактировать сотрудников может любой
  сотрудник организации. Блокировка следует этому же правилу.
- Сервер запускается одним инстансом, Redis нет.

## Goals / Non-Goals

**Goals:**
- Статусы из спеки `employee-access` без хранимого enum.
- Блокировка действует со следующего запроса.
- Учёт активности без записи в БД на каждый запрос.

**Non-Goals:**
- Отдельное право «управление сотрудниками» — отдельное изменение.
- Отзыв выданных refresh-токенов, принудительный выход из открытых вкладок в реальном времени
  (вкладка получит 401 на следующем запросе).
- Живое обновление «в сети» без перезапроса (websocket, polling чаще обычного).
- Хранение даты именно входа по паролю — «последняя активность» её заменяет.

## Decisions

### Данные: `blocked_at` и `last_seen_at` вместо `is_active`

`employees.blocked_at TIMESTAMPTZ NULL`, `employees.last_seen_at TIMESTAMPTZ NULL`; `is_active`
удаляется. «Может работать в системе» = `user_id IS NOT NULL AND blocked_at IS NULL` — этим
условием заменяется `is_active` во всех запросах. Колонки в `employees`, а не в `users`:
статус и активность относятся к сотруднику организации.

Статус вычисляется в read-проекциях (`DbEmployeeListView`, `DbEmployeeDetailView`):
`blocked_at` → BLOCKED, иначе нет `user_id` → NO_ACCESS, иначе нет `last_seen_at` → INVITED,
иначе ACTIVE. В `shared` — `enum class EmployeeAccessStatus`; схемы получают `status`,
`lastSeenAt: Instant?`, `online: Boolean` вместо `isActive`.

`blocked_at` вместо булева флага: дата блокировки пригодится в карточке и журнале, стоит столько же.
Хранимый enum отвергнут: «не входил/активен» производны от `last_seen_at`, хранить их — значит
синхронизировать два источника правды.

### «В сети» считается в SQL с `now` из запроса

`online = blocked_at IS NULL AND last_seen_at > :now - interval '5 minutes'`. `now` передаётся
в `XxxQuery` из routes (правило слоя `read/`), чтобы сценарии тестировались по времени. Порог —
константа в проекции. Сравнение на клиенте отвергнуто: часы браузера могут расходиться с сервером.

### Активность: `EmployeePresence` — throttle в памяти, синхронная запись

```
contextFromRequest (своя транзакция, сотрудник уже загружен)
   |
   v
presence.touch(employeeId, now)
   |-- lastWritten[id] >= now - 1 мин --> ничего (обычный путь)
   '-- иначе --> UPDATE employees SET last_seen_at = :now WHERE id = :id
                 lastWritten[id] = now
```

`EmployeePresence` — класс с `ConcurrentHashMap<EmployeeId, Instant>`, создаётся в `Di.kt`,
передаётся в `contextFromRequest`. Запись идёт в транзакции `contextFromRequest`, а не в транзакции
бизнес-запроса: откат бизнес-ошибки не откатывает активность. После рестарта карта пустая — первый
запрос каждого сотрудника пишет сразу, данных не теряется.

Альтернативы:
- UPDATE на каждый запрос — лишняя запись на каждый запрос.
- Буфер в памяти + фоновый сброс раз в минуту — та же нагрузка на БД (≤1 запись на сотрудника
  в минуту), но нужна фоновая задача, сброс при остановке, потеря последней минуты при падении,
  а проекции видят БД с отставанием.
- Redis — новая инфраструктура ради одного поля при одном инстансе.

Гонка двух параллельных запросов одного сотрудника даёт максимум два UPDATE — допустимо. При
нескольких инстансах решение продолжает работать (каждый ограничивает частоту сам).

### Блокировка проверяется в трёх местах

- Вход и refresh (`DbAuth.verifyCredentials`, `userById`): условие `is_active = true` заменяется
  на `e.blocked_at IS NULL` (наличие `user_id` уже гарантирует JOIN).
- `contextFromRequest`: загруженный сотрудник с `blockedAt != null` → ответ 401, как при
  недействительном токене. Ошибка моделируется отдельным `AppError` (`EmployeeBlocked`), который
  `StatusPages` переводит в 401; фронт уже обрабатывает 401 выходом на экран входа.

Проверка в `jwt { validate }` отвергнута: это второй запрос к БД на каждый запрос, а сотрудник и
так загружается в `contextFromRequest`.

### Доменная модель

`Employee` получает `blockedAt: Instant?` и команды `block()` / `unblock()` (CQS: глаголы, `Unit`).
`block()` отклоняет владельца (`EMPLOYEE_OWNER_CANNOT_BE_BLOCKED`) и самого себя
(`EMPLOYEE_CANNOT_BLOCK_SELF`); повторная блокировка не меняет `blocked_at`. `AuditEmployee`
логирует обе команды. `invite()` больше не трогает флаг активности — только `user_id` и email;
повторный `invite()` при наличии `user_id` отклоняется доменной ошибкой, а не падением на
`users.new`. `last_seen_at` в агрегат не входит: это не бизнес-состояние, им владеет
`EmployeePresence`.

Маршруты: `POST /employees/block`, `POST /employees/unblock` с `{ employeeId }` в теле.

### Веб: режим «все филиалы» и выбор

Форма получает признак `branchesTouched` (подтверждён выбор в панели филиалов). При сохранении:
`allBranchesAccess = employee.allBranchesAccess && !branchesTouched`. Если флаг включён, панель
выбора открывается со всеми филиалами отмеченными — подтверждение без изменений переводит
сотрудника на явный список всех текущих филиалов (новые филиалы ему уже не достанутся); сводка
секции до подтверждения продолжает показывать «Все филиалы». Отдельный флажок «все филиалы»
не добавляется — спека его запрещает.

Относительное время «Был(а) … назад» — через `Intl.RelativeTimeFormat` с локалью из i18n.

Фильтр тренеров в `CreateSessionSheet` меняется с `isActive` на `status !== "BLOCKED"`: тренер без
доступа в CRM может вести занятия (раньше он отфильтровывался — это поведение исправляется).

## Risks / Trade-offs

- [Изменение API ломает старый фронт во время деплоя] → фронт и сервер поставляются одним образом;
  контракты перегенерируются в том же коммите.
- [Миграция теряет смысл `is_active = false` у сотрудников с `user_id`] → такие строки переводятся
  в `blocked_at = now()`, чтобы они не получили доступ после миграции.
- [Сотрудник без `last_seen_at` после миграции показывается «Не входил», хотя входил раньше] →
  при миграции не восстанавливаем: истории нет; статус станет «Активен» после первого запроса.
- [Подтверждение выбора филиалов без изменений лишает сотрудника будущих филиалов] → сводка после
  подтверждения показывает явный список, сохранение требует нажатия «Сохранить».
- [Заблокированный держит refresh-токен] → refresh отклоняется проверкой `blocked_at`, токен
  бесполезен.

## Migration Plan

1. Liquibase-изменение: добавить `blocked_at`, `last_seen_at`; `UPDATE employees SET blocked_at =
   now() WHERE user_id IS NOT NULL AND NOT is_active`; заменить частичный индекс
   `WHERE is_owner AND is_active` на `WHERE is_owner`; удалить `is_active`.
2. Откат: rollback-блок возвращает `is_active = (user_id IS NOT NULL AND blocked_at IS NULL)`.
