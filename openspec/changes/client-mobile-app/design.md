## Context

Мотивация — см. proposal.md. Требования — `specs/client-app-*/spec.md` и `specs/attendance-journal/spec.md`.
Макеты экранов: https://claude.ai/artifact/USGK1UdgF7BxB3kEoDS8ox (строки «Подключение и вход»,
«Приложение клиента», «CRM»; экраны магазина и подключения по QR в макетах есть, в изменение не входят).

Что уже есть и на что опираемся:

- **Аутентификация** только для сотрудников: `JwtConfig` (HMAC256, issuer `athletica-crm`,
  audience `athletica-crm-users`, access + refresh в cookie), провайдер `auth-jwt` в
  `Application.kt`, `EmployeeRequestContext` — вариант `sealed interface RequestContext`
  (есть ещё `SystemRequestContext`, `AdminRequestContext`). Около 86 файлов `domain/`,
  `usecases/` и `routes/` принимают `context(ctx: RequestContext)`.
- **Контакты клиента** — `domain/clientcontacts`: список `ClientContact(type, value)`, нормализация
  `PhoneDigits`, поиск `clientsByPhone(phone)` внутри организации. Замена контактов —
  `ClientContacts.replace(client, contacts)` (полная замена набора). `DbClientContacts.replace` —
  единственное место, которое пишет в `client_contacts`; вызывается из `ClientsRoutes`
  (создание и изменение клиента) и из инструмента ассистента `ClientDrafts`.
- **Клиент**: `birthday: LocalDate?`, архивирование через `ActiveClient.archive()`.
- **Каналы** — `sealed interface ChannelConfig` в `shared` с `addressing`
  (`ByContact(PHONE)` у SMSC/Twilio, `ByBinding` у Telegram-бота), отправка через
  `MessageDispatcher` и `deliveries`, беседа клиента — `conversations`/`messages`, единые
  «Входящие» — `read/messaging/InboxView`.
- **Платежи**: `PaymentGateway` + ЮKassa на **платформенном** магазине Athletica — только для
  пополнения баланса организации (`organization-payment`), вебхук `POST /api/checkout/yookassa`
  вне `authenticate`. `PaymentCreateRequest` без данных чека. Магазинов организаций нет.
- **Деньги клиента** — главная книга (`docs/ledger.md`, `client-payments`, `sales`): двойная
  запись `ledger_transactions`/`ledger_postings`, кассы `cash_accounts` с видом `online`,
  системная статья `client_receipts` («Поступления от клиентов»). Баланс клиента = аванс минус
  долги по продажам. Готовые шаблоны: «Пополнение аванса» (`cash +C, advance -C`) и «Оплата
  кассами и авансом»; выдача абонемента — продажа с позицией, продажа и оплата — одна транзакция.
  Автор продажи и транзакции (`created_by`) допускает `NULL`. Старого журнала
  `client_balance_journal` нет (удалён миграцией 0086).
- **Сессии**: `origin_date`, `origin_start_time`, `is_rescheduled`, `cancelled_at`, `completed_at`
  — хватает для «Перенесено с 10:00» и «Отменено».
- **Задачи** допускают системного автора и отсутствие исполнителя (`tasks`).
- **Мобильного клиента нет.** Модуль `shared` — KMP (пока только `jvm()`), «задел под мобильные
  KMP-клиенты»; прежний `composeApp` (desktop/wasm) удалён, в `settings.gradle.kts` только
  `:server` и `:shared`. `Dockerfile.server` собирает `./gradlew :server:shadowJar`, CI
  (`contracts.yml`) запускает `:server:generateWebContracts` — оба без Android SDK.

## Goals / Non-Goals

**Goals:**
- Клиентский контур полностью отделён от контура сотрудников: отдельные токены, контекст,
  маршруты. Клиентский токен не может вызвать ни один маршрут CRM, и наоборот.
- Данные клиента физически не покидают сервер до подтверждения доступа на устройстве —
  проверка в каждой проекции, а не только в UI.
- Переиспользовать готовое: контакты, беседы и «Входящие», задачи, абонементы, главную книгу,
  шаблон `organization-payment` для платежей.

**Non-Goals:**
- Магазин товаров, запись на разовые занятия, покупка абонемента нового тарифа (только тот же).
- Подключение по QR-коду на месте: требует, чтобы клиент ставил приложение прямо на ресепшене.
  Клиента без даты рождения подключают после того, как администратор её заполнит.
- Брендированные приложения, вход по email, звонок с кодом (flash call) — после первой версии.
- Офлайн-режим приложения; WebSocket — обновление опросом и push.
- Перенос админских действий сотрудника в мобильное приложение.

## Decisions

### 1. Мобильное приложение — Kotlin Multiplatform + Compose Multiplatform

Новый Gradle-модуль `:mobile` (общий код + `androidApp` + `iosApp`), зависит от `:shared`;
в `shared` добавляются таргеты `androidTarget()`, `iosArm64()`, `iosSimulatorArm64()`.
Схемы запросов и ответов, `Money`, ID и правила вроде `ActiveStatus` используются напрямую —
без генерации контрактов, как в `web/`.

Android-плагин требует Android SDK уже на конфигурации проекта, а серверная Docker-сборка и CI
идут без него. Поэтому Android- и iOS-таргеты `shared` и модуль `:mobile` подключаются только
при включённом свойстве Gradle (`athletica.mobile=true` в `gradle.properties` разработчика
мобильного приложения и в мобильном CI). Сборка сервера не меняется.

- *Альтернатива — React Native / Expo:* команда уже пишет web на TS/React, но пришлось бы
  дублировать схемы через генерацию и терять общие доменные правила из `shared`.
- *Альтернатива — нативные Swift + Kotlin:* два кодовых базы на одну команду — дорого.
- Риск: Compose Multiplatform на iOS моложе, чем на Android. Принимаем: экраны простые
  (списки, карточки, формы), без сложной анимации и нативных виджетов.

### 2. Отдельный контур аутентификации клиентов

- Новый JWT-аудиенс `athletica-client-app`, свой провайдер `client-jwt` в `Application.kt`.
  Access-токен 15 минут, refresh — 60 дней, хранятся в защищённом хранилище устройства
  (Keychain / EncryptedSharedPreferences), передаются заголовком `Authorization`, без cookie.
- Refresh-токен привязан к записи устройства `client_app_devices`; завершение сеанса удаляет
  запись → refresh перестаёт работать, а access истекает за ≤15 минут (требование «не позднее
  15 минут» в `client-app-access`).
- Контексты: `ClientAccountContext(accountId, deviceId, lang)` — из токена; у аккаунта нет
  организации (одна учётная запись на все организации). Для запросов по конкретному клиенту
  routes строят `ClientProfileContext(accountId, deviceId, orgId, clientId, currency, lang)` —
  только после проверки доступа (см. п. 4).
- `ClientProfileContext` **не** вариант `sealed interface RequestContext`. Иначе все функции с
  `context(ctx: RequestContext)` (абонементы, сотрудники, каналы, организация, главная книга)
  стали бы по типам вызываемы из клиентских маршрутов, а `actingEmployeeId` молча записывал бы
  клиента в аудит как систему. Клиентский контур вызывает только:
  - проекции `read/clientapp/*` с `context(ctx: ClientProfileContext)`;
  - собственные команды `domain/clientapp/*` (доступы, предупреждения, платежи);
  - существующие команды других доменов (беседы, главная книга, выдача абонемента) — в
    `SystemRequestContext` организации, собранном через `SystemContexts.forOrg`, с аккаунтом
    клиента в данных события аудита.
- *Альтернатива — переиспользовать `users` сотрудников:* смешало бы два мира и права;
  клиентский аккаунт не имеет организации и пароля.

### 3. Модель данных

| Таблица | Суть |
|---|---|
| `client_app_accounts` | аккаунт по номеру: `phone_digits` UNIQUE, `terms_accepted_at`, `terms_version`, `deleted_at` |
| `client_app_devices` | устройство аккаунта: платформа, модель, push-токен, `last_seen_at`, хэш refresh-токена |
| `client_app_codes` | одноразовые коды: хэш кода, `expires_at`, `attempts`, канал доставки; для лимитов частоты |
| `client_app_access` | доступ: `org_id`, `client_id`, `phone_digits`, `status`, `failed_attempts`, `invited_at`, `invite_channel`, `status_changed_at`; UNIQUE (`org_id`, `client_id`, `phone_digits`) |
| `client_app_device_verifications` | подтверждение доступа на устройстве: (`access_id`, `device_id`), время подтверждения, `last_seen_at` по этому доступу |
| `client_app_payments` | платежи клиентов: `org_id`, `client_id`, `account_id`, сумма, назначение, тариф, статус, `external_payment_id`, `ledger_transaction_id`, `sale_id` |
| `client_app_absence_notices` | предупреждения «Не придём»: `session_id`, `client_id`, `access_id`, время |
| `org_payment_shops` | магазин ЮKassa организации: `shop_id`, секрет (зашифрован), `cash_account_id`, система налогообложения, ставка НДС |

Доступ хранит `phone_digits`, а не ссылку на `client_contacts.id`: контакты заменяются целиком
(`replace`), и идентификаторы контактов не стабильны. Синхронизация — в `DbClientContacts.replace`,
в той же транзакции, что и замена: для номеров, которых больше нет, доступ → `отключён` и
удаляются подтверждения устройств; для новых номеров ничего не создаётся (отсутствие строки =
`не приглашён`). Не в отдельном usecase: `replace` вызывается из трёх мест (два маршрута и
ассистент), и путь в обход синхронизации оставил бы старому номеру доступ к данным ребёнка.

Время последней активности для CRM — `client_app_device_verifications.last_seen_at`, обновляется
только запросами по профилю этой организации. `client_app_devices.last_seen_at` — общее для
аккаунта и показывается только в самом приложении: иначе организация видела бы, что человек
пользуется приложением в другой организации.

Настройка «приложение включено» — колонка в `organizations` (`client_app_enabled`), а не
отдельная таблица: одна булева настройка без истории, изменение — через аудит.

Статус доступа — enum `ClientAppAccessStatus` в `shared` (нужен и web, и mobile).
Агрегат `ClientAppAccess` в `domain/clientapp/` с переходами по таблице статусов из
`client-app-access`; недопустимые переходы невыразимы, как у `ActiveClient`/`ArchivedClient`.

### 4. Проверка доступа на каждом запросе — в проекциях

Все проекции `read/clientapp/*` принимают `ClientProfileContext` и в том же SQL соединяются с
`client_app_access` (статус `подключён`) и `client_app_device_verifications` (текущее устройство),
плюс `organizations.client_app_enabled` и неархивный клиент. Нет строки — `CLIENT_NOT_FOUND`
(одинаково для чужого и несуществующего). Это соответствует правилу `read/`: видимость живёт
в проекции. Отдельный «middleware-фильтр» не делаем — проверка в SQL не может разойтись с данными.

### 5. Подтверждение датой рождения и защита от перебора

- Даты сравниваются на сервере; клиенту не возвращается, какая дата совпала, кроме итогового
  списка подключённых профилей.
- Счётчик `failed_attempts` — на доступе, а не на устройстве: смена телефона не даёт новых
  попыток. Успешное подтверждение обнуляет счётчик. Третья неудача подряд → `проверка не
  пройдена` + задача (в одной транзакции), с какого бы устройства она ни была.
- Блокировка закрывает данные на **всех** устройствах аккаунта, включая уже подтверждённые:
  три неверные даты с нового телефона — признак того, что номер сменил владельца.
- Перебор дат с разных аккаунтов невозможен: доступ привязан к номеру, а номер подтверждён кодом.
- Клиента без даты рождения подключить нельзя: приложение просит обратиться к администратору,
  CRM показывает это в карточке и в счётчиках массового приглашения.

### 6. Коды: Telegram Gateway, затем SMS

- Telegram Gateway API (официальная отправка кодов проверки по номеру телефона, не требует бота
  и предварительного контакта). Если Gateway ответил, что доставка невозможна, — сразу SMS.
- SMS — платформенный аккаунт SMS-провайдера (тот же SMSC, что и для каналов организаций, но
  с ключами платформы в `application.conf`), не каналы организации: код — дело платформы.
- Код — 6 цифр, хранится хэшем. Лимиты по `client_app_codes`: 60 с между кодами, 5 в час,
  10 в сутки на номер. С 5 попытками на код это не больше 50 догадок в сутки из миллиона;
  4 цифры при 5 кодах в час без суточного предела давали ~600 догадок в сутки из 10 000.
  Дополнительно лимит по IP на уровне nginx, чтобы ограничить «SMS-накрутку».
- Одинаковый ответ для известного и неизвестного номера — `client-app-access`.

### 7. Приглашения — статус плюс уведомление «по возможности»

Приглашение — это прежде всего смена статуса доступа. Уведомление отправляется через
существующий `MessageDispatcher` по каналам организации с адресацией `ByContact(PHONE)`
(SMSC, Twilio). Telegram-бот организации не подходит: он пишет только по привязке, а не
по номеру. Нет такого канала — приглашение всё равно действует, сотрудник сообщает клиенту
о приложении сам.
Текст — шаблон из i18n с названием организации и ссылкой на установку, без данных клиента.

- *Альтернатива — отправлять приглашения SMS платформы:* расходы платформы на рассылки
  организаций и риск блокировки отправителя за массовые сообщения. Отложено.

### 8. Отключение доступа не трогает сеансы аккаунта

Сеанс (refresh-токен) принадлежит устройству аккаунта, а аккаунт общий для всех организаций.
Поэтому «Отключить» в CRM и все автоматические закрытия доступа (номер удалён, клиент в архиве)
удаляют подтверждения устройств по этому доступу и меняют статус, но не завершают сеансы:
иначе «Динамо» разлогинивала бы маму и из «Волны». Данные закрываются сразу проверкой в SQL
проекций (п. 4). Завершает сеансы только сам человек — из списка устройств или удалением аккаунта.

### 9. Канал «Приложение» в переписке

Новый подтип `ChannelConfig.ClientApp` с `addressing = ByContact(PHONE)`: «Входящие» и выбор
адреса в ответе работают без изменений модели. Встроенная интеграция заводится автоматически
при включении приложения (одна на организацию) и не показывается в списке настраиваемых каналов.
Транспорт канала сохраняет сообщение и ставит push в очередь; доставка «прочитано» —
по отметке клиента. Переписка в приложении — сообщения канала `ClientApp` с адресом номера
аккаунта (фильтр в проекции), поэтому родители не видят переписку друг друга.

### 10. Push — FCM для Android, APNs для iOS

Push-токен приходит при регистрации устройства и обновляется приложением. Отправка — фоновым
обработчиком с повторами (как `MessageDispatcher`), только на устройства с подтверждением доступа
этого клиента. Мёртвые токены (ответ провайдера «unregistered») удаляются.

### 11. Платежи клиентов — магазин ЮKassa организации и главная книга

- Деньги клиента принадлежат организации, поэтому платёж создаётся в её магазине: `shop_id` +
  секретный ключ, ключ хранится зашифрованным (ключ шифрования — в `application.conf`).
- `PaymentGateway` расширяется параметром магазина (сейчас он неявно платформенный), данными
  чека (позиция, НДС, система налогообложения, телефон покупателя — 54-ФЗ) и запросом статуса
  платежа.
- Вебхук — отдельный маршрут `POST /api/checkout/yookassa/org`. Магазины организаций настраивают
  уведомления сами, общего секрета подписи у нас нет, поэтому платёж ищется по
  `external_payment_id` в `client_app_payments`, а перед проводкой статус перепроверяется
  запросом к API ЮKassa с ключом магазина этой организации (телу уведомления не доверяем).
- Учёт — существующими шаблонами главной книги, без нового типа операции. Магазин привязан к
  кассе вида `online`, в которую идут все его оплаты.
- **Пополнение** — шаг 1: в одной транзакции платёж `ожидает` → `зачислен` и «Пополнение аванса»
  (`cash +C, advance -C`) в кассу магазина по статье `client_receipts`, `created_by = NULL`.
- **Покупка того же абонемента** — шаг 1, затем шаг 2 в отдельной транзакции: выдача абонемента
  через существующую выдачу с оплатой при оформлении продажи — продажа на цену тарифа и оплата
  этой суммой с аванса — и платёж → `выполнен`. Если выдача отклонена доменом (тариф или группа
  в архиве, цена изменилась), в той же второй транзакции платёж → `требует внимания` и задача
  «Оплата абонемента без выдачи»; деньги остаются на авансе.
- Вебхук отвечает успехом только после того, как платёж дошёл до конечного статуса. Сбой
  инфраструктуры на шаге 2 → неуспешный ответ, ЮKassa повторяет уведомление, шаг 1 пропускается
  по статусу `зачислен`, повторяется только шаг 2. Ни одна последовательность сбоев не теряет
  деньги и не зачисляет их дважды.
- Операции пишутся в `SystemRequestContext` организации (п. 2): автора-сотрудника нет, в CRM
  они показываются с отметкой «из приложения» по ссылке из `client_app_payments`.

### 12. Маршруты

- `/api/client-app/auth/*` — запрос кода, вход, refresh, выход (без токена, лимиты).
- `/api/client-app/*` — под `client-jwt`: профили, подтверждение, данные, оплата, переписка,
  устройства, удаление аккаунта. Без path-переменных, ID в теле или query — по правилам проекта.
- `/api/client-app-admin/*` — под `auth-jwt` (сотрудники): включение, приглашения, статусы,
  ЮKassa. Права: `CAN_MANAGE_CLIENT_APP` — включение, массовое приглашение, ЮKassa;
  остальное — любой сотрудник организации (как работа с карточкой клиента).

### 13. Удаление аккаунта

Человек удаляет аккаунт в приложении (требование App Store 5.1.1(v) и отзыв согласия по 152-ФЗ).
Удаление завершает все сеансы, удаляет устройства, подтверждения и push-токены, а доступы
аккаунта во всех организациях переводит в `отключён`. Сообщения переписки и платежи остаются
у организаций: это их данные учёта. Запись аккаунта помечается `deleted_at` с обезличенным
номером; повторный вход с тем же номером создаёт новый аккаунт без прежних подтверждений.

## Risks / Trade-offs

- [Посторонний знает дату рождения ребёнка (соседи, родственники)] → защита не абсолютна;
  дополняют её задача администратору и видимость подключённых устройств в карточке.
- [Клиенты без даты рождения не могут подключиться] → в настройках CRM показываем число таких
  клиентов со ссылкой на дозаполнение, в карточке — предупреждение. Подключение по QR на месте
  можно вернуть позже, если дозаполнение не справится.
- [SMS-накрутка через запрос кодов] → лимиты по номеру и IP, Telegram Gateway в приоритете;
  мониторинг расхода SMS.
- [Неверный статус после частичного сбоя оплаты абонемента] → зачисление и выдача разделены,
  при отказе выдачи деньги на авансе и задача; повтор уведомления доводит выдачу; ни один
  сценарий не теряет деньги.
- [Ошибка в налоговых настройках магазина] → чек уйдёт с неверной ставкой НДС; настройку
  делает сотрудник с `CAN_MANAGE_CLIENT_APP`, рядом — подсказка свериться с бухгалтером.
- [Модерация App Store: приложение-«каркас» для многих организаций] → одно приложение
  с одной учётной записью разработчика Athletica, без брендирования под клубы — правило 4.2.6
  не затрагивается. Вход без пароля требует демо-доступа для ревьюера: заводим тестовый номер
  с фиксированным кодом, работающий только в демо-организации. Удаление аккаунта — п. 13.
- [Compose Multiplatform на iOS] → простые экраны; в первой итерации проверяем сборку и
  публикацию iOS раньше, чем пишем все экраны.
- [Android SDK в серверной сборке] → мобильные таргеты за свойством Gradle (п. 1); серверный
  Docker и CI собираются как раньше.

## Migration Plan

1. Миграции БД аддитивные; `client_app_enabled` по умолчанию `false` — у существующих
   организаций ничего не меняется до явного включения.
2. Серверная часть выкатывается раньше приложения; маршруты клиента без включённой
   организации возвращают пустые профили.
3. Приложение — закрытое тестирование (TestFlight, внутренний трек Google Play) на одной
   организации, затем публикация.
4. Откат: выключить приложение в организациях (данные не теряются); маршруты `/client-app/*`
   можно снять с роутинга без отката миграций. Проводки оплат из приложения — обычные операции
   главной книги и при откате остаются.
