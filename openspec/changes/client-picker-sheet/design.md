## Context

Мотивация — в proposal.md. Что уже есть и на что опирается решение:

- `web/src/ui/EditSheet.tsx` — панель справа: вложенность (дочерняя панель сдвигает родительскую влево), защита несохранённых изменений через `reportGuard`, нижняя строка выбора `EditSheetSelection`. Клик мимо панель не закрывает.
- `AddParticipantSheet` в `web/src/sessions/SessionDetailPage.tsx` — фактически уже выбор клиента, но шторкой снизу, без debounce (запрос на каждый символ), с жёстким `limit: 20` и только одиночный.
- `ClientAddToGroupSheet` в `web/src/clients/ClientGroupsSection.tsx` — выбор **группы** для клиента; к выбору клиента отношения не имеет и в этой работе не трогается.
- Сервер: `clients/list` (поиск `name ILIKE`, `limit`/`offset`, `total`, по умолчанию `archived = false`), `clients/add-to-group` и `clients/remove-from-group` принимают `clientIds[]`; повторная запись в группу — no-op (`ON CONFLICT DO NOTHING`). `sessions/journal/add-participant` принимает один `clientId`.
- `GroupDetailResponse.clients` — только `{id, name}`.

## Goals / Non-Goals

**Goals:**
- Один компонент выбора клиента, у которого с первого дня два реальных потребителя: группа (множественный выбор) и занятие (одиночный).
- Компонент не знает, зачем выбирают клиента: недоступность, подписи и обработку выбора задаёт экран.

**Non-Goals:**
- Серверные изменения и новые контракты.
- Фильтры, сортировка, аватары и прочие колонки в списке выбора.

## Decisions

### 1. `ClientPickerSheet` на базе `EditSheet`, в `web/src/clients/`

Компонент строится как содержимое `EditSheet` (`size="md"`), а не на голом `Sheet`: бесплатно получаем вложенность (выбор клиента из будущей панели выдачи абонемента), запрет закрытия кликом мимо и подтверждение отказа от изменений.

Файл — в `clients/`, не в `ui/`: компонент знает про `clients/list`, `ClientId` и `ApiClient`, а `ui/` остаётся без доменных зависимостей.

Контракт (ориентир, имена уточняются при реализации):

```
ClientPickerSheet
  api, branchId
  open, onOpenChange
  title
  mode: "single" | "multiple"
  unavailable: ReadonlyMap<ClientId, string>     // id -> причина
  submitLabel                                    // только для "multiple"
  onSubmit: (clients: readonly PickedClient[]) => Promise<string | null>
                                                 // null — успех, панель закрывается;
                                                 // строка — текст ошибки, панель остаётся
PickedClient = { id: ClientId, name: string }
```

`onSubmit` возвращает текст ошибки, а не бросает: ошибки API — значения (`ApiResult`), как в `GroupScheduleDialog.onSave`. В режиме `single` массив всегда из одного элемента — один колбэк на оба режима, без перегрузок.

*Альтернатива:* обобщённый `EntityPickerSheet<T>` с передачей запроса снаружи. Отклонено: потребителей с другими сущностями нет, а обобщение утяжелит типы раньше, чем появится второй вид сущности.

### 2. Выбор хранится как `{id, name}`, а не набор id

Отмеченный клиент может пропасть из списка при смене поиска, но должен остаться в выборе и уйти в `onSubmit` с именем (для уведомлений, будущих чипов выбранных). Поэтому черновик выбора — `ReadonlyMap<ClientId, PickedClient>`.

### 3. Недоступные клиенты — видны, но заблокированы

Передаются картой `id -> причина`; строка выводится рядом с именем, чекбокс/кнопка `disabled`. Скрывать их нельзя: поиск «Сидоров» без результата не отличает «нет такого клиента» от «уже в группе». Фильтрация недоступных на сервере (`NOT IN group`) — забота будущей проекции под фильтры, не этой работы.

### 4. Данные — `clients/list` через `useInfiniteQuery`, поиск с debounce, «Показать ещё»

- Запрос: `{ name, limit: CLIENTS_PAGE_SIZE, offset }`; ключ кэша — `["api", branchId, "clients/list", { picker: name }]`-подобный, отдельный от ключа страницы клиентов, чтобы не смешивать с её фильтрами. Запрос включён только пока панель открыта.
- Поиск — локальное состояние поля + debounce по образцу `ClientsPage` (`SEARCH_DEBOUNCE_MS`, `setTimeout` в `useEffect`).
- Догрузка — кнопка «Показать ещё» в конце списка, как на странице клиентов. `IntersectionObserver` не используется: в проекте его нет, а в jsdom он требует моков.

*Компромисс:* `ClientListItem` тяжёлый (контакты, кастомные поля, группы, баланс), выбору нужны только `id` и `name`. Принимаем: объём порции ограничен, а лёгкая проекция `read/` появится вместе с фильтрами.

### 5. Режимы

- `multiple`: строки с чекбоксами; при непустом выборе внизу `EditSheetSelection` с числом и кнопкой `submitLabel`. На время `onSubmit` кнопка и строки заблокированы. Непустой выбор передаётся в `reportGuard({ dirty: true, submitting })`.
- `single`: строки — кнопки; нажатие сразу вызывает `onSubmit([client])`, пока он идёт — все строки заблокированы. `dirty` всегда `false`.
- Успех: панель закрывается через `useEditSheet().close()` (без подтверждения). Ошибка: текст показывается `FormAlert` над списком, выбор сохраняется.

### 6. Карточка группы

- Секция «Клиенты»: заголовок с кнопкой «Добавить клиентов»; строки — ссылка на карточку клиента + крестик удаления (`aria-label` с именем).
- Добавление: `mode="multiple"`, `unavailable` = клиенты из `detail.clients` с причиной «уже в группе», `onSubmit` → `clients/add-to-group { groupId, clientIds }` → инвалидация `groups/detail`, `groups/list` и `clients/list` (у клиентов в списке колонка групп) → тост «Добавлено клиентов: N».
- Удаление: `clients/remove-from-group { groupId, clientIds: [id] }` без подтверждения — как дисциплины и тренеры; запись в группу закрывается (`left_at`), а не удаляется, и восстанавливается повторным добавлением. Те же инвалидации; ошибка — тост.

### 7. Карточка занятия

`AddParticipantSheet` удаляется. Действие «Добавить участника» открывает `ClientPickerSheet` с `mode="single"`, `unavailable` = текущий состав с причиной «уже участник», `onSubmit` → `sessions/journal/add-participant` → существующий `apply` журнала. Строки `sessionDetail.addParticipantSearch` / `addParticipantEmpty` / `alreadyParticipant` заменяются общими строками панели либо переиспользуются как причина.

## Risks / Trade-offs

- [Повторное добавление уже записанного клиента между открытием панели и подтверждением] → сервер идемпотентен (`ON CONFLICT DO NOTHING`), ошибки не будет; карточка обновится после инвалидации.
- [Тяжёлый ответ `clients/list` в панели] → ограничен размером порции; при жалобах на скорость — проекция `read/clients/ClientPickView` вместе с фильтрами.
- [Тесты карточки занятия завязаны на старую шторку] → переписываются в рамках работы; поведение для пользователя (одиночный выбор, «уже участник») сохраняется.
- [Удаление без подтверждения — промах крестиком] → действие обратимо повторным добавлением; если окажется частым — добавить отмену в тосте, а не диалог.

## Migration Plan

Только фронтенд, контракты не меняются — выкатывается обычным деплоем, откат — откатом коммита.
