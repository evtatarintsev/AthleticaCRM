## Context

Веб-клиент — TypeScript + React + Vite (`web/`), маршрутизация через TanStack Router
(`web/src/app/router.tsx`), данные — TanStack Query поверх сгенерированных Zod-схем
(`web/src/api/generated/contracts.ts`). `SessionId` уже существует как реальный, сгенерированный
из Kotlin тип (`SessionIdSchema`) и уже используется в `ScheduleSessionSchema.id` (расписание) и
`TodaySessionItem.sessionId` (главная) — оба места уже показывают реальные занятия с реальными id,
просто пока некликабельны. См. proposal.md - Why.

Данных о посещаемости и деталей карточки занятия (полный список участников, имена тренеров, имя
зала) в контрактах нет — сервер их не отдаёт. Эта страница строится полностью на mock-данных внутри
`web/`, без изменений `shared`/`server`/`contracts.ts`.

## Goals / Non-Goals

**Goals:**
- Собрать страницу карточки занятия под реальный `SessionId`, кликабельную из расписания и с главной.
- Дать интерактивный, но не персистентный UI для действий и посещаемости — достаточно полный, чтобы
  оценить дизайн вживую (клики, переключение статусов, диалоги), не дожидаясь бэкенда.
- Сохранить форму данных максимально близкой к вероятной будущей `SessionDetailResponse` (те же
  имена полей, где возможно), чтобы замена мока на реальный `useQuery` была локальной правкой одного
  файла, а не переписыванием страницы.

**Non-Goals:**
- Реальные API-вызовы, персистентность, оптимистичные обновления с откатом при ошибке сервера.
- Итоговый набор статусов посещаемости и действий — фиксируются здесь для дизайна, но могут
  измениться при проектировании API отдельным change.
- Обработка прав доступа (кто может отменять/переносить занятия) — не моделируется, все действия
  доступны всем.

## Decisions

**Новый модуль `web/src/sessions/`** (не `web/src/schedule/`), по аналогии с `web/src/tasks/`:
страница занятия — самостоятельный раздел, а не часть расписания, хотя открывается из него.
- `SessionDetailPage.tsx` — страница.
- `sessionDetailMock.ts` — mock-типы (`MockSessionDetail`, `AttendanceStatus`) и функция
  `mockSessionDetail(id: SessionId): MockSessionDetail`, детерминированно порождающая данные по
  `id` (хэш id → индекс в паре фикстур), чтобы разные занятия в расписании открывали видимо разные
  карточки (разный статус, разный состав) вместо одной и той же заглушки — так дизайн проверяется
  на всех трёх статусах занятия без ручного переключения.
- `AttendanceToggle.tsx` — переключатель статуса посещения одного участника.

**Локальный state вместо query/mutation-инфраструктуры.** Страница держит один
`useState<MockSessionDetail>`, инициализированный из `mockSessionDetail(sessionId)`; действия и
отметки посещаемости — чистые функции-трансформации этого state (`copy`-паттерн, как в
конвенции ViewModel-state из CLAUDE.md: один объект, а не россыпь `useState`). Без TanStack Query —
нет реального запроса, оборачивать нечего; переход на реальные данные позже поменяет только источник
начального состояния и добавит `useMutation` на месте локальных трансформаций.

**Набор статусов посещаемости для дизайна**: `PRESENT` (был) / `ABSENT` (не был) / `SICK` (болел) /
`LATE` (опоздал). Зафиксирован для UI; при проектировании реального API может измениться без
переписывания вёрстки — набор живёт в одном mock-файле.

**Действия на карточке — кнопки с локальным откликом, без модальных форм с полями.** «Отменить» —
confirm-диалог (как есть, например, паттерн подтверждения в `TaskDetailPage`/`GroupDetailPage`) и
сразу меняет статус в state. «Перенести», «Сменить зал», «Сменить тренеров» — открывают простой
диалог с выбором нового значения из mock-справочника (даты/залов/тренеров — те же данные, что уже
используются на странице группы, `groupsQueries.ts`, чтобы не плодить отдельные mock-справочники) и
применяют выбор к state. «Оставить заметку» — textarea + сохранить, пишет в state.

**Кнопки действий скрываются/дизейблятся по статусу**: у отменённого и завершённого занятия
недоступны «отменить», «перенести», «сменить зал», «сменить тренеров» (см. спеку, сценарий
«Открытие карточки отменённого занятия»); посещаемость остаётся редактируемой всегда — отметить
задним числом это нормальный сценарий CRM.

**Параметр маршрута** `/sessions/$sessionId` — тот же паттерн, что `taskRoute` в `router.tsx`:
`params.parse` через `SessionIdSchema.safeParse`, некорректный id не матчит маршрут (даёт 404, а
не краш страницы).

**Точки входа**: `SessionCard` в `ScheduleWeekGrid.tsx` оборачивается в `<Link to="/sessions/$sessionId" params={{ sessionId: session.id }}>` (карточка уже кликабельна по всей площади — курсор pointer, `hover`-стиль добавляется). Список в `SessionsWidgetCard.tsx` (главная) — каждая `<li>` оборачивается так же, `sessionId` уже есть в `TodaySessionItem`.

## Risks / Trade-offs

- **[Риск]** Mock-форма данных разойдётся с реальной `SessionDetailResponse`, когда её спроектируют
  → **Митигация**: mock-типы и вся логика трансформации state изолированы в `sessionDetailMock.ts`;
  переезд на реальные данные — замена этого файла на `useQuery`, без переписывания
  `SessionDetailPage.tsx`.
- **[Риск]** Пользователь может принять мок за реальное сохранение (нажал «Сохранить заметку»,
  обновил страницу — заметка пропала) → **Митигация**: страница пока не выкатывается в прод, это
  внутренний этап дизайна, а не пользовательская фича — риск принят, отдельного UI-предупреждения
  не делаем.
- **[Trade-off]** Список участников на карточке использует ту же mock-фикстуру, что и общий список
  клиентов группы, а не «ростер занятия» — соответствует известному ограничению из explore-обсуждения
  (нет `session_attendance` как источника ростера); при проектировании реального API это решится
  отдельно.
