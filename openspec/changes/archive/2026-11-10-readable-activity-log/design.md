## Context

См. `proposal.md` для мотивации и `specs/activity-log/spec.md` для внешнего поведения.

- `GET /audit/log` сейчас принимает страницу и фильтры, но `AuditRoutes` читает записи через `AuditLog.list/count`.
- `PostgresAuditLog` отвечает за запись и чтение из `audit_logs`; таблица содержит снимок имени автора, тип/ID субъекта, JSONB `data`, IP и время.
- `data` не является общим контрактом: его форматы различаются, поэтому эта работа не строит по нему diff или подпись субъекта.
- В проекте чтение списков с фильтрами и JOIN-ами реализуется через интерфейс/DB-класс в `read/` и регистрируется в `ReadViews`.
- Серверная локализация уже централизована в `i18n/Messages`; схемы API находятся в `shared`.

## Goals / Non-Goals

**Goals:**

- Сохранить `audit_logs` источником истории и оставить write-репозиторий ответственным только за запись.
- Собрать данные для списка в одном организационно-изолированном read-запросе.
- Возвращать локализованное описание и типизированную цель, не заставляя web-клиент знать формат JSON-снимков.
- Перенести действующие фильтры, сортировку, пагинацию и `total` на read-проекцию.

**Non-Goals:**

- Перестраивать аудит в уведомления: у событий журнала нет адресатов и состояния прочтения.
- Показывать детальный diff полей из `data`, менять формат уже записываемых событий или исправлять покрытие аудита.
- Добавлять аудит задач или новые категории событий.
- Создавать переходы для сущностей, у которых нет экрана в приложении.

## Decisions

### Выделить `ActivityLogView` в `read/audit/`

Добавить `ActivityLogView` с запросом, содержащим `AuditFilter`/параметры списка, и DB-реализацию `DbActivityLogView`. Регистрировать её в `ReadViews`; `AuditRoutes` использует проекцию и строит ответ API. Удалить `list` и `count` из `AuditLog` и соответствующее чтение из `PostgresAuditLog`, сохранив `log(event)` для записи.

Это соответствует принятому разделению команд и запросов и позволяет тестировать поведение списка на SQL-уровне. Альтернатива — оставить чтение в репозитории аудита и добавить туда JOIN-ы. Она отвергнута: `AuditLog` является write-моделью и не должен быть источником UI-проекций.

Проекция выбирает записи только по `ctx.orgId`, применяет существующие фильтры до пагинации и выполняет отдельный `COUNT` с тем же условием. Сортировка — `created_at DESC` с `id DESC` как устойчивым вторичным ключом. Параметры `page` и `pageSize` нормализуются в маршруте, как сейчас.

### Разрешать субъект и подпись в серверном слое API

Добавить схему субъекта `{ type, id, title, isAvailable, targetId? }` и поле локализованного `description` в элемент ответа. `targetId` используется для связанного экрана, например ID клиента для `client_doc`; `isAvailable` не даёт создавать ссылку на удалённую сущность. Проекция соединяет `audit_logs` с таблицами субъектов для поддерживаемых типов и возвращает nullable/типизированные данные цели. Существующий `username` остаётся историческим снимком имени автора. Маршрут, имеющий `RequestContext.lang`, формирует короткое описание через `Messages`, используя `actionType`, имя автора и разрешённое название субъекта.

Такое разделение оставляет SQL ответственным за чтение данных, а локализацию — на сервере, где уже живут `Messages`. Альтернатива — собирать фразу в web-клиенте. Она отвергнута, потому что дублирует грамматику и перевод на клиентах и не позволяет маршруту учитывать серверные данные субъекта.

Для `client`, `client_doc`, `group`, `employee`, `session`, `branch`, `hall`, `discipline`, `lead_source`, `subscription_tariff` и `channel_integration` определить человекочитаемое название и маршрут в web-клиенте по соответствию из issue #59. Для `enrollment`, `membership`, `upload` и неизвестных типов маршрут не задавать. Если субъект удалён или не разрешился, его отображаемое имя — локализованное обозначение отсутствующего объекта с типом сущности; ID остаётся идентификатором цели и не становится основным заголовком. Для типов без экрана доступное имя выводится обычным текстом.

Существующая форма `data` не используется для получения названий и полей изменения: это потребовало бы сначала унифицировать и исправить записи JSONB, что вынесено за рамки change.

### Сохранить контракт фильтров и доработать web-экран

Сохранить существующие фильтры `actionType`, `userId`, `from`, `to` и добавить/использовать интерфейс фильтров на экране настроек. UI передаёт активные значения в запрос при загрузке страницы; смена фильтров сбрасывает страницу на первую. Добавить `GET /audit/log/users`, который возвращает уникальных авторов, уже присутствующих в аудите текущей организации (`userId` и сохранённое имя). `employees/list` возвращает `EmployeeId`, а фильтр журнала принимает `UserId`, поэтому список авторов из самого аудита сохраняет правильное соответствие идентификаторов и включает только пользователей, у которых есть события. Маршруты для `entityType` из API можно оставить поддержанными сервером, но отдельный фильтр типа сущности в обязательный UI этого change не входит.

Альтернатива — фильтровать только уже загруженную страницу на клиенте. Она отвергнута, так как даст неверные `total` и страницы и потребует загрузить все события.

### Разделить уровни отображения цели и фразы

Субъект в ответе остаётся структурированным (`type`, `id`, `title`), а описание — отдельной локализованной строкой. Web отображает цель как отдельное название/ссылку; он не извлекает URL и текст цели из описания. Это позволяет навигации работать даже при изменении формулировки перевода.

Для сущностей без отдельной страницы или без найденной строки API возвращает отсутствие перехода; UI показывает переданный title либо безопасное локализованное обозначение. URL-маршруты сопоставляются через существующий `AppRoute`, а не конструируются из произвольного `entityType`.

## Risks / Trade-offs

- **Новые JOIN-ы и типы сущностей могут усложнить SQL** → держать разрешение субъекта в одном read-запросе и проверить все заявленные entity types DB-тестами, включая неизвестный и отсутствующий.
- **Удалённая сущность не имеет текущего названия** → показать локализованное обозначение недоступной сущности без ссылки; сохранение названия на момент события потребовало бы общего валидного исторического snapshot-контракта.
- **Фраза может быть неестественной для некоторых комбинаций action/entity** → покрыть все имеющиеся `AuditActionType` локализованными шаблонами и использовать нейтральные фразы для действий без субъекта.
- **Фильтр сотрудника зависит от идентификаторов и списка доступных сотрудников** → использовать `userId` API и выдавать варианты из текущей организации; системные события без `userId` остаются доступными при сброшенном фильтре.
- **Старые значения `data` иногда могут быть невалидным JSON** → новая проекция не читает это поле для построения текста или имени субъекта; отдельную проверку write-путей вести отдельно.

## Migration Plan

Изменение не требует миграции БД: форма `audit_logs` остаётся прежней. Выпустить совместно обновлённые серверные схемы и web-клиент; внутренний ответ API журнала расширяется структурированным описанием/субъектом. При откате кода можно вернуть чтение через прежний `AuditLog` до удаления его методов отдельным коммитом релиза либо выполнить откат релиза целиком; данные журнала не затрагиваются.
