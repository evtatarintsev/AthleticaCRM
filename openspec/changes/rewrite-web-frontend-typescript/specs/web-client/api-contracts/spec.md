## Purpose

Гарантирует, что веб-клиент и сервер пользуются одним контрактом API: типы и проверки на стороне TypeScript выводятся из Kotlin-схем модуля `shared` и маршрутов сервера, а данные от сервера проверяются на входе в клиент.

## ADDED Requirements

### Requirement: Контракты выводятся из сервера и shared

Описание каждого JSON-эндпоинта для веб-клиента (путь, HTTP-метод, схема запроса, схема ответа) SHALL строиться автоматически из зарегистрированных маршрутов сервера и сериализуемых Kotlin-типов. Ручное описание схем на стороне TypeScript SHALL быть запрещено. Эндпоинты, которые не принимают и не отдают JSON (загрузка файлов multipart, выгрузка файлов), описываются явно, и таких SHALL быть не больше, чем сейчас на сервере.

#### Scenario: Новое поле в ответе

- **WHEN** в Kotlin-схему ответа добавлено обязательное поле и контракты перегенерированы
- **THEN** поле появляется в TypeScript-типе ответа без правок клиентского кода

#### Scenario: Удалённое поле

- **WHEN** из Kotlin-схемы удалено поле, которое читает веб-клиент, и контракты перегенерированы
- **THEN** проверка типов веб-клиента завершается ошибкой в месте чтения поля

#### Scenario: Новый эндпоинт

- **WHEN** на сервере зарегистрирован новый типизированный маршрут
- **THEN** после генерации он доступен в клиенте с типами запроса и ответа, и вызвать его с запросом другого типа нельзя

### Requirement: Сгенерированный контракт не устаревает

Сгенерированные контракты SHALL храниться в репозитории. CI SHALL перегенерировать их и завершаться ошибкой, если результат отличается от закоммиченного.

#### Scenario: Забыли перегенерировать

- **WHEN** в PR изменена Kotlin-схема, а сгенерированный файл контрактов не обновлён
- **THEN** проверка CI падает и сообщает, что контракты устарели

### Requirement: Отображение Kotlin-типов в TypeScript однозначно

Генерация SHALL отображать типы так:

| Kotlin | TypeScript |
|---|---|
| `String`, `Boolean`, `Int`, `Long`, `Double` | `string`, `boolean`, `number` с проверкой целочисленности для целых |
| value class идентификатора сущности | строка UUID с брендом этой сущности; идентификаторы разных сущностей не взаимозаменяемы |
| `Instant`, `LocalDate`, `LocalTime`, `DayOfWeek` | строка в формате ISO с отдельным брендом для каждого типа |
| `enum class` | объединение строковых литералов |
| sealed-иерархия | размеченное объединение по полю-дискриминатору сериализации |
| `T?` | `T \| null` |
| `List<T>`, `Set<T>` | массив `readonly` |
| `Map<String, T>` | объект только для чтения с ключами-строками |

Если генератор встречает тип со своим сериализатором и для него нет явного правила отображения, генерация SHALL завершаться ошибкой, а не выводить `unknown` или `any`.

#### Scenario: Перепутанные идентификаторы

- **WHEN** код передаёт `GroupId` туда, где запрос ожидает `ClientId`
- **THEN** проверка типов завершается ошибкой

#### Scenario: Неизвестный сериализатор

- **WHEN** в схему добавлен тип со своим `KSerializer`, для которого нет правила отображения
- **THEN** генерация контрактов завершается ошибкой с именем типа

#### Scenario: Sealed-иерархия

- **WHEN** схема содержит sealed-иерархию с вариантами `skip`, `name`, `custom_field`
- **THEN** в TypeScript это объединение из трёх вариантов, и после проверки дискриминатора доступны поля только выбранного варианта

### Requirement: Ответы сервера проверяются на входе

Каждый JSON-ответ сервера SHALL проверяться схемой из контракта до того, как попадёт в код интерфейса. Если ответ не соответствует контракту, клиент SHALL вернуть типизированную ошибку «нарушение контракта» и записать детали (эндпоинт и путь к несовпавшему полю) в консоль браузера, а если подключена система сбора ошибок — и в неё. Данные, не прошедшие проверку, в интерфейс SHALL не попадать.

#### Scenario: Сервер вернул лишнее поле

- **WHEN** в ответе есть поле, которого нет в контракте
- **THEN** ответ принимается, лишнее поле отбрасывается

#### Scenario: Сервер вернул поле другого типа

- **WHEN** в ответе поле `total` — строка, а по контракту число
- **THEN** вызов возвращает ошибку «нарушение контракта», экран показывает общую ошибку загрузки, а не частично заполненные данные

### Requirement: Типизированные ошибки вызова

Вызов API SHALL не выбрасывать исключения в код интерфейса и возвращать либо значение, либо одну из ошибок: ошибка бизнес-логики (ответ 4xx с кодом и сообщением сервера, в том числе отказ в правах), нет авторизации (401 после неудачного обновления сессии), сервис недоступен (сеть или ответ 5xx), нарушение контракта. Все места обработки ошибок SHALL разбирать эти варианты исчерпывающе.

#### Scenario: Ошибка бизнес-логики

- **WHEN** сервер отвечает 400 с кодом `BRANCH_ACCESS_DENIED`
- **THEN** вызов возвращает ошибку бизнес-логики с этим кодом и сообщением сервера

#### Scenario: Сеть недоступна

- **WHEN** запрос не дошёл до сервера
- **THEN** вызов возвращает ошибку «сервис недоступен», исключение не выбрасывается

### Requirement: Сервер отдаёт поля со значениями по умолчанию

Сервер SHALL включать в JSON-ответы все поля схемы, в том числе равные значению по умолчанию. Поле ответа в контракте SHALL быть обязательным, если оно не объявлено nullable. В схемах запросов поля со значением по умолчанию SHALL оставаться необязательными для клиента.

#### Scenario: Поле равно значению по умолчанию

- **WHEN** у поля схемы ответа есть значение по умолчанию и в ответе оно равно этому значению
- **THEN** поле присутствует в JSON с этим значением

#### Scenario: Запрос без необязательного поля

- **WHEN** клиент отправляет запрос без поля, у которого в схеме запроса есть значение по умолчанию
- **THEN** сервер применяет значение по умолчанию, запрос проходит проверку типов на клиенте
