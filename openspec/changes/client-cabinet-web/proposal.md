## Why

Сейчас клиент (чаще родитель ребёнка) узнаёт о расписании, остатке абонемента и долге только
от администратора — в мессенджере или на ресепшене. Это нагружает администраторов и не даёт
клиенту самому предупредить о пропуске. Нужен кабинет клиента, в который клиент входит без
пароля и где видит только свои данные.

Начинаем с веб-кабинета на `clients.${DOMAIN}`, а не с мобильных приложений: на вебе дешевле
отработать контракты API, сценарии и дизайн. Мобильные приложения (`client-mobile-android`,
`client-mobile-ios`) затем рисуют экраны поверх готового API.

Главный риск — администратор ошибся в номере телефона, и посторонний получает доступ к
персональным данным ребёнка (152-ФЗ). В первой версии от этого защищают приглашение без данных
клиента, кнопка «Это не я» и отключение старого номера при исправлении карточки; проверка
личности сверх кода — в [#314](https://github.com/evtatarintsev/AthleticaCRM/issues/314).

## What Changes

Изменение — серверный контур клиентов, клиентское API и веб-кабинет. Выпускается шагами;
каждый шаг добавляет API и экраны кабинета и выкатывается отдельно:

1. **Вход и подключение.** Отдельный проект `cabinet/` со своим образом, хост
   `clients.${DOMAIN}`. Организация включает клиентский кабинет в настройках и приглашает
   клиентов — по одному из карточки или всех сразу; без приглашения войти нельзя. Вход по
   номеру телефона и одноразовому коду, без паролей. Код уходит за счёт пригласившей организации:
   в Telegram через её Telegram Gateway (`telegram-gateway`), при недоставке — по её SMS-каналу
   (`sms-aero-channel`). Включить кабинет можно только при хотя бы одном таком способе. Один номер — один аккаунт со всеми клиентами всех организаций.
   Подключение к организации — кнопкой «Подключить», ошибка в номере — «Это не я» и задача
   администратору. Переключатель клиентов и организаций, главная с приветствием. В карточке
   клиента CRM — статус по каждому номеру, «Пригласить», «Напомнить», «Отключить».
2. **Сеансы и выход.** Список сеансов аккаунта, выход, завершение сеанса на другом устройстве,
   удаление аккаунта.
3. **Баланс** и его история, неоплаченные занятия.
4. **Абонементы** и история списаний.
5. **Расписание** с отметкой «Не придём»; предупреждение видно сотруднику в журнале занятия.
6. **История посещений.**

Доступ закрывается сразу, если номер удалён из карточки, клиент архивирован, кабинет в
организации выключен или сотрудник отключил доступ. Закрытие доступа в одной организации не
трогает сеансы и доступы в других.

**Не входит**: мобильные приложения (`client-mobile-android`, `client-mobile-ios`), переписка
с клубом (`client-app-chat`), push (`client-app-push`), онлайн-оплата, магазин товаров,
самостоятельная запись на разовые занятия, брендирование кабинета под клуб, вход по email,
подключение по QR-коду на месте, проверка личности сверх кода
([#314](https://github.com/evtatarintsev/AthleticaCRM/issues/314)).

### Связанные изменения

| Изменение | Что делает | Зависит от |
|---|---|---|
| `client-app-chat` | переписка с клубом, канал «Приложение» во «Входящих» | шаг 1: доступы, `ClientProfileContext`, порт `ClientAppPushes` |
| `client-app-push` | push через FCM и APNs | шаг 2: сеансы; порт `ClientAppPushes` |
| `client-mobile-android` | модуль `:mobile` на KMP + Compose Multiplatform, Android | клиентское API всех шагов |
| `client-mobile-ios` | iOS-таргет приложения | `client-mobile-android` |

## Capabilities

### New Capabilities
- `client-app-access`: приглашения, вход по коду, аккаунт по номеру, подключение и
  «Это не я», сеансы, отзыв доступа, изоляция организаций, удаление аккаунта. Общие для
  веб-кабинета и мобильных приложений.
- `client-app-admin`: включение кабинета в организации, массовое и единичное приглашение,
  статусы доступа в карточке клиента, задачи по ошибкам в номере.
- `client-app-overview`: что клиент видит — главная, расписание, посещения, абонементы, баланс,
  переключение между клиентами и организациями. Общие для веб-кабинета и мобильных приложений.
- `client-cabinet-web`: веб-кабинет — адрес, сеанс в браузере, раскладка под телефон,
  отдельный контракт API.

### Modified Capabilities
- `attendance-journal`: клиент может заранее предупредить об отсутствии; предупреждение видно
  сотруднику в журнале занятия, отметку по-прежнему ставит сотрудник.

## Impact

- **server**: новый контур аутентификации клиентов (отдельный JWT-аудиенс, контексты
  `ClientAccountContext`/`ClientProfileContext` вне `RequestContext`), домен `clientapp`
  (аккаунты, доступы, сеансы, коды), отправители кодов над Telegram Gateway и SMS-каналами организаций,
  порт `ClientAppPushes` с заглушкой, проекции `read/clientapp/*`, маршруты `/api/client-app/*` и
  `/api/client-app-admin/*`; генератор контрактов пишет два файла по префиксу маршрута.
- **shared**: схемы клиентского API, `ClientAppAccessStatus`, право `CAN_MANAGE_CLIENT_APP`.
- **cabinet** (новый проект): TypeScript + React + Vite, строгие правила как в `web/`,
  собственный образ.
- **web**: блок «Клиентский кабинет» в карточке клиента, страница настроек, предупреждения об
  отсутствии в журнале; перегенерация `web/src/api/generated/`.
- **БД**: таблицы аккаунтов, доступов, сеансов, кодов, предупреждений об отсутствии; колонка
  `organizations.client_app_enabled`.
- **Инфраструктура**: сервис `cabinet` в `docker-compose.prod.yaml`, хост `clients.${DOMAIN}`
  в `nginx/prod.conf.template` и в сертификате, job сборки образа в CI. Параметры клиентского
  JWT — в `application.conf`, `docker-compose.prod.yaml`, `.env.prod.example`.
