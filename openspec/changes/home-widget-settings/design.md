## Context

См. `proposal.md` для мотивации и `specs/web-client/home-dashboard/spec.md` для пользовательских требований. Сейчас главная хранит настройки виджетов в едином `DashboardSettings`; виджеты используют общий запрос обновления настроек отображения. Тип клиента списка уже содержит `avatarId`, а общий компонент аватара умеет показывать инициалы при отсутствии изображения.

## Goals / Non-Goals

**Goals:**
- Сохранить единую модель и механизм сохранения настроек, разделив элементы управления по месту использования.
- Сделать настройки карточки компактными и доступными с её шестерёнки, включая явное действие скрытия.
- Оставить общие настройки точкой управления порядком и восстановления скрытых карточек.

**Non-Goals:**
- Изменение API или схемы сохранённых настроек.
- Изменение бизнес-логики выборки клиентов для виджетов.
- Новые варианты сортировки или новые типы виджетов.

## Decisions

- **Одна модель настроек, разные поверхности управления.** Настройки карточки и общий диалог изменяют существующий объект настроек главной и используют текущее сохранение. Это позволяет не вводить отдельное состояние и сохраняет текущую совместимость данных.
- **Шестерёнка карточки открывает компактную контекстную панель.** В ней редактируются пользовательское название, параметры соответствующего типа и действие скрытия. Рассматривался переход в общий диалог, но он хуже подходит для быстрого изменения одного виджета и смешивает индивидуальные параметры с настройками раскладки.
- **Общий диалог показывает фиксированные локализованные названия типов.** Пользовательские названия остаются свойством карточек и не используются как названия строк управления порядком/видимостью. Это сохраняет однозначность общей настройки независимо от переименования.
- **Скрытие из карточки и включение в общем диалоге — парные действия.** Карточка может быть скрыта там, где она отображается; скрытая карточка возвращается через общий диалог. Название и параметры при этом не сбрасываются.
- **Аватар использует общий компонент.** Переиспользование существующего `Avatar` обеспечивает единый размер/вид инициала и обработку отсутствующего либо недоступного изображения без отдельной загрузочной логики.

## Risks / Trade-offs

- [Параллельные контролы обновляют настройки на основе устаревшего состояния] → передавать изменения через актуальный кэш настроек и сохранять все существующие поля объекта, чтобы настройка карточки не перезаписывала порядок или видимость.
- [Компактная панель неудобна на узком экране или для клавиатуры] → использовать доступные существующие UI-примитивы, обеспечить управление фокусом и проверить размещение на мобильной ширине.
- [Два места управления видимостью могут показаться дублированием] → в карточке оставить действие «Скрыть», а в общих настройках — единый список включения/выключения, необходимый в том числе для восстановления скрытых карточек.

## Migration Plan

Миграция данных не требуется: текущие названия, лимиты, периоды, порядок и видимость остаются в существующих настройках. После обновления пользовательские названия редактируются из карточек; общие настройки продолжают показывать фиксированные названия типов.
