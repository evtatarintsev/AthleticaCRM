## Context

Сейчас роли — отдельная страница `RolesPage` (маршрут `/settings/roles`) с модальным `RoleDialog`.
В `RoleDialog` название живёт в `useForm`, а набор прав — в отдельном `useState`, поэтому признак
«форма изменена» права не видит. Готовый образец «список в панели + вложенная панель формы» — пункт
«Дополнительные атрибуты клиентов»: `CustomFieldsSheet` (`EditSheet size="lg"` + `EditSheetBody`)
и `CustomFieldSheet` (`EditSheet` + `EditSheetForm` + `useEditSheet().close`). Панели настроек
регистрируются в `SettingsPanelSchema` (`settingsSearch.ts`) и словаре `SHEETS` в `SettingsPage.tsx`.

Форма сотрудника — панель `EmployeeSheet` (`EditSheet` поверх списка `/employees` или поверх
карточки `EmployeeCardSheet`). `EmployeeSheetContent` загружает `employees/roles` и `branches/list`
и показывает заглушку, пока данных нет; `EmployeeForm` держит выбор в `useForm` (`roleIds`,
`permissions`, `branchIds`), а вложенные панели выбора (`ChecklistSheet` ролей и филиалов,
`PermissionsSheet`) рендерятся в слоте `nested` у `EditSheetForm` и управляются состоянием
`picker`. Секция «Роли» — `FormSection` с кнопкой «Изменить»; при пустом списке ролей кнопки нет,
а вместо сводки — `Link` на `/settings/roles`.

## Goals / Non-Goals

**Goals:**
- Одна панель роли (`RoleSheet`), которую используют и список ролей, и панель сотрудника.
- Права — часть состояния формы, чтобы защита несохранённых изменений `EditSheet` работала на них.

**Non-Goals:**
- Общий «справочник» для ролей через `DirectorySheet`: у ролей нет удаления и выделения, а карточки
  с ярлыками прав не укладываются в табличную модель справочников.
- Действие «создать» внутри общего `ChecklistSheet`: компонент общий (тренеры, филиалы, роли), и
  создание прямо из выбора потребовало бы слота действия и правил для черновика выбора.

## Decisions

### Панель `roles` на странице настроек, маршрут удаляется

`SettingsPanelSchema` получает значение `"roles"`, пункт «Роли» — `panel("roles")` вместо
`app("/settings/roles")`, `SHEETS.roles = RolesSheet`. Маршрут `rolesRoute` и запись
`"/settings/roles"` в `staticAppPaths` удаляются; редиректа нет — обратная совместимость адресов не
нужна.

### `RolesSheet` по образцу `CustomFieldsSheet`

```
RolesSheet (EditSheet lg, "Роли")
  +- RolesPanel (EditSheetBody)
       [+ Добавить роль]
       карточки ролей (кнопка -> edit)
  +- RoleSheet (вложенная EditSheet md)   open/editing — локальное состояние
```

Состояние `editing` (`create | edit(role)`) хранится отдельно от `open` и не сбрасывается при
закрытии — как в `CustomFieldsSheet`, чтобы содержимое не пропадало во время анимации закрытия.
Вложенная панель роли в адрес не попадает: адресуется только список.

Ширина `lg`: карточки с ярлыками прав в `md` переносятся слишком часто, а отдельная таблица не нужна.

### `RoleSheet` — переиспользуемая панель формы

`RoleSheet({ open, onOpenChange, initial: RoleItem | null, onSave(terms) => Promise<string | null> })`,
внутри — `EditSheetForm` и `useEditSheet().close()` после успешного `onSave`, как в
`CustomFieldSheet`. `onSave` по-прежнему возвращает текст ошибки или `null`, а API вызывает
владелец панели: так `RoleSheet` не знает, что делать с результатом (обновить список или отметить
роль у сотрудника).

Права переносятся в `defaultValues` формы: `{ name: string, permissions: UserPermission[] }`, чекбоксы
работают через `form.Field name="permissions"` (добавление/удаление элемента массива). Порядок прав в
запросе по-прежнему задаётся `UserPermissionSchema.options`. Альтернатива — оставить `useState` и
вручную вычислять `dirty` для прав — отвергнута: дублирует признак изменённости, который форма уже
считает сама и который передаётся в `EditSheetForm`, как в `CustomFieldSheet`.

`RoleDialog.tsx` удаляется; `RoleTerms` переезжает в `RoleSheet.tsx`.

### Создание роли из панели сотрудника

`EmployeePicker` расширяется значением `"new-role"`; `RoleSheet` с `initial = null` рендерится в
слоте `nested` рядом с остальными вложенными панелями и открывается тем же `picker`. Секция «Роли»:

```
ролей нет:   "Нет настроенных ролей"                 [Добавить роль]
роли есть:   ярлыки выбранных ролей      [Добавить роль] [Изменить]
```

`FormSection` получает возможность показать несколько действий в заголовке (сейчас одна кнопка
`onEdit`); `Link` на `/settings/roles` удаляется. Обработчик сохранения роли в `EmployeeForm`:

1. `api.call("employees/roles/create", { id: uuidv7(), ...terms })`, ошибка возвращается в `RoleSheet`;
2. при успехе — `queryClient.invalidateQueries` для ключа `employees/roles` текущего филиала (тот же
   запрос, что у панели сотрудника и панели ролей в настройках);
3. `form.setFieldValue("roleIds", [...roleIds, id])` — роль выбрана, форма становится изменённой.

Сотрудник не сохраняется. `EmployeeSheetContent` при перезапросе ролей не возвращается к заглушке:
`roles.data` остаётся определённым, поэтому `EmployeeForm` не размонтируется и введённые данные не
теряются. Пока перезапрос не завершился, сводка секции строится фильтром `roles` по `roleIds` и
новую роль ещё не показывает; после ответа она появляется ярлыком. Чтобы не было мигания, допустимо
до инвалидации положить созданную роль в кэш `employees/roles` через `setQueryData` — решается при
реализации, на поведение спеки не влияет.

Глубина вложенности при редактировании: список → карточка → сотрудник → роль. `EditSheet` сдвигает
каждого родителя через контекст, отдельной поддержки уровней не требуется; проверяется в превью.

## Risks / Trade-offs

- [Внешние ссылки и закладки на `/settings/roles` перестанут работать] → принято осознанно; в коде
  единственная ссылка — из секции «Роли» панели сотрудника, она заменяется кнопкой.
- [Создание роли из панели сотрудника обходит страницу настроек] → создание идёт тем же API и той же
  панелью, сервер права на создание ролей сейчас не проверяет; поведение совпадает с панелью настроек.
- [Устаревший кэш ролей в другом месте] → все потребители используют один ключ `employees/roles`
  текущего филиала, инвалидация после создания и изменения роли обновляет их.
- [Роль создана, а сотрудник не сохранён] → роль остаётся в организации; это ожидаемо и закреплено
  сценарием спеки — роль самостоятельная сущность, а не часть сотрудника.
- [Требование `web-client/employees` вводит ещё не архивированное `employee-side-sheets`] → архивировать
  его первым; иначе MODIFIED-дельта этого изменения не найдёт требование в основной спеке.
