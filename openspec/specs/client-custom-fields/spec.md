# client-custom-fields Specification

## Purpose

Дополнительные поля позволяют организации расширить профиль клиента собственными атрибутами (размер формы, школа, номер полиса и т.п.) с типом и правилами проверки, не меняя продукт, и видеть, кто и как менял их набор.

## Requirements

### Requirement: Набор дополнительных полей организации
Организация SHALL вести собственный упорядоченный набор определений дополнительных полей клиента; определения одной организации MUST NOT быть видны другой. Определение SHALL содержать машинный ключ, название, тип, признаки «обязательное», «участвует в поиске», «доступно для сортировки» и параметры своего типа. Набор SHALL управляться в настройках, в разделе «Дополнительные атрибуты клиента».

#### Scenario: Изоляция организаций
- **WHEN** у двух организаций заведены разные дополнительные поля
- **THEN** сотрудник каждой организации видит в настройках, форме и карточке клиента только поля своей организации

#### Scenario: Пустой набор
- **WHEN** организация не завела ни одного дополнительного поля
- **THEN** список полей пуст, а форма и карточка клиента не показывают раздел дополнительных полей

### Requirement: Типы полей и их параметры
Поле SHALL иметь один из типов: строка, число, дата, выбор из списка, флаг, телефон, email, URL. Строка MAY ограничивать минимальную и максимальную длину, число — минимальное и максимальное значение, выбор SHALL содержать список вариантов. Определение с выбором без непустых вариантов, отрицательной минимальной длиной или минимумом больше максимума SHALL отклоняться с ошибкой `CUSTOM_FIELD_INVALID_DEFINITION`.

#### Scenario: Выбор без вариантов
- **WHEN** сотрудник сохраняет поле типа «выбор» без вариантов
- **THEN** сохранение отклоняется, набор полей остаётся прежним

#### Scenario: Минимум больше максимума
- **WHEN** сотрудник сохраняет числовое поле с минимумом 10 и максимумом 5
- **THEN** сохранение отклоняется с ошибкой `CUSTOM_FIELD_INVALID_DEFINITION`

#### Scenario: Поле без ограничений
- **WHEN** сотрудник сохраняет строковое поле без минимальной и максимальной длины
- **THEN** поле сохраняется и принимает строку любой длины

### Requirement: Машинный ключ поля
Ключ SHALL состоять только из строчных латинских букв и символа подчёркивания и MUST быть уникален в наборе организации. Ключ с другими символами SHALL отклоняться с ошибкой `INVALID_FIELD_KEY`. После создания поля ключ MUST NOT меняться: значения клиентов привязаны к ключу.

#### Scenario: Недопустимый ключ
- **WHEN** сотрудник задаёт ключ `Shoe-Size`
- **THEN** поле не сохраняется, пользователь видит требование к формату ключа

#### Scenario: Повтор ключа
- **WHEN** сотрудник создаёт поле с ключом, который уже есть в наборе
- **THEN** форма не даёт сохранить поле с этим ключом

#### Scenario: Повтор ключа в запросе API
- **WHEN** запрос сохранения содержит два определения с одним ключом
- **THEN** сохранение отклоняется с ошибкой `CUSTOM_FIELD_DUPLICATE_KEY`, набор остаётся прежним

#### Scenario: Редактирование существующего поля
- **WHEN** сотрудник открывает существующее поле на редактирование
- **THEN** название, тип-параметры и признаки можно изменить, а ключ доступен только для чтения

### Requirement: Сохранение набора целиком
Сохранение SHALL принимать полный набор определений для типа сущности и делать его текущим: поля, отсутствующие в запросе, удаляются, порядок в запросе становится порядком показа. Ответ SHALL содержать сохранённый набор. Ошибка в любом определении SHALL отменять сохранение всего набора.

#### Scenario: Удаление выбранных полей
- **WHEN** сотрудник выбирает два поля и подтверждает удаление
- **THEN** набор сохраняется без этих полей, остальные поля и их порядок не меняются

#### Scenario: Порядок показа
- **WHEN** набор сохранён в порядке «Школа», «Размер формы»
- **THEN** список, форма и карточка клиента показывают поля в этом порядке

### Requirement: Проверка значений по определениям
Значение SHALL относиться к существующему полю (`UNKNOWN_CUSTOM_FIELD`) и совпадать с ним по типу (`CUSTOM_FIELD_TYPE_MISMATCH`); строка, телефон, email и URL принимают текстовое значение. Значение выбора MUST входить в варианты (`CUSTOM_FIELD_INVALID_OPTION`); длина строки и число MUST укладываться в границы, а число — быть конечным (`CUSTOM_FIELD_OUT_OF_RANGE`).

#### Scenario: Вариант вне списка
- **WHEN** клиенту передаётся значение «XXL» для поля выбора с вариантами «S», «M», «L»
- **THEN** сохранение клиента отклоняется с ошибкой `CUSTOM_FIELD_INVALID_OPTION`

#### Scenario: Несовпадение типа
- **WHEN** для числового поля передаётся текстовое значение
- **THEN** сохранение клиента отклоняется с ошибкой `CUSTOM_FIELD_TYPE_MISMATCH`

### Requirement: Обязательные поля
При создании клиента каждое обязательное поле MUST быть заполнено, иначе создание отклоняется с ошибкой `CUSTOM_FIELD_REQUIRED`; пустая строка и пустой выбор считаются незаполненными. При редактировании SHALL запрещаться очистка ранее заполненного обязательного поля; клиент, у которого поле было пустым до того, как его сделали обязательным, SHALL сохраняться без его заполнения.

#### Scenario: Создание без обязательного поля
- **WHEN** сотрудник создаёт клиента, не заполнив обязательное поле «Школа»
- **THEN** клиент не создаётся, ошибка указывает на поле

#### Scenario: Поле стало обязательным позже
- **WHEN** поле «Школа» сделали обязательным, а сотрудник редактирует имя клиента, у которого школа не заполнена
- **THEN** изменения клиента сохраняются

#### Scenario: Очистка обязательного поля
- **WHEN** сотрудник очищает заполненное обязательное поле клиента
- **THEN** сохранение отклоняется с ошибкой `CUSTOM_FIELD_REQUIRED`

### Requirement: Значения после изменения определения
При редактировании клиента SHALL проверяться только новые и изменённые значения; неизменённые значения, не соответствующие новым ограничениям поля, SHALL сохраняться без ошибки. Удаление определения MUST NOT удалять сохранённые значения клиентов, но удалённое поле SHALL перестать показываться в форме, карточке, списке и экспорте.

#### Scenario: Сузили варианты выбора
- **WHEN** из поля выбора удалили вариант «XL», а сотрудник меняет имя клиента со значением «XL»
- **THEN** клиент сохраняется, значение «XL» остаётся

#### Scenario: Поле удалено
- **WHEN** поле удалено из набора
- **THEN** колонка поля пропадает из списка клиентов и выбора полей экспорта

### Requirement: Отображение и обмен данными
Форма клиента SHALL показывать ввод для каждого поля набора по его типу. Карточка клиента SHALL показывать раздел дополнительных полей с названием и значением каждого поля. Поля SHALL быть доступны как колонки списка клиентов, как поля CSV-экспорта и как цели сопоставления колонок при импорте (вручную и помощником) с теми же правилами проверки.

#### Scenario: Одинаковое представление значения
- **WHEN** у клиента флаг установлен, а число равно 42.0
- **THEN** карточка, список и CSV-экспорт показывают «✓» и «42»

#### Scenario: Импорт с ошибочным значением
- **WHEN** в импортируемой строке значение поля выбора не входит в варианты
- **THEN** строка помечается ошибкой и не создаёт клиента, остальные строки импортируются

### Requirement: Аудит изменения дополнительных полей
Каждое добавление, изменение и удаление определения при сохранении набора SHALL записываться в журнал действий отдельным событием `CREATE`, `UPDATE` или `DELETE` с типом сущности `custom_field`, автором из контекста запроса и снимком определения (включая тип сущности и позицию). Поле, не изменившееся ни определением, ни местом относительно других сохранённых полей, MUST NOT порождать событие: сдвиг позиции из-за добавления или удаления соседнего поля изменением не считается. Событие SHALL записываться в той же транзакции, что и сохранение.

#### Scenario: Добавление поля
- **WHEN** сотрудник добавляет поле «Размер формы» к двум существующим
- **THEN** в журнале появляется одно событие `CREATE` для «Размер формы», для двух других полей событий нет

#### Scenario: Изменение и удаление за одно сохранение
- **WHEN** сотрудник переименовывает одно поле и удаляет другое одним сохранением
- **THEN** в журнале появляются событие `UPDATE` со снимком после изменения и событие `DELETE` со снимком удалённого поля

#### Scenario: Удаление поля сдвигает остальные
- **WHEN** сотрудник удаляет первое из трёх полей
- **THEN** в журнале появляется одно событие `DELETE`, для сдвинутых полей событий нет

#### Scenario: Сохранение без изменений
- **WHEN** набор сохраняется в неизменном виде
- **THEN** журнал не пополняется

#### Scenario: Ошибка сохранения
- **WHEN** сохранение отклонено из-за некорректного определения
- **THEN** ни одного события по дополнительным полям в журнал не записано

### Requirement: Субъект события дополнительного поля в журнале
Изменённое или созданное поле SHALL сохранять идентификатор между сохранениями набора, чтобы события одного поля ссылались на один субъект. В журнале субъект `custom_field` SHALL показываться текущим названием поля и вести в раздел настроек дополнительных полей; для удалённого поля SHALL показываться обозначение недоступного субъекта без ссылки.

#### Scenario: Переход из журнала
- **WHEN** сотрудник открывает событие изменения существующего поля «Школа»
- **THEN** субъект показан как «Школа» и ведёт в настройки дополнительных полей

#### Scenario: История одного поля
- **WHEN** поле создано, затем переименовано
- **THEN** оба события ссылаются на один и тот же субъект и показывают его текущее название

#### Scenario: Удалённое поле
- **WHEN** сотрудник открывает событие поля, которое затем удалили
- **THEN** субъект показан как недоступный, без ссылки и без UUID вместо названия
