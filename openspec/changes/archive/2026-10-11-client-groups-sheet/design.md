## Context

Мотивация — в proposal.md, требования — в `specs/web-client/client-groups/spec.md`. Что есть сейчас:

- `web/src/clients/ClientGroupsSection.tsx` — чипы групп с крестиком (`clients/remove-from-group`) и `ClientAddToGroupSheet`: шторка снизу, группы из `groups/list-for-select`, уже записанные скрыты, клик по группе сразу вызывает `clients/add-to-group` и закрывает шторку.
- `web/src/ui/ChecklistSheet.tsx` — панель справа на `EditSheet`: чекбоксы, поиск, `submitLabel`, черновик отметок как `Set<Id>`, `dirty` = черновик отличается от `selected`, `onSubmit(ids) → Promise<string | null>` (строка — ошибка, панель остаётся с прежними отметками). Используется для дисциплин и тренеров группы, ролей сотрудника.
- `ClientPickerSheet` уже показывает недоступных клиентов: чекбокс `disabled`, причина серым справа от имени.
- Сервер: `clients/add-to-group { groupId, clientIds[] }` — одна группа, идемпотентно (`ON CONFLICT DO NOTHING`). `groups/list-for-select` — все группы филиала, архива групп нет.
- `ClientDetailPage` передаёт в секцию `onChanged`, который инвалидирует `clients/detail`; сейчас результат не ожидается (`void`).

## Goals / Non-Goals

**Goals:**
- Перевести добавление в группы на `ChecklistSheet` без нового компонента выбора.
- Запись в несколько групп — одной транзакцией, без состояния «записан в часть групп».

**Non-Goals:**
- Изменение поведения `ChecklistSheet` для существующих потребителей (дисциплины, тренеры, роли): без `disabledReason` всё работает как раньше.

## Decisions

### 1. Заблокированные записи в `ChecklistSheet` — поле `disabledReason` у записи

`ChecklistItem` получает необязательное `disabledReason?: string`. Строка с ним:
- чекбокс `disabled`, отображается неотмеченным (`checked = draft.has(id) && disabledReason === undefined`);
- причина выводится серым справа от подписи — так же, как в `ClientPickerSheet`;
- поиск её находит, как любую другую.

*Альтернатива:* отдельный проп `unavailable: ReadonlyMap<Id, string>`, как в `ClientPickerSheet`. Отклонено: у `ChecklistSheet` записи и так приходят готовым списком от экрана, причина — свойство записи, а не отдельная структура, которую надо держать согласованной со списком.

*Альтернатива:* передать уже записанные группы в `selected` и заблокировать — «отмечено и нельзя снять». Отклонено: тогда `dirty` и подтверждаемый набор смешивают «уже есть» и «добавить», а `onSubmit` пришлось бы вычитать.

### 2. Подтверждаемый набор — только доступные отмеченные записи

`onSubmit` получает `draft` за вычетом записей с `disabledReason`; по этому же набору считаются `dirty` и доступность кнопки. Черновик сам по себе не чистится: если запись стала заблокированной, пока панель открыта (новые `items` после перечитывания), она молча выпадает из набора. Чистка черновика эффектом при смене `items` дала бы тот же результат, но с лишним рендером и состоянием, которое легко рассинхронизировать.

### 3. Новый маршрут `clients/add-to-groups` — одна транзакция

```
POST /clients/add-to-groups
AddClientToGroupsRequest { clientId: ClientId, groupIds: List<GroupId> }  ->  Unit

db.transaction {
    enrollments.addToGroups(request.clientId, request.groupIds)
}
```

- Маршрут собирается из существующего `Enrollments.add(groupId, clientIds)`: проверка принадлежности группы организации, идемпотентность (`ON CONFLICT DO NOTHING`), ошибка `CLIENT_NOT_FOUND` и аудит через `AuditEnrollments` — всё как у `clients/add-to-group`.
- Атомарность даёт `Database.transaction`: `raise` внутри блока — исключение, транзакция откатывается целиком, `either` маршрута превращает его в ответ с ошибкой.
- `addToGroups` — функция-расширение `Enrollments` рядом с интерфейсом, вызывающая `add` для каждой группы; DB-тест проверяет её вместе с транзакцией. Членом интерфейса она не сделана: реализация по умолчанию, вызывающая `add`, при делегировании `AuditEnrollments ... by delegate` ушла бы мимо аудита, а отдельная реализация в обоих классах — дублирование. Расширение вызывает `add` конкретного экземпляра, поэтому аудит сохраняется. Usecase-слой не заводится — так устроены и `add-to-group`/`remove-from-group`.
- Пустой `groupIds` — no-op: фронт его не отправляет (подтверждение недоступно без отметок), серверу отдельная ошибка не нужна.

*Альтернатива:* последовательные вызовы `clients/add-to-group` с фронта. Отклонено: при ошибке на второй группе клиент оказывается записан в часть групп, а пользователь видит ошибку — состояние «наполовину» приходится объяснять в интерфейсе.

*Альтернатива:* расширить `AddClientsToGroupRequest` до `groupIds[]`. Отклонено: запрос «многие клиенты × многие группы» никому не нужен, а у карточки группы и карточки клиента разные формы запроса.

### 4. Обновление данных после успеха

`onChanged` секции становится `() => Promise<void>`, `ClientDetailPage` передаёт ожидаемую инвалидацию `clients/detail`. Секция дополнительно инвалидирует `clients/list` (колонка групп в списке клиентов), `groups/list` и `groups/detail` (состав групп). При ошибке состав не менялся — перечитывать нечего, `onSubmit` сразу возвращает текст ошибки (`apiErrorMessage`). Тост «Добавлено в группы: N» — после успешного перечитывания.

Крестик на чипе использует тот же набор инвалидаций.

### 5. Строки

Новые: заголовок панели «Добавить в группы», тост «Добавлено в группы: {count}». Переиспользуются: кнопка — `action.add`, причина — `groups.detail.alreadyInGroup`, поиск — `clients.detail.searchGroup`, пустой список — `groups.empty`. Действие в заголовке секции остаётся «Добавить в группу».

## Risks / Trade-offs

- [Клиента записали в отмеченную группу параллельно, пока панель открыта] → `ON CONFLICT DO NOTHING`: повторная запись — no-op, операция успешна.
- [Одна недоступная группа валит всю операцию] → это и есть требуемое «всё или ничего»; панель остаётся с отметками, пользователь снимает проблемную группу и повторяет.
- [`disabledReason` расширяет общий компонент] → поле необязательное, существующие потребители не меняются; покрывается тестом `ChecklistSheet.test.tsx`.
- [Группы клиента из другого филиала] → `list-for-select` отдаёт только текущий филиал; такие группы видны чипами, в панели их нет — как и сейчас.

## Migration Plan

Новый маршрут только добавляется, существующие не меняются: сервер и фронт выкатываются одним деплоем, откат — откатом коммита.
