# Design

## Context

Мотивация и границы описаны в `proposal.md`. Сейчас `RouteWithContext.contextFromRequest` в отдельной транзакции читает валюту организации и `Employees.byId`. Последний делегирует в `DbEmployees.byIds`, где последовательно загружаются весь каталог ролей организации, назначения ролей, персональные права, филиалы и запись сотрудника. `AssistantService.status` повторяет загрузку сотрудника в своей транзакции.

`DbEmployeeDetailView` уже использует коррелированные JSONB-агрегаты для связанных коллекций. Его HTTP-проекция содержит только ID и имя роли; для доменного `EmployeeRole` дополнительно нужны права. `EmployeePermission` вычисляет персональные выдачи/отзывы, а `DbEmployee.hasPermission` сохраняет особое правило владельца. Эти правила не переносятся в SQL.

Дизайн нужен из-за сочетания оптимизации общего метода чтения и требований к актуальности авторизации.

## Goals / Non-Goals

**Goals:**

- Один запрос к драйверу для непустого `byIds`, включая случай одного сотрудника, без роста числа запросов при нескольких ID.
- Существующие доменные типы, интерфейсы и декораторы без отдельного пути загрузки для HTTP-контекста.
- Явное различие между снимком для статуса и повторной проверкой перед командой после долгого ожидания модели.

**Non-Goals:**

- Изменения JWT, проверки аутентификации, HTTP-контрактов и кодов ошибок.
- Кэширование доступа в этом change, параллельные запросы на одном соединении, настройка пула, удаление BEGIN/COMMIT или объединение транзакций контекста и обработчика. Спека требует только, чтобы изменения, зафиксированные до запроса, были видны в нём; будущий кэш прав обязан это сохранить (инвалидацией), а не запрещён спекой.
- Общая библиотека SQL-проекций либо обязательное ускорение ответа на заданное число миллисекунд.

## Decisions

### 1. Объединить чтение в общем `DbEmployees.byIds`

Оставить ранний выход для пустого набора, дедупликацию ID и проверку числа найденных сотрудников. Основной запрос начинается с `employees e WHERE e.org_id = :orgId AND e.id = ANY(:ids)` и возвращает одну строку на сотрудника. Роли с их правами, персональные выдачи/отзывы и филиалы агрегируются независимыми коррелированными подзапросами; пустые коллекции возвращаются как `[]`.

Роли выбираются только из назначений данного сотрудника, с `r.org_id = e.org_id`. Права каждой роли агрегируются вложенным подзапросом по `role_permissions`, а не `LEFT JOIN` с `FILTER`: так роль без прав сохраняется с `[]` и не превращается в `[null]`. Каждая коллекция оборачивается в `COALESCE(jsonb_agg(...), '[]'::jsonb)`. Нужные индексы уже есть: `idx_employee_roles_employee_id`, `UNIQUE (employee_id, permission_key)`, PK `employee_branches (employee_id, branch_id)`, PK `role_permissions (role_id, permission_key)`. Филиалы и персональные права привязаны к выбранной записи сотрудника, как в существующей модели. Несколько коллекций не соединяются общим плоским JOIN, чтобы не создавать произведение ролей, прав и филиалов.

Использовать существующие JSON-декодирование и доменные конструкторы. Если для роли потребуется десериализуемая форма, держать её приватной рядом с загрузчиком и преобразовывать в `EmployeeRole`; HTTP DTO не становятся зависимостью доменного репозитория. `DbRoles` остаётся для каталога и разрешения назначений при записи, поэтому `roles` остаётся в конструкторе `DbEmployees` (`new`, `roleCatalog` у `DbEmployee`); устаревшие вспомогательные методы чтения в `DbEmployees` удаляются.

Альтернативы: объединение только ролей уменьшит пять запросов до четырёх, но оставит последовательные обращения для независимых коллекций. Отдельный загрузчик контекста продублирует отображение данных и правила доступа. Один SQL использует уже существующий в проекте подход без нового API или кэша.

### 2. Сохранить семантику и всех вызывающих общего метода

`byId` продолжает делегировать в `byIds`; `EMPLOYEE_NOT_FOUND` сохраняется и для отсутствующего единственного ID, и для частично найденного набора. Порядок сотрудников не объявляется новым контрактом: сейчас `ORDER BY` отсутствует. Признаки активности и владельца, пользователь, контакты и данные, нужные для последующего `save/invite/withNew`, загружаются полностью.

Проверка совместимости охватывает `RouteWithContext`, `DbAuth`, `EmployeesRoutes`, группы, занятия, назначение задач, `ClosePendingNotice` и делегирующие `AuditEmployees`/`EmailEmployees`. Изменять их интерфейсы и реализации без выявленной необходимости не требуется. Существующий кэш организации не затрагивается.

### 3. Удалить повторное чтение только из `AssistantService.status`

`status` использует `ctx.employee.isActive && ctx.employee.hasPermission(CAN_USE_ASSISTANT)`. Транзакция для `storage.settings` остаётся. `available`, `enabled` и независимое от них значение `permitted` сохраняют смысл.

Граница актуальности статуса — снимок, загруженный при сборке контекста этого запроса. Если доступ изменён после снимка, текущий статус может отразить прежнее значение; следующий запрос читает новые данные. Это не разрешение на исполнение команд. `access()` и `requireOwner()` продолжают перечитывать сотрудника, в частности перед tools после ожидания модели. Тест `AssistantGuardTest.reloadsPermissionBeforeSavingTool` остаётся обязательным.

Альтернатива — оставить вторую загрузку: она уменьшает окно между чтением сотрудника и выдачей статуса, но не гарантирует актуальность после выдачи ответа и сохраняет необязательную работу. Общее удаление всех повторных проверок отвергнуто: оно допускает сохранение клиента после отзыва права во время ответа модели.

### 4. Проверять число SQL тестом, время — простым замером

Число statements — деталь реализации, поэтому фиксируется тестами и этим design, а не нормативной спекой.

**Загрузчик.** В `DbEmployeesTest` небольшой тестовый декоратор `Transaction` считает вызовы `sql()` и делегирует настоящему PostgreSQL; BEGIN/COMMIT идут мимо `sql()` и не считаются. Для `byIds` каждый вызов `sql()` исполняется, поэтому счёт вызовов равен счёту statements. Цель: 1 для непустого набора (включая повторы ID), 0 для пустого. Тест пишется первым и падает на старом коде с фактическим значением 5 — это и есть подтверждение исходной цифры.

**Статус помощника.** `Database.transaction` создаёт `LazyTransactionScope` сам, и декоратор `Transaction` в HTTP-тест без production-изменений не попадает. Поэтому на уровне HTTP считаются вызовы загрузки: тестовый декоратор `Employees` считает `byId/byIds` и подставляется через `Di.copy` и в контекст маршрутов, и в `AssistantService`. Цель: 1 вызов на запрос `assistant/status` (сейчас 2); вместе с тестом загрузчика это даёт 10 → 1 statements.

| Загрузка сотрудника | Сейчас | После |
| --- | ---: | ---: |
| Контекст одного запроса | 5 | 1 |
| Контекст и `assistant/status` | 10 | 1 |

Пять параллельных контекстов — это 5 × строка 1 (25 → 5), отдельно не измеряются.

**Время.** Issue требует сравнить время сборки контекста до/после на прогретом приложении. Достаточно одного сценария: сотрудник с несколькими ролями, персональными правами и выбранными филиалами; прогрев (например, 200 запросов, в выборку не входят), затем N последовательных HTTP-запросов к простому защищённому эндпоинту с замером `contextFromRequest`. Одинаковые данные, JVM и PostgreSQL до и после. Результат (среда, ревизии, медиана до/после) — в `measurements.md` этого change. Это не тест с порогом задержки; выигрыш в миллисекундах не обещается. Без сопоставимой среды критерий остаётся явно незавершённым.

## Risks / Trade-offs

- [Размножение строк или потеря ролей без прав] --> Независимые агрегаты, пустые коллекции и интеграционная проверка нескольких ролей, прав и филиалов у двух сотрудников.
- [Нарушение изоляции организаций] --> Фильтр организации на сотруднике и роли; тесты чужого сотрудника, смешанного набора и отсутствие выдачи чужой роли.
- [Изменение приоритета прав или режима филиалов] --> Существующие доменные правила сохраняются; проверки владельца, персонального запрета, `All` и пустого `Selected`.
- [Сложный SQL уменьшает round-trip, но может увеличить работу БД на больших наборах] --> Подзапросы коррелированы по `employee_id`/`role_id`, все нужные индексы уже есть; новые индексы не добавлять.
- [Статус может устареть внутри запроса] --> Явный контракт снимка; повторная авторизация перед командами остаётся.
- [Прогрев JVM маскирует эффект] --> Прогрев не входит в выборку, одинаковая среда до/после, без обещания выигрыша.

## Migration Plan

Миграции БД и клиентского контракта не требуются. После регрессионных проверок и сравнительных замеров изменение разворачивается обычным обновлением сервера. Откат — возврат предыдущей версии сервера: сохранённые данные и схема не меняются. Перенос delta specs в основные спецификации выполняется отдельным шагом завершения OpenSpec change.
