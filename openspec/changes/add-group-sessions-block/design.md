## Context

Карточка группы (`web/src/groups/GroupDetailPage.tsx`) — одна колонка `max-w-3xl`: заголовок, дисциплины, расписание (слоты), тренеры, клиенты. Каркас приложения на `lg` отдаёт под боковое меню 15rem, поэтому на контент остаётся около 720px при ширине окна 1024px и около 976px при 1280px.

Что уже есть:
- `read/schedule/DbScheduleView` — занятия филиала за период (≤ 62 дней) с названиями зала, тренеров и дисциплин, тренеры собираются JSONB-агрегатом по `session_employees`. Фильтра по группе нет.
- Модель занятия хранит всё, что нужно для бейджей: `is_rescheduled` и `origin_date` (исходная дата по расписанию), `origin_slot_id IS NULL` — занятие вне расписания, `is_employee_assignment_overridden`.
- Журнал посещаемости (`0067-session-attendance`) — источник «пришли из состава» для проведённого занятия.
- «Наступило ли занятие» уже считается в `DbSession` как `(s.date + s.start_time) AT TIME ZONE o.timezone <= now()`.
- Действия в карточке занятия (`SessionDetailPage`) частично на моках — одна из причин, по которой блок только читает.

Мотивация и объём — в proposal.md, требования — в `specs/group-sessions` и `specs/schedule`.

## Goals / Non-Goals

**Goals:**
- Одна read-проекция, отдающая блок целиком за один запрос: строки периода и закреплённые последнее/ближайшее.
- Раскладка, при которой длинный состав группы не отодвигает занятия за первый экран.

**Non-Goals:**
- Переиспользование `schedule/list` как источника блока.
- Кэширование, бесконечная прокрутка, выбор произвольного периода календарём.

## Decisions

### 1. Две колонки со sticky-клиентами вместо вкладок

```
xl и шире                                        уже xl
+-----------------------------------+----------+  +------------------+
| Название               [Редакт.]  |          |  | Название         |
+-----------------------------------+ Клиенты  |  | Дисциплины       |
| Дисциплины                        | (sticky, |  | Расписание       |
| Расписание                        |  своя    |  | Тренеры          |
| Тренеры                           |  прокр.) |  | Занятия          |
+-----------------------------------+          |  | Клиенты          |
| Занятия  [<] период [>] [Календ.] |          |  +------------------+
|  последнее / ближайшее            |          |
|  список окна                      |          |
+-----------------------------------+----------+
```

Сетка `xl:grid xl:grid-cols-[minmax(0,1fr)_20rem]`, контейнер расширяется с `max-w-3xl` до `max-w-6xl`. Колонка клиентов — `xl:sticky` под шапкой приложения с `max-h` по высоте экрана и `overflow-y-auto`.

Почему так: занятиям нужна ширина (дата, время, зал, тренеры, статус, бейджи, посещаемость), клиентам — высота (имя и крестик). Брейкпоинт `xl`, а не `lg`: на `lg` основной колонке осталось бы около 400px.

Рассмотренные альтернативы:
- *Вкладки «Обзор / Занятия»* (вариант из комментария к #60) — прячут то, что помещается рядом, и вводят в карточку паттерн, которого в приложении нет.
- *Клиенты справа от коротких блоков, занятия во всю ширину ниже* — при группе в 20+ клиентов слева остаётся пустота, а занятия уходят за первый экран; ограничивать список клиентов окошком хуже, чем закрепить колонку.
- *Тренеры во второй колонке* — отклонено: тренер у группы чаще всего один, отдельная колонка ему не нужна.

На узком экране порядок — занятия перед клиентами: карточку группы чаще открывают ради «когда ближайшее», чем ради состава.

### 2. Отдельная проекция `read/groups/` вместо `schedule/list` с фильтром

Проекция `GroupSessionsView` (рабочее имя) в `read/groups/`, маршрут чтения в `GroupsRoutes`, собственные схемы запроса/ответа в `api.schemas.groups`.

Почему не `schedule/list` + `groupId`: строке нужны поля, которых карточка календаря не показывает и которые ей не нужны (исходная дата переноса, ручное занятие, замена тренера, посещаемость), а закреплённые последнее/ближайшее лежат вне периода — их не получить фильтром по датам. Расширять общую схему расписания под нужды одного экрана противоречит правилу «проекция под экран». Фрагмент SQL агрегата тренеров переиспользуется (вынести в общую константу `read/`).

Ответ (рабочие имена): `sessions` — строки периода; `last`, `next` — nullable строки. Строка: `id`, `date`, `startTime`, `endTime`, `hall {id, name}`, `coaches [{id, name}]`, `coachesOverridden`, `status`, `rescheduledFrom: LocalDate?` (заполнено, только если занятие перенесено и `origin_date` отличается от `date`), `isManual`, `attendance: {present, total}?` (только для `COMPLETED`).

Запрос: `groupId`, `from`, `to`; проверки периода — в маршруте, лимит длины — тот же 62 дня, что у расписания (окно блока — 43 дня). Группа ищется в `ctx.orgId` и `ctx.branchId`; не найдена — `GROUP_NOT_FOUND`/404.

### 3. Последнее и ближайшее — в той же проекции, по часовому поясу организации

Два дополнительных подзапроса `ORDER BY date, start_time LIMIT 1` в обе стороны от `now()`, с тем же сравнением `(date + start_time) AT TIME ZONE o.timezone`, что и в `DbSession`. Последнее — неотменённое (`scheduled` или `completed`) занятие, начало которого наступило; ближайшее — `scheduled`, начало не наступило. Отдельный запрос на клиенте отклонён: блок отрисовывается одним ответом и не мигает частями.

Индекс по `(group_id, date)` — проверить при реализации; без него поиск последнего занятия у старой группы идёт по всей истории.

### 4. Посещаемость — подзапросом по журналу

Для проведённого занятия: `present` — отметки «пришёл», `total` — состав занятия на момент закрытия (снимок журнала). Для остальных статусов — `null`: незакрытый журнал — черновик, у отменённого отметки аннулированы (см. `attendance-journal`).

### 5. Окно и пагинация — на клиенте, без адреса

Окно `[today − 14, today + 28]`, шаг сдвига — длина окна (43 дня, обе границы включительно). Состояние окна — локальный `useState` карточки, не search-параметры: окно вторично для страницы, и ссылка на карточку группы не должна зависеть от того, куда пользователь листал. Запрос через `apiQuery` с ключом `[branchId, groupId, from, to]`.

### 6. Фильтр по группе в расписании

`ScheduleListRequest`/`ScheduleQuery` получают `groupIds` (в запросе — пустой список по умолчанию, в `ScheduleQuery` — `null`) по образцу остальных фильтров (`AND s.group_id = ANY(:groupIds)`). В search-параметрах расписания — `groupIds`. Отдельный выпадающий выбор групп на странице расписания не добавляется: фильтр приходит только по ссылке из карточки и показывается снимаемым чипом с названием группы. Название берётся из списка групп филиала (`groups/list-for-select` — только id и название, запрашивается лишь при активном фильтре) — без нового эндпоинта; если группы в списке нет, чип показывает общий текст «Группа».

Множественное значение (`groupIds`, а не `groupId`) — ради единообразия с остальными фильтрами и будущего выбора групп в расписании.

## Risks / Trade-offs

- [Колонка клиентов sticky внутри страницы с sticky-шапкой] → смещение `top` равно высоте шапки (`top-14`), `max-h-[calc(100dvh-...)]`; проверить в браузере на `xl` и при прокрутке длинной группы.
- [Поиск последнего занятия по всей истории группы] → индекс по `(group_id, date)`; DB-тест на группу с занятиями вне окна.
- [Блок сильнее нагружает карточку группы: ещё один запрос на каждое открытие] → запрос независим от `groups/detail`, рендерится своим состоянием загрузки и не блокирует остальные секции.
- [Ближайшее за горизонтом материализации (#45)] → если будущие занятия ещё не созданы, ближайшего не будет; при горизонте 3 месяца и регулярном расписании на практике не проявится.
- [Пользователь ждёт действий из строки] → строка целиком — ссылка в карточку занятия, где действия есть; кнопок в строке нет, чтобы не обещать недоступное.
