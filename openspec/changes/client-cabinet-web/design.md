## Context

Мотивация и шаги — см. proposal.md. Требования — `specs/client-app-*/spec.md`,
`specs/client-cabinet-web/spec.md` и `specs/attendance-journal/spec.md`.
Макеты экранов мобильного приложения — [mockups/](mockups/README.md) (копия строк
«Подключение и вход», «Приложение клиента», «CRM» из https://claude.ai/artifact/USGK1UdgF7BxB3kEoDS8ox) — отправная точка для дизайна кабинета;
экраны магазина, оплаты, QR и ввода дат рождения в изменение не входят.

Что уже есть и на что опираемся:

- **Аутентификация** только для сотрудников: `JwtConfig` (HMAC256, issuer `athletica-crm`,
  audience `athletica-crm-users`), access и refresh в HttpOnly cookie с `SameSite=Strict`
  (`AuthRoutes.setJwtCookies`), провайдер `auth-jwt` в `Application.kt`,
  `EmployeeRequestContext` — вариант `sealed interface RequestContext` (есть ещё
  `SystemRequestContext`, `AdminRequestContext`). Около 86 файлов `domain/`, `usecases/` и
  `routes/` принимают `context(ctx: RequestContext)`.
- **Контакты клиента** — `domain/clientcontacts`: `ClientContact(type, value)`, нормализация
  `PhoneDigits`, поиск `clientsByPhone(phone)` внутри организации. `DbClientContacts.replace` —
  единственное место, которое пишет в `client_contacts`; вызывается из `ClientsRoutes`
  (создание и изменение клиента), из инструментов ассистента `ClientDrafts` и `ImportDrafts`
  и из `DemoData`. Импорт и демо-данные только создают клиентов, номера у существующих не меняют.
- **Сеансы сотрудников** — `AuthSessions`/`DbAuthSessions` (`auth-sessions`): запись сеанса с
  `refresh_jti`/`prev_refresh_jti`/`rotated_at`, ротация refresh с окном 60 с, завершение сеанса
  при повторном предъявлении старого refresh, `requireActive` на каждом защищённом запросе.
- **Клиент**: архивирование через `ActiveClient.archive()`.
- **Каналы** — `sealed interface ChannelConfig` в `shared` с `addressing`
  (`ByContact(PHONE)` у SMS-каналов, `ByBinding` у Telegram-бота), отправка через
  `MessageDispatcher` и `deliveries`.
- **Сессии**: `origin_date`, `origin_start_time`, `is_rescheduled`, `cancelled_at`, `completed_at`
  — хватает для «Перенесено с 10:00» и «Отменено».
- **Задачи** допускают системного автора и отсутствие исполнителя (`tasks`).
- **Веб-фронтенд CRM** — `web/` (Vite + React + TypeScript, строгие правила, `npm run check`),
  образ `frontend` (CRM + лендинг). Контракты генерирует `:server:generateWebContracts` в один
  файл `web/src/api/generated/contracts.ts` из всех зарегистрированных маршрутов.
- **nginx** (`nginx/prod.conf.template`): `${DOMAIN}` — лендинг, `app.${DOMAIN}` — CRM и `/api/`,
  сертификат один на все имена; адрес CRM в письмах — `CRM_PUBLIC_URL`.

## Goals / Non-Goals

**Goals:**
- Клиентский контур полностью отделён от контура сотрудников: отдельные токены, контекст,
  маршруты, хост. Клиентский токен не может вызвать ни один маршрут CRM, и наоборот.
- Данные клиента не покидают сервер до подключения доступа — проверка в каждой проекции, а не
  только в UI.
- Клиентское API пишется под общие для веба и мобильных требования: мобильные приложения
  добавляют только способ передачи токена и экраны.
- Каждый шаг из proposal выкатывается отдельно и не ломает предыдущие.

**Non-Goals:**
- Общий npm-пакет для `web/` и `cabinet/`.
- Офлайн-режим и PWA-установка кабинета; WebSocket — обновление по запросу.
- Передача токена заголовком `Authorization` — в `client-mobile-android`.

## Decisions

### 1. Порты и схемы — до остального ядра

- **Порт `VerificationCodeSender`** (`domain/clientapp/codes`) — граница между политикой
  доставки (§8) и способами доставки организации:

  ```kotlin
  enum class CodeChannel { TELEGRAM, SMS }

  interface VerificationCodeSender {
      val channel: CodeChannel

      context(raise: Raise<CodeDeliveryError>)
      suspend fun send(phone: PhoneDigits, code: VerificationCode)
  }

  sealed interface CodeDeliveryError : AppError {
      data object Undeliverable : CodeDeliveryError
      data class Failed(val reason: String) : CodeDeliveryError
  }
  ```

  Реализации `TELEGRAM` и `SMS` — в этом изменении (§8). При `development` в `Di.kt` вместо них
  подключается заглушка, которая пишет код в лог и отвечает успехом.
- Порт push (`ClientAppPushes`) в это изменение не входит: здесь у него нет вызывающих. Его
  заводит `client-app-chat`, первый потребитель.
- **Схемы клиентского API** (`shared/commonMain`, `api.schemas.clientapp.*`) добавляются по
  шагам, вместе с маршрутами шага. Отдельного PR «все схемы сразу» нет: веб-кабинет пишется
  вместе с сервером, а мобильные изменения начинаются после всех шагов.

### 2. Кабинет — отдельный проект `cabinet/`

- Корневой каталог `cabinet/` рядом с `web/` и `e2e/`: Vite + React + TypeScript, собственный
  `package.json`, `Dockerfile` и образ `cabinet`.
- Строгость как в `web/`: конфигурации `tsconfig`, ESLint `strictTypeChecked`,
  `type-coverage --strict` 100%, prettier, vitest копируются; `npm run check` в Docker-сборке и
  CI. Раздел «When touching `cabinet/`» в CLAUDE.md.
- UI-компоненты shadcn копируются в проект (так устроен shadcn), дальше живут своей жизнью.
  `api/client.ts` и i18n-подход берутся из `web/` и адаптируются: другая обработка истёкшего
  сеанса, свой словарь.
- *Альтернатива — второй вход в `web/`, как `landing/` и `widget/`:* меньше копирования, но
  кабинет выпускается вместе с CRM, делит с ней зависимости и `npm run check`, а дизайн
  кабинета (телефон, другая аудитория) расходится с CRM. Общий npm-пакет при двух потребителях
  с разными нуждами не окупается; вернёмся, если копируемый код начнёт расходиться с ошибками.

### 3. Хост `clients.${DOMAIN}`

- Новый блок `server` в `nginx/prod.conf.template`: `/api/client-app/` → `server:8080`,
  остальное → `cabinet:80`. Маршруты CRM (`/api/*` кроме `/api/client-app/`) и
  `/api/client-app-admin/` на этом хосте не проксируются — `404` от nginx.
- Заголовки уровня `server`: `X-Robots-Tag: noindex, nofollow`,
  `Content-Security-Policy: frame-ancestors 'none'`, как у CRM.
- Имя `clients.${DOMAIN}` добавляется в сертификат по процедуре `DEPLOY.md`
  (`certbot --expand`). Изменение nginx и compose требует прогона `mise run e2e`.
- Запросы кабинета идут на свой же хост: CORS не нужен.
- Адрес кабинета в приглашениях — `CABINET_PUBLIC_URL`, по умолчанию `https://clients.${DOMAIN}`,
  по аналогии с `CRM_PUBLIC_URL`; в `application.conf`, `docker-compose.prod.yaml` и
  `.env.prod.example`.

### 4. Отдельный контур аутентификации клиентов

- Новый JWT-аудиенс `athletica-client-app`, свой провайдер `client-jwt` в `Application.kt`.
  Access-токен 15 минут, refresh — 60 дней.
- Веб: токены в HttpOnly cookie с `Secure`, `SameSite=Strict`, без атрибута `Domain` (только
  хост кабинета), со своими именами, отличными от cookie CRM. Путь access-cookie —
  `/api/client-app`, refresh-cookie — только `/api/client-app/auth/refresh`, как у CRM
  (`REFRESH_TOKEN_COOKIE_PATH`): refresh не уходит с каждым запросом.
  Так cookie CRM на `app.${DOMAIN}` и cookie кабинета никогда не встречаются в одном запросе.
  Запись cookie — тот же приём, что `AuthRoutes.setJwtCookies`.
- Мобильные приложения позже передают те же токены заголовком: провайдер `client-jwt`
  расширяется в `client-mobile-android`, домен и проекции не меняются.
- Сеансы — по образцу `DbAuthSessions` (`auth-sessions`): access-токен несёт идентификатор
  сеанса, `validate` провайдера `client-jwt` проверяет, что сеанс жив (иначе 401); refresh
  ротируется с окном 60 с, повторное предъявление заменённого refresh позже окна завершает
  сеанс. Завершение сеанса удаляет запись — следующий же запрос получает 401. Код
  `DbAuthSessions` не обобщается: таблицы и ключи разные (аккаунт вместо пользователя и
  организации), а общая часть — несколько SQL-запросов.
- Контексты: `ClientAccountContext(accountId, sessionId, lang)` — из токена; у аккаунта нет
  организации. Для запросов по конкретному клиенту routes строят
  `ClientProfileContext(accountId, sessionId, orgId, clientId, currency, lang)` — только после
  проверки доступа (§6).
- `ClientProfileContext` **не** вариант `sealed interface RequestContext`. Иначе все функции с
  `context(ctx: RequestContext)` стали бы по типам вызываемы из клиентских маршрутов, а
  `actingEmployeeId` молча записывал бы клиента в аудит как систему. Клиентский контур вызывает
  только проекции `read/clientapp/*`, собственные команды `domain/clientapp/*` и команды
  других доменов (задачи) — в `SystemRequestContext` организации через `SystemContexts.forOrg`,
  с аккаунтом клиента в данных события аудита.
- *Альтернатива — переиспользовать `users` сотрудников:* смешало бы два мира и права; у
  клиентского аккаунта нет организации и пароля.

### 5. Модель данных

| Таблица | Суть |
|---|---|
| `client_app_accounts` | аккаунт по номеру: `phone_digits` UNIQUE, `terms_accepted_at`, `terms_version`, `deleted_at` |
| `client_app_sessions` | сеанс аккаунта (браузер или устройство): платформа, название (`Safari, iOS`), `created_at`, `last_seen_at`, `refresh_jti`, `prev_refresh_jti`, `rotated_at` — как `auth_sessions` |
| `client_app_codes` | одноразовые коды: `phone_digits`, хэш кода, `created_at`, `expires_at`, `attempts`, канал доставки (`NULL` — не отправлялся); строка пишется на каждый запрос кода, в том числе для постороннего номера, — по ней считаются лимиты |
| `client_app_access` | доступ: `org_id`, `client_id`, `phone_digits`, `status`, `invited_at`, `invite_channel`, `status_changed_at`, `last_seen_at`; UNIQUE (`org_id`, `client_id`, `phone_digits`) |
| `client_app_absence_notices` | предупреждения «Не придём»: `session_id` (занятие, `sessions.id`), `client_id`, `access_id`, время (шаг 5) |

Push-токены заводит `client-app-push` в своей таблице со ссылкой на сеанс
(`ON DELETE CASCADE`).

Код хранится как SHA-256 от `id` строки и кода. Секрет не добавляем: 6 цифр перебираются при
любом хэше, от утечки защищают TTL 5 минут и 5 попыток, а хэш лишь не держит код в открытом
виде в БД и бэкапах. Зато сквозной тест может подставить известный код (§14).

Доступ хранит `phone_digits`, а не ссылку на `client_contacts.id`: контакты заменяются целиком,
идентификаторы контактов не стабильны. Синхронизация — в `DbClientContacts.replace`, в той же
транзакции: для номеров, которых больше нет, доступ → `отключён`; для новых ничего не создаётся
(нет строки = `не приглашён`). Не в отдельном usecase: путь в обход синхронизации оставил бы
старому номеру доступ к данным ребёнка. Номер, удалённый и записанный снова, находит свою
строку в `отключён` и остаётся в нём до нового приглашения: возвращать доступ без участия
сотрудника нельзя.

`client_app_access.last_seen_at` обновляется только запросами по профилю этой организации и
показывается в CRM. Обновляет его не проекция (чтение ничего не пишет), а routes после
успешного ответа: команда `touch` — один `UPDATE` с тем же предикатом доступа (§6) и условием
«прошло больше 5 минут», чтобы не писать на каждый запрос. `client_app_sessions.last_seen_at` — общее для аккаунта, показывается только
самому человеку: иначе организация видела бы активность в другой организации.

Настройка «кабинет включён» — колонка `organizations.client_app_enabled`: одна булева настройка
без истории, изменение — через аудит.

Статус доступа — enum `ClientAppAccessStatus` в `shared`. Агрегат `ClientAppAccess` в
`domain/clientapp/` с переходами по `client-app-access`; недопустимые переходы невыразимы, как у
`ActiveClient`/`ArchivedClient`.

Таблицы шагов 2–6 появляются миграциями своих шагов. Миграции `client-app-chat` и
`client-app-push` ссылаются на таблицы шага 1, поэтому их номер больше (`includeAll` сортирует по
имени файла).

### 6. Проверка доступа на каждом запросе — в проекциях

Все проекции `read/clientapp/*` принимают `ClientProfileContext` и в том же SQL соединяются с
`client_app_access` (статус `подключён`, номер аккаунта запроса), плюс
`organizations.client_app_enabled` и неархивный клиент. Нет строки — `CLIENT_NOT_FOUND`
(одинаково для чужого и несуществующего). Отдельный «middleware-фильтр» не делаем — проверка в
SQL не может разойтись с данными. Тот же предикат используют команды от имени клиента
(«Не придём», `touch`) и `client-app-chat`: команда сначала находит подключённый доступ этим
предикатом и без него отвечает `CLIENT_NOT_FOUND`.

### 7. Подключение без проверки личности сверх кода

- Подключение — команда аккаунта по организации: все доступы его номера в статусе `приглашён`
  переходят в `подключён`. Код подтверждает владение номером; в первой версии этого достаточно.
- Подключение принадлежит доступу, а не сеансу: новый браузер после входа по коду видит
  подключённые профили сразу.
- Риск ошибочного номера закрывают приглашение без данных клиента, «Это не я» с задачей
  администратору и отключение старого номера при правке контактов (§5). Вторая проверка —
  [#314](https://github.com/evtatarintsev/AthleticaCRM/issues/314).

### 8. Коды: политика доставки в ядре, отправители — отдельно

- Запрос кода в транзакции проверяет лимиты, пишет строку `client_app_codes` и отвечает — для
  любого номера одинаково: «код отправлен» и время до следующего запроса, без канала. Доставка
  идёт после ответа, в фоновой корутине приложения, поэтому время ответа не зависит от
  номера и провайдера. Канал по умолчанию — `TELEGRAM`, явный запрос — `SMS`. Если отправитель
  Telegram ответил `Undeliverable`, доставка сразу уходит в SMS; канал, которым код реально
  ушёл, записывается в строку кода. Если не доставил никто — только лог: человек нажмёт
  «Отправить по SMS» (обычный повторный запрос с каналом `SMS` под теми же лимитами), а
  организация видит предупреждение в настройках кабинета.
- Код — 6 цифр, хранится хэшем (§5). Лимиты по `client_app_codes`, общие для всех каналов и
  одинаковые для любого номера: 60 с между кодами, 5 в час, 10 в сутки на номер; 5 попыток на
  код. Дополнительно лимит по IP в nginx на `request-code` и `login` (refresh без лимита: за одним IP много сеансов).
- Вход: запрос несёт номер, код и версию принятых условий (если человек их принял на экране).
  Если аккаунта нет или принята не текущая версия, а версии в запросе нет — ошибка
  `CLIENT_APP_TERMS_REQUIRED` до проверки кода: попытка не тратится, кабинет показывает условия и
  повторяет вход. Промежуточного состояния «код подтверждён, условия не приняты» нет.
- Код платит организация, а не платформа. Плательщиком может быть только организация с
  включённым кабинетом (`client_app_enabled`). Отправитель `TELEGRAM` — адаптер над существующим
  `TelegramGateway` (`telegram-gateway`): среди организаций с включённым кабинетом, где у номера
  доступ `приглашён` или `подключён` и включён Telegram Gateway, берётся организация с самым
  свежим приглашением, и код
  уходит в её `SystemRequestContext` (`SystemContexts.forOrg`). Нет такой организации или Gateway
  ответил `NotConfigured`/`Undeliverable` — `Undeliverable`, и запрос уходит в SMS.
  `GatewayCodeResult.Failed` → `CodeDeliveryError.Failed`. Вызов — вне транзакции, как требует
  `TelegramGateway`.
- Отправитель `SMS` выбирает организацию тем же правилом среди тех, где включён SMS-канал
  (адресация `ByContact(PHONE)`), и отправляет код через `ChannelTransports.transport(config)`
  напрямую, мимо `MessageDispatcher` и `deliveries`: повтор кода бессмыслен, а в переписке клуба
  ему не место. Окончательный отказ провайдера → `Failed`, нет организации → `Undeliverable`.
- Включение кабинета проверяет, что у организации включён Telegram Gateway или SMS-канал
  (`CLIENT_APP_NO_CODE_TRANSPORT`, `client-app-admin`). Проверка — только при включении:
  выключение канала не выключает кабинет, а настройки кабинета показывают предупреждение,
  вычисленное проекцией настроек.
- Номер без доступа `приглашён`/`подключён` в организации с включённым кабинетом получает тот же
  ответ «код отправлен», строка кода пишется (лимиты), но доставка не запускается: платить за
  код некому, а одинаковый ответ требует `client-app-access`.

### 9. Приглашения — статус плюс уведомление «по возможности»

Приглашение — прежде всего смена статуса доступа. Уведомление отправляется через
`MessageDispatcher` по каналам организации с адресацией `ByContact(PHONE)`. Telegram-бот
организации не подходит: он пишет только по привязке. Нет такого канала — приглашение всё равно
действует, сотрудник сообщает клиенту о кабинете сам. Текст — шаблон из i18n с названием
организации и `CABINET_PUBLIC_URL`, без данных клиента.

- *Альтернатива — SMS платформы:* расходы платформы на рассылки организаций и риск блокировки
  отправителя. Отложено.

### 10. Отключение доступа не трогает сеансы аккаунта

Сеанс принадлежит аккаунту, а аккаунт общий для всех организаций. Поэтому «Отключить» в CRM и
автоматические закрытия доступа (номер удалён, клиент в архиве) меняют статус доступа, но не
завершают сеансы: иначе «Динамо» разлогинивала бы маму и из «Волны». Данные закрываются сразу
проверкой в SQL проекций (§6). Завершает сеансы только сам человек — из списка сеансов или
удалением аккаунта.

### 11. Маршруты

- `/api/client-app/auth/*` — запрос кода, вход, refresh, выход (без токена, лимиты).
- `/api/client-app/*` — под `client-jwt`: профили, подключение, «Это не я», данные шагов,
  сеансы, удаление аккаунта. Без path-переменных, ID в теле или query.
- `/api/client-app-admin/*` — под `auth-jwt` (сотрудники, хост CRM): включение, приглашения,
  статусы. `CAN_MANAGE_CLIENT_APP` — включение и массовое приглашение; остальное — любой
  сотрудник организации.
- Генератор контрактов разбивает маршруты по префиксу: `/api/client-app/` (кроме
  `/api/client-app-admin/`) → `cabinet/src/api/generated/contracts.ts`, остальные →
  `web/src/api/generated/contracts.ts`. Задача `generateWebContracts` пишет оба файла, CI-job
  `contracts` проверяет оба; `npm run contracts` есть в обоих проектах.

### 12. Удаление аккаунта

Удаление завершает все сеансы и переводит доступы аккаунта во всех организациях в `отключён`
(отзыв согласия по 152-ФЗ; для мобильных — App Store 5.1.1(v)). Данные учёта остаются у
организаций. Запись аккаунта помечается `deleted_at` с обезличенным номером; повторный вход с тем
же номером создаёт новый аккаунт без прежних подключений.

### 13. Шаги выпуска

Каждый шаг из proposal — отдельные PR «сервер (миграция, домен, проекция, маршрут, тесты) +
экраны кабинета + сквозной тест». Шаг 1 включает инфраструктуру кабинета и CRM-часть:
без приглашения и «Подключить» кабинет бесполезен. Пункты меню кабинета появляются вместе с
шагом; главная получает блок данных вместе с шагом, который отдаёт эти данные.

Шаг 1 выкатывается одним шагом, но выпускается несколькими PR (группы `tasks.md`): каркас и
инфраструктура кабинета (1), домен доступа (2), вход по коду (3), подключение и главная (4),
CRM (5). До PR группы 5 включить кабинет в организации нечем, поэтому промежуточные PR
пользователям не видны.

### 14. Сквозной тест входа по коду

Стенд e2e не может получить код из Telegram или SMS, а подключить Telegram Gateway или SMS-канал
через API нельзя: учётные данные проверяются у провайдера. Поэтому сценарий Playwright ходит в
Postgres стенда напрямую: раннер в той же сети compose, `pg` — dev-зависимость `e2e/`, учётные
данные — из `e2e/stand/e2e.env`. Помощник в `e2e/support/`:

- включает кабинет организации (`UPDATE organizations SET client_app_enabled = true`), минуя
  проверку способа доставки; эту проверку покрывают тесты сервера;
- после запроса кода в интерфейсе заменяет хэш последнего кода номера на хэш известного кода
  (схема хэша — §5).

Приглашение, вход, условия, подключение и главная проходят через интерфейс и API, как у
пользователя. Доставка кода падает в фоне и в результат теста не попадает.

## Risks / Trade-offs

- [Номер записан с ошибкой или передан другому владельцу, и получатель нажал «Подключить»] →
  посторонний видит данные клиента. В первой версии — текст приглашения без данных, «Это не я» и
  отключение номера при правке карточки; проверка личности — #314.
- [Код в `cabinet/` и `web/` расходится: клиент API, компоненты] → осознанная цена отдельного
  проекта; общий пакет заводим, когда копируемый код начнёт чинить дважды.
- [SMS-накрутка через запрос кодов] → лимиты по номеру и IP, Telegram Gateway в приоритете;
  SMS оплачивает организация со своего канала, на неизвестные номера SMS не уходят (§8).
- [Организация выключила все способы доставки после включения кабинета] → её клиенты не
  получат код; настройки кабинета предупреждают об этом. Если номер пригласили несколько
  организаций, код уйдёт за счёт другой, у которой способ доставки есть.
- [Все доступы человека отключены или он нажал «Это не я»] → код ему больше не уходит, войти и
  удалить аккаунт из приложения он не может. Его данных в аккаунте при этом нет (доступы
  закрыты), сеансы, открытые раньше, позволяют удалить аккаунт; иначе — запрос к организации или
  в поддержку. Приемлемо для первой версии.
- [Мобильным понадобится другое API, чем вебу] → требования `client-app-*` пишутся без
  веб-специфики; веб-специфичное — только в `client-cabinet-web` и способе передачи токена.

## Migration Plan

1. Миграции аддитивные; `client_app_enabled` по умолчанию `false` — у существующих организаций
   ничего не меняется до явного включения.
2. Перед выкаткой шага 1: имя `clients.${DOMAIN}` в сертификате, сервис `cabinet` в compose.
3. Откат: выключить кабинет в организациях (данные не теряются); блок `clients.${DOMAIN}` и
   маршруты `/api/client-app/*` можно снять без отката миграций.
