# Командная строка приложения

Приложение поставляется одним исполняемым артефактом `athletica.jar`, который выбирает
режим работы по подкоманде: либо поднимает веб-сервер, либо выполняет административные
операции над данными.

```
athletica serve
athletica admin org find <запрос>...
athletica admin org credit <организация> <сумма> --description=<описание>
athletica admin org debit  <организация> <сумма> --description=<описание>
athletica admin org seed <организация> [--size=small|medium|large] [--seed=<число>]
athletica admin user reset-password <логин>
athletica admin events retry-failed [--org <организация>] [--event <событие>]
```

Справка доступна на каждом уровне: `athletica --help`, `athletica admin --help`,
`athletica admin org --help`. Для справки и разбора аргументов подключение к базе данных
не открывается.

## Запуск

### В продакшене

Административные команды выполняются внутри контейнера сервера — там уже есть и сеть до
базы данных, и переменные окружения:

```bash
docker compose -f docker-compose.prod.yaml exec server java -jar athletica.jar admin org find ЦР
```

Веб-сервер запускается образом по умолчанию (`CMD ["serve"]`), поэтому
`docker-compose.prod.yaml` не задаёт `command:`.

### Локально

Скрипт `bin/athletica` молча пересобирает `athletica.jar` и запускает его с переданными
аргументами. Через [mise](https://mise.jdx.dev) (`mise.toml` в корне) `bin/` добавляется в `PATH`,
и нужная версия Java ставится автоматически:

```bash
athletica serve
athletica admin org find ЦР
```

То же самое через задачи mise: `mise run server`, `mise run admin org find ЦР`
(`--help` передаётся после `--`: `mise run admin -- --help`). Без mise скрипт вызывается
как `./bin/athletica ...`, но тогда в `PATH` должна быть Java 25.

### Переменные окружения

Административным командам нужны те же параметры подключения к базе данных, что и серверу:

- `POSTGRES_URL` — JDBC URL подключения (например, `jdbc:postgresql://localhost:5432/athletica`)
- `POSTGRES_USER` — имя пользователя
- `POSTGRES_PASSWORD` — пароль

Остальные переменные окружения сервера (`JWT_SECRET`, `MINIO_*`, `SMTP_*`, `YOOKASSA_*`)
административным командам не требуются.

## Команды

### `serve` — веб-сервер

Поднимает HTTP-сервер: применяет миграции базы данных и стартует фоновые процессы.
Собственных опций не имеет — конфигурация читается из `application.conf` и переменных
окружения.

### `admin org find` — поиск организаций

Поиск по вхождению подстроки в название организации или в логин её владельца. Принимает
один или несколько запросов; неудача одного запроса не прерывает обработку остальных.

```bash
athletica admin org find ЦР
athletica admin org find ЦР admin
```

Вывод:

```
Результаты для "ЦР":
  019e1c25-7d23-7234-9ef8-160057bc67e4  ЦРФКС  (владелец: admin, валюта: RUB)
```

Если ничего не найдено, печатается сообщение об отсутствии результатов, код возврата
остаётся нулевым.

### `admin org credit` и `admin org debit` — корректировка баланса организации

```bash
athletica admin org credit <организация> <сумма> --description=<описание>
athletica admin org debit  <организация> <сумма> --description=<описание>
```

Аргументы:

- `<организация>` — UUID организации либо её название. Если названию соответствует
  несколько организаций, операция отклоняется, а список подходящих организаций с их
  идентификаторами выводится в поток ошибок.
- `<сумма>` — величина корректировки в основных единицах валюты организации (рубли,
  доллары и т.д.). Валюта операции определяется валютой организации и в командной строке
  не задаётся.
- `--description` — описание операции; обязательно. Вызов без описания отклоняется на
  этапе разбора аргументов, до обращения к базе данных.

Примеры:

```bash
athletica admin org credit ЦРФКС 1000 --description="Тестовое зачисление"
athletica admin org debit 019e1c25-7d23-7234-9ef8-160057bc67e4 500 --description="Возврат средств"
```

Вывод:

```
Организация: ЦРФКС (019e1c25-7d23-7234-9ef8-160057bc67e4)
Корректировка: +1 000,00 ₽
Новый баланс:  15 000,00 ₽
```

### `admin org seed` — наполнение организации демонстрационными данными

```bash
athletica admin org seed <организация> [--size=small|medium|large] [--seed=<число>]
```

Наполняет существующую **пустую** организацию историей работы за несколько месяцев:
филиалы, залы, роли, сотрудники без учётных записей, дисциплины, тарифы, клиенты с контактами
(почта `@example.com`, телефоны `+7 000 …`), группы с расписанием и составом, проведённые
занятия с отметками, продажи абонементов, оплаты, должники, заморозки и задачи.
История заканчивается сегодняшней датой организации. Пользователей и паролей команда не создаёт:
входить в наполненную организацию нужно учётной записью её владельца.

Аргументы:

- `<организация>` — UUID организации либо её название, как в `credit`/`debit`.
- `--size` — профиль объёма, по умолчанию `small`:

  | Профиль | Клиенты | Группы | Филиалы | История, мес. |
  |---|---|---|---|---|
  | `small` | 60 | 6 | 2 | 4 |
  | `medium` | 300 | 15 | 3 | 8 |
  | `large` | 1500 | 40 | 4 | 12 |

- `--seed` — зерно генератора, по умолчанию `1`. Одинаковые профиль, зерно и дата дают одинаковые
  данные с точностью до идентификаторов.

Организация, в которой уже есть клиенты или группы, не наполняется: команда завершается
ненулевым кодом, данные не меняются. Наполнение выполняется одной транзакцией — при ошибке
не остаётся ничего.

Пример для стенда: зарегистрировать организацию через веб-клиент, затем

```bash
mise run admin org seed "Мой клуб"
```

Вывод:

```
Организация: Мой клуб (019e1c25-7d23-7234-9ef8-160057bc67e4)
Клиентов: 60, групп: 6, занятий: 396, продаж: 190
Списания по посещениям применит воркер событий запущенного сервера.
```

Списания абонементов по посещениям и закрытие истёкших абонементов выполняют фоновые задачи
сервера, а не команда: если сервер с этой базой запущен, они применятся в течение нескольких
секунд после наполнения; если нет — при следующем запуске сервера.

### `admin user reset-password` — сброс пароля пользователя

Задаёт пользователю новый пароль без проверки старого. Пользователь ищется по точному
совпадению логина; организацию указывать не нужно: логин уникален во всей системе, и новый
пароль действует во всех организациях, где пользователь — сотрудник.

Пароль передать аргументом или опцией нельзя, чтобы он не попал в историю shell и в список
процессов: команда запрашивает его скрыто и дважды. `docker compose exec` выделяет терминал
по умолчанию, поэтому в продакшене команда работает в обычном виде:

```bash
docker compose -f docker-compose.prod.yaml exec server java -jar athletica.jar admin user reset-password trainer@example.com
```

Вывод:

```
Новый пароль:
Повторите пароль:
Пароль пользователя trainer@example.com изменён
```

Если терминала нет (`exec -T`, перенаправленный stdin), пароль и подтверждение читаются
построчно из стандартного ввода.

Пустой пароль и несовпадение двух вводов отклоняются, пароль при этом не меняется. Других
требований к паролю нет.

Действующие сессии пользователя сброс не завершает: выданные раньше токены работают до
истечения срока refresh-токена. Если аккаунт скомпрометирован, одного сброса пароля
недостаточно.

## Вывод и коды возврата

Вывод рассчитан на чтение человеком и не является контрактом для скриптов: машиночитаемого
режима нет. Денежные суммы печатаются в формате валюты организации. Результаты идут в
стандартный поток вывода, сообщения об ошибках — в поток ошибок.

Ненулевой код возврата означает, что операция не выполнена: неизвестная подкоманда,
отсутствующее `--description`, ненайденная или неоднозначно указанная организация,
ненайденный пользователь, пустой или неподтверждённый пароль, наполнение непустой
организации или недопустимый `--size`, незаданные переменные окружения
с параметрами подключения к базе данных.

## Демо-режим локально

В демо-режиме сервер наполняет каждую регистрируемую организацию профилем `small` прямо при
регистрации, а веб-клиент показывает баннер демо-режима. По умолчанию режим выключен
(`DEMO_MODE=false`) и включается только переменной окружения при запуске:

```bash
DEMO_MODE=true mise run server
```

Затем зарегистрируйтесь через веб-клиент (`cd web && npm run dev`, страница регистрации):
после входа в организации уже есть клиенты, группы с прошлыми занятиями, абонементы, должники
и занятия на сегодня. Регистрация занимает несколько секунд дольше обычного — наполнение идёт
в той же транзакции; если оно не удалось, регистрация отклоняется целиком.

## Требования

- Java 25+ (базовый образ `Dockerfile.server` — `eclipse-temurin:25`)
- PostgreSQL с базой данных AthleticaCRM

### `admin events retry-failed` — перезапуск неуспешных доменных событий

Обработка доменного события (например, списание абонементов при проведении занятия)
повторяется с нарастающей задержкой: 10 секунд, затем вдвое больше, но не реже раза в час.
После 12 неудачных попыток (около 10 часов) событие помечается неуспешным (`failed_at`):
оно не выполнено и больше не выбирается воркером. После устранения причины сбоя событие
возвращается в обработку этой командой — сбрасываются `failed_at`, счётчик попыток и время
следующей попытки.

Без опций перезапускаются все неуспешные события. `--org <uuid>` ограничивает организацией,
`--event <uuid>` — одним событием; опции можно сочетать.

```bash
athletica admin events retry-failed
athletica admin events retry-failed --org 019e1c25-7d23-7234-9ef8-160057bc67e4
```

Вывод:

```
Возвращено в обработку событий: 3
```

Найти неуспешные события можно запросом
`SELECT id, org_id, event_type, last_error FROM domain_events WHERE failed_at IS NOT NULL`.
