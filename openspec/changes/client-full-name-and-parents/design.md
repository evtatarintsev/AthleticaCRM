# Design

## Context

Сейчас клиент хранит ФИО одной колонкой `clients.name VARCHAR(255) NOT NULL` (`0007-create-clients.sql`).
Тип в API — `NonBlankName`. Около 13 проекций `read/` читают `c.name` напрямую: журнал, касса,
задачи, входящие, состав группы, лента действий и другие. Пол `clients.gender` объявлен
`NOT NULL` (`0025-client-gender.sql`), и форма подставляет `MALE`.

Контакты клиента — отдельный домен `domain/clientcontacts`: таблица `client_contacts`, правило
основного внутри типа `List<ClientContact>.normalized()` и поиск клиентов по телефону
`clientsByPhone`. Через `clientsByPhone` входящий чат автоматически привязывается к клиенту
(`usecases/messaging/Inbound.kt`). Маршрут `clients/create` и `clients/edit` сохраняет клиента
и заменяет набор его контактов (`contacts.replace`).

Адресат сообщения сейчас выбирается из контактов клиента правилом `ChannelAddressing` (`shared`).
Проекция `DbClientChannelsView` отдаёт пары «канал × контакт». Напоминаний, рассылок и счетов
пока нет. Правило адресата из `client-parents` они получат, когда появятся.

Продукт не запущен (см. proposal.md), поэтому совместимость старых запросов не нужна.

## Goals / Non-Goals

**Goals:**
- части ФИО хранятся раздельно, а проекции продолжают читать одно отображаемое имя;
- родители хранятся рядом с клиентом и проходят через те же правила контактов;
- один источник правила «кто адресат клиента», общий для отправки и проекции чата.

**Non-Goals:**
- общая «семья», в которой один родитель привязан к нескольким детям (решение владельца);
- создание родителей помощником и импортом;
- приглашение родителя в клиентский кабинет. Это делает `client-cabinet-web`, здесь только
  данные, на которые он опирается;
- напоминания, рассылки и счета как функции.

## Decisions

### 1. ФИО: три колонки и вычисляемое `name`

Новый changeset `0092-client-full-name.sql`:
- добавляет `last_name`, `first_name`, `middle_name`;
- разбирает старое `name` по пробелам: первое слово — фамилия, второе — имя, остальное —
  отчество. Если слово одно, оно становится именем, а фамилия получает `'—'`;
- удаляет `name` и заводит `name TEXT GENERATED ALWAYS AS (concat_ws(' ', last_name, first_name, middle_name)) STORED`.

Так 13 проекций и поиск `c.name ILIKE` работают без правок, а правило «Отображаемое имя
клиента» реализовано в одном месте. Сортировка `NAME` в `DbClientListView` меняется на
`last_name, first_name, middle_name NULLS FIRST`.

Альтернатива — переписать все проекции на `concat_ws(...)`. Это даёт лишь шум в 13 файлах и риск,
что где-то склеят иначе. Отвергнута.

Домен: `Client` получает `lastName: NonBlankName`, `firstName: NonBlankName` и
`middleName: String?` (обрезка и пустое в `null` — в фабрике). Поле `name` остаётся вычисляемым
свойством для аудита и логов. В `shared` `CreateClientRequest` и `EditClientRequest` получают
`lastName`, `firstName`, `middleName` вместо `name`. `ClientDetailResponse` отдаёт и части, и
`name`. Элементы списков оставляют `name`, так как экрану нужно только отображаемое имя.

### 2. Пол — nullable

Changeset снимает `NOT NULL` с `clients.gender`. Для `Gender?` в домене и схемах значение по
умолчанию `null`. Фильтр по полу в списке не находит клиентов без пола; это ожидаемо и в
спецификации не меняется.

### 3. Родители — часть агрегата клиента, отдельный домен по образцу контактов

Таблицы (changeset `0093-client-parents.sql`):
- `client_parents (id, org_id, client_id → clients ON DELETE CASCADE, last_name, first_name,
  middle_name, relation parent_relation, is_primary, position)`, ограничения: частичный уникальный
  индекс `uq_client_parents_primary` на `(client_id) WHERE is_primary` и
  `uq_client_parents_position` на `(client_id, position)`;
- `client_parent_contacts (id, org_id, parent_id → client_parents ON DELETE CASCADE, type, value,
  label, is_primary)` с тем же частичным индексом основного по `(parent_id, type)`, что у
  `client_contacts`;
- enum `parent_relation`: `MOTHER, FATHER, GRANDMOTHER, GRANDFATHER, GUARDIAN, OTHER`.

Домен `domain/clientparents`: `ClientParent(id, clientId, lastName, firstName, middleName,
relation, isPrimary, contacts: List<ClientContact>)`, а также `ClientParents.byClient`, `byClients`
и `replace(client, parents)`. Нормализация `List<ClientParent>.normalized()` по образцу
контактов: ровно один основной, у каждого телефон, контакты через существующий
`List<ClientContact>.normalized()` (правило основного внутри типа не дублируется). Ошибки
`PARENT_PHONE_REQUIRED` и `PARENT_PRIMARY_DUPLICATE`.

`replace` удаляет и вставляет набор, как `contacts.replace`. У родителя нет собственной истории
и ссылок извне, поэтому стабильные id не нужны. Идентификатор родителя генерирует сервер.

Почему отдельные таблицы, а не `client_contacts.parent_id`: тогда в одной таблице жили бы
контакты двух владельцев, и каждый запрос по контактам клиента должен был бы помнить
`parent_id IS NULL`. Это ломает `clientsByPhone`, проекцию каналов и экспорт.

Запрос: `CreateClientRequest.parents: List<ClientParentInput> = emptyList()`, где
`ClientParentInput(lastName, firstName, middleName?, relation, isPrimary, contacts)`.
`ClientDetailResponse.parents: List<ClientParentSchema>`. Маршруты `clients/create` и
`clients/edit` вызывают `parents.replace` в той же транзакции, что и `contacts.replace`.

Сервер не запрещает родителей у взрослого: при редактировании 18-летнего они должны
сохраняться (`client-parents`, «Совершеннолетие ничего не меняет»). Правило «у взрослого при
создании родителей нет» живёт только на форме (`web-client/client-form`).

### 4. Адресат клиента — одно правило в `shared`

Функция `recipientContacts(clientContacts, parents)` в `shared` (рядом с `ChannelAddressing`)
возвращает упорядоченный список кандидатов-адресов. Если есть родители, сначала идут контакты
основного родителя, затем остальных родителей, затем контакты клиента. Иначе только контакты
клиента. Каждый кандидат несёт «владельца» (клиент или родитель с отношением и именем) для
подписи. Первый кандидат, который принимает канал (`accepts`), — адрес по умолчанию.

Правило используют обе стороны, как и `ChannelAddressing`:
- `DbClientChannelsView` дополнительно соединяет `client_parent_contacts` и отдаёт кандидатов с
  подписью «мама, Мария»;
- отправка (`domain/messagedelivery`) проверяет, что выбранный адрес — контакт клиента или его
  родителя.

Шапка карточки (`web-client/client-detail`) показывает первый телефон из того же списка, но
список приходит готовым в `ClientDetailResponse`, а веб не вычисляет порядок сам.

### 5. Поиск и входящие по телефону родителя

- `DbClientListView`: к условию поиска добавляются `EXISTS` по `client_parents` (подстрока
  `concat_ws(' ', last_name, first_name, middle_name)`) и по `client_parent_contacts` с той же
  нормализацией цифр телефона, что у клиента. Нормализацию цифр вынести в SQL-фрагмент, чтобы
  не копировать `regexp_replace`/`CASE` дважды.
- `ClientContacts.clientsByPhone` возвращает объединение клиентов, у которых номер свой или
  родительский (`DISTINCT`). `Inbound.kt` не меняется: `singleOrNull()` уже даёт «двое детей →
  в очередь разбора».

### 6. Форма — переписанная `ClientFormPage`

Компоненты:
- `ClientFormPage` — общая форма создания и редактирования;
- шапка `ClientNameFields`: фото, ФИО, дата рождения с возрастом, пол;
- `ClientParentsFields`: карточки родителей, внутри — существующий `ClientContactsFields` для
  контактов родителя;
- блоки «Контакты клиента» и «Дополнительно».

Видимость блока родителей вычисляет чистая функция `parentsSectionState(birthday, today,
hasSavedParents, manuallyOpened)`. Она возвращает `hidden`, `prompt` (строка «Добавить
родителя»), `open` или `adultWarning` и покрывается unit-тестами vitest. Возраст считается по той
же функции, что и «Пол и возраст под именем» в списке.

Проверка формы — zod-схема на всё значение формы, родители проверяются, только когда блок
`open`. «Отмена» — `navigate` назад, по умолчанию `/clients`.

Выбор пола — сегментный переключатель с `aria-pressed` и снятием повторным нажатием вместо
`RadioGroupField`: у радиогруппы нельзя снять выбор.

Макет: `mockups/client-form.html`. Это кликабельный прототип, его владелец проверил и принял.
Прототип отличается от спецификации в одном месте: строка контакта в нём с выбором типа. Верна
спецификация `web-client/client-contacts` — тип задаётся при добавлении.

### 7. Помощник, импорт, демо-данные, фикстуры

- Черновик клиента помощника (`assistant/tools/ClientDrafts.kt`) и схема инструмента получают
  `lastName`, `firstName` и `middleName`. Описание инструмента требует фамилию и запрещает
  переспрашивать пол.
- Импорт: модель уже сопоставляет «ФИО целиком или по частям». Колонка целиком разбирается
  моделью при сопоставлении, а проверка строки требует фамилию и имя.
- Демо-данные: детям генерировать родителей (мама и, у части детей, папа с телефонами), взрослым
  не генерировать. Пол оставлять у всех, чтобы демо выглядело живым.
- Тестовая фикстура `insertClient(orgId, name)` принимает `lastName`/`firstName` со значениями по
  умолчанию, чтобы сотни вызовов не менялись.

## Risks / Trade-offs

- [Разбор старого `name` в миграции угадывает фамилию неверно] → Реальных клиентов нет. Затронуты
  только тестовые и демо-базы, демо пересоздаётся генератором.
- [Generated-колонка `name` нельзя записать] → Все `INSERT`/`UPDATE` `clients` проходят через
  `DbClient` и фикстуры, их правим в одной задаче. Компилятор этого не поймает, поймают
  DB-тесты.
- [Один и тот же телефон мамы у двоих детей — дубли в импорте] → Импорт сравнивает только
  телефоны клиентов, родителей не создаёт. Совпадение по маминому номеру не исключает строку.
  Поведение не меняется.
- [Клиентский кабинет считает номера карточки только по `client_contacts`] → В proposal есть
  пункт согласования с `client-cabinet-web`: телефон основного родителя должен стать номером
  карточки. Без этого родителей нельзя будет пригласить.
- [Адресат «основной родитель» навсегда, если сотрудник забыл поправить после 18] → Решение
  владельца: автоматическое переключение опаснее, потому что сообщения о долге уйдут не тому,
  кто платит.

## Migration Plan

Два Liquibase changeset (`0092` — ФИО и пол, `0093` — родители) применяются при старте. Откат — восстановление базы из бэкапа, так как
продукт не запущен. Порядок выкладки не важен: веб и сервер собираются из одного коммита.
