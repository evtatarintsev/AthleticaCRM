# Design

## Context

Мотивация — в `proposal.md`. Что есть сейчас:

- `client_contacts(id, org_id, client_id, type, value, created_at)`; доменная сущность
  `ClientContact(id, clientId, type, value)`.
- Единственный, кто пишет в таблицу, — `DbClientContacts.replace`: удаляет все контакты клиента и
  вставляет новый набор. Его вызывают `ClientsRoutes` (создание и изменение клиента) и
  `assistant/tools/ClientDrafts`.
- Контакты читают три места: `DbClientContacts.byClient/byClients` (карточка клиента),
  `read/clients/DbClientListView` (`jsonb_agg` в списке), `read/messaging/DbClientChannelsView`
  (выбор адреса в переписке). Все сортируют по `created_at`.
- `created_at` берётся из `DEFAULT now()`, а `now()` в PostgreSQL — время начала транзакции.
  У всех контактов, записанных одним `replace`, `created_at` одинаковый, так что их порядок сейчас
  не определён. Это нужно исправить: от порядка зависит, какой контакт станет основным, если его
  не отметили.
- Веб: на форме строки `{type, value}` с селектом типа (`ClientContactsFields.tsx`,
  `clientContacts.ts`); шапка карточки берёт первый `PHONE`; `ConversationThread` выбирает
  `contacts[0]` канала.
- Связанный change `client-mobile-app` тоже дописывает `replace` (синхронизация доступов по
  `phone_digits`). Поля, которые добавляет этот change, на ту синхронизацию не влияют.

## Goals / Non-Goals

**Goals:**

- Правило «основного» и нормализация комментария в одном месте, одинаковые для формы, ассистента и
  любого будущего входа.
- Детерминированный порядок контактов, хранимый явно.
- Обратная совместимость API: старый запрос `{type, value}` продолжает работать.

**Non-Goals:**

- Массовые рассылки. «SMS на основной» в этом change — только адрес по умолчанию в переписке.
- Отдельные «основные» под разные цели (для рассылок, для звонков): основной один на тип.
- Справочник ролей («мама», «папа»): комментарий — свободный текст.
- Перетаскивание строк на форме.

## Decisions

### 1. Флаг `is_primary` и колонка `position` в `client_contacts`

Миграция (следующий свободный номер в `db/changelog/changes/`):

- `label TEXT NULL`, `is_primary BOOLEAN NOT NULL DEFAULT false`, `position INT NOT NULL DEFAULT 0`;
- заполнение существующих строк: `position` — `row_number()` внутри клиента по `(created_at, id)`,
  основным — первый контакт каждого типа по `position`;
- частичный уникальный индекс `uq_client_contacts_primary ON client_contacts (client_id, type)
  WHERE is_primary`.

Инвариант «у типа ровно один основной» держит и сама БД: отложенный до конца транзакции
constraint-триггер `ck_client_contacts_one_primary` проверяет пары «клиент, тип», которых коснулась
строка, и отклоняет фиксацию, если основных не один. Частичный индекс дополнительно отсекает два
основных сразу на вставке. Удаление и вставка `replace` идут в одной транзакции, поэтому
отложенная проверка видит только итоговый набор. Понятную ошибку пользователю даёт домен (решение 2);
триггер — гарантия против любого другого писателя, поэтому читатели (шапка карточки, переписка)
полагаются на наличие основного без запасного варианта.

Альтернатива — вычислять основной как «первый по порядку», без флага. Отказались по решению
пользователя: основной — явная отметка, а не побочный эффект порядка.

### 2. Нормализация в `ClientContacts.replace`

`replace` перед записью нормализует набор чистой функцией домена (в `domain/clientcontacts`,
покрыта unit-тестом):

1. комментарий обрезается, пустой → `null`; длиннее `MAX_CONTACT_LABEL_LENGTH` (100) →
   `raise(CommonDomainError("CONTACT_LABEL_TOO_LONG", ...))`;
2. если в типе отмечено больше одного основного → `raise(CommonDomainError("CONTACT_PRIMARY_DUPLICATE", ...))`;
3. если в типе основных нет → основным становится первый контакт типа;
4. порядок: типы идут в порядке появления первого контакта, внутри типа основной первым, остальные —
   в порядке запроса; `position` = индекс в результате.

Почему в домене, а не в маршруте: у `replace` два входа (форма через маршрут, ассистент), и правило
должно совпадать на обоих (см. `domain-write-validation`). `replace` уже работает в
`Raise<AppError>`, `DomainError` подходит без смены сигнатуры.

Почему порядок раскладывается при записи, а не в `ORDER BY`: тогда все три места чтения сортируют
просто по `position`, а правило порядка живёт в одной функции, а не копируется в три SQL.

`ClientContact` получает `label: String?` и `isPrimary: Boolean`.

### 3. API

- `ClientContactInput`: `label: String? = null`, `isPrimary: Boolean = false` — значения по
  умолчанию сохраняют совместимость со старыми клиентами API и с черновиками ассистента.
- `ClientContactSchema`: `label: String?`, `isPrimary: Boolean`. `ClientChannelSchema` использует
  ту же схему, поэтому выбор адреса в переписке получает признак без отдельного изменения.
- После изменения схем — `npm run contracts` и коммит `web/src/api/generated/`.

### 4. Веб-форма

- `ContactFormEntry` = `{type, value, label, isPrimary}`. Логику держат чистые функции в
  `clientContacts.ts` (с vitest-тестами): добавление строки типа (первая строка типа — основная),
  отметка основного (снимает отметку с других строк того же типа), удаление (если удалили основную —
  основной становится первая оставшаяся строка типа).
- Флажок «основной» показывается, только если строк этого типа больше одной. Отметку держит
  состояние формы всегда, а не только когда флажок виден: сервер получает однозначный набор.
- Пустые строки по-прежнему отбрасываются при отправке. Если основная строка была пустой, сервер
  выберет первый из оставшихся (решение 2, шаг 3).
- Кнопки: «+ Телефон», «+ Email» и «+ Ещё» на существующем `components/ui/dropdown-menu.tsx`.
  Новая строка получает фокус в поле значения.
- Иконки — те же, что в `ClientContactList` (`contactView`); выносятся в общую функцию, чтобы форма
  и список не расходились.

### 5. Отображение

- `ClientContactList`: подпись под значением — комментарий, иначе название типа; пометка «основной»
  только если контактов этого типа больше одного. Порядок — как пришёл с сервера.
- `ClientCardHeader`: телефон с `isPrimary`, а не первый `PHONE`.
- `ConversationThread`: при выборе канала по умолчанию берётся контакт канала с `isPrimary`, иначе
  первый.

### 6. Ассистент

`ClientDrafts` передаёт `label` и `isPrimary` из черновика. Проверка контактов в `prepare` прогоняет
их через ту же `normalized()`, так что карточка подтверждения хранит и показывает контакты уже
в сохраняемом виде (комментарий, основной, порядок), а ошибки правил видит модель до карточки.
Системная подсказка просит модель класть в `label` чей это контакт («телефон мамы» → «мама») и
ставить `isPrimary` только когда пользователь назвал основной. Формат `ClientContactInput` в
аргументах инструмента расширяется теми же необязательными полями.

## Risks / Trade-offs

- [Порядок на форме редактирования меняется после сохранения: если основным отмечен второй телефон,
  при следующем открытии он стоит первым] → это и есть правило «основной первым»; на форме видно, что
  основной — верхний.
- [Пользователь отметил основной пустую строку, она отброшена] → сервер выберет основным первый из
  оставшихся; ошибки нет.
- [Триггер, индекс и нормализация дублируют инвариант] → осознанно: домен даёт понятную ошибку,
  БД гарантирует инвариант для любого писателя. Цена — тестовые фикстуры, вставляющие контакты
  напрямую, обязаны отмечать основной.
- [Конфликт миграций с `client-mobile-app`, который тоже добавляет миграции] → номер берётся при
  реализации, последним из двух change; при конфликте перенумеровать.

## Migration Plan

Миграция только добавляет колонки с значениями по умолчанию и заполняет их для существующих строк;
данных с мессенджерами на проде нет. Откат кода безопасен: старый код не читает новые колонки, а
вставка без `is_primary` не нарушает частичный индекс (по умолчанию `false`).
