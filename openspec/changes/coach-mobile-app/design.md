## Context

Почти все данные, которые нужны тренеру, сервер уже отдаёт (см. proposal.md — Why):

| Экран | Маршрут |
|---|---|
| Вход | `POST /auth/branches` → `POST /auth/login` (два шага: проверка пароля и список филиалов, затем вход в филиал) |
| Смена филиала | `POST /auth/switch-branch` |
| Профиль | `GET /auth/me` (`employeeId`) |
| Обновление токенов | `POST /auth/refresh-token`, refresh-токен в заголовке `X-Refresh-Token` |
| Список занятий | `POST /schedule/list` с `from`, `to`, `employeeIds = [me]` |
| Карточка | `GET /sessions/journal`, `GET /sessions/detail` (заметка) |
| Отметки | `POST /sessions/journal/mark`, `POST /sessions/journal/mark-remaining-absent` |
| Метки | `GET /attendance-labels/list` |

Сервер принимает `Authorization: Bearer`, поэтому мобильному клиенту cookies не нужны. Access-токен живёт 15 минут, refresh-токен — 30 дней. GET-запросы передают параметры плоскими query-параметрами: сервер собирает из них JSON-объект примитивов (`RouteWithContext.decode`).

`shared` — KMP-модуль, который сейчас собирается только под `jvm()`, с `jvmToolchain(25)`. Его зависимости (arrow-core, kotlinx-datetime, kotlinx-serialization) мультиплатформенные.

## Goals / Non-Goals

**Goals:**
- Вся логика (HTTP, авторизация, состояние экранов, проверки отметок) пишется один раз в Kotlin. Нативные UI только отображают состояние и передают действия пользователя.
- Схемы запросов и ответов берутся из `shared`, без ручного дублирования в Swift или Kotlin-клиенте.
- iOS- и Android-приложения собираются локально из этого репозитория.

**Non-Goals:**
- Локальная БД и кэш между запусками: в онлайн-версии данные живут в памяти экрана.
- Генерация мобильного клиента из `ApiContract`, как это сделано для web.
- CI-сборка, подпись релизных сборок и публикация в сторы.

## Decisions

### Структура модулей

```
shared/          + androidTarget, iosArm64, iosSimulatorArm64
mobile/core/     KMP: ApiClient, TokenStore (expect/actual), сессия входа, ViewModel-ы
mobile/android/  Android-приложение, Jetpack Compose, зависит от :mobile:core
mobile/ios/      Xcode-проект, SwiftUI; :mobile:core подключается XCFramework-ом
```

`mobile/ios` не является Gradle-модулем, `mobile/android` — является. В `settings.gradle.kts` добавляются `:mobile:core` и `:mobile:android`. Модули подключаются только при наличии Android SDK, чтобы `./gradlew build` на сервере и в CI без SDK продолжал работать.

Альтернатива — отдельный репозиторий. Отклонена: `shared` пришлось бы публиковать артефактом, и схемы начали бы расходиться с сервером.

### Граница между Kotlin и нативным UI — ViewModel со `StateFlow`

На каждый экран в `mobile/core` есть класс состояния (`data class`/`sealed interface`) и ViewModel с методами-действиями. Compose подписывается на него через `collectAsState`. Swift получает его через SKIE: `StateFlow` → `AsyncSequence`, sealed → Swift `enum`, `suspend` → `async`.

Альтернативы:
- Голый Kotlin/Native-интероп без SKIE: на Swift-стороне придётся писать обёртки над `Flow` и колбэками вручную.
- Compose Multiplatform: противоречит требованию нативного UI.

ViewModel — собственный базовый класс поверх `CoroutineScope`, без `androidx.lifecycle`. Каждая платформа сама управляет временем жизни: `remember`/`DisposableEffect` в Compose и `@StateObject` + `deinit` в SwiftUI.

### HTTP-клиент: Ktor + схемы из `shared`, маршруты описаны вручную

`ApiClient` в `mobile/core` содержит по одной `suspend`-функции на каждый маршрут из таблицы выше. Функции возвращают `Either<ApiError, T>`. Тела запросов и ответов — типы из `org.athletica.crm.api.schemas`. Движки: OkHttp на Android, Darwin на iOS. JSON настраивается так же, как `appJson` в `shared`.

Пути и HTTP-методы описаны в клиенте вручную. Маршрутов всего около десяти. Вынос описаний маршрутов в `shared`, которыми пользовались бы и сервер, и клиент, затрагивает все `routes/*.kt`, и в этом change он не окупается. От расхождения защищает тест в `server`: он проверяет, что каждый путь из списка мобильного клиента зарегистрирован с тем же методом. Список путей и методов лежит в `shared`, `mobile/core` берёт его оттуда же.

GET-запросы кодируются как на сервере: схема сериализуется в `JsonObject`, а каждое примитивное поле становится query-параметром.

### Авторизация

- Вход повторяет веб: `/auth/branches`. Если филиал один, сразу выполняется `/auth/login`. Если филиалов несколько — экран выбора, затем `/auth/login`.
- Токены хранятся в `TokenStore` (expect/actual): Keychain на iOS, значение, зашифрованное ключом Android Keystore, в DataStore на Android. `EncryptedSharedPreferences` не используется: библиотека `security-crypto` объявлена устаревшей.
- Обновление токенов идёт через плагин Ktor `Auth { bearer { refreshTokens { ... } } }`: на 401 он вызывает `/auth/refresh-token` с `X-Refresh-Token` и повторяет запрос. Если обновить не удалось, токены удаляются и приложение возвращается на экран входа.
- Смена филиала: `/auth/switch-branch` → новые токены сохраняются → экраны перезагружаются.
- Выход: `/auth/logout` вызывается без ожидания ответа (для аудита), локальные токены удаляются в любом случае.

Адрес сервера задаётся при сборке (`BuildConfig` / `Info.plist`). Отдельные значения для эмулятора Android (`10.0.2.2`), симулятора iOS (`localhost`) и прода. На экране входа адрес не настраивается.

### Сервер: команда изменения заметки

`POST /sessions/update-notes` с телом `UpdateSessionNotesRequest(sessionId, notes: String?)` отвечает обновлённым `SessionDetailResponse`. Пустая строка или строка из одних пробелов сохраняется как `null`. Длина ограничена 2000 символами и проверяется в домене. Изменение пишется в аудит через существующий `AuditSession`. Команда не зависит от статуса занятия: заметку можно менять и у проведённого, и у отменённого занятия.

Приложение берёт заметку из `/sessions/detail`, а журнал — из `/sessions/journal`. Это два параллельных запроса при открытии карточки. Добавлять заметку в `SessionJournalResponse` ради одного запроса не стоит: журнал — проекция посещаемости, заметка к ней не относится.

### Проверки отметки — в `mobile/core`

Правила «не пришёл требует метку» и «метка применима к состоянию» дублируются в ViewModel карточки, чтобы кнопка «Сохранить» была недоступна заранее. Окончательную проверку делает сервер. Его ошибка показывается сообщением, локальное состояние откатывается к последнему ответу журнала.

## Risks / Trade-offs

- [`jvmToolchain(25)` в `shared` несовместим с Android: D8 не принимает байткод новее поддерживаемого] → для `androidTarget` задать `jvmTarget = 17`. JVM-таргет сервера не меняется.
- [В `commonMain` модуля `shared` может оказаться код, который не собирается под Kotlin/Native (`@JvmInline` без `expect`, `java.*`)] → первая задача — сборка `shared` под iOS; найденное исправляется до начала остальной работы.
- [Ручные пути в `ApiClient` расходятся с сервером] → серверный тест на список мобильных маршрутов.
- [Версии SKIE, Kotlin 2.4 и Xcode могут быть несовместимы] → проверить в задаче настройки iOS-сборки. Если SKIE не поддерживает текущий Kotlin, на время обойтись ручными обёртками для `StateFlow`.
- [Сборка требует Android SDK и Xcode] → мобильные модули подключаются условно (см. «Структура модулей»), `./gradlew build` для сервера не затрагивается.
- [Без кэша каждое открытие экрана требует сети] → принято осознанно: офлайн-режим будет отдельным change, и тогда ViewModel-ы перейдут с `ApiClient` на репозиторий с локальной БД.

## Migration Plan

Миграций БД нет: колонка `sessions.notes` уже существует. Новый маршрут сервера обратно совместим.
