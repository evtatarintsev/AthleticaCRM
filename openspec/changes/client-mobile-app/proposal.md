## Why

Сейчас клиент (чаще родитель ребёнка) узнаёт о расписании, остатке абонемента и долге только
от администратора — в мессенджере или на ресепшене. Это нагружает администраторов и не даёт
клиенту самому предупредить о пропуске. Нужно одно мобильное приложение «Athletica» для
клиентов всех организаций, в которое клиент входит без пароля и где видит только свои данные.
Главный риск — администратор ошибся в номере телефона, и посторонний получает доступ к
персональным данным ребёнка (152-ФЗ); защита от этого — часть требований, а не доработка
«на потом».

Это изменение — **серверное ядро** клиентского контура: доступы, вход, подтверждение личности,
управление из CRM и данные клиента для приложения. Остальное вынесено в отдельные изменения,
которые идут параллельно после ядра (см. «Связанные изменения»).

## What Changes

- Организация включает клиентское приложение в настройках и приглашает клиентов — по одному
  из карточки или всех сразу. Без приглашения войти нельзя.
- Вход по номеру телефона и одноразовому коду. Паролей нет: нет ни выдачи первого пароля,
  ни восстановления. Политика доставки (Telegram, при недоставке — SMS) и лимиты — в ядре;
  сами отправители подключаются отдельными изменениями, до них работает отправитель-заглушка.
- Один номер — один аккаунт. В аккаунте все клиенты всех организаций, у которых записан этот
  номер (родитель видит всех своих детей). Организации друг о друге не узнают.
- Подключение к организации подтверждается датой рождения **каждого** клиента отдельно;
  клиента без даты рождения подключить нельзя, пока администратор её не заполнит. До
  подтверждения человек видит только название организации. Три неверные даты подряд —
  блокировка на всех устройствах и задача администратору «проверьте номер». Кнопка «Это не я»
  сообщает об ошибке в номере. Та же проверка — на новом устройстве.
- Доступ закрывается сразу, если номер удалён из карточки, клиент архивирован, приложение
  в организации выключено или сотрудник отключил доступ. Закрытие доступа в одной организации
  не трогает сеансы и доступы в других.
- Человек может удалить аккаунт.
- В карточке клиента CRM — статус приложения по каждому номеру, кнопки «Пригласить»,
  «Напомнить», «Отключить», «Разблокировать».
- API приложения: профили, главная, расписание с отметкой «Не придём», история посещений,
  абонементы, баланс и его история, список устройств и выход.
- Схемы клиентского API в `shared` и порты для отправки кодов и push — первый шаг, чтобы
  параллельные изменения могли начать работу.
- **Не входит**: онлайн-оплата (отдельная задача: юридическая и организационная работа,
  комиссии), публикация в App Store и Google Play
  ([#274](https://github.com/evtatarintsev/AthleticaCRM/issues/274),
  [#275](https://github.com/evtatarintsev/AthleticaCRM/issues/275)), магазин товаров,
  самостоятельная запись на разовые занятия, брендированные приложения клубов, вход по email,
  вход сотрудников через это приложение, подключение по QR-коду на месте.

### Связанные изменения

| Изменение | Что делает | Зависит от ядра |
|---|---|---|
| `telegram-gateway-codes` | отправитель кодов через Telegram Gateway API | только порт `VerificationCodeSender` |
| SMS-коды (изменение ещё не заведено) | отправитель кодов по SMS через SMS-канал организации последнего приглашения; провайдер — `sms-aero-channel` | только порт `VerificationCodeSender` |
| `client-app-chat` | переписка с клубом, канал «Приложение» во «Входящих» | доступы, `ClientProfileContext`, порт `ClientAppPushes` |
| `client-app-push` | push через FCM и APNs | устройства, порт `ClientAppPushes` |
| `client-mobile-android` | модуль `:mobile` на KMP + Compose Multiplatform, общие экраны, Android | схемы в `shared` |
| `client-mobile-ios` | iOS-таргет приложения | модуль `:mobile` из `client-mobile-android` |

## Capabilities

### New Capabilities
- `client-app-access`: приглашения, вход по коду, аккаунт по номеру, подтверждение личности
  датой рождения, блокировка и «Это не я», устройства, отзыв доступа, изоляция организаций,
  удаление аккаунта.
- `client-app-admin`: включение приложения в организации, массовое и единичное приглашение,
  статусы доступа в карточке клиента, задачи по ошибкам в номере.
- `client-app-overview`: что клиент видит в приложении — главная, расписание, посещения,
  абонементы, баланс, переключение между клиентами и организациями.

### Modified Capabilities
- `attendance-journal`: клиент может заранее предупредить об отсутствии; предупреждение видно
  сотруднику в журнале занятия, отметку по-прежнему ставит сотрудник.

## Impact

- **server**: новый контур аутентификации клиентов (отдельный JWT-аудиенс, контексты
  `ClientAccountContext`/`ClientProfileContext` вне `RequestContext`), домен `clientapp`
  (аккаунты, доступы, устройства, коды), порты `VerificationCodeSender` и `ClientAppPushes` с
  заглушками, проекции `read/clientapp/*`, маршруты `/client-app/*` и `/client-app-admin/*`.
- **shared**: схемы запросов и ответов клиентского API, `ClientAppAccessStatus`, новое право
  `CAN_MANAGE_CLIENT_APP`.
- **web**: блок «Мобильное приложение» в карточке клиента, страница настроек «Клиентское
  приложение», предупреждения об отсутствии в журнале; перегенерация `web/src/api/generated/`.
- **БД**: новые таблицы аккаунтов, доступов, устройств, кодов, подтверждений на устройствах,
  предупреждений об отсутствии; колонка `organizations.client_app_enabled`.
- **Конфигурация**: параметры клиентского JWT — в `application.conf`,
  `docker-compose.prod.yaml`, `.env.prod.example`. Ключи Telegram Gateway, FCM и APNs
  добавляют соответствующие изменения; SMS отправляются с аккаунтов организаций (настройки
  их каналов), ключей платформы для SMS нет.
