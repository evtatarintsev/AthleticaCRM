## Context

Мотивация — в proposal.md, требования — в `specs/sport-catalog/spec.md`. На что опирается решение:

- Дисциплины организации — таблица `disciplines(id, org_id, name)` с `UNIQUE (org_id, name)` (регистрозависимо). Маршруты `/disciplines/*` в `server/src/main/kotlin/org/athletica/crm/routes/DisciplinesRoutes.kt`; создание — `POST /disciplines/create {id, name}`.
- В вебе дисциплины — один из четырёх справочников (`web/src/settings/directories.ts`: залы, дисциплины, источники, филиалы), которые показывает общий `DirectorySheet`. Создание и переименование — общая панель `DirectoryItemSheet` с полем «Название» (TanStack Form + zod). Расширения справочников уже делаются необязательными полями `DirectoryDefinition` (`describable`, `alsoInvalidates`).
- В UI-ките (`web/src/components/ui`) нет combobox; из Radix подключены dialog, dropdown-menu, checkbox, tabs, label, slot.
- Язык запроса (`ctx.lang`) берётся из `Accept-Language` браузера, а не из настроек организации.
- Маршруты регистрируются в `Application.kt` внутри `authenticate("auth-jwt")`; веб-контракты генерируются из Kotlin задачей `:server:generateWebContracts` (`npm run contracts`).

## Goals / Non-Goals

**Goals:**
- Каталог в одном месте (`shared`), пригодный для будущих KMP-клиентов и для последующего переноса в БД.
- Выбор из каталога встраивается в общую панель записи справочника без отдельной формы для дисциплин.
- Поиск и пометка «уже добавлено» — чистые функции, покрытые unit-тестами.

**Non-Goals:**
- Обобщённый combobox для всего приложения с порталом и позиционированием: делается ровно то, что нужно панели справочника.
- Нечёткий поиск (опечатки, расстояние Левенштейна): только вхождение подстроки после нормализации.

## Decisions

### 1. Каталог — Kotlin-данные в `shared`, а не таблицы

```
shared/.../core/sportcatalog/
  SportCatalog.kt          // object SportCatalog { val sports: List<CatalogSport> }
  CatalogSport.kt          // key, names: Map<Lang, String>, disciplines
  CatalogDiscipline.kt     // key, names: Map<Lang, String>, aliases: List<String>
shared/.../api/schemas/sportcatalog/
  SportCatalogResponse.kt  // sports: List<SportCatalogSportSchema>
```

Каталог — `object` с литералами в коде. Схема ответа отделена от данных, маппинг — в маршруте, как у остальных ресурсов. `key` — стабильная латинская строка (`dance`, `breaking`): уникальна в каталоге, используется как ключ элемента списка в вебе и как будущий ключ сопоставления при переносе в БД. Названия хранятся словарём по `Lang`; тест в `shared`/`server` проверяет, что у каждого элемента есть название на каждом `Lang`, ключи уникальны, синонимы непусты.

*Альтернатива:* таблицы + Liquibase-seed (как в issue). Отклонено пользователем: любая правка каталога — миграция, при этом связь с дисциплинами организации пока не нужна. Перенос в БД остаётся возможным: `key` даёт стабильный идентификатор.

*Альтернатива:* JSON-ресурс. Отклонено: в KMP `commonMain` ресурсы читаются неудобно, а литералы Kotlin проверяются компилятором.

### 2. Эндпоинт отдаёт весь каталог со всеми языками

`GET /sport-catalog/list` → `SportCatalogResponse`. Маршрут в `routes/SportCatalogRoutes.kt`, внутри `authenticate("auth-jwt")`, без транзакции и без обращения к БД; ответ не зависит от `ctx.orgId` и `ctx.lang`.

```
SportCatalogResponse
  sports: [
    { key, names: { ru, en },
      disciplines: [ { key, names: { ru, en }, aliases: [...] } ] }
  ]
```

Каталог мал (~18 видов, ~100 дисциплин, единицы КБ), поэтому поиск — на клиенте. Это снимает зависимость от `Accept-Language`: язык основного названия выбирает интерфейс, а поиск идёт по всем языкам сразу.

Проекция в `read/` не заводится: правило слоя — SQL со скоупом по организации, а здесь нет ни SQL, ни организации. Маршрут читает `SportCatalog` напрямую. При переносе в БД появится `read/sportcatalog/SportCatalogView`, маршрут переключится на него без изменения ответа.

`names` сериализуется как объект с полями по коду языка (`ru`, `en`), а не как `Map<Lang, String>` с произвольными ключами: так сгенерированная zod-схема строгая, а добавление языка ломает сборку веба явно.

*Альтернатива:* отдавать только название на `ctx.lang`. Отклонено: поиск по «break» в RU-интерфейсе требует EN-названий, а синонимы и так многоязычные.

### 3. Расширение `DirectoryDefinition` — подсказки названия при создании

```
DirectoryDefinition<Id>
  ...
  useNameSuggestions?: (api, branchId) => UseQueryResult<readonly SuggestionGroup[]>

SuggestionGroup  { key, label, items: Suggestion[] }
Suggestion       { key, label, hint?, terms: string[] }   // terms: всё, по чему ищется
```

`DirectorySheet` вызывает хук, если он задан, и передаёт группы в `DirectoryItemSheet` **только в режиме создания**. Без подсказок или при редактировании панель рисует обычный `TextField`, как сейчас. Для дисциплин в `directories.ts` хук делает `apiQuery(api, branchId, "sport-catalog/list")` и через `select` переводит каталог в `SuggestionGroup[]` с подписями на языке интерфейса (`useI18n().locale`); в `terms` попадают названия на всех языках и синонимы.

Пометка «уже добавлено» считается в панели: у неё уже есть записи справочника (`useItems`). Чистая функция `markExisting(groups, items)` для каждой подсказки ищет запись, чьё нормализованное название совпадает с любым из `terms`, и возвращает её название для подписи «уже добавлено как «…»».

*Альтернатива:* отдельная панель создания дисциплины. Отклонено: дублирует форму, проверки, ошибки сервера и защиту несохранённых изменений.

### 4. Нормализация для поиска и сравнения

`normalize(s)`: `trim` → нижний регистр → `ё`→`е` → дефисы и подчёркивания в пробелы → схлопывание пробелов. Подсказка подходит, если нормализованный ввод — подстрока любого нормализованного `term`. Пустой ввод — показываются все группы. Группа без подходящих элементов скрывается. Порядок групп и элементов — как в каталоге.

Та же `normalize` используется для «уже добавлено», поэтому «Jazz funk» в организации совпадает с «Jazz-funk» каталога.

### 5. Combobox — собственный, список встроен в панель, без новой зависимости

```
[ Название: брейк|                      ]   <- input role=combobox, aria-expanded,
+---------------------------------------+      aria-controls, aria-activedescendant
| Танцы                                 |   <- role=group, aria-labelledby
|   Брейкинг          брейк-данс        |   <- role=option; hint — сработавший синоним
|   ...                                 |
| Ударные единоборства                  |
|   Бокс   уже добавлено как «Бокс»     |   <- option, приглушён, но выбираемый
+---------------------------------------+
| + Добавить «брейк» как есть            |   <- последний option; только при непустом вводе,
+---------------------------------------+      если ввод не равен названию подсказки
```

Список рисуется в потоке панели под полем (ограниченная высота, своя прокрутка), а не во всплывающем окне: панель — Radix Dialog с ловушкой фокуса, и встроенный список не требует портала и позиционирования. Клавиатура: ↑/↓ — активный вариант, Enter — выбрать, Esc — закрыть список (повторный Esc отдаётся панели), Tab — уйти из поля без выбора. Выбор подсказки подставляет её название в поле и закрывает список; «Добавить как есть» оставляет введённый текст. Значение поля — всегда строка: сохранение, проверки (`required`) и ошибки сервера работают как раньше. Подсказка, совпавшая по синониму, показывает синоним как `hint`, чтобы было видно, почему она найдена.

Компонент `NameComboboxField` в `web/src/forms/` принимает поле TanStack Form, как `TextField`.

*Альтернатива:* `<input list>` + `<datalist>`. Отклонено: нет групп, фильтрация и вид различаются между браузерами, нельзя показать «уже добавлено».

*Альтернатива:* `cmdk` / Ariakit / Base UI. Отклонено на этом шаге: новая зависимость ради одного поля, плюс проверка совместимости со строгими правилами (`type-coverage --strict`, без `as`). Если combobox понадобится ещё где-то, вопрос пересматривается.

### 6. Ошибка загрузки каталога не блокирует создание

Пока каталог грузится или если запрос упал, поле работает как обычный `TextField` (список не показывается). Отдельного сообщения об ошибке нет: каталог — подсказка, а не обязательная часть формы.

## Risks / Trade-offs

- [Содержимое каталога спорно (латиница в RU-названиях, принадлежность элемента одному виду)] → данные в одном файле, правка — без миграции; список согласован в обсуждении и зафиксирован в спеке.
- [Совпадение по синониму даёт ложное «уже добавлено» (например, «Латина» и синоним «румба»)] → пометка не запрещает выбор; точный дубль всё равно отклонит уникальный индекс.
- [Собственный combobox — доступность и клавиатура] → ARIA-шаблон combobox с `aria-activedescendant`; тесты на клавиатуру и роли в vitest + Testing Library.
- [Дубли с другим регистром («плавание» при наличии «Плавание») по-прежнему проходят в БД] → пометка «уже добавлено» видна при вводе; регистронезависимый индекс — отдельное изменение (non-goal).
- [`ctx.lang` из браузера не совпадает с языком организации] → основное название на языке интерфейса, поиск по всем языкам; сохраняется то, что видно в поле, и это можно поправить до сохранения.

## Migration Plan

Только добавления: новый эндпоинт и новое необязательное поле `DirectoryDefinition`. Миграций БД нет. Откат — revert коммита; существующие дисциплины не затрагиваются.
