## Context

См. `proposal.md` и delta specs. Дата окончания хранится в `memberships`; маршруты абонементов находятся в `MembershipsRoutes`. Изменения выдачи уже обёрнуты в `AuditMemberships`, который пишет изменения в общий аудит. История событий `membership_events` существует отдельно от общего аудита.

## Goals / Non-Goals

**Goals:**

- Сохранять продление как изменение состояния доменного абонемента.
- Проверять состояние и новую дату на сервере.
- Записывать аудит в той же транзакции, что и изменение абонемента.
- Дать администратору форму продления в существующей панели абонемента.

**Non-Goals:**

- Продление неактивированных, закрытых или отозванных абонементов.
- Изменение даты начала, остатка занятий, оплаты, тарифа или групп.
- Отдельное событие в `membership_events`: требование говорит о записи в общий аудит.

## Decisions

- Добавить команду продления в доменную модель активного абонемента и выполнять её через маршрут абонементов. Команда принимает целевую дату окончания и причину; домен отклоняет дату, которая не позже текущей даты окончания.
- Реализовать аудит через существующий `AuditMemberships`, сохраняя автора из контекста запроса, исходную и целевую даты окончания и причину в payload операции. Изменение и audit-запись выполнять в одной транзакции, чтобы не оставлять изменение без аудита или аудит без изменения.
- Добавить контракт запроса/ошибок для API и форму в `MembershipSheet`. Кнопку показывать для активного состояния; клиентская валидация даты и причины дополняет, но не заменяет серверную.
- Существующий общий аудит предназначен для операционных записей, а `membership_events` — для отображаемой хронологии жизненного цикла. Не дублировать продление во второй журнал без отдельного продуктового требования.

## Risks / Trade-offs

- [Аудит может не описывать изменения полей в формате, удобном для activity log] → согласовать payload с существующим форматом update audit и убедиться, что он читаем в интерфейсе аудита.
- [Клиент может отправить устаревшую дату окончания при параллельном изменении] → сервер повторно проверяет текущую дату окончания в транзакции и отклоняет устаревший запрос.

## Migration Plan

Миграция схемы БД не требуется, если изменение использует текущую колонку `end_date` и существующее хранилище аудита. Развернуть серверный контракт и клиент вместе; при откате кода дополнительных данных для миграции не остаётся.
