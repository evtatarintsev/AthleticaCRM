## Context

Мотивация — см. proposal.md. Требования — `specs/client-app-*/spec.md` и `specs/attendance-journal/spec.md`.
Макеты экранов: https://claude.ai/artifact/USGK1UdgF7BxB3kEoDS8ox (строки «Подключение и вход»,
«Приложение клиента», «CRM»; экран магазина в макетах есть, в изменение не входит).

Что уже есть и на что опираемся:

- **Аутентификация** только для сотрудников: `JwtConfig` (HMAC256, issuer `athletica-crm`,
  audience `athletica-crm-users`, access + refresh в cookie), провайдер `auth-jwt` в
  `Application.kt`, `EmployeeRequestContext` — вариант `sealed interface RequestContext`
  (есть ещё `SystemRequestContext`, `AdminRequestContext`).
- **Контакты клиента** — `domain/clientcontacts`: список `ClientContact(type, value)`, нормализация
  `PhoneDigits`, поиск `clientsByPhone(phone)` внутри организации. Замена контактов —
  `ClientContacts.replace(client, contacts)` (полная замена набора).
- **Клиент**: `birthday: LocalDate?`, архивирование через `ActiveClient.archive()`.
- **Каналы** — `sealed interface ChannelConfig` в `shared` с `addressing`
  (`ByContact(PHONE)` у SMSC/Twilio, `ByBinding` у Telegram-бота), отправка через
  `MessageDispatcher` и `deliveries`, беседа клиента — `conversations`/`messages`, единые
  «Входящие» — `read/messaging/InboxView`.
- **Платежи**: `PaymentGateway` + ЮKassa на **платформенном** магазине Athletica — только для
  пополнения баланса организации (`organization-payment`), вебхук `POST /api/checkout/yookassa`
  вне `authenticate`. Магазинов организаций нет.
- **Баланс клиента** — журнал `client_balance_journal`, баланс = `SUM(amount)`; по
  `docs/client-balance.md` баланс меняется только как часть операции (продажа, возврат, корректировка).
- **Сессии**: `origin_date`, `origin_start_time`, `is_rescheduled`, `cancelled_at`, `completed_at`
  — хватает для «Перенесено с 10:00» и «Отменено».
- **Задачи** допускают системного автора и отсутствие исполнителя (`tasks`).
- **Мобильного клиента нет.** Модуль `shared` — KMP (пока только `jvm()`), «задел под мобильные
  KMP-клиенты»; прежний `composeApp` (desktop/wasm) удалён, в `settings.gradle.kts` только
  `:server` и `:shared`.

## Goals / Non-Goals

**Goals:**
- Клиентский контур полностью отделён от контура сотрудников: отдельные токены, контекст,
  маршруты. Клиентский токен не может вызвать ни один маршрут CRM, и наоборот.
- Данные клиента физически не покидают сервер до подтверждения доступа на устройстве —
  проверка в каждой проекции, а не только в UI.
- Переиспользовать готовое: контакты, беседы и «Входящие», задачи, абонементы, баланс,
  шаблон `organization-payment` для платежей.

**Non-Goals:**
- Магазин товаров, запись на разовые занятия, покупка нового (не продление) абонемента.
- Брендированные приложения, вход по email, звонок с кодом (flash call) — после первой версии.
- Офлайн-режим приложения; WebSocket — обновление опросом и push.
- Перенос админских действий сотрудника в мобильное приложение.

## Decisions

### 1. Мобильное приложение — Kotlin Multiplatform + Compose Multiplatform

Новый Gradle-модуль `:mobile` (общий код + `androidApp` + `iosApp`), зависит от `:shared`;
в `shared` добавляются таргеты `androidTarget()`, `iosArm64()`, `iosSimulatorArm64()`.
Схемы запросов и ответов, `Money`, ID и правила вроде `ActiveStatus` используются напрямую —
без генерации контрактов, как в `web/`.

- *Альтернатива — React Native / Expo:* команда уже пишет web на TS/React, но пришлось бы
  дублировать схемы через генерацию и терять общие доменные правила из `shared`.
- *Альтернатива — нативные Swift + Kotlin:* два кодовых базы на одну команду — дорого.
- Риск: Compose Multiplatform на iOS моложе, чем на Android. Принимаем: экраны простые
  (списки, карточки, формы), без сложной анимации и нативных виджетов.

### 2. Отдельный контур аутентификации клиентов

- Новый JWT-аудиенс `athletica-client-app`, свой провайдер `client-jwt` в `Application.kt`.
  Access-токен 15 минут, refresh — 60 дней, хранятся в защищённом хранилище устройства
  (Keychain / EncryptedSharedPreferences), передаются заголовком `Authorization`, без cookie.
- Refresh-токен привязан к записи устройства `client_app_devices`; завершение сеанса удаляет
  запись → refresh перестаёт работать, а access истекает за ≤15 минут (требование «не позднее
  15 минут» в `client-app-access`).
- Контексты: `ClientAccountContext(accountId, deviceId, lang)` — из токена, **не** вариант
  `RequestContext` (у аккаунта нет организации: одна учётная запись на все организации).
  Для запросов по конкретному клиенту routes строят `ClientProfileContext(accountId, deviceId,
  orgId, clientId, currency, lang)` — новый вариант `sealed interface RequestContext`, — только
  после проверки доступа (см. п. 4). Так существующие функции с `context(ctx: RequestContext)`
  получают `orgId`, а `EmployeeRequestContext`-функции клиенту недоступны по типам.
- *Альтернатива — переиспользовать `users` сотрудников:* смешало бы два мира и права;
  клиентский аккаунт не имеет организации и пароля.

### 3. Модель данных

| Таблица | Суть |
|---|---|
| `client_app_accounts` | аккаунт по номеру: `phone_digits` UNIQUE, `terms_accepted_at`, `terms_version` |
| `client_app_devices` | устройство аккаунта: платформа, модель, push-токен, `last_seen_at`, хэш refresh-токена |
| `client_app_codes` | одноразовые коды: хэш кода, `expires_at`, `attempts`, канал доставки; для лимитов частоты |
| `client_app_access` | доступ: `org_id`, `client_id`, `phone_digits`, `status`, `failed_attempts`, `invited_at`, `invite_channel`, `status_changed_at`; UNIQUE (`org_id`, `client_id`, `phone_digits`) |
| `client_app_device_verifications` | подтверждение доступа на устройстве: (`access_id`, `device_id`), способ (дата/QR), время |
| `client_app_qr_tokens` | одноразовые QR: хэш токена, `client_id`, `expires_at`, `used_at`, кем выдан |
| `client_app_payments` | платежи клиентов: `org_id`, `client_id`, `account_id`, сумма, назначение, тариф, статус, `external_payment_id` |
| `client_app_absence_notices` | предупреждения «Не придём»: `session_id`, `client_id`, `access_id`, время |
| `org_payment_shops` | магазин ЮKassa организации: `shop_id`, секрет (зашифрован), проверен ли |

Доступ хранит `phone_digits`, а не ссылку на `client_contacts.id`: контакты заменяются целиком
(`replace`), и идентификаторы контактов не стабильны. Синхронизация — в usecase сохранения
контактов: для номеров, которых больше нет, доступ → `отключён` и удаляются подтверждения
устройств; для новых номеров ничего не создаётся (отсутствие строки = `не приглашён`).

Настройка «приложение включено» — колонка в `organizations` (`client_app_enabled`), а не
отдельная таблица: одна булева настройка без истории, изменение — через аудит.

Статус доступа — enum `ClientAppAccessStatus` в `shared` (нужен и web, и mobile).
Агрегат `ClientAppAccess` в `domain/clientapp/` с переходами по таблице статусов из
`client-app-access`; недопустимые переходы невыразимы, как у `ActiveClient`/`ArchivedClient`.

### 4. Проверка доступа на каждом запросе — в проекциях

Все проекции `read/clientapp/*` принимают `ClientProfileContext` и в том же SQL соединяются с
`client_app_access` (статус `подключён`) и `client_app_device_verifications` (текущее устройство),
плюс `organizations.client_app_enabled` и неархивный клиент. Нет строки — `CLIENT_NOT_FOUND`
(одинаково для чужого и несуществующего). Это соответствует правилу `read/`: видимость живёт
в проекции. Отдельный «middleware-фильтр» не делаем — проверка в SQL не может разойтись с данными.

### 5. Подтверждение датой рождения и защита от перебора

- Даты сравниваются на сервере; клиенту не возвращается, какая дата совпала, кроме итогового
  списка подключённых профилей.
- Счётчик `failed_attempts` — на доступе, а не на устройстве: смена телефона не даёт новых
  попыток. Третья неудача → `проверка не пройдена` + задача (в одной транзакции).
- Перебор дат с разных аккаунтов невозможен: доступ привязан к номеру, а номер подтверждён кодом.

### 6. Коды: Telegram Gateway, затем SMS

- Telegram Gateway API (официальная отправка кодов проверки по номеру телефона, не требует бота
  и предварительного контакта). Если Gateway ответил, что доставка невозможна, — сразу SMS.
- SMS — платформенный аккаунт SMS-провайдера (тот же SMSC, что и для каналов организаций, но
  с ключами платформы в `application.conf`), не каналы организации: код — дело платформы.
- Код хранится хэшем; лимиты 60 с / 5 в час — по `client_app_codes`. Дополнительно лимит по IP
  на уровне nginx, чтобы ограничить «SMS-накрутку».
- Одинаковый ответ для известного и неизвестного номера — `client-app-access`.

### 7. Приглашения — статус плюс уведомление «по возможности»

Приглашение — это прежде всего смена статуса доступа. Уведомление отправляется через
существующий `MessageDispatcher` по каналам организации с адресацией `ByContact(PHONE)`
(SMSC, Twilio). Telegram-бот организации не подходит: он пишет только по привязке, а не
по номеру. Нет такого канала — приглашение всё равно действует, сотрудник показывает QR.
Текст — шаблон из i18n с названием организации и ссылкой на установку, без данных клиента.

- *Альтернатива — отправлять приглашения SMS платформы:* расходы платформы на рассылки
  организаций и риск блокировки отправителя за массовые сообщения. Отложено.

### 8. QR-код подключения

Сотрудник запрашивает токен для клиента → в web показывается QR со ссылкой
`athletica://connect?t=<token>` (и https-fallback на страницу установки). Токен — 128 бит,
хранится хэшем, 10 минут, однократный. Сканирование подключает **только** доступ номера
аккаунта, если этот номер есть в контактах клиента; QR не добавляет номер в контакты —
это остаётся явным действием сотрудника.

### 9. Канал «Приложение» в переписке

Новый подтип `ChannelConfig.ClientApp` с `addressing = ByContact(PHONE)`: «Входящие» и выбор
адреса в ответе работают без изменений модели. Встроенная интеграция заводится автоматически
при включении приложения (одна на организацию) и не показывается в списке настраиваемых каналов.
Транспорт канала сохраняет сообщение и ставит push в очередь; доставка «прочитано» —
по отметке клиента. Переписка в приложении — сообщения канала `ClientApp` с адресом номера
аккаунта (фильтр в проекции), поэтому родители не видят переписку друг друга.

### 10. Push — FCM для Android, APNs для iOS

Push-токен приходит при регистрации устройства и обновляется приложением. Отправка — фоновым
обработчиком с повторами (как `MessageDispatcher`), только на устройства с подтверждением доступа
этого клиента. Мёртвые токены (ответ провайдера «unregistered») удаляются.

### 11. Платежи клиентов — магазин ЮKassa организации

- Деньги клиента принадлежат организации, поэтому платёж создаётся в её магазине: `shop_id` +
  секретный ключ, ключ хранится зашифрованным (ключ шифрования — в `application.conf`).
- `PaymentGateway` расширяется параметром магазина (сейчас он неявно платформенный).
- Вебхук — отдельный маршрут `POST /api/checkout/yookassa/org`. Магазины организаций настраивают
  уведомления сами, общего секрета подписи у нас нет, поэтому перед зачислением статус платежа
  перепроверяется запросом к API ЮKassa с ключом магазина организации (телу уведомления не доверяем).
- Зачисление: новый тип журнала баланса `online_payment` (положительная сумма) — это операция
  «оплата из приложения», согласуется с правилом «баланс меняется только как часть операции».
- Продление: в той же транзакции после зачисления — выдача абонемента через существующий
  `memberships.issue(...)` и списание цены с баланса (`sale_payment`). Если выдача невозможна —
  транзакция выдачи откатывается отдельно от зачисления (зачисление уже закоммичено), создаётся
  задача (см. `client-app-payments`). Порядок: commit зачисления → попытка выдачи → задача при
  неудаче; повторное уведомление не повторяет ни зачисление, ни выдачу (статус платежа).

### 12. Маршруты

- `/api/client-app/auth/*` — запрос кода, вход, refresh, выход (без токена, лимиты).
- `/api/client-app/*` — под `client-jwt`: профили, подтверждение, QR, данные, оплата, переписка,
  устройства. Без path-переменных, ID в теле или query — по правилам проекта.
- `/api/client-app-admin/*` — под `auth-jwt` (сотрудники): включение, приглашения, статусы,
  QR, ЮKassa. Права: `CAN_MANAGE_CLIENT_APP` — включение, массовое приглашение, ЮKassa;
  остальное — любой сотрудник организации (как работа с карточкой клиента).

## Risks / Trade-offs

- [Посторонний знает дату рождения ребёнка (соседи, родственники)] → защита не абсолютна;
  дополняют её задача администратору и видимость подключённых устройств в карточке.
  Для особо чувствительных клиентов — подключение только по QR (можно добавить настройку позже).
- [SMS-накрутка через запрос кодов] → лимиты по номеру и IP, Telegram Gateway в приоритете;
  мониторинг расхода SMS.
- [Неверный статус после частичного сбоя оплаты продления] → зачисление и выдача разделены,
  при сбое выдачи деньги на балансе и задача; ни один сценарий не теряет деньги.
- [Модерация App Store: приложение-«каркас» для многих организаций] → одно приложение
  с одной учётной записью разработчика Athletica, без брендирования под клубы — правило 4.2.6
  не затрагивается. Вход без пароля требует демо-доступа для ревьюера: заводим тестовый номер
  с фиксированным кодом, работающий только в демо-организации.
- [Compose Multiplatform на iOS] → простые экраны; в первой итерации проверяем сборку и
  публикацию iOS раньше, чем пишем все экраны.
- [Дата рождения не заполнена у многих клиентов] → в настройках CRM показываем число таких
  клиентов со ссылкой на дозаполнение; QR как запасной путь.

## Migration Plan

1. Миграции БД аддитивные; `client_app_enabled` по умолчанию `false` — у существующих
   организаций ничего не меняется до явного включения.
2. Серверная часть выкатывается раньше приложения; маршруты клиента без включённой
   организации возвращают пустые профили.
3. Приложение — закрытое тестирование (TestFlight, внутренний трек Google Play) на одной
   организации, затем публикация.
4. Откат: выключить приложение в организациях (данные не теряются); маршруты `/client-app/*`
   можно снять с роутинга без отката миграций.

## Open Questions

- Текст пользовательского соглашения и политики обработки ПД — готовит юрист; в приложении
  нужна только ссылка и версия.
- Конкретный SMS-провайдер платформы (SMSC или другой) — на реализацию не влияет, интерфейс
  отправки один.
