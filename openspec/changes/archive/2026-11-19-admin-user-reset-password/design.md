# Design

## Context

- Административные команды построены на clikt 5.1 (`admin/`). Зависимости собирает `AdminDi`:
  подключение к БД создаётся лениво, при первом обращении, поэтому справка и разбор аргументов
  работают без переменных окружения.
- Для операций поверх всех организаций уже есть образцы, которые обходятся без `RequestContext`:
  `OrgSearch` и `FailedDomainEvents`. Они ходят прямым SQL через `database.transaction { orThrow { ... } }`.
- `users` — глобальная таблица: `login` уникален (`users_login_key`), хеш пароля лежит в `password_hash`.
  При входе (`DbAuth.verifyCredentials`) логин сравнивается точно, `u.login = :username`.
- Сервер хеширует пароли через `PasswordHasher()` с параметрами по умолчанию (`Di.kt`).
- В продакшене команды запускаются через `docker compose ... exec server java -jar athletica.jar ...`,
  а `docker compose exec` по умолчанию выделяет TTY.

## Goals / Non-Goals

**Goals:**
- Пароль не попадает ни в аргументы процесса, ни в историю shell, ни в вывод команды.
- Новый хеш получается в том же формате и с теми же параметрами, что и при регистрации,
  так что вход работает без особых случаев.

**Non-Goals:**
- Общая политика паролей (длина, сложность) для регистрации, смены пароля и сброса.
- Неинтерактивный режим для скриптов как поддерживаемый контракт.

## Decisions

### Команда в группе `admin user`, пользователь по точному логину

`UserCommand` — новая группа рядом с `OrgCommand` и `EventsCommand`. В ней одна подкоманда,
`ResetPasswordCommand` с одним позиционным аргументом `login`. Других аргументов и опций
у неё нет, поэтому лишний аргумент clikt отклонит ещё при разборе, до обращения к `AdminDi.database`.

Логин сравнивается точно, как при входе. Поиск по подстроке, как в `org find`, отвергнут:
сброс пароля «похожему» пользователю — слишком дорогая ошибка.

### Пароль вводится внутри `run()` через терминал clikt со скрытым вводом

Пароль запрашивается в `run()` дважды, через терминал команды (mordant), со скрытым вводом.
Затем сравниваются два значения и проверяется, что пароль не пустой.

Отвергнутые варианты:
- `option("--password").prompt(hideInput = true, requireConfirmation = true)`. Clikt
  заводит у такого поля настоящую опцию `--password`, и пароль можно передать в командной
  строке. Это противоречит требованию к интерактивному вводу.
- Генерация пароля и печать в stdout. Решили иначе: пароль задаёт администратор,
  а в выводе команды пароля быть не должно.
- Аргумент `<пароль>`. Утекает в историю shell и в `ps`.

### Порядок: сначала проверка логина, затем ввод пароля, затем запись

1. Убедиться, что пользователь с таким логином существует. Если нет — `CliktError`
   (stderr и ненулевой код), пароль не запрашивается.
2. Запросить пароль дважды и проверить его.
3. Выполнить `UPDATE users SET password_hash = :hash WHERE login = :login`.
   Если обновлено 0 строк (пользователя удалили между шагами), ошибка та же, что на шаге 1.

Отдельная проверка на шаге 1 стоит одного лишнего `SELECT`, зато администратор не набирает
пароль дважды ради ответа «пользователь не найден». Ради этого шага два оператора
в одну транзакцию не объединяются: запрос пароля ждёт человека, а держать транзакцию
открытой на время ввода нельзя.

### SQL — в классе `UserPasswords` в `admin/`, по образцу `OrgSearch`

`UserPasswords(database, passwordHasher)` с методами `exists(login)` и
`reset(login, password): Boolean` (true, если строка обновлена). Объект регистрируется
в `AdminDi` лениво, рядом с `orgSearch`. Внутри используется `PasswordHasher()`
с параметрами по умолчанию, как в `Di.kt`.

В `domain/auth` (`Auth`, `DbAuth`) сброс не добавляется: все их методы требуют
`EmployeeRequestContext` или работают в рамках входа, а у CLI нет ни сотрудника,
ни организации. Подставлять для этого синтетический контекст хуже, чем держать
одну прямую SQL-операцию в `admin/`, где так уже сделаны `OrgSearch` и `FailedDomainEvents`.

## Risks / Trade-offs

- [Действующие JWT-сессии не отзываются: токены, выданные до сброса, работают до конца
  срока refresh-токена] → Записано в proposal как известное ограничение. Исправлять нужно
  отдельным изменением: например, отметкой `password_changed_at` и её проверкой при refresh.
- [Запуск без TTY (`docker compose exec -T`, пайп): mordant может читать строки из stdin
  без скрытия или не читать вовсе] → Проверить при реализации и описать фактическое
  поведение в `docs/cli.md`. Контрактом это не считается.
- [Сброс пароля нигде не фиксируется] → Принято осознанно (см. proposal). Если журнал
  понадобится, его можно добавить отдельно, без изменения интерфейса команды.
- [У найденного пользователя может не быть активного сотрудника: тогда сброс проходит,
  но войти он всё равно не сможет] → Не блокирует операцию. Включать или нет предупреждение
  в выводе — решить при реализации; в спеке это не зафиксировано.

## Migration Plan

Схема БД не меняется. Команда появляется со следующим деплоем образа сервера, откат —
предыдущим образом.
