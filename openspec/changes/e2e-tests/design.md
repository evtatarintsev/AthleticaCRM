# Design

## Context

Мотивация в proposal.md. На решения влияют следующие факты из кода:

- **Прод-стенд.** `docker-compose.prod.yaml` состоит из postgres, rustfs, server, frontend, nginx и certbot (профиль `tools`).
  - Образы указаны как `ghcr.io/${GITHUB_REPOSITORY}/{server,frontend}:latest`.
  - nginx публикует порты 80 и 443 и берёт сертификат из тома `letsencrypt`.
- **nginx.** `nginx/prod.conf.template` знает только HTTPS-хосты `${DOMAIN}`, `app.${DOMAIN}`, `minio.${DOMAIN}` и `console.minio.${DOMAIN}`.
  - Он ссылается на `/etc/letsencrypt/live/${DOMAIN}/{fullchain,privkey}.pem`, `options-ssl-nginx.conf` и `ssl-dhparams.pem`.
  - Фронту нужен secure context (`nginx/gen-dev-cert.sh`), так что HTTPS обязателен и в e2e.
- **Сессия.** Это HttpOnly-cookie с `SameSite=Strict`, без `Secure`. Refresh-cookie выставляется на путь `/api/auth/refresh-token`.
  - `POST /api/auth/sign-up` сразу возвращает сессию, подтверждение email вход не блокирует.
- **Почта.** `SmtpMailbox` ходит на `smtp.host` по фиксированному порту 587.
  - Аутентификация включена всегда, STARTTLS включается, только если его предлагает сервер.
  - Логин и пароль нового сотрудника приходят ему письмом (`EmailEmployee.invite`).
- **Файлы.** Файл загружается на сервер, а скачивается по presigned GET на `MINIO_PUBLIC_ENDPOINT`. Подпись считается с публичным хостом, бакет сервер создаёт сам.
- **Готовность сервера.** Health-эндпоинта нет. Признак готовности: `GET /api/auth/me` через nginx отвечает 401.
- **Строгость TS.** В `web/` действуют строгие правила (`strictTypeChecked`, запрет `as`/`!`, zod на внешних данных). Тексты интерфейса лежат в `web/src/i18n/ru.ts`, схемы API — в `web/src/api/generated/contracts.ts`.

## Goals / Non-Goals

**Goals:**
- Проверять ровно те образы и ту конфигурацию nginx, которые уйдут в прод.
- Одна команда для локального запуска, с тем же путём, что в CI.
- Стенд не конфликтует с dev-окружением: никаких портов на хосте, отдельное имя compose-проекта.

**Non-Goals:**
- Подмена времени на сервере.
- Покрытие граничных случаев. Они остаются в DB- и vitest-тестах, e2e проверяет только связки.
- Изменение кода server, web и shared ради тестов. Допустимы только `data-testid` там, где у элемента нет доступной роли или подписи (см. риски).

## Decisions

### 1. Playwright, один инструмент для браузера и API

API-сценарии идут через фикстуру `request` того же раннера, браузерные — через `page`. Отчёт, ретраи, трассы и параллелизм общие.

- *Альтернатива:* API-e2e на Kotlin (Ktor client) рядом с `ApplicationTest`. Это второй стек и второй отчёт, а связки контейнеров проверяются одинаково из любого клиента. Отклонено.
- *Альтернатива:* Cypress. Нет нативного API-клиента вне браузера, медленнее параллелизм. Отклонено.

### 2. Отдельный пакет `e2e/`, а не часть `web/`

У `e2e/` свой `package.json`, `tsconfig.json` (strict, как в `web/`) и `eslint.config.js`, который переиспользует правила `web/eslint.config.js`.

- Тексты для селекторов импортируются из `../web/src/i18n/ru.ts`. Переименование строки не ломает тест молча: меняется словарь, тест берёт новое значение.
- Ответы API декодируются схемами из `../web/src/api/generated/contracts.ts`. Так выполняется правило «внешние данные — через zod», и расхождение контракта со стендом видно сразу.
- *Почему не в `web/`:* `npm run check` в `web/` запускается в Docker-сборке фронта. Playwright и браузеры ей не нужны, а vitest не должен подбирать e2e-файлы.

### 3. Стенд — прод-compose плюс оверлей

Стенд поднимается командой:

```
docker compose -p athletica-e2e \
  -f docker-compose.prod.yaml -f e2e/stand/docker-compose.e2e.yaml \
  --env-file e2e/stand/e2e.env up -d --wait
```

Что меняет оверлей:

- **server и frontend.** `image: ${E2E_SERVER_IMAGE:-athletica-server:e2e}` с секцией `build:` из `Dockerfile.server` и `web/Dockerfile`, аналогично для frontend.
  - Локально `--build` собирает образы из рабочей копии.
  - В CI переменные указывают на `ghcr.io/…:sha-<sha>`, и стенд поднимается с `--no-build` после `pull`.
- **nginx.**
  - `ports: !reset []`: наружу ничего не публикуется.
  - Том `/etc/letsencrypt` заменяется каталогом `e2e/stand/.letsencrypt` (в `.gitignore`), который генерирует скрипт.
  - Сетевые алиасы `e2e.test`, `app.e2e.test`, `minio.e2e.test`.
- **mailpit.** Новый сервис `axllent/mailpit`, слушает SMTP на `:587` (`MP_SMTP_BIND_ADDR`), принимает любой логин (`MP_SMTP_AUTH_ACCEPT_ANY`, `MP_SMTP_AUTH_ALLOW_INSECURE`), HTTP API на `:8025`.
- **playwright.** Новый сервис на образе `mcr.microsoft.com/playwright:<версия как в @playwright/test>` в профиле `test`.
  - Монтирует `e2e/` и `web/src` (только чтение).
  - Запускается так: `docker compose … run --rm playwright`.
- **certbot** не стартует: он и так в профиле `tools`.

`e2e/stand/e2e.env` коммитится. В нём только тестовые значения: `DOMAIN=e2e.test`, `MINIO_PUBLIC_ENDPOINT=https://minio.e2e.test`, `SMTP_HOST=mailpit`, `YOOKASSA_TEST_MODE=true` с фиктивными ключами, пустые `AI_*` и `TELEGRAM_PROXIES`.

Почему не отдельный `docker-compose.e2e.yaml` с нуля: он разошёлся бы с продом. Сейчас из прода в оверлей не копируется ни одной строки, кроме переопределённых.

### 4. Боевой `prod.conf.template` на самоподписанном сертификате

`e2e/stand/certs.sh` создаёт в `.letsencrypt/` раскладку, которую ждёт шаблон:

- `live/e2e.test/{fullchain,privkey}.pem` с SAN на все четыре хоста;
- минимальный `options-ssl-nginx.conf`;
- `ssl-dhparams.pem` — закоммиченная группа ffdhe2048 из RFC 7919, чтобы не генерировать DH-параметры на каждый прогон.

Playwright запускается с `ignoreHTTPSErrors: true`.

- *Альтернатива:* отдельный `nginx/e2e.conf` по HTTP. Он не проверяет главный источник поломок, маршрутизацию прод-шаблона, и не даёт secure context. Отклонено.

### 5. Раннер внутри сети compose

Браузер и `request` резолвят `app.e2e.test` и `minio.e2e.test` через Docker DNS по алиасам nginx. Поэтому:

- не нужны `/etc/hosts` и `sudo` ни локально, ни в CI;
- presigned-ссылка `https://minio.e2e.test/…` открывается тем же браузером без переписывания хоста;
- порты 80 и 443 хоста свободны, и dev-стенд может работать параллельно.

Для отладки с UI-режимом `e2e/README.md` описывает запуск раннера на хосте: временно опубликовать 443 у nginx и добавить строки в `/etc/hosts`. Это ручной режим, CI его не использует.

### 6. Изоляция данных: организация на тест

Фикстура `org` регистрирует организацию через `POST /api/auth/sign-up`:

- email вида `e2e-<uuid>@e2e.test`, пароль из констант фикстуры;
- cookie сохраняются в `storageState` контекста;
- браузерный сценарий начинается уже залогиненным, кроме самих сценариев регистрации и входа.

Базу никто не чистит, `workers` > 1 безопасно. Сценарий регистрации через UI проходит форму целиком один раз.

### 7. Почта через API Mailpit

Хелпер `mailbox.latest(to)` опрашивает `GET http://mailpit:8025/api/v1/search?query=to:"<email>"` через `expect.poll` и возвращает тело письма, декодированное zod. Из тела регулярным выражением достаются ссылка подтверждения, ссылка сброса или пароль сотрудника. Уникальный email на тест делает поиск однозначным без очистки ящика.

### 8. Селекторы и ожидания

- Селекторы: `getByRole` и `getByLabel` с текстами из `ru`.
- Локаль контекста — `ru-RU`. Язык фиксируется явно, если веб выбирает его по `navigator.language`.
- Никаких `waitForTimeout`, только web-first assertions.
- `retries: 1` в CI. Трасса, скриншот и видео сохраняются при первом ретрае и при падении.

### 9. CI: гейт перед `deploy` и перенос `latest`

В `docker.yml`:

- Jobs `server` и `frontend` пушат только тег `sha-<sha>`.
- Новый job `e2e` (`needs: [server, frontend]`):
  1. `certs.sh`;
  2. `pull`;
  3. `up -d --wait --no-build`;
  4. `run --rm playwright`.

  HTML-отчёт выкладывается артефактом при любом исходе, логи контейнеров — при падении (`docker compose logs`).
- Новый job `promote` (`needs: e2e`) проставляет `latest` через `docker buildx imagetools create`, без пересборки.
- `deploy` зависит от `promote`.
- Отдельный `.github/workflows/e2e.yml` с `workflow_dispatch` собирает образы из выбранной ветки локально в раннере (`up --build`) и ничего не пушит. Через него проверяется ветка до мерджа.

Почему так: сейчас `latest` пушится до любых проверок. Если оставить так и e2e упадёт, `deploy` не случится, но в реестре `latest` уже будет сломан. А прод тянет именно `latest` (в том числе при ручном `pull` на сервере).

- *Альтернатива:* e2e на каждый PR. Это +5–10 минут на каждый PR. Отложено (см. proposal, «Вне объёма»).

### 10. Локальный запуск

Задача `mise run e2e` выполняет: `certs.sh` → `up -d --wait --build` → `run --rm playwright` → `down -v`. Последний шаг выполняется всегда, через `trap` в скрипте `e2e/stand/run.sh`. Флаг `--keep` оставляет стенд поднятым для повторных прогонов.

## Risks / Trade-offs

- **[Нестабильные тесты разрушат доверие к гейту]** → Только web-first assertions, один ретрай. Тест, упавший дважды за неделю без изменения кода, чинится или удаляется. Объём держится смоуком, см. спеку.
- **[Длительность job `e2e` растёт и тормозит выкладку]** → Цель < 10 минут на весь job, параллельные workers. Тяжёлые проверки уходят в DB-тесты.
- **[Минимальный `options-ssl-nginx.conf` расходится с certbot-овским]** → Он задаёт только протоколы и шифры. Сама маршрутизация, ради которой всё затевается, из этого файла не берётся.
- **[`docker-compose.prod.yaml` сменит имена сервисов или томов, и оверлей молча перестанет переопределять]** → `up --wait` с healthcheck и сценарий «стенд отвечает» падают сразу. В `CLAUDE.md` добавляется правило «меняя prod-compose, прогнать `mise run e2e`».
- **[У элемента нет доступной роли или подписи]** → Сначала чинится доступность (это и так дефект), `data-testid` — в крайнем случае.
- **[Тексты из `ru.ts` с интерполяцией]** → Для таких строк используется regex по постоянной части или подписи соседних элементов. Конкретные случаи разбираются при реализации.
- **[Версия образа Playwright разойдётся с `@playwright/test`]** → Версия пакета закрепляется точно (без `^`), тег образа берётся из неё в оверлее.
- **[Образы `sha-…` без `latest` неудобны для ручного отката]** → Откат и так делается на конкретный `sha`. В `DEPLOY.md` добавляется строка про это.

## Migration Plan

1. Слить `e2e/`, оверлей и задачу `mise` — CI не меняется. Прогонять локально, добиваясь стабильности.
2. Добавить `e2e.yml` (`workflow_dispatch`) и прогнать на нескольких ветках.
3. Перевести `docker.yml` на схему `sha` → `e2e` → `promote` → `deploy`.

Откат: вернуть `deploy` к `needs: [server, frontend]` и тег `latest` в метаданные сборки. Код продукта не затронут.

## Open Questions

- Нужен ли отдельный проект Playwright под Firefox или WebKit, или достаточно Chromium. Ответ влияет только на конфиг и время прогона.
- Порог длительности, после которого e2e начнёт гоняться на PR по метке `e2e`.
