# Design

## Context

- `DbAuth.signup` одной транзакцией создаёт организацию, пользователя, владельца, филиал «по умолчанию» и зал. Маршрут `POST /auth/sign-up` вызывает его внутри `db.transaction` и там же выдаёт сессию. Контекст владельца собирается так же, как в `DbAuth.bootstrapContext`: `SystemContexts.forOrg(orgId)`, затем `employees.byId`.
- Доменные операции принимают деловую дату явно:
  - `Sales.create(..., date, ...)`, `issueMembership(..., issuedOn)`, `ClientPayments.pay(..., occurredOn)`;
  - `freezeMembership(calendar, start, end, ...)`, `closeMembership(calendar, ...)`;
  - `ScheduleSync.sync(today: LocalDate?)` материализует занятия от `today` на 3 месяца вперёд, `createSession(date, ...)`;
  - «сегодня» доменные операции берут из интерфейса `OrgCalendar`, а не из часов БД.
- Отметки посещаемости (`SessionJournal.mark`) требуют `EmployeeRequestContext` и не ограничены по давности.
- Списания по посещениям идут через outbox `domain_events`: `publish` пишет событие в текущей транзакции, `DomainEventWorker` после коммита вызывает обработчики, и каждый из них открывает свою транзакцию.
- Технические времена (`created_at` клиентов, продаж, задач, журнала действий и т.п.) заполняет `DEFAULT now()`. В PostgreSQL `now()` — время начала транзакции, поэтому внутри одной транзакции оно одинаково для всех строк.
- Админ-CLI (`admin/`) получает зависимости из `AdminDi`, а БД подключает лениво. Сервер собирает граф в `Di` (data class с дефолтами `Db*`/`Audit*`).

## Goals / Non-Goals

**Goals:**
- Организация выглядит так, будто в ней несколько месяцев работали: история событий, а не срез «на сегодня».
- Один наполнитель для CLI и для демо-режима.
- Всё, у чего есть инварианты, проходит через доменные операции.

**Non-Goals:**
- Скорость. Батчевого SQL и параллелизма нет, наполнение `large` может идти минуты.
- Развёртывание демо-стенда, изоляция демо-данных и периодический сброс. Решение уже принято: демо будет на отдельном сервере с тем же `docker-compose.prod.yaml` и своим `.env`. Реализация — отдельным изменением, когда стенд понадобится.
- Синхронная обработка событий внутри наполнения.

## Decisions

### 1. Симуляция по дням

Генерацию ведёт не набор независимых «создай N сущностей», а цикл по дням периода истории — от `today - historyMonths` до `today`. В каждый день:

1. новые клиенты: лиды из источников, часть из них записывается в группы;
2. открытие групп, запланированное на этот день, — `setGroupSchedule` со стартом в этот день;
3. продажи абонементов тем, у кого нет действующего (новичкам, а также после исчерпания или истечения прежнего);
4. оплаты: сразу полностью, частями, с задержкой в N дней или никогда (будущие должники);
5. занятия этого дня: отметки по вероятности посещения клиента, «не пришёл» с меткой, иногда разовый участник, редкая отмена занятия;
6. события жизненного цикла: заморозка, уход клиента (перестаёт ходить и не продлевает);
7. задачи: создание и закрытие с исполнителями.

Решения симуляция принимает по собственной модели в памяти (`DemoWorld`: клиенты, их вероятность посещения, текущий абонемент и остаток, долги). Записывает их доменными операциями с деловой датой текущего дня. Перед циклом один раз вызывается `ScheduleSync.sync(start)`, чтобы материализовать занятия. Группы, открытые позже, получают свои занятия повторным `sync(day)` в день открытия. Последний вызов `sync(today)` достраивает будущее расписание.

Последние 1–3 дня перед `today` симулируются частично: журналы части занятий не закрываются, чтобы на экранах был незакрытый журнал (спека «Разнообразие состояний на сегодня»).

*Альтернатива:* срез на сегодня — сразу создать абонементы в нужных состояниях и задним числом проставить посещения. Так проще, но получаются абонементы без предыстории, продления не видны, а журнал действий и движение денег пусты по датам. Именно этого пользователь просил избежать.

### 2. Календарь симулируемого дня

`DemoCalendar(day) : OrgCalendar` возвращает текущий день симуляции. Операции, которым нужно «сегодня» (`freezeMembership`, `closeMembership`, `ScheduleSync`), получают его вместо `DbOrgCalendar`. Операции с явной датой получают день напрямую. Доменный код не меняется.

### 3. Однозначный подбор абонемента для списаний

Списания применяет воркер после коммита, в порядке `created_at` событий. Чтобы модель симуляции и правила подбора абонемента (`membership-debits`) давали одинаковый результат, у клиента в любой день не больше одного неокончательного абонемента: новый продаётся только после исчерпания или истечения прежнего. Подбор при этом однозначен, а модель заранее знает остаток и момент исчерпания. Правила подбора в наполнителе не дублируются: если модель с ними разойдётся, тест «остаток не отрицателен, каждое посещение списано» это поймает.

Активация — в основном датой продажи. Активация по первому посещению используется только у продаж последних дней без посещений, чтобы получить неактивированные абонементы.

Истечение абонементов закрывает `MembershipScheduler` по «сегодня». После наполнения он сам догонит просроченные абонементы. В тестах он вызывается явно, так же как обработчики событий.

### 4. Технические времена сдвигаются в день истории

Доменные операции не принимают `created_at`. После каждого дня симуляции `DemoTimestamps.shift(day)` выполняет для фиксированного списка таблиц организации:

```sql
UPDATE <table> SET created_at = :dayTs WHERE org_id = :orgId AND created_at = transaction_timestamp()
```

Строки этого дня ещё имеют время начала транзакции, а строки прошлых дней уже сдвинуты, поэтому отбор точен без учёта идентификаторов. `:dayTs` — день плюс рабочее время, в часовом поясе организации. Для таблиц без `org_id` (`session_attendance.marked_at`) отбор идёт через родительскую таблицу. Список таблиц: `clients`, `client_notes`, `sales`, `memberships`, `ledger_transactions`, `tasks`, `notifications`, `audit_logs`, `domain_events`, `session_attendance` — уточняется по миграциям при реализации.

Это единственное место, где наполнитель пишет SQL в таблицы домена. Сдвигаются только технические времена, на которые не опираются инварианты. Деловые даты задают сами доменные операции.

*Альтернатива:* добавить `createdAt` в доменные операции. Это изменило бы API десятка репозиториев ради инструмента наполнения.

### 5. Пакет `demo/` и класс `DemoData`

```kotlin
class DemoData(/* доменные репозитории и usecase'ы; дефолты — Db*/Audit*, как в Di */) {
    context(ctx: EmployeeRequestContext, tr: Transaction, raise: Raise<AppError>)
    suspend fun fill(profile: DemoProfile, random: Random, today: LocalDate): DemoSummary
}
```

- `ctx` — контекст владельца организации. От его имени пишутся аудит, отметки и оплаты, поэтому журнал действий наполняется естественным образом.
- `DemoProfile` — enum с числами. Ориентир:

  | Профиль | Клиенты | Группы | История, мес. |
  |---|---|---|---|
  | `small` | 60 | 6 | 4 |
  | `medium` | 300 | 15 | 8 |
  | `large` | 1500 | 40 | 12 |

- `DemoSummary(clients, groups, sessions, sales)` — для вывода команды.
- Генераторы ФИО, телефонов `+7 000 …`, почты `@example.com` и заметок — приватные функции пакета от `Random`. Списки имён лежат статичными массивами в коде, без зависимостей.
- Проверка «пустая организация» — первым шагом, одним `SELECT EXISTS` по `clients` и `groups` в `ctx.orgId`. Ошибка — `CommonDomainError("DEMO_ORG_NOT_EMPTY", ...)`.

Почему не `usecases/`: это не одна команда пользователя, а сценарий из тысяч команд. Отдельный пакет держит генерацию вместе.

### 6. Детерминизм

`Random(seed)` и `today` передаются явно, вся случайность симуляции идёт только из них. Идентификаторы (UUID v7) случайны: спека требует совпадения с точностью до id. CLI по умолчанию берёт `--seed=1` и `today` из `DbOrgCalendar`. Демо-регистрация использует случайное зерно.

### 7. Демо-регистрация — декоратор `DemoAuth`

```kotlin
class DemoAuth(private val delegate: Auth, private val demoData: DemoData, ...) : Auth by delegate {
    override suspend fun signup(...): AuthenticatedUser =
        delegate.signup(...).also { /* контекст владельца → demoData.fill(SMALL, Random.Default, today) */ }
}
```

Наполнение идёт в транзакции маршрута, поэтому атомарность из спеки обеспечивается без новой логики. В `Di` декоратор подключается только при `demo.enabled` (`DEMO_MODE`, по умолчанию `false`). Композиция вместо ветвления внутри `DbAuth`.

### 8. Признак демо — поле `demo` в `AuthMeResponse`

Веб-клиент уже запрашивает `/auth/me` на страницах CRM и показывает рядом `EmailVerificationBanner`. Новый `DemoBanner` выводится по `me.demo`. Публичный эндпоинт конфигурации не нужен: баннер показывается только вошедшему пользователю.

### 9. Команда `admin org seed`

`SeedCommand` в `admin/`. Аргумент организации разрешается так же, как в `credit`/`debit`. `--size` (`choice`, по умолчанию `small`) и `--seed` (`int`, по умолчанию 1) разбираются до подключения к БД. Контекст владельца собирается через `SystemContexts.forOrg` и `employees.byId(ownerId)`. `adminContext()` не подходит: он не `EmployeeRequestContext`. Обработчиков событий в CLI нет: списания применит воркер запущенного сервера, и это описывается в `docs/cli.md`.

## Risks / Trade-offs

- [Демо-регистрация `small` идёт десятки секунд — тысячи доменных вызовов в HTTP-запросе] → Сейчас это допустимо: режим только локальный, скорость не важна. Для публичного демо наполнение уйдёт в фон отдельным изменением, вместе с развёртыванием.
- [Первые секунды после наполнения списания и закрытия истёкших абонементов ещё не применены] → Принимаем: воркер и планировщик догоняют их за секунды. Экраны остаются согласованными, только без списаний.
- [Модель симуляции разойдётся с правилами подбора абонемента] → Правило «один неокончательный абонемент на клиента» делает подбор однозначным. Тест на остатки и списания ловит расхождение.
- [Новая таблица с `created_at` не попадёт в сдвиг времён] → Её записи будут датированы моментом наполнения. Это видно, но не ломает данные. Тест «журнал действий растянут по истории» ловит самый заметный случай.
- [Изменения доменных правил ломают наполнение] → Тест на чистой базе прогоняет профили через основные проекции `read/` и входит в `./gradlew build`. `large` в тестах не гоняется целиком, только проверяется число клиентов на урезанной истории.
- [`admin org seed` по ошибке запущен на реальной организации] → Отказ на непустой организации.
- [Длинная транзакция блокирует строки] → Наполняется новая пустая организация, которую никто другой не читает и не пишет.
