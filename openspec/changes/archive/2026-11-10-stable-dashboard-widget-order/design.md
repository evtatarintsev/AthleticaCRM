## Context

Мотивация и требования описаны в `proposal.md` и `specs/web-client/home-dashboard/spec.md`.

`DashboardSettings` уже содержит `widgets` — список экземпляров с настройками — и `layout` — идентификаторы видимых карточек в порядке отображения. Сервер сохраняет структуру в JSONB без перестановки элементов. Сейчас web-клиент меняет порядок только в `layout`, а повторное включение добавляет идентификатор в конец. Поэтому порядок `widgets` в старых данных может отличаться от порядка видимых карточек.

В рабочем дереве уже есть switch, ручка перетаскивания на Pointer Events и управление стрелками клавиатуры в `DashboardSettingsDialog`. Этот change расширяет существующее управление на общий список, а не создаёт его заново. Дизайн нужен для однозначного перехода со старой семантики порядка и согласования чтения и записи настроек.

## Goals / Non-Goals

**Goals:**

- Использовать существующий формат данных для независимого порядка всех экземпляров.
- Получить детерминированное, идемпотентное чтение старых настроек без потери видимости и параметров.
- Применять одни правила порядка к общим настройкам, скрытию из карточки и повторному включению.

**Non-Goals:**

- Новое поле порядка, версия формата, миграция БД или новый маршрут API.
- Новая библиотека перетаскивания, редактор параметров скрытой карточки или изменение состава виджетов.
- Новый механизм разрешения конфликтов между вкладками и переработка общего механизма сохранения настроек.

## Decisions

### 1. Общий порядок хранится в `widgets`, видимость остаётся в `layout`

Для нормализованных настроек действует инвариант: `layout` равен последовательности идентификаторов из `widgets`, отфильтрованной по включённости. Идентичность и индивидуальные параметры экземпляров не меняются.

- Общие настройки показывают все элементы `widgets` в их порядке.
- Главная по-прежнему использует `orderedVisible()` и порядок `layout`.
- Выключение удаляет идентификатор только из `layout`.
- Включение добавляет идентификатор в множество видимых и строит `layout` фильтрацией общего порядка, а не добавлением в конец.
- Перемещение переставляет экземпляр в `widgets` и пересобирает `layout` с прежним множеством видимых идентификаторов.
- Редактирование названия или параметров заменяет экземпляр на месте, сохраняя оба порядка.

Альтернатива — отдельный массив `order` или признак видимости внутри экземпляра — дублирует имеющиеся данные и требует изменения контрактов. Переопределять `layout` как список всех виджетов нельзя: существующие потребители считают его списком видимых карточек.

### 2. Старые данные нормализуются по видимым слотам

Нормализация читает `widgets` и текущую последовательность существующих видимых идентификаторов из `layout`. Позиции скрытых экземпляров в `widgets` остаются занятыми этими экземплярами. Остальные позиции заполняются видимыми экземплярами в порядке `layout`.

Пример, где `B` выключен:

```text
Stored widgets: [A, B, C, D]
Stored layout:  [D, A, C]
Normalized:    [D, B, A, C]
Visible:       [D, A, C]
```

Это сохраняет текущий порядок карточек и использует единственный доступный порядок скрытых экземпляров. После нормализации видимая подпоследовательность `widgets` уже совпадает с `layout`; повторное применение ничего не меняет. Если все виджеты выключены, порядок `widgets` сохраняется целиком.

Нормализация применяется к данным для отображения и к актуальным данным перед изменением через общий путь `updateDashboardSettings`. Нельзя нормализовать только отображаемый fallback: актуальный кэш может содержать старый порядок при тех же идентификаторах. Существующая обработка неизвестных идентификаторов при чтении сохраняется; нормализация не создаёт новые экземпляры и не восстанавливает отсутствующие ссылки.

Альтернатива — видимые сначала, скрытые в конце — теряет доступные позиции скрытых экземпляров. Маркер миграции не нужен благодаря идемпотентности.

### 3. Дополнение дефолтами и сохранение используют тот же общий порядок

Существующее дополнение недостающих типов через `withDashboardDefaults` сохраняется. Новый тип добавляется в конец общего порядка и включается, как и раньше. Непустой пул с пустым `layout` означает, что все существующие виджеты выключены; это не повод восстанавливать их видимость.

Путь записи использует актуальный кэш с нормализацией, сохраняя уже сделанное исправление для экземпляров, добавленных при отображении и ещё отсутствующих в кэше. Первый пользовательский edit сохраняет нормализованные `widgets` и `layout` вместе. Открытие страницы само по себе не отправляет запрос сохранения.

Альтернатива — отдельная фоновая миграция на сервере — избыточна для существующего JSON-формата и требует записи при чтении.

### 4. Один тип строки и одни операции для включённых и выключенных виджетов

`DashboardSettingsDialog` отображает один список с ключом по идентификатору экземпляра. Отдельные раздел и компонент скрытой строки удаляются. Switch управляет только видимостью; выключенность обозначается `text-muted-foreground` у названия, а не отключением или общей прозрачностью строки. Ручка и switch сохраняют обычный контраст и доступность.

Существующие перетаскивание и клавиатурное управление используют идентификаторы и индексы полного списка `widgets`. При завершении перетаскивания сохраняется одна перестановка, при отмене запись не выполняется. Фокус ручки сохраняется за счёт стабильного ключа строки. Скрытие из `WidgetSettingsButton` вызывает тот же helper видимости и не меняет общий порядок.

Удаляются только ставшие неиспользуемыми helpers и ключи локализации после проверки всех вызовов. Публичные Kotlin-методы не удаляются ради очистки web-интерфейса.

Альтернатива — два списка с визуально скрытым разделителем — сохраняет проблему смены позиции строки и усложняет перемещение.

## Risks / Trade-offs

- [Историческая позиция ранее скрытой карточки не записана отдельно] → использовать её слот в сохранённом `widgets`; не обещать восстановление утраченной истории.
- [Другой или старый клиент меняет только `layout`] → при следующем чтении нормализация сохраняет его порядок видимых карточек; формат остаётся читаемым, но старый клиент не гарантирует новое поведение позиций скрытых виджетов.
- [Нормализация только на экране теряется при записи из кэша] → применять её также в общем пути изменения и покрыть первым edit старых настроек.
- [Управление порядком случайно включает скрытый виджет] → перестановка всегда сохраняет множество видимых идентификаторов; проверить перетаскивание и клавиатуру при смешанной видимости.
- [Изменение порядка `widgets` затронет другие потребители] → структуру и семантику `layout` сохранить; уточнить документацию `widgets` в общем контракте, не меняя сериализуемые поля.

## Migration Plan

1. Добавить нормализацию и операции общего порядка в web-клиент; обновить документацию существующих полей общего контракта без изменения формата.
2. Перевести отображение и редактирование на единый список. Сохранить существующее дополнение новыми типами и работу индивидуальных настроек.
3. Проверить старые переставленные настройки со скрытыми виджетами, повторное открытие после сохранения и состояние со всеми выключенными виджетами.
4. Развернуть web-клиент; данные нормализуются в памяти при чтении и сохраняются при следующем действии пользователя. Массовая миграция БД и регенерация контрактов не требуются, если меняются только комментарии.

Откат не требует преобразования данных: старый код прочитает те же поля и покажет видимые карточки в сохранённом `layout`. После отката возвращается прежнее поведение повторного включения в конец.
