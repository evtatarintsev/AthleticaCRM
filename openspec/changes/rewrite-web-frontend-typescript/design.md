## Context

Мотивация — в `proposal.md`, требования — в `specs/web-client/*`. Здесь только то, что определяет подход.

- `web/` уже существует ([#82](https://github.com/evtatarintsev/AthleticaCRM/pull/82)): Vite + React 19 + TypeScript 6 + Tailwind 4 + React Router 8, вход и регистрация, образ `frontend`, путь `/web/`. `tsconfig` там строгий, но не максимальный. Если включить недостающие флаги, код сразу получает ошибки (`exactOptionalPropertyTypes` в `src/ui/fields.tsx`). Схемы авторизации написаны вручную, ответ приводится через `as`.
- Сервер регистрирует ~95 JSON-маршрутов через `RouteWithContext.get<Req, Res>` / `post<Req, Res>` с reified-типами. Маршруты `/auth/*` (кроме `me`, `logout`, `my-branches`, `switch-branch`) и `/checkout/*` объявлены напрямую через Ktor, загрузка файлов идёт multipart (`UploadRoutes`).
- `Json` сервера — `Json { ignoreUnknownKeys = true }`: `encodeDefaults = false`, дискриминатор полиморфизма по умолчанию `type`. GET-запросы декодируются из плоских query-параметров (`queryParametersJson`).
- В схемах `shared`: 21 value class идентификаторов (UUID), `Instant` (28 мест), `LocalDate` (46), `LocalTime` (18), `DayOfWeek`, `Money`, sealed-иерархии (`ImportTarget`, `LeadSourceAction`, `DashboardWidget`, `CustomFieldValue`, `CustomFieldDefinition`, `MessageSchema`, `ChannelConfig`). Свои `KSerializer` есть у `Currency`, `CustomFieldKey`, `ClientNoteText`, `SessionColorKey`, `Validity`.
- KMP-клиент адресует страницы путями `/clients/{id}` и т. п. (`AppNavUrlEncoder`) и при старте разбирает `window.location.pathname`. Поэтому из веб-клиента можно ссылаться прямо в нужный экран KMP-клиента.

## Goals / Non-Goals

**Goals:**

- Ни одного `any`, `as` и `!` в коде веб-клиента, включая сгенерированный. Строгость держат инструменты, а не дисциплина.
- Один источник истины для контрактов — Kotlin. На стороне TS нет ручных схем API.
- Выбор библиотек определяется полнотой вывода типов (маршруты, параметры адреса, формы, запросы).
- Перенос по разделам без остановки продукта.

**Non-Goals:**

- Генерация клиентского кода для других платформ из того же манифеста (Swift, Kotlin/Android). Манифест это позволит, но в изменение не входит.
- Изменение API ради удобства фронтенда. Меняется только `encodeDefaults`.
- Визуальный редизайн и дизайн-система сверх набора компонентов для паритета.

## Decisions

### 1. Максимальная строгость: tsconfig

К текущему `tsconfig.app.json` добавляются:

```jsonc
"exactOptionalPropertyTypes": true,
"noPropertyAccessFromIndexSignature": true,
"noImplicitOverride": true,
"noImplicitReturns": true,
"allowUnreachableCode": false,
"allowUnusedLabels": false,
"erasableSyntaxOnly": true,
"noUncheckedSideEffectImports": true,
"forceConsistentCasingInFileNames": true,
"libReplacement": false,
"skipLibCheck": false
```

Уже включённые `strict`, `noUncheckedIndexedAccess`, `noUnused*`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax` остаются. Базовые опции выносятся в `tsconfig.base.json`; проекты `app`, `test`, `node` его расширяют и ослаблять ничего не могут.

**Тесты — отдельный проект TS.** С `skipLibCheck: false` типы `@testing-library/jest-dom` конфликтуют с `vitest` (`All declarations of 'Assertion' must have identical type parameters`), когда оба попадают в `types` приложения. Поэтому в `tsconfig.app.json` тестовых типов нет. `tsconfig.test.json` включает `**/*.test.ts(x)`, в тестах используется явный `import { describe, it, expect } from "vitest"` вместо глобалов, а матчеры `jest-dom` подключаются через `@testing-library/jest-dom/vitest` в setup-файле. Если конфликт останется и так, `skipLibCheck: true` включается **только** в `tsconfig.test.json` с комментарием о причине. Для кода приложения проверка объявлений зависимостей остаётся.

*Альтернатива:* `skipLibCheck: true` везде, как в шаблоне Vite. Отклонена: сломанные типы зависимостей молча превращаются в `any` на границе.

### 2. Максимальная строгость: ESLint

Flat config на `typescript-eslint` с проверкой типов (`parserOptions.projectService`):

- наборы `strictTypeChecked` + `stylisticTypeChecked`;
- `@typescript-eslint/consistent-type-assertions: { assertionStyle: "never" }` запрещает все `as`, кроме `as const` (правило само пропускает const-утверждения);
- `@typescript-eslint/no-non-null-assertion`, `no-explicit-any`, семейство `no-unsafe-*` — из `strictTypeChecked`;
- `@typescript-eslint/ban-ts-comment` запрещает `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck` без исключений;
- `@typescript-eslint/switch-exhaustiveness-check` с `requireDefaultForNonUnion: true` и `considerDefaultExhaustiveForUnions: false`: `default` не маскирует пропущенный вариант объединения;
- `@typescript-eslint/strict-boolean-expressions` с запретом nullable-строк и чисел в условиях;
- `@typescript-eslint/no-floating-promises`, `no-misused-promises`, `only-throw-error`, `prefer-readonly`, `no-unnecessary-condition`, `restrict-template-expressions` — из наборов, уровень `error`;
- `linterOptions: { noInlineConfig: true, reportUnusedDisableDirectives: "error" }` — директивы `eslint-disable` в коде не действуют и сами считаются ошибкой. Исключения задаются только блоком `files: [...]` в конфиге с комментарием;
- `eslint --max-warnings 0`.

Тесты подчиняются тем же правилам. Моки строятся через типизированные фабрики (`satisfies AuthApi`), а не через `as`.

### 3. Покрытие типами

`type-coverage --strict --at-least 100 --detail` в `npm run check`. `--strict` дополнительно считает `any` в аргументах generic-типов и в `as unknown as`. Это страховка на случай, если `any` пришёл из объявлений зависимости и правила `no-unsafe-*` его не поймали.

### 4. Единая команда проверки

`npm run check` = `tsc -b` (все проекты) → `eslint . --max-warnings 0` → `type-coverage` → `prettier --check` → `vitest run`. Актуальность контрактов проверяется отдельно (решение 7). `web/Dockerfile` уже вызывает `npm run check` перед `vite build`, так что CI и `deploy_to_stand.sh --only frontend` получают все проверки без изменений. Отдельный CI-job на PR запускает `npm run check` и генерацию контрактов, чтобы ошибки находились до `master`.

### 5. Контракты: манифест из дерева маршрутов Ktor

`RouteWithContext.get/post` уже знают `Req`, `Res`, метод и путь. Хелпер кладёт в атрибуты созданного `Route` запись `ApiContract(method, requestSerializer, responseSerializer, requestIn = Body | Query)`. Маршруты, объявленные напрямую (`/auth/branches`, `/auth/login`, `/auth/sign-up`, `/auth/refresh-token`, `/checkout/*`), помечаются той же записью явно, одной строкой рядом с объявлением.

Gradle-задача `:server:generateWebContracts` (JavaExec на отдельном source set `contracts`, не попадает в jar):

1. Поднимает приложение в `testApplication` с `Di` без инфраструктуры (`offlineDi()`): пул R2DBC и клиенты MinIO создаются лениво и при регистрации маршрутов не подключаются, внешние сервисы заменены отказывающими заглушками. БД и Testcontainers генератору не нужны.
2. Обходит все маршруты, собирает полный путь по цепочке селекторов и записи `ApiContract`.
3. Проверяет инварианты: у каждого JSON-маршрута под `/api` есть контракт (иначе ошибка с путём маршрута); запросы GET — плоские объекты из примитивов, enum и идентификаторов.
4. Обходит `SerialDescriptor` запросов и ответов с учётом `appSerializersModule` для открытого полиморфизма и генерирует `web/src/api/generated/contracts.ts`.

*Почему не отдельный реестр эндпоинтов в `shared`:* реестр дублировал бы объявления маршрутов, и расхождение реестра с сервером снова ловилось бы только на рантайме. Дерево маршрутов и есть сервер.

*Почему не OpenAPI (плагин Ktor + `openapi-typescript`):* потерялись бы брендированные идентификаторы и точные типы дат. Sealed-иерархии через OpenAPI передаются ненадёжно, а маршруты пришлось бы аннотировать вручную. Своя генерация по дескрипторам — несколько сотен строк Kotlin под полным контролем.

*Почему не Kotlin/JS + `@JsExport` из `shared`:* на выходе получаются классы Kotlin-рантайма, а не простые TS-типы, плюс тяжёлый рантайм в бандле.

### 6. Контракты: что генерируется

Один файл, только объявления, без логики:

- для каждого сериализуемого типа — zod-схема `XxxSchema` и тип `type Xxx = z.output<typeof XxxSchema>`;
- идентификаторы: `z.uuid().brand<"ClientId">()`. Бренд берётся из serial name value class;
- `Instant` → `z.iso.datetime({ offset: true }).brand<"Instant">()`, `LocalDate` → `z.iso.date().brand<"LocalDate">()`, `LocalTime` → `z.iso.time().brand<"LocalTime">()`, `DayOfWeek` → объединение литералов `"MONDAY" | …`;
- `Int` → `z.int()`, `Long` → `z.int()` в диапазоне safe integer (суммы `Money` в минорных единицах туда помещаются), `Double` → `z.number()`;
- enum → `z.enum([...])`; sealed и открытый полиморфизм → `z.discriminatedUnion("type", [...])`, у каждого варианта `type: z.literal(serialName)`;
- nullable → `.nullable()`; коллекции → `z.array(...).readonly()`; `Map<String, T>` → `z.record(z.string(), T).readonly()`;
- объекты — `z.object` (лишние поля отбрасываются по умолчанию — поведение из спеки), выведенные типы `Readonly<...>`;
- таблица правил для своих сериализаторов (`Currency` → enum кодов, `CustomFieldKey` → строка с регулярным выражением и брендом, `ClientNoteText`, `SessionColorKey`, `Validity`). Тип со своим сериализатором вне таблицы — ошибка генерации;
- совпадение простых имён классов из разных пакетов — ошибка генерации. Один из классов переименовывается в Kotlin;
- `endpoints` — объект `as const` вида `{ "tasks/list": { method: "POST", in: "body", request: TaskListRequestSchema, out: "json", response: TaskListResponseSchema }, ... }`. `in` — `none | body | query | multipart`, `out` — `empty | json | file`. `request` и `response` — всегда схемы: пустой вход и выход — `z.undefined()`, `multipart` — `z.instanceof(FormData)`, файл — `z.instanceof(Blob)`. Поэтому типы данных любого эндпоинта выводятся одинаково: `z.output<Endpoints[P]["request"|"response"]>`. Параметры пути (`sessions/{id}/cancel`) сохраняются в ключе, клиент требует их отдельным аргументом.

**Роли запроса и ответа.** В ответах поля с дефолтом всегда присутствуют (решение 8), в запросах они необязательны. Если тип встречается только в запросах, поля с дефолтом генерируются как `.optional()`; если только в ответах — обязательными. Если в обеих ролях, генерируются две схемы: `Xxx` (ответ) и `XxxInput` (запрос). Роль определяется обходом графа типов от эндпоинтов.

Клиент поверх манифеста — рукописный и маленький: `api.call(path, ...args): Promise<ApiResult<ResponseOf<path>>>`. Типы запроса и ответа выводятся из `endpoints`, ответ декодируется `z.safeParse` схемой `endpoints[path].response`. Связать generic-путь с типом результата `z.safeParse` TypeScript не может (схемы раскладываются в объединение), поэтому `call` объявлен публичной generic-сигнатурой над реализацией с `unknown`. Тип результата верен по построению: схема декодирования и выведенный тип берутся из одной записи манифеста. Приведений `as` нет.

*Альтернатива zod:* valibot (меньше бандл) или генерация собственных декодеров. zod 4 выбран за зрелость, встроенные ISO-форматы, бренды и нативную поддержку в TanStack Router/Form. Если бандл станет проблемой, генератор можно переключить на `zod/mini` без изменения клиентского кода.

### 7. Контроль устаревания

`contracts.ts` коммитится. CI-job `contracts` запускает генерацию и `git diff --exit-code web/src/api/generated`. Локально `npm run contracts` вызывает Gradle-задачу. В `npm run check` проверка актуальности не входит (Gradle и Docker внутри образа Node недоступны), она живёт в CI и в чек-листе `CLAUDE.md`.

### 8. `encodeDefaults = true` на сервере

`Json { ignoreUnknownKeys = true; encodeDefaults = true }` в `Application.kt` и `queryParametersJson` без изменений. KMP-клиент декодирует с `ignoreUnknownKeys`, и появление полей со значениями по умолчанию для него безопасно. Серверные тесты, сравнивающие JSON целиком, при необходимости обновляются. `explicitNulls` остаётся `true`: `null` в ответе присутствует явно, это соответствует `T | null` в контракте.

### 9. Библиотеки каркаса

| Задача | Выбор | Почему, против чего |
|---|---|---|
| Маршрутизация | **TanStack Router** (code-based routes) | Полностью типизированные `Link`/`navigate`: несуществующий путь или пропущенный параметр — ошибка компиляции. Параметры и search-параметры валидируются zod-схемами при входе на страницу. React Router 8 даёт такой уровень только в framework mode с кодогенерацией. Сейчас в нём два маршрута, миграция тривиальна |
| Данные | **TanStack Query** | Кэш, повторы, инвалидация после мутаций, `queryOptions` с выводом типов. Ключи запросов строятся фабриками поверх `endpoints`, в ключ входит филиал: смена филиала не показывает чужой кэш |
| Формы | **TanStack Form** + zod | Имена полей типизированы глубоко (`"contacts[0].phone"` проверяется компилятором). Валидация общими zod-схемами. react-hook-form строже по производительности, но слабее по выводу типов путей |
| Таблицы | **TanStack Table** | Типизированные колонки, headless, сортировка и видимость колонок в пользовательских настройках |
| Компоненты | **shadcn/ui** на Radix + Tailwind | Код компонентов в репозитории (под наши правила линтинга), доступность Radix. Компоненты правятся под `exactOptionalPropertyTypes`, если исходник его не выдерживает |
| i18n | свой модуль на ~50 строк | `ru` — источник ключей (`as const`), `en: Messages<typeof ru>` — неполный или лишний ключ ломает компиляцию. Параметры сообщений типизированы (`t("clients.count", { count })`), плюрализация через `Intl.PluralRules`, форматирование через `Intl`. Библиотеки вроде i18next потребовали бы типизирующих обёрток ради того же |
| Даты | тонкий модуль над брендами ISO и `Intl` | Без moment/dayjs. `Temporal` — открытый вопрос |

### 10. Результаты и ошибки без исключений

`ApiResult<T> = { ok: true; value: T } | { ok: false; error: ApiError }`, где `ApiError = business | unauthenticated | unavailable | contract`. Функции загрузки для TanStack Query переводят `ApiResult` в исключение ровно в одном адаптере: Query требует `throw` для состояния ошибки. Интерфейс получает типизированную `ApiError` через `error` запроса и разбирает её исчерпывающим `switch`.

### 11. Сессия

Обёртка над `fetch` в клиенте (решение 6):

- `credentials: "same-origin"`, заголовок `Accept-Language` из выбранной локали;
- на 401 — один общий промис `refresh` на все параллельные запросы (single-flight), затем повтор исходного запроса один раз; `/auth/refresh-token` и `/auth/login` в эту логику не заходят;
- неудачный refresh → `queryClient.clear()` и переход на `/login?redirect=<путь>`. `redirect` при входе валидируется схемой «относительный путь, начинается с одного `/`, без `//` и `\`».

Токены из тела ответов входа не сохраняются, cookie выставляет сервер.

### 12. Сосуществование и адреса

- Базовый путь веб-клиента — константа сборки `BASE_PATH` (`/web` сейчас, `""` после переключения). Маршруты повторяют пути `AppNavUrlEncoder`.
- Реестр перенесённых разделов — `const migratedSections = { clients: true, groups: false, ... } as const`. Навигационный компонент для неперенесённого раздела рендерит обычную `<a href="/<section>">` на KMP-клиент, для перенесённого — типизированную ссылку роутера. Включение раздела — изменение одной строки.
- KMP-клиент не меняется. Ссылки из него на веб-клиент не добавляются: при переключении `/` уходит на веб-клиент целиком.

|---|---|---|

| 1. Профиль и аккаунт | профиль, смена пароля, смена филиала, выход, уведомления | Маленькие экраны, обкатывают формы, мутации и инвалидацию на реальном API |
| 2. Настройки-справочники | залы, дисциплины, источники клиентов, тарифы, филиалы, дополнительные поля, роли | Однотипные CRUD-экраны, на них вырабатываются общие компоненты списков и форм. Справочники нужны как выпадающие списки в следующих фазах |

| 7. Главная, сообщения, остальные настройки | главная с виджетами, переписка, каналы, основные настройки, баланс организации, импорт клиентов, журнал действий | Главная собирает данные нескольких разделов, делается последней |

Каждая фаза — отдельный PR (или несколько) и отдельная выкатка. После фазы раздел включается в реестре.

## Risks / Trade-offs

- **[Библиотека не выдерживает `exactOptionalPropertyTypes` или `skipLibCheck: false`]** → Для кода приложения флаги не ослабляются. Проблемный компонент shadcn правится в репозитории. Проблемная зависимость заменяется, а если замены нет — оборачивается модулем с явными типами, и исключение фиксируется в конфиге ESLint с комментарием (не в коде).
  Случаи, найденные в фазе 0в: объявления `@radix-ui/react-select` не проходят `skipLibCheck: false` с `exactOptionalPropertyTypes` — Radix подключается пакетами `@radix-ui/react-*`, выпадающий список нативный; тип роутера TanStack Router содержит `any` (родитель корневого маршрута), и `type-coverage --strict` засчитывает его каждому идентификатору этого типа — тип роутера не выходит за `src/app/router.tsx`, который вместе с тестом типов маршрутов исключён из `type-coverage` в `package.json` (подробности в `web/README.md`).
  Случай фазы 2: у `FilterFn` TanStack Table значение фильтра — `any`, поэтому фильтрация таблицы не подключается; списки фильтруются до передачи в таблицу, таблица отвечает за выбор строк.
- **[Генератору нужна БД для построения маршрутов]** → Не понадобилась: `Di` строится без подключения (`offlineDi()`). Если в `Di` появится компонент, который подключается при создании, генератор упадёт при старте, а не выдаст неверный результат.
- **[Свой сериализатор с дескриптором-классом не распознаётся]** → Сериализатор с примитивным дескриптором или полиморфный без вариантов без правила роняет генерацию. Сериализатор через суррогат-класс (как `Validity`) неотличим от обычного класса и генерируется по суррогату; такие типы перечислены в таблице правил явно.
- **[Генерация по дескрипторам не видит значения по умолчанию]** → Дескриптор знает только факт наличия дефолта (`isElementOptional`), самого значения не знает. Клиенту оно и не нужно: значение подставляет сервер.
- **[Рантайм-проверка каждого ответа стоит CPU]** → Для списков в сотни строк это единицы миллисекунд. Если где-то станет заметно, профилируем; отказ от проверки — только осознанным исключением в клиенте для конкретного эндпоинта.
- **[`encodeDefaults = true` увеличивает размер ответов]** → Разница в процентах, gzip съедает повторяющиеся ключи.
- **[Паритет растягивается, два клиента живут долго]** → Фазы упорядочены по ценности. Новая функциональность после фазы 0 делается сразу в веб-клиенте, если её раздел перенесён, иначе — в обоих. В `CLAUDE.md` записывается правило: новые экраны в KMP-вебе не создаются.
- **[Строгие правила замедляют агента и разработчика]** → Это осознанная цена. Типовые обходы (декодирование, сужение, исчерпывающие `switch`) выносятся в маленькие утилиты `web/src/lib/` с примерами в `web/README.md`.

## Migration Plan

- Фазы 0–7 выкатываются обычным путём: push в `master` → CI → `frontend`. Откат — предыдущий образ `frontend:sha-…` или выключение раздела в реестре (навигация снова ведёт в KMP-клиент).
- `encodeDefaults` (фаза 0) выкатывается вместе с сервером. Откат — предыдущий образ сервера; веб-клиент с `XxxInput`/обязательными полями при этом получит ошибки контракта, поэтому откатываются оба образа.
- Фаза 8: изменение `nginx/prod.conf.template` и `BASE_PATH` в одной выкатке. Откат — возврат шаблона nginx; wasm-клиент на этом этапе ещё жив.
- Фаза 9 — не раньше, чем фаза 8 проработала в проде без откатов (ориентир — неделя).

## Open Questions

- **`Temporal` или свои хелперы над ISO-строками.** К моменту фазы 4 (расписание) решить по поддержке браузерами: нативный `Temporal`, полифилл или остаёмся на `Intl`. Контракт (бренды ISO-строк) от этого не зависит.
- **Сбор ошибок контракта.** В `.env.prod.example` есть `SENTRY_DSN` (GlitchTip). Подключать ли браузерный SDK в фазе 0 или писать ошибки в консоль до отдельного решения — зависит от лимитов GlitchTip; на требования не влияет.
