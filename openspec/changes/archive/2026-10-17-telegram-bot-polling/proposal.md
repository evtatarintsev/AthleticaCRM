## Why

Каркас переписки готов: интеграции каналов, исходящие доставки с фоновым диспетчером, связки «адрес ↔ клиент», инбокс входящих и ручной разбор. Но Telegram в нём — заглушка: бот ничего не отправляет и не принимает. Вебхук не подходит: Bot API недоступен напрямую с серверов, а публичный вход сервера под Telegram не нужен. Поэтому бот работает через long-poll `getUpdates` и исходящие прокси, и клиенты начинают писать в организацию через Telegram, а сотрудники отвечают им из CRM.

## What Changes

- **Подключение бота.** Администратор в настройках каналов вводит токен бота. Сервер проверяет его вызовом `getMe` и сохраняет имя бота. В настройках канала видна ссылка `https://t.me/<username>`, её можно выложить на сайт и в соцсети (QR-код — позже). Один бот подключается только к одной интеграции во всей системе.
- **Приём через long-poll.** Каждую включённую Telegram-интеграцию опрашивает фоновый поллер. Позиция опроса (offset) хранится в БД, поэтому после рестарта апдейты не теряются и не дублируются. Если инстансов сервера несколько, одного бота в каждый момент опрашивает только один из них.
- **Прокси.** Все запросы к Bot API (`getUpdates`, `sendMessage`, `getMe`) идут через HTTP- или SOCKS5-прокси из списка в `application.conf`. Если прокси недоступен, запрос повторяется через следующий из списка.
- **Привязка чата к клиенту.** На `/start` бот просит поделиться номером телефона кнопкой `request_contact`. Если номер однозначно совпал с телефоном одного клиента организации, чат привязывается к нему автоматически. Если совпадения нет, совпало несколько клиентов или номер не прислан, чат попадает в очередь ручного разбора. Один чат относится к одному клиенту, у клиента может быть несколько чатов.
- **Ручной разбор по чату.** Очередь разбора показывает неразобранные чаты, а не отдельные сообщения. Сотрудник выбирает клиента, и все накопившиеся сообщения чата попадают в его беседу. Следующие сообщения из этого чата доходят до клиента сами.
- **UI разбора в `web/`.** Страница неразобранных чатов: последние сообщения, присланный номер, выбор клиента.
- **Реальная отправка.** Ответ сотрудника из беседы отправляется через `sendMessage`. Временные сбои (сеть, 429, 5xx) повторяются диспетчером. Окончательные отказы (бот заблокирован, чат не найден) переводят доставку в `FAILED` без повторов.
- **Только текст.** Текстовые сообщения клиента попадают в беседу как есть. Вместо нетекстовых (фото, голосовые, стикеры, документы) в беседу пишется заглушка вида «[вложение: фото]».
- **Входящие обрабатываются без сотрудника.** Приём и автопривязка выполняются в системном контексте организации, а не в контексте сотрудника.
- **BREAKING (контракты).** `GET /messaging/triage/list` возвращает чаты вместо отдельных входящих. `POST /messaging/triage/assign` принимает идентификатор чата (интеграция + адрес) вместо идентификатора входящего.

Не входит в изменение: медиа-вложения, QR-код, привязка одного чата к нескольким клиентам (семья), шифрование секретов провайдеров, вебхуки.

## Capabilities

### New Capabilities
- `telegram-bot`: подключение Telegram-бота к организации, приём сообщений через long-poll и прокси, автопривязка чата по номеру телефона, отправка ответов сотрудников.
- `inbound-triage`: очередь неразобранных входящих чатов и ручная привязка чата к клиенту (для всех связанных каналов, Telegram — первый).

## Impact

- **Сервер.** `infra/messaging/telegram` — клиент Bot API на Ktor HTTP client с прокси, поллер, транспорт. Затронуты `domain/channels` (уникальность токена, имя бота в конфиге), `domain/inbound` и `usecases/messaging/Inbound.kt`: системный контекст, разбор по чату. Ещё затронуты `read/messaging/DbInboundTriageView` (группировка по чату) и `Di.kt`/`Application.kt` (запуск поллеров).
- **Shared.** `ChannelConfig.TelegramBot` получает имя бота. Меняются схемы триажа в `api/schemas/messaging`.
- **БД.** Новая миграция: позиция опроса по интеграции и номер телефона, присланный чатом. Уникальность токена бота.
- **Конфиг.** Новая секция `telegram { proxies = [...] }` в `application.conf`. Переменные окружения добавляются в `docker-compose.prod.yaml` и `.env.prod.example`.
- **Web.** Диалог канала Telegram (ссылка на бота), страница разбора входящих, перегенерация `web/src/api/generated/contracts.ts`.
- **Зависимости.** Используются `ktor-client` и OkHttp-движок; OkHttp нужен для SOCKS5, CIO умеет только HTTP-прокси.
