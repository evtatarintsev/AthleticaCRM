## Context

Мотивация — см. `proposal.md`, раздел «Why».

Существенные детали текущего состояния, которые формируют подход:

- `admin-cli/build.gradle.kts` объявляет `implementation(project(":server"))`. Модульной независимости нет; `:admin-cli` — надстройка над `:server`, а не параллельное приложение.
- `AdminDi` — не дубликат серверного `Di`, а самостоятельный минимальный контейнер: `Database` + `OrgBalances` + `OrgSearch`, конфигурируемый тремя переменными окружения (`POSTGRES_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Серверный `Di` требует дополнительно `JWT_SECRET`, `MINIO_*`, `SMTP_*`, `YOOKASSA_*`.
- `Application.module()` при старте запускает Liquibase-миграции и четыре фоновые корутины (`emailDispatcher`, `eventWorker`, `generateSessionsDaily`, `messageDispatcher`). Ни одна из них не нужна админским командам.
- `application.conf` — единственный конфиг-файл проекта; порт берётся из `ktor.deployment.port` с оверрайдом `${?PORT}`. `docker-compose.prod.yaml` запускает сервис `server` без аргументов и без `command:`.
- Clikt в проекте — версия 5.0.3. Проверено содержимое артефактов в Gradle-кэше: `SuspendingCliktCommand`, `SuspendingNoOpCliktCommand`, `NoSuchSubcommand`, `MutuallyExclusiveOptions` присутствуют.

## Goals / Non-Goals

**Goals:**

- Один Gradle-модуль, один fat-jar, один Docker-образ на все режимы запуска.
- Декларативное дерево команд: маршрутизация, парсинг аргументов и валидация обязательности — целиком на библиотеке, без ручных `when`/`if` по наличию опций.
- Ни один режим запуска не платит за зависимости другого: `serve` не поднимает `AdminDi`, админские команды не поднимают серверный `Di` и не запускают фоновые воркеры.
- Имя исполняемого артефакта, имя корневой команды и строка в `--help` совпадают.

**Non-Goals:**

- Изменение поведения самих административных операций (что делает поиск организации, как считается корректировка баланса).
- Изменение способа конфигурирования сервера: `application.conf` + переменные окружения остаются единственным источником правды.
- Изоляция админских команд по правам доступа: `AdminRequestContext` с фиксированным нулевым `adminId` остаётся как есть.
- Вынос миграций из старта приложения в отдельную команду. Дерево команд проектируется так, чтобы это было можно добавить позже, но в этот change не входит.

## Decisions

### 1. Clikt остаётся; меняется способ его использования

**Решение:** не заменять библиотеку.

Clikt — Kotlin-порт питоновского Click, и запрошенная декларативная модель «команда + её аргументы + обработчик, роутинг силами библиотеки» — его штатный `subcommands()`. Отсутствие декларативности сегодня — свойство кода, а не библиотеки: `AdminCli.run()` содержит собственный `when {}` по наличию опций и три ручные проверки (`--credit` и `--debit` одновременно, отсутствие обеих, пустой `--description`), каждая из которых выражается средствами Clikt.

**Альтернативы:** kotlinx-cli (архивирована, беднее по возможностям), собственный диспетчер (ровно та проблема, от которой уходим), picocli (Java-центричная, аннотации, не даёт suspend-команд).

### 2. Дерево команд с сохранением уровня `admin`

```
                        AthleticaCommand
                    SuspendingNoOpCliktCommand
                         name = "athletica"
                                |
              +-----------------+------------------+
              |                                    |
        ServeCommand                          AdminCommand
      EngineMain.main()                  SuspendingNoOpCliktCommand
                                                   |
                        +--------------------------+------------------+
                        |                                             |
                   OrgCommand                              (резерв: migrate,
              SuspendingNoOpCliktCommand                     и прочие технические
                        |                                    команды)
        +---------------+---------------+
        |               |               |
   FindCommand    CreditCommand    DebitCommand
```

**Решение:** уровень `admin` сохраняется, хотя при текущем наборе команд он избыточен (всё, кроме `serve`, и так административное).

Обоснование: узел `admin` — граница, отделяющая «эксплуатационные операции над данными» от «режимов работы приложения». Ожидаемые пополнения (отдельный запуск миграций вместо запуска при старте, прочие технические команды) естественно ложатся под `admin`, а не рядом с `serve`. Убрать уровень позже дороже, чем не вводить его сейчас: это ломает уже задокументированные команды.

**Альтернатива:** плоское `athletica {serve|find|credit|debit}` — короче в наборе, но `serve` и `credit` оказываются на одном уровне, будучи сущностями разного порядка.

`credit` и `debit` — отдельные команды, а не флаги одной. Это снимает необходимость в `mutuallyExclusiveOptions` и делает невозможным состояние «указаны обе суммы» на уровне парсера: `athletica admin org credit <org> <amount>` просто не имеет места, куда положить вторую сумму.

### 3. `serve` вызывает `EngineMain.main(emptyArray())` (вариант A)

**Решение:** подкоманда `serve` не имеет собственных опций и делегирует запуск `EngineMain` с пустыми аргументами.

Переход `main()` на Clikt означает, что собственный парсер `EngineMain` (`-config=`, `-port=`, `-P:key=value`) больше не получает `args` прозрачно. Из трёх вариантов выбран самый узкий:

| Вариант | Суть | Почему не выбран |
|---|---|---|
| **A (выбран)** | `serve` без опций, `EngineMain.main(emptyArray())` | — |
| B | `serve --port/--config`, трансляция в system properties | дублирует конфигурацию в двух местах, создаёт возможность рассинхрона с `application.conf` |
| C | `serve` вызывает `embeddedServer(Netty, ...)` напрямую | `ktor.application.modules` уезжает из `application.conf` в код, изменение крупнее задачи |

Практических потерь нет: конфиг-файл в проекте один, переопределять `-config=` нечем; порт уже переопределяется через `${?PORT}`; `docker-compose.prod.yaml` никаких аргументов серверу не передаёт.

**Компромисс:** пробрасывать сквозные аргументы Ktor в будущем станет неудобно. Если такая потребность возникнет, `serve` можно расширить до варианта B без изменения дерева команд.

### 4. Ленивое построение зависимостей через `Context.obj`

**Решение:** корневая команда регистрирует `AdminDi` через `findOrSetObject { AdminDi.fromEnv() }`; листовые админские команды получают его через `requireObject<AdminDi>()`.

```
  athletica ──► findOrSetObject { AdminDi.fromEnv() }   (ленивая инициализация)
      │                        │
      ├─ serve ────────────────┼──►  obj не запрашивается => AdminDi не создаётся,
      │                        │     БД-коннект не открывается
      │                        │
      └─ admin org find ───────┴──►  requireObject<AdminDi>() => коннект открывается
```

Лень здесь принципиальна, а не косметична: `AdminDi.fromEnv()` падает с `error("Переменная окружения ... не задана")`, если `POSTGRES_*` не выставлены. Энергичная инициализация в корневой команде сделала бы `athletica --help` зависящим от наличия переменных окружения и подключения к БД.

Обратное направление тоже важно: админские команды не строят серверный `Di` и не вызывают `Application.module()`, а значит не запускают миграции и четыре фоновые корутины на каждый вызов `athletica admin org find`.

**Альтернатива:** передавать `AdminDi` конструктором в каждую команду при сборке дерева в `main()`. Это сделало бы инициализацию энергичной со всеми описанными последствиями.

### 5. Suspend-нативное дерево

**Решение:** `SuspendingCliktCommand` / `SuspendingNoOpCliktCommand` вместо `CliktCommand`.

Сегодня `AdminCli.run()` начинается с `runBlocking`, потому что всё ниже (`Database.transaction`, `OrgSearch`) — `suspend`. С suspend-командами `override suspend fun run()` вызывает доменный код напрямую, а единственный `runBlocking` остаётся в `fun main`.

### 6. Артефакт `athletica.jar`

**Решение:** `archiveFileName` для fat-jar сервера — `athletica.jar`; `Dockerfile.server` копирует его под тем же именем.

`AdminCli` уже объявлен как `CliktCommand(name = "athletica")`, то есть `--help` печатает имя, которого не носил ни один артефакт (`server-all.jar`, копируемый в образ как `app.jar`). После переименования локальный и продовый запуск записываются одинаково:

```
java -jar server/build/libs/athletica.jar admin org find <query>
```

### 7. `ENTRYPOINT` / `CMD` вместо единственного `ENTRYPOINT`

**Решение:**

```dockerfile
ENTRYPOINT ["java", "-jar", "athletica.jar"]
CMD ["serve"]
```

Разделение даёт два свойства одновременно: `docker-compose.prod.yaml` продолжает работать без правок (сервис `server` не задаёт `command:`, применяется `CMD`), а админский вызов переопределяет только `CMD`:

```
docker compose exec server java -jar athletica.jar admin org find <query>
```

Это и есть решение исходной проблемы доступности: команда выполняется внутри контейнера, где `postgres:5432` резолвится docker-сетью, а `POSTGRES_*` уже переданы через `environment:`.

### 8. Вывод — человекочитаемый, без машиночитаемого режима

**Решение:** вывод административных команд форматируется для чтения человеком; опция вида `--format=json` не вводится.

Административные команды предназначены для ручных правок администратором — это единственный сценарий их использования на обозримом горизонте. Денежные суммы выводятся через `Money.formatted` (в валюте организации, с разделителями разрядов и символом валюты), а не в минорных единицах; результаты идут в стандартный поток вывода, ошибки — в поток ошибок.

Из этого следует, что вывод не является контрактом для скриптов: его можно менять, не считая это ломающим изменением. Требования зафиксированы в `specs/admin-cli/spec.md` (требование «Человекочитаемый вывод»).

**Альтернатива:** сразу заложить `--format=json`. Отклонена как решение задачи, которой нет: потребителя-программы не существует, а поддержка второго формата удваивает работу по каждой новой команде. Добавить его позже дешево — это опция на листовых командах, не затрагивающая дерево.

## Risks / Trade-offs

- **`:server` получает зависимость от Clikt, попадающую в рантайм веб-сервера** → Clikt — небольшая библиотека без транзитивных зависимостей за пределами Mordant; цена в размере fat-jar пренебрежимо мала по сравнению с ценой двух сборочных конвейеров.
- **Ошибка в дереве команд ломает не только CLI, но и запуск сервера** — теперь это одна точка входа → покрыть тестами разбор аргументов; Clikt даёт `test()`-хелпер, позволяющий проверять команды без запуска процесса.
- **`athletica` без аргументов больше не поднимает сервер** — печатает help → сознательно: `CMD ["serve"]` делает поведение образа прежним, а обратная совместимость по CLI не требуется (проект не в проде).
- **Наличие админских команд в том же образе, что и веб-сервер** → доступ к ним ограничен доступом к хосту и `docker exec`; отдельный артефакт этой границы всё равно не создавал, так как требовал тех же `POSTGRES_*`.
- **Известный долг: конвертация суммы через `Double`.** В `AdminCli.runBalance` сумма разбирается как `Double` и умножается на `10.0.pow(currency.fractionDigits)` с последующим `roundToLong()`, что нарушает правило «деньги только через `Money`» из `CLAUDE.md`. Этот change переносит код как есть, не усугубляя проблему. Корректное решение — `argument().convert { }`, разбирающий десятичную строку в минорные единицы без плавающей точки; сложность в том, что валюта известна только после резолва организации, поэтому разбор двухфазный: сначала «сумма как десятичная строка», затем привязка к `Currency`. → Выносится в отдельный change.

## Migration Plan

Развёртывание одношаговое, специальной миграции не требуется.

1. Слить изменение в `master`; `.github/workflows/docker.yml` соберёт `Dockerfile.server` и задеплоит как обычно.
2. `docker-compose.prod.yaml` правок не требует — сервис `server` подхватит новый образ с `CMD ["serve"]`.
3. Проверка после деплоя: сервер отвечает как прежде; `docker compose exec server java -jar athletica.jar admin org find <query>` возвращает организации.

Откат — возврат к предыдущему тегу образа. Схема БД не затрагивается, данные не мигрируют.
