## Context

Абонементы клиента в карточке приходят одним запросом `memberships/list` (`membershipsQuery` в
`clients/card/clientCardQueries.ts`). Его используют три потребителя:

- `SubscriptionTile` в `ClientCardQuickInfo`: берёт `find(status === "ACTIVE")`;
- `clientAlerts`: вариант `subscriptionEnding` через `membershipEndingSoon`;
- `ClientSubscriptionsSection` / `MembershipRow`: пилюля «Истёк / Заканчивается / Активен».

`MembershipSchema` содержит id, название, занятия (`sessionsTotal`, `sessionsRemaining`; оба `null`
у безлимита), `startDate`, `endDate`, `price` и `status`. Статус сервер считает в маршруте только по
дате окончания (`ACTIVE | EXPIRED`), поэтому не начавшийся абонемент приходит как `ACTIVE`. Бэкенд
в этом изменении не трогаем: доменная модель состояний вынесена в
[#162](https://github.com/evtatarintsev/AthleticaCRM/issues/162).

Образец панели в карточке — `ClientBalanceSheet`: `EditSheet` + `EditSheetBody`, открытие через
локальный `useState` в `ClientDetailPage`, без записи в адрес. `EditSheetForm` не подходит: в его
подвале только «Сохранить» и «Отмена».

`Tile` в `ClientCardQuickInfo` уже умеет быть кликабельным целиком (`onClick`, `actionLabel`,
кнопка с `after:absolute after:inset-0`, стрелка у подписи).

## Goals / Non-Goals

**Goals:**
- Одно место, где фронт решает, в каком состоянии абонемент. Его легко удалить, когда состояние
  будет приходить с сервера.
- Одна панель абонемента, которую открывают и плитка, и строка ленты.

**Non-Goals:**
- Работающие действия «Продлить», «Заморозить», «Закрыть», а также подтверждения к ним.
- Новые поля в панели (тариф, кто выдал, дата выдачи): их нет в `MembershipSchema`.
- Запись открытой панели в адрес страницы.
- Часовой пояс организации: «сегодня» берётся из браузера (`todayLocalDate`), как и сейчас.

## Decisions

### Временная функция `membershipView` — единственный источник состояния

`web/src/clients/membership/membershipView.ts`:

```ts
type MembershipPhase = "upcoming" | "active" | "ending" | "expired";
interface MembershipView {
  readonly phase: MembershipPhase;
  readonly endingByDate: boolean;      // true только при phase === "ending"
  readonly endingBySessions: boolean;  // true только при phase === "ending"
}
function membershipView(m: MembershipSchema, today: LocalDate): MembershipView
```

Правила — из spec («Состояние абонемента для отображения»): `expired` при `endDate < today`
(совпадает с сервером), `upcoming` при `startDate > today`, а дальше пороги `membershipEndingSoon`
(7 дней, ≤ 1 занятия) без изменений. `membershipEndingSoon` удаляется, всё зависящее от него
переходит на `membershipView`. KDoc функции говорит, что она временная, и ссылается на #162: когда
сервер начнёт отдавать состояние, функция и её тесты удаляются, а потребители читают поле схемы.

Рассматривали вариант оставить проверки по местам (плитка сама смотрит `startDate`, лента сама
зовёт `membershipEndingSoon`). Именно так появилось нынешнее расхождение, поэтому вариант отклонён.

Две логических причины, а не одна `reason`, нужны потому, что оба условия могут выполняться сразу:
на плитке тогда выделяются и остаток, и дата.

`today` передаётся параметром. Вызывающие получают его один раз на рендер (`todayLocalDate()` в
`ClientDetailPage`, как для `clientAlerts`), а тесты фиксируют дату.

### Плитка на абонемент, а не одна плитка со строками

`SubscriptionTile` превращается в плитку одного абонемента: `MembershipTile({ membership, view,
onOpen })`. `ClientCardQuickInfo` рендерит:

```
memberships === undefined         -> одна плитка со Skeleton
shown = !expired, по startDate    -> по MembershipTile на каждый
shown пуст                        -> одна некликабельная плитка «Нет действующего»
```

Рассматривали вариант с одной плиткой и строкой на абонемент внутри. Отказались: в ней кнопками
пришлось бы делать строки, а не плитку, и высота всех плиток в ряду росла бы. Плитка на абонемент
повторно использует кликабельный `Tile` как есть. Плиток при двух абонементах становится 7, на xl
одна переносится на вторую строку; случай редкий, это приемлемо.

`Tile` получает необязательный `muted` для не начавшегося абонемента (приглушённый текст). Выделение
причины — `text-amber-700 dark:text-amber-400` на соответствующем фрагменте второй строки, как у
предупреждений шапки.

Вторая строка собирается из двух фрагментов: «Осталось N из M» / «Безлимит» и «до <дата>». Это два
ключа i18n с разделителем ` · ` в разметке, чтобы каждый фрагмент можно было выделить отдельно.
Для не начавшегося — один ключ «с {date}».

### Панель `MembershipSheet`

`web/src/clients/membership/MembershipSheet.tsx`:
`MembershipSheet({ membership: MembershipSchema | null, today, onOpenChange })`. Панель открыта,
когда `membership !== null`. Внутри — `EditSheet size="md"` и `EditSheetBody`: список `<dl>`
(период, занятия с полосой, стоимость), пилюля состояния под заголовком и ряд кнопок действий внизу
тела. Пилюля и полоса — те же, что в `MembershipRow`, поэтому выносятся в общий модуль
`membership/`.

В `ClientDetailPage` хранится `openMembershipId: MembershipId | null`, а не сам объект: панель берёт
абонемент из данных `membershipsQuery` по id и показывает актуальные данные после обновления
списка. Если абонемента с таким id в данных нет, панель закрыта.

`ClientSubscriptionsSection` получает `onOpen(id)` от страницы. `BlockRow` — это `<li>`, поэтому
оборачивать его в `<button>` нельзя. Строка остаётся `<li>`, название внутри становится кнопкой с
доступным именем «Открыть абонемент «{name}»». Зона нажатия растягивается на всю строку
(`relative` у строки, `after:absolute after:inset-0` у кнопки), как в кликабельном `Tile`.

Кнопки действий — обычные `Button variant="outline"` без обработчика с эффектом. Набор кнопок
зависит от `phase` (у `expired` — только «Продлить»). Рассматривали неактивные кнопки и подсказку
«Скоро»; по решению пользователя кнопки выглядят как настоящие.

### Удаление предупреждения `subscriptionEnding`

Из `ClientAlert` удаляется вариант `subscriptionEnding`, из `AlertChip` — его ветка, из словарей —
`clientCard.alert.subscriptionEnding`. `noActiveSubscription` теперь срабатывает, когда нет ни
одного абонемента с `phase !== "expired"`. Будущий абонемент считается действующим, иначе клиент
с заранее купленным продлением получал бы ложное предупреждение.

## Risks / Trade-offs

- [Фронт продолжает вычислять бизнес-состояние, что противоречит целевой архитектуре] → вся логика
  в одной функции со ссылкой на #162, её удаление — механическая замена на поле схемы.
- [«Сегодня» из браузера, а не из часового пояса организации; на стыке суток фронт и сервер могут
  расходиться в `expired`] → поведение не хуже текущего, исправляется в #162.
- [Кнопки-заглушки выглядят рабочими, сотрудник может решить, что действие выполнено] → панель не
  закрывается и данные не меняются, так что эффекта явно нет; работающие действия придут
  следующими изменениями.
- [Предупреждение об окончании пропадает из шапки, а плитка менее заметна] → цвет на плитке и
  пилюля «Заканчивается» в ленте; плитка стоит в шапке рядом с местом прежнего предупреждения.
