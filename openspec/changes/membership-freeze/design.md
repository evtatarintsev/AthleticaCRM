## Context

См. `proposal.md` — мотивация и охват. Сейчас жизненный цикл хранит состояния `INACTIVE`, `ACTIVE`, `CLOSED` и `REVOKED`; активный абонемент содержит `start_date` и `end_date`. Общее SQL-правило `MembershipCandidateSql` используется как фактическим списанием, так и превью списания. История абонемента собирается из событий жизненного цикла. Закрытие по сроку, признаки «заканчивается» / «к закрытию» и уведомления считаются от `end_date`.

## Goals / Non-Goals

**Goals:**
- Представить заморозку активного абонемента как временное ограничение с датами и причиной.
- Сохранять единые правила списания, продления срока и истории в серверной доменной модели.
- Сделать состояние и доступные действия понятными в панели абонемента.

**Non-Goals:**
- Заморозка неактивированных абонементов.
- Заморозка задним числом (дата начала раньше сегодняшней). Для прошедшего периода администратор продлевает абонемент или замораживает его с текущего дня на меньший срок; списанные за период занятия отменяются правкой отметки.
- Ограничения на число заморозок и суммарную длительность.
- Заморозка нескольких абонементов клиента одним действием.
- Автоматическая коррекция срока по поздней отметке за период уже снятой заморозки.

## Decisions

### Сдвигать срок сразу при оформлении заморозки

При оформлении заморозки с `fs` по `fe` (включительно) дата окончания абонемента сразу увеличивается на всю длину периода: `end_date += fe − fs + 1`. Досрочное снятие возвращает неиспользованные дни. Так `end_date` всегда позже `fe`, и правила, которые считаются от `end_date` (закрытие по сроку, «заканчивается», «к закрытию», уведомления, условие подбора `дата занятия в сроке`), работают без особых случаев для заморозки: замороженный абонемент не может закрыться по сроку. Снятие заморозки по окончании периода срок не меняет, поэтому опоздание планировщика или поздняя отметка ничего не ломают.

Альтернатива — продлевать срок при разморозке — отклонена: во время заморозки абонемент закрывался бы по старому сроку, а формулу продления пришлось бы ограничивать для занятий вне периода и опоздавшего планировщика.

Цена решения: во время заморозки панель показывает уже продлённую дату окончания, поэтому сдвиг виден в истории и рядом с датой.

### Хранить только текущую заморозку

Оставить `ACTIVE` как жизненный статус абонемента и добавить одно необязательное поле `freeze: MembershipFreeze?` с обязательными датой начала, датой окончания, причиной и идентификатором оформившего сотрудника. Не представлять заморозку независимыми nullable-полями; слой хранения сохраняет обязательность полей и их связь как одной заморозки, формат хранения выбирается при реализации.

Объект хранит только запланированную или действующую заморозку. Завершённая заморозка удаляется, прошлые заморозки остаются в истории абонемента и аудите — абонемент можно замораживать многократно. Одновременно существует не больше одной заморозки: новая оформляется, только когда объекта нет.

Состояние вычисляется из дат и даты организации «сегодня», не хранится:
- **запланирована** — сегодня < `fs`; абонемент обычный активный;
- **действует** — `fs ≤ сегодня ≤ fe`;
- `fe < сегодня` — заморозки нет; объект удаляет планировщик, до этого чтение и подбор считают его отсутствующим.

### Изменения срока

| Событие | `end_date` | объект |
|---|---|---|
| Оформление `fs..fe` | `+ (fe − fs + 1)` | создаётся |
| Отмена запланированной | `− (fe − fs + 1)` | удаляется |
| Ручная разморозка в день `T` | `− (fe − T + 1)` | удаляется |
| Посещение в день `D ∈ [fs, fe]` | `− (fe − D + 1)`, затем списание | удаляется |
| Посещение вне `[fs, fe]` | без изменений | без изменений |
| Наступил день после `fe` | без изменений | удаляется |

Каждое изменение выполняется в одной транзакции со своей записью в историю и аудит.

### Замороженный абонемент остаётся кандидатом, но последним в ступени

Замороженный абонемент остаётся кандидатом по общему условию `MembershipCandidateSql.condition`. В `MembershipCandidateSql.ORDER` внутри ступени активных абонемент с действующей на дату занятия заморозкой идёт после остальных: если у клиента есть другой подходящий абонемент, посещение спишется с него и не снимет заморозку. Превью и списание используют один порядок.

Несколько абонементов в одну группу — редкая ситуация, поэтому основная защита в интерфейсе: форма заморозки предупреждает о других активных абонементах клиента с пересекающимися группами.

### Отражать заморозку в API и истории

Список абонементов отдаёт необязательный объект заморозки целиком (период, причина, сотрудник) и вычисленное состояние, чтобы клиент не считал его по датам. Серверные операции: заморозка, отмена запланированной, ручная разморозка — с проверкой организации и допустимого состояния. События оформления, отмены, ручной разморозки, разморозки посещением и окончания заморозки попадают в историю абонемента и системный аудит с автором (сотрудник или система), основанием, периодом и изменённой датой окончания.

### Представить действия в панели абонемента

Добавить форму заморозки и действия «Отменить заморозку» / «Разморозить» в существующую панель. Сервер остаётся источником состояния, после операций клиент обновляет список и историю.

### Показать заморозку в карточке занятия

Расширить ответ превью списания данными заморозки выбранного кандидата, если дата занятия попадает в период заморозки. Карточка занятия показывает дату окончания заморозки и причину вместо обычной строки с остатком.

## Risks / Trade-offs

- [Во время заморозки отображается продлённая дата окончания] → Показывать рядом пометку о заморозке и записывать сдвиг в историю.
- [Поздняя отметка за период уже снятой заморозки] → Срок не пересчитывается; посещение списывается по общим правилам, исправление остаётся администратору.
- [Правка «пришёл» → «не пришёл» после разморозки посещением] → Заморозка не восстанавливается и срок не откатывается, как возврат не отменяет активацию.

## Migration Plan

Добавить nullable-данные текущей заморозки с миграцией без изменения существующих абонементов. Развернуть серверное чтение/запись и правила списания совместно с API и клиентом. Откат кода требует, чтобы действующих заморозок не осталось: их сдвиг уже записан в `end_date`, и без объекта заморозки абонемент считается обычным активным.
