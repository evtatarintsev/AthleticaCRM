# Design

## Context

Мотивация и границы изменения — в `proposal.md`. Сейчас `birthdaysRequest` отправляет только диапазон и лимит, поэтому `ClientListRequest` и `ClientListQuery` выбирают имя по умолчанию. `DbClientListView` применяет `ORDER BY` перед `LIMIT`, но принимает одну колонку; `BIRTHDAY` означает полную `c.birthday` и проверяется существующим тестом.

Периоды виджета хранятся в `BirthdayWindow`. Его `WEEK` означает `[today, today + 7]`, тогда как самостоятельный фильтр клиентов `week` — `[today, today + 6]`. Ссылка виджета сейчас использует именно этот более короткий фильтр. `TOMORROW` и `tomorrow` сейчас означают только завтра. Главная уже получает единую локальную дату браузера и обновляет её при смене дня.

Состояние таблицы клиентов и адрес `/clients` поддерживают одну колонку и направление. Общая `SortStateSchema` используется также другими разделами и сохранёнными видами; расширять её для нужд одного виджета не требуется. TypeScript-контракты генерируются из Kotlin.

## Goals / Non-Goals

**Goals:** выразить порядок виджета через составную сортировку API клиентов; сохранить существующие запросы и полную дату рождения как отдельный критерий; согласовать карточку и полный список без сортировки загруженного среза в браузере.

**Non-Goals:** общий движок сортировок для всех разделов, пользовательский конструктор нескольких колонок, миграция сохранённых видов, новые индексы без измеренной необходимости, изменение политики 29 февраля и возраста в карточке.

## Decisions

### 1. Добавить массив критериев только в API клиентов

В `ClientListRequest` добавить `sort: List<ClientSort>? = null`; элемент содержит `field: ClientSortField` и `direction: SortDirectionSchema = Asc`. Старые `sortField` и `sortDirection` остаются. Непустой `sort` имеет приоритет, отсутствие/null/пустой массив нормализуются в один старый критерий. Повтор одного поля в новом массиве отклоняется как 400; при четырёх разрешённых полях это также ограничивает длину корректного массива четырьмя.

На границе API нормализовать порядок один раз. В read-проекции хранить список критериев вместо пары колонка/флаг; найти и адаптировать все вызовы `ClientListQuery`, включая тесты. Экспорт продолжает использовать прежний порядок по умолчанию. Не создавать второй параллельный способ сортировки внутри проекции.

Альтернативы: заменить старые поля сразу — ломает запросы существующих клиентов; расширить общую `SortStateSchema` — затрагивает сохранённые настройки и разделы вне задачи; жёстко дописать имя после дня рождения — решает только одну комбинацию и не даёт запрошенной сортировки по нескольким полям.

### 2. NEXT_BIRTHDAY — отдельный вычисляемый критерий

Добавить `NEXT_BIRTHDAY` в API enum и соответствие в read-проекции. Опорная дата — `birthday.from`; если эффективный порядок использует этот критерий без диапазона, вернуть обычную ошибку валидации 400 по принятому в сервере механизму. Отдельное поле `today` и часы сервера не нужны: оба потребителя уже передают диапазон от даты браузера.

Для упорядочивания использовать существующее представление `MMDD`. Вычисляемый ключ состоит из двух частей: сначала даты с `MMDD >= birthdayFromMd`, затем остальные; внутри частей — `MMDD`. Направление критерия применяется к обеим частям. Это циклический календарный порядок, а не расстояние в днях; конструировать дату из года рождения не требуется. Null остаётся в конце и при `Desc`. Следующий критерий `NAME` применяется ко всей группе одинаковых месяца и дня, независимо от года рождения. Последний ключ всегда `c.id ASC`.

SQL-выражения и направления выбираются только из закрытых enum, параметры фильтров остаются привязанными. Составной `ORDER BY` применяется до `LIMIT/OFFSET`; подсчёт совпадений и область доступа организации не меняются.

Альтернативы: `BIRTHDAY, NAME` сохраняет влияние года рождения; обычный `MMDD, NAME` ломает декабрь–январь; сортировка в React теряет клиентов за серверным лимитом. Перенос 29 февраля на 1 марта изменил бы существующий отбор; здесь сохраняется точное совпадение месяца и дня.

### 3. Сохранить настройки виджета, изменить диапазон TOMORROW

Оставить значения `TODAY`, `TOMORROW`, `WEEK`. Меняется только диапазон `TOMORROW` на `[today, today + 1]` и его описание в shared. Сохранённые название, лимит, положение и видимость не переписываются. Селект получает подписи «Сегодня», «Сегодня и завтра», «На неделю вперёд» / “Today”, “Today and tomorrow”, “A week ahead”. Недельный диапазон остаётся `[today, today + 7]`, то есть восемь календарных дат с учётом сегодняшней.

`birthdaysRequest` всегда передаёт `sort = [NEXT_BIRTHDAY Asc, NAME Asc]`. Дату и прибавление дней вычислять общим существующим средством `web/src/lib/localDate.ts`, а не добавлять ещё одну реализацию. По возможности сделать общий источник границ для виджета и его перехода в список.

### 4. Ссылка хранит режим, таблица сохраняет обычное управление

В `clientListSearch.ts` добавить фильтры `todayTomorrow` и `weekAhead` с диапазонами `[today, today + 1]` и `[today, today + 7]`. Старые `tomorrow` и `week` не переопределять: это сохраняет смысл существующих самостоятельных ссылок и фильтров.

Добавить значение `sort=nextBirthday` в адресное состояние списка. В этом режиме `clientListRequest` отправляет фиксированную пару `NEXT_BIRTHDAY Asc, NAME Asc`; направление нормализуется к `asc`. «Показать всех» передаёт этот режим и соответствующий фильтр (`today`, `todayTomorrow`, `weekAhead`). Не сериализовать произвольный массив сортировки в адрес: пользовательского конструктора в этой задаче нет.

`ClientsPage` показывает локализованную метку выбранного периода. Панель фильтров корректно отображает новый активный режим, позволяет заменить/сбросить его, не расширяя задачу до переработки всей панели. Если фильтр дней рождения снят при `sort=nextBirthday`, сбросить порядок к `name asc`, чтобы не отправлять недопустимый запрос. Неверная комбинация этих search-параметров нормализуется аналогично.

Клик по обычному заголовку колонки заменяет `nextBirthday` на одиночную сортировку. Вычисляемый режим не выдаётся за сортировку по полной дате рождения и не помечает неверную колонку активной; заголовки сохраняют доступные подписи и фокус. Тип состояния страницы при необходимости отделить от типа реальных сортируемых колонок таблицы.

### 5. Проверить поведение на границах

Тесты API проверяют нормализацию нового/старого формата, приоритет массива и ошибки. PostgreSQL-тесты в `DbClientListViewTest` проверяют смешанные направления, null, имя при одинаковых месяце/дне, декабрь–январь, ограниченную первую страницу и стабильный порядок равных записей. Существующий тест полной даты рождения остаётся.

Во фронтенде проверить запросы и диапазоны чистыми тестами, а переход в полный список, метку, перезагрузку и обычный клик сортировки — через существующий тестовый app-server. Неправильно отсортированный ответ не пересортировывать компонентным тестом: это обязанность серверного теста. Проверить смену даты, годовую границу, сохранённый `TOMORROW` и подписи ru/en.

## Risks / Trade-offs

- [Сохранённый TOMORROW расширяет выборку] → это намеренное изменение смысла виджета; новая подпись объясняет его без потери конфигурации.
- [Два формата сортировки в API] → один явный приоритет и одна нормализация; удаление старых полей не входит в изменение.
- [Вычисляемая сортировка может потребовать сортировать много совпадений] → фильтровать до сортировки; не добавлять индекс без измеренной проблемы.
- [Неверная дата браузера] → сохраняется существующий источник времени; сервер использует переданный диапазон и не вводит второе понятие «сегодня».
- [Старый сервер игнорирует новое поле sort] → выкладывать совместимый сервер раньше веб-клиента; не обещать новый порядок при смешанных версиях.
- [29 февраля отличается от уведомления в карточке клиента, которое переносит дату на 1 марта] → здесь сохраняется текущий отбор виджета; объединение политик вынесено за рамки.

## Migration Plan

Миграций БД и пользовательских настроек нет. Сначала выложить сервер, принимающий оба формата, затем веб-клиент с перегенерированными контрактами. Старый веб-клиент работает с новым сервером. Для отката сначала вернуть веб-клиент на прежний запрос, затем сервер; новые search-значения старый клиент сбросит по существующим правилам разбора.
