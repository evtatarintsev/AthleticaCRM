## Context

Зачем это нужно — в proposal.md, требования — в `specs/telegram-gateway/spec.md`.

На что опираемся:

- **Gateway API** (`https://gatewayapi.telegram.org/<method>`):
  - авторизация заголовком `Authorization: Bearer <token>`;
  - ответ — `{ok, result | error}`, где `result` — `RequestStatus` с полями `request_id`,
    `request_cost`, `remaining_balance`; `remaining_balance` приходит только в ответах со
    списанием;
  - `checkSendAbility` оплачивается, только если сообщение можно отправить;
    `sendVerificationMessage` с `request_id` из проверки уже не оплачивается;
  - недоставленное за `ttl` сообщение возвращается на баланс автоматически;
  - `code` — 4–8 цифр, `ttl` — 30–3600 секунд;
  - из строк ошибок документирована только `ACCESS_TOKEN_INVALID`.
- **Telegram Bot API** (`infra/messaging/telegram/`): прокси `telegram.proxies` из
  `application.conf` и `createTelegramHttpClients`, потому что из российских сетей Telegram
  доступен не всегда. Gateway — другой сервис, общий с Bot API у него только прокси.
- **Каналы организации** (`domain/channels`): секреты хранятся в БД организации и отдаются
  только маской, `ChannelConfigVerifier` проверяет настройки у провайдера до открытия
  транзакции, изменения пишутся в аудит (`AuditChannelIntegrations`).
- **`SystemContexts.forOrg`**: строит контекст организации для кода вне HTTP-запроса сотрудника.

## Goals / Non-Goals

**Goals:**
- Сервис отправки кода, которым будущие сценарии (вход в приложения, 2FA) пользуются, не зная
  ничего про Gateway, кроме исходов.
- Проверка токена при сохранении бесплатна.

**Non-Goals:**
- Выбор канала доставки и переход на SMS — это забота вызывающего, он получает исход
  «на номер доставить нельзя».
- Хранение кода и проверка введённого кода: код генерирует и проверяет вызывающий.
- Платформенный аккаунт Gateway и учёт расходов на балансе организации в Athletica.

## Decisions

### 1. Отдельный домен, а не вид канала

Пакет `domain/telegramgateway`: агрегат настроек организации и сервис отправки кода.
`ChannelConfig` не подходит. Канал — это переписка: входящие, привязки, `MessageDispatcher`,
доставки. У Gateway ничего этого нет, это разовая отправка кода с синхронным ответом.

- *Альтернатива — `ChannelConfig.TelegramGateway`:* в список каналов и «Входящие» попал бы
  канал, через который нельзя написать клиенту, а диспетчер пришлось бы учить его пропускать.

### 2. Хранение: строка на организацию

```
telegram_gateway_integrations
  org_id        PK, FK organizations
  token         text
  enabled       boolean
  balance       numeric(12,2) NULL   -- остаток по последнему ответу со списанием
  balance_at    timestamptz NULL
```

Один аккаунт на организацию, поэтому ключ — `org_id`. Токен хранится так же, как секреты
каналов: открытым текстом в БД, а наружу отдаётся маской. Остаток — `Money` в `Currency.USD`.
Это баланс у внешнего поставщика в его валюте, а не деньги организации в её валюте, поэтому
ни с чем в главной книге он не складывается.

### 3. Бесплатная проверка токена

`checkSendAbility` с заведомо недопустимым номером: сообщение отправить нельзя, поэтому
проверка не оплачивается.

- Ответ `ACCESS_TOKEN_INVALID` → `TELEGRAM_GATEWAY_TOKEN_INVALID`.
- Любая другая ошибка Gateway → токен действителен.
- Сбой сети → обычная ошибка «Gateway недоступен», настройки не сохраняются.

Проверка идёт до транзакции, как у `ChannelConfigVerifier`. Предположение о поведении Gateway
сверяется на тестовом токене (задача 1.3).

- *Альтернатива — проверка на номер владельца аккаунта (это бесплатно):* номер владельца нам
  неизвестен, просить его у администратора ради проверки — лишний шаг.

### 4. Отправка: `checkSendAbility`, затем `sendVerificationMessage` с тем же `request_id`

```
send(phone, code, ttl)   context(ctx: RequestContext)
  |
  +-- tr: настройки организации ctx.orgId --- нет / выключено --> NotConfigured
  |
  +-- checkSendAbility(phone) --- ok:false, кроме ACCESS_TOKEN_INVALID --> Undeliverable
  |                           --- ACCESS_TOKEN_INVALID / сеть / таймаут --> Failed(reason)
  |
  +-- sendVerificationMessage(phone, request_id, code, ttl)
  |                           --- ok:false / сеть / таймаут --> Failed(reason)
  |
  +-- tr: сохранить remaining_balance и balance_at, если пришли ----------> Sent(requestId)
```

- Организация берётся из `RequestContext`. Вызывающий вне запроса сотрудника строит контекст
  через `SystemContexts.forOrg`. Явного параметра `orgId` нет, чтобы нельзя было отправить
  код с токеном чужой организации, передав не тот id.
- HTTP-вызовы идут вне транзакции: чтение настроек и запись остатка — две короткие транзакции,
  соединение БД не держится, пока ждём Telegram.
- Код — value class `GatewayCode` (4–8 цифр), срок — `GatewayCodeTtl` (30–3600 с), оба со
  smart constructor. Граница проверяется при создании, до обращения к Telegram.
- Номер передаётся как `PhoneDigits` и превращается в E.164 (`+` и цифры) в клиенте API.
- Таймаут запроса — 5 секунд: вызывающий ждёт синхронно, человек смотрит на экран.
- Исходы — `sealed interface GatewayCodeResult`. «Не настроено» и «недоставляемо» — тоже
  исходы, а не ошибки `Raise`: вызывающий почти всегда разбирает их по-своему (например,
  уходит в SMS).

### 5. HTTP-клиент — `infra/telegram/gateway/TelegramGatewayApi`

Ktor-клиенты из `createTelegramHttpClients(telegramProxies())`, с тем же перебором прокси,
что у `TelegramBotApi`. Токен передаётся в каждый вызов, а не в конструктор: один клиент
обслуживает все организации.

### 6. Тестовый код

Маршрут настроек генерирует случайный 6-значный код, вызывает тот же `send` со сроком 300 с
и отвечает исходом. Код в ответе не возвращается: администратор видит его только в Telegram.
Так тест проверяет то же, что увидит человек.

### 7. Журналы и аудит

- В журнал пишутся организация, метод, причина и последние 4 цифры номера. Код и токен не
  пишутся никогда.
- Ktor-логирование запросов для клиента Gateway не включается: заголовок `Authorization`
  и тело с `code` в журнал не попадают.
- В аудит пишутся подключение, замена токена и включённость — без токена.

### 8. Web

Пункт «Telegram Gateway» в настройках (`web/src/settings/`) и в поиске по настройкам.
На странице:
- форма токена: маска и «Изменить»;
- переключатель включённости;
- остаток баланса со временем;
- форма «Отправить тестовый код» с номером.

Строки — в `ru.ts` и `en.ts`.

## Risks / Trade-offs

- [Gateway отвечает на недопустимый номер так же, как на неверный токен, или списывает
  деньги] → задача 1.3 проверяет это на тестовом токене. Если предположение не подтвердится,
  проверку при сохранении заменяет тестовый код, а спецификация меняется до реализации.
- [Строки ошибок Gateway не документированы, и «закончился баланс» на `checkSendAbility`
  выглядит как «недоставляемо»] → вызывающий в обоих случаях уходит в другой канал. Настоящие
  строки ошибок записываются в задаче 1.3, чтобы при необходимости разделить исходы.
- [Gateway недоступен из сети сервера] → прокси `telegram.proxies`, исход `Failed`.
- [Остаток баланса устаревает, если организация отправляет коды и с другого сервиса] →
  показывается время последнего ответа.
- [Токен в БД открытым текстом] → на том же уровне, что секреты каналов. Шифрование секретов
  организации — общая задача, не этого изменения.

## Migration Plan

Миграция только добавляет таблицу. У существующих организаций интеграции нет, никто не
вызывает отправку. Откат — снять маршруты и страницу, таблица не мешает.
