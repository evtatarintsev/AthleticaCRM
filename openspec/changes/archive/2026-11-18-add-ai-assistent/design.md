## Context

Мотивация и область описаны в `proposal.md`. Сервер — Kotlin/Ktor с Arrow, kotlinx.serialization, R2DBC/PostgreSQL; маршруты получают `EmployeeRequestContext` и вызывают доменные модели в `Database.transaction`. Транзакция занимает соединение с БД, поэтому вызовы AI внутри неё недопустимы.

Клиент создаётся маршрутом `POST /clients/create`: `Clients.new` с идентификатором `ClientId`, сгенерированным вызывающей стороной, и `ClientContacts.replace`. `Gender` обязателен и имеет только `MALE`/`FEMALE`. Обязательные дополнительные поля описывает `CustomFieldDefinition.isRequired`. `AuditClients.new` сейчас не пишет событие CREATE, хотя `AuditGroups`, `AuditEmployees` и `AuditEnrollments` пишут. `OrgCalendar.today()` даёт дату в часовом поясе организации.

Фронтенд — React, TanStack Router/Query, генерируемые JSON-контракты и UI-примитивы проекта. `AppLayout` живёт между переходами. `EditSheet` — панель с оверлеем: справа на широком экране, на весь экран на телефоне; её тело размонтируется при закрытии.

`nginx/prod.conf.template` проксирует `/api/` без `proxy_read_timeout`, то есть с таймаутом по умолчанию 60 секунд.

## Goals / Non-Goals

**Goals:**
- Один проверяемый вертикальный сценарий: клиент с контактами создаётся из свободной фразы в чате после явного подтверждения сотрудника.
- Зависимость в одном направлении: `assistant` использует доменные модели, домен ничего не знает об AI.
- Авторизация, квота и подтверждение записи контролируются сервером независимо от ответа LLM.

**Non-Goals:**
- Поиск клиентов/групп, расписание, аналитика, контекст текущей страницы, список прежних диалогов, быстрые команды — следующие change.
- Отдельный Gradle-модуль, универсальная платформа агентов, собственный LLM framework.
- Потоковая выдача, WebSocket, фоновые AI-задания, RAG, MCP.
- Зачисление в группу, абонементы, оплата, аватар и источник клиента через чат.
- Биллинг по токенам: квота сообщений — ограничитель использования, а не финансовый учёт.

## Decisions

### 1. `assistant` — прикладной пакет, а не домен

```text
server/.../crm/assistant/
  AssistantRoutes.kt         HTTP + существующий request context
  ...                        ход диалога, конфигурация, квота
  tools/                     prepare_client, save_client
  storage/                   диалоги, сообщения, черновики, настройки, квота
  provider/                  Koog и обмен с моделью

shared/.../api/schemas/assistant/
web/src/assistant/
```

Везде используется написание `assistant`; в UI — «AI-помощник» / «AI assistant». Идентификатор capability `ai-assistent` в OpenSpec не переименовывается.

Модуль зависит от доменных интерфейсов, `core`/`storage` и контрактных DTO. Он не импортирует HTTP-маршруты и `ReadViews`, не ходит в собственный сервер по HTTP и не пишет в доменные таблицы напрямую. Его SQL меняет только таблицы помощника. Точки подключения вне пакета — `Di.kt`/`Application.kt`, каталог прав, shared API, миграции, конфигурация, локализация, генерация контрактов, `AppLayout` и настройки.

Альтернатива — разнести tools по общим `routes/read/usecases` — смешивает AI-интеграцию с доменом и усложняет её удаление.

### 2. Koog и одно общее подключение

Koog отвечает за формат обмена с провайдером, описание tools и ограниченный цикл. Его типы не выходят за пределы `assistant`. Цикл явно исполняет только зарегистрированные tools.

Оператор задаёт одно подключение: `provider`, `model`, `apiKey`. Поддерживаемые `provider` — `openai`, `anthropic`, `openrouter` через готовые клиенты Koog; используется ровно одно. Без подключения сервер работает, модуль сообщает `available=false`; неполная конфигурация диагностируется без вывода секретов. Новые ключи `application.conf` добавляются в `docker-compose.prod.yaml` и `.env.prod.example` тем же коммитом.

Перед подключением проверяем стабильную версию Koog на текущих Kotlin/Ktor и tool calling. Адаптер подменяется fake в тестах; реальные ключи в CI не нужны.

Альтернатива — ручной HTTP через Ktor Client — потребует самостоятельно поддерживать протоколы tools трёх провайдеров.

### 3. Права, настройки и квота

`CAN_USE_ASSISTANT` добавляется в каталог прав с RU/EN-подписями. Владелец проходит проверку существующим правилом, остальным право выдаётся ролью или персонально. Настройки помощника меняет только владелец.

`assistant_settings`: `org_id`, `enabled`, `daily_message_limit`; отсутствие строки означает `enabled=false`, лимит формы по умолчанию — 100. `assistant_usage`: `(org_id, local_date)`, `accepted_messages`; дата — из `OrgCalendar`. В одной короткой транзакции с блокировкой строки настроек проверяем включение и остаток, резервируем единицу и сохраняем входное сообщение. Принятый запрос при ошибке провайдера квоту не возвращает.

Перед отправкой проверяются активность сотрудника, право и включение. Подтверждение кнопкой — обычный HTTP-запрос со свежим контекстом. Перед `save_client` внутри хода сотрудник перечитывается в короткой транзакции, потому что `EmployeeRequestContext.employee` — снимок начала долгого запроса.

Технические пределы — константы: 4 000 символов входа, до 6 обращений к модели и 6 вызовов tools за ход, 45 секунд на ход, ограниченный output и история из последних целых обменов. 45 секунд меньше таймаута прокси; для `/api/assistant/` таймаут nginx поднимается до 90 секунд с запасом.

### 4. Диалог и ход

| Таблица | Назначение |
| --- | --- |
| `assistant_dialogs` | `id`, `org_id`, `employee_id`, даты |
| `assistant_messages` | диалог, порядок, роль, текст, статус хода и дедлайн, структурированные блоки ответа |
| `assistant_client_drafts` | `client_id` (PK, будущий ID клиента), диалог, сообщение-карточка, payload, статус `pending/executed/superseded` |
| `assistant_settings` | включение и лимит организации |
| `assistant_usage` | суточный счётчик организации |

Диалог принадлежит организации и сотруднику; филиал не учитывается, потому что клиенты общие для организации. Все обращения к сообщениям и черновикам проверяют владельца через диалог. Сотрудник видит текущий (последний) диалог и может начать новый; списка прежних диалогов в первой версии нет.

Ход: `processing -> completed | failed`. Короткая блокировка строки диалога гарантирует не больше одного `processing`; новое сообщение во время обработки получает `busy` без расхода квоты. Сеть ходит без открытой транзакции. Ответ записывается, только пока ход `processing` и дедлайн не истёк. Просроченный ход переводится в `failed` при следующем чтении или отправке — отдельный воркер не нужен.

`messages/send` ждёт завершения хода и возвращает его. При потере ответа фронтенд перечитывает сообщения диалога; автоматического повторного вызова модели нет. Повторная отправка не дедуплицируется по request ID: фронтенд блокирует двойную отправку, сервер — параллельный ход, а дубль клиента исключён тем, что сохраняется черновик с заранее выданным `client_id`.

Альтернатива — история только в памяти — теряет карточки после рестарта, и карточку нельзя подтвердить.

### 5. Подготовка клиента и подтверждение

Модель получает два tools:

| Tool | Вход | Результат |
| --- | --- | --- |
| `prepare_client` | имя, контакты (тип+значение), дата рождения, пол, значения дополнительных полей по ключу | новый черновик и карточка либо список недостающих/неверных полей с подписями |
| `save_client` | `client_id` черновика | квитанция с `client_id` либо отказ |

`prepare_client` разбирает значения существующими value objects и проверками, загружает определения дополнительных полей через домен и требует все обязательные. Пол модель может предположить по имени; все значения, в том числе предположенные и значения по умолчанию, видны в карточке. Неполный набор возвращается модели как уточнение, черновик не создаётся. Полный набор создаёт черновик `pending` с новым `client_id` и помечает прежний `pending`-черновик диалога как `superseded`. Карточка — структурированный блок ответа, собранный сервером из черновика, а не текст модели.

Исправление — обычное сообщение («телефон 8909…»): модель вызывает `prepare_client` с исправленными данными, сервер показывает новую карточку, старая становится неисполняемой. Формы редактирования и версий черновика нет.

Подтверждение двумя путями, оба вызывают одну серверную функцию сохранения:
- **Кнопка «ОК»** — `POST assistant/drafts/confirm` с `client_id`, без вызова модели и без расхода квоты.
- **Ответ текстом** («да») — модель вызывает `save_client`. Сервер исполняет его, только если черновик — последний `pending` в этом диалоге и его карточка показана сотруднику в уже завершённом ходе, предшествующем текущему сообщению. Черновик, созданный в этом же ходе, сохранить нельзя: модель не может подготовить и сохранить клиента за один ход, даже если сотрудник попросил «без подтверждения».

Функция сохранения в одной короткой транзакции: блокирует черновик; если он `executed` — возвращает прежнюю квитанцию; если `superseded` или чужой — отказ; иначе повторяет доменную валидацию, вызывает `Clients.new` с `client_id` черновика и `ClientContacts.replace`, переводит черновик в `executed`. Ошибка откатывает всё, черновик остаётся `pending`. Аудит — тот же, что при создании из формы: `AuditClients.new` начинает писать CREATE, это одна строка в доменном декораторе, которая чинит оба пути.

Компромисс текстового пути: решение «это подтверждение» принимает модель. Риск ограничен тем, что сохранить можно только данные, которые сотрудник уже видел в карточке, и только в следующем ходе. Если сотрудник написал исправление, а модель всё же вызвала `save_client`, сохранятся показанные данные, а не исправленные. Кнопка «ОК» — детерминированный путь.

Альтернатива из прошлой редакции — версионированный черновик, редактирование формой, отдельные `actions/update|cancel` — сложнее и не нужна при исправлении через чат.

### 6. API и доверие к результату

Маршруты определяются внутри `assistant`, регистрируются в аутентифицированной ветке через `RouteWithContext`. Endpoints относительно `/api`:

- `GET assistant/status`: доступность подключения, включение и право — для кнопки.
- `GET assistant/settings`, `POST assistant/settings/update`: настройки и использование за сегодня, только владелец.
- `GET assistant/dialogs/current`, `POST assistant/dialogs/create`: текущий диалог с сообщениями, карточками и их статусами; новый диалог.
- `POST assistant/messages/send`: dialog ID и текст; в ответе ход и структурированные блоки.
- `POST assistant/drafts/confirm`: `client_id` черновика; в ответе квитанция.

DTO — явные варианты блоков с discriminator, поддерживаемые генератором контрактов. Ошибки — `DomainError` с различимыми кодами: unavailable/disabled, forbidden, limit, busy, draft superseded, validation, provider failure.

Карточки и квитанции собирает сервер; модель пишет только поясняющий текст. Успех создания показывается только по квитанции. Тексты модели и данные CRM не считаются командами. Тексты переписки, контакты, ключи и полные payload не пишутся в логи по умолчанию; диагностика — ID хода, операция, время, статус, счётчики.

### 7. Frontend

`web/src/assistant/` владеет состоянием панели, диалога и ввода, запросами и отображением карточек. `AppLayout` подключает хост и кнопку рядом с `NotificationBell`. Чат открывается в существующем `EditSheet`; состояние (диалог, неотправленный текст) живёт в хосте над размонтируемым телом, поэтому переживает закрытие панели и навигацию. Общий чат клиентов и его transport не переиспользуются.

Ключи TanStack Query включают сотрудника; хост сбрасывается при выходе или смене организации. Ответы модели выводятся обычным React-текстом без Markdown/HTML-парсера; ссылка на созданного клиента строится из `client_id` штатным роутером. После квитанции инвалидируются списки клиентов.

Альтернатива — немодальная колонка рядом со страницей — имела смысл с контекстом страницы, который из первой версии убран.

## Risks / Trade-offs

- [Общий аккаунт создаёт общие расходы] -> суточная квота организации, пределы шагов/размеров/времени, нет автоматического повтора вызова модели.
- [Модель приняла исправление за подтверждение] -> сохраняются только показанные данные и только в следующем ходе; есть детерминированная кнопка «ОК»; клиента можно отредактировать обычной формой.
- [Модель ошибочно предположила пол] -> пол виден в карточке до сохранения.
- [Персональные данные уходят внешнему провайдеру] -> передаются только данные создаваемого клиента и короткая история; владелец включает помощника явно; условия обработки — ответственность оператора подключения.
- [История хранит персональные данные бессрочно] -> доступ только своему сотруднику; срок хранения и удаление диалогов — отдельный change.
- [Koog может конфликтовать с текущими Kotlin/Ktor] -> проверка совместимости первой задачей, фиксированная версия.
- [Без streaming ответ появляется целиком] -> видимое состояние обработки, ход ограничен 45 секундами.

## Migration Plan

1. Проверить Koog на текущем стеке, добавить зависимость и конфигурацию без обязательного ключа.
2. Применить добавочные миграции таблиц помощника. Настройки выключены по умолчанию.
3. Подключить backend, право и таймаут nginx, сгенерировать контракты, выпустить UI. Без доступности кнопка скрыта.
4. Настроить подключение в окружении, проверить на отдельной организации цикл «фраза → карточка → исправление → ОК/да»; владелец включает помощника и выдаёт право.
5. Откат: выключить помощника или убрать подключение и развернуть прежний код. Таблицы помощника можно оставить; созданные клиенты остаются обычными доменными записями.
