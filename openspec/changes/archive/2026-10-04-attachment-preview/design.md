## Context

Мотивация — в proposal.md, требования — в `specs/attachment-preview/spec.md`. На что опирается решение:

- `TaskSheet.tsx` и `TaskCreateSheet.tsx` получают вложения сразу как `UploadResponse` (`id`, `url`, `originalName`, `contentType`, `sizeBytes`). В карточке — из `tasks/detail`, ссылки подписаны на 7 дней (`ATTACHMENT_URL_TTL` в `TaskRoutes.kt`). В панели создания — из ответа `POST /upload`, подпись на 1 час (значение по умолчанию в `MinioService.presignedGetUrl`).
- `ClientDocumentsSection.tsx` получает `ClientDoc` (`id`, `uploadId`, `name`, `createdAt`) без ссылки и типа. Каждая строка `DocRow` отдельно запрашивает `uploadInfoQuery` (`upload/info`, подпись на 7 дней, `staleTime` 1 час).
- Удаление: в задачах — кнопка ✕, срабатывает сразу; в документах клиента — корзина и `ConfirmDialog`.
- Файлы отдаёт S3-совместимое хранилище (RustFS) по `MINIO_PUBLIC_ENDPOINT` — это другой origin, CORS не настроен. Поэтому `<a download>` и `fetch` к файлам не подходят, а `<img>`, `<video>`, `<audio>` и `<iframe>` работают.
- `contentType` приходит от браузера при загрузке и сервером не проверяется.
- `components/ui/dialog.tsx` — Radix Dialog. `EditSheet` тоже построен на Radix Dialog, поэтому Esc и клик снаружи обрабатывает только верхний слой.
- Тесты — vitest + Testing Library в jsdom: изображения там не загружаются, `load`/`error` вызываются вручную.

## Goals / Non-Goals

**Goals:**
- Один компонент в `ui/`, не знающий о задачах и клиентах: список, просмотрщик, удаление через колбэк.
- Тип показа определяется одной чистой функцией с юнит-тестами.
- Ни одна внешняя ссылка не встраивается так, чтобы её содержимое могло выполняться.

**Non-Goals:**
- Зум, поворот и жесты (pinch, свайп) в просмотрщике изображений.
- Синхронизация открытого вложения с адресом страницы: просмотрщик — локальное состояние.
- Обновление подписанных ссылок из компонента.

## Decisions

### 1. Модули и граница компонента

```
web/src/ui/attachments/
  attachmentKind.ts      previewKind(contentType) -> "image" | "pdf" | "video" | "audio" | "file"
                         + юнит-тесты
  AttachmentList.tsx     сетка плиток + состояние "какое вложение открыто"
  AttachmentTile.tsx     миниатюра | карточка файла | заглушка загрузки; кнопка удаления
  AttachmentViewer.tsx   Dialog: заголовок, позиция, "Открыть в новой вкладке", <-/->, контент
  FileCard.tsx           иконка типа + имя + размер (используют и плитка, и просмотрщик)
```

Вход `AttachmentList`:

```ts
interface AttachmentItem {
  readonly key: string;                // стабильный ключ: UploadId или ClientDocId
  readonly name: string;               // подпись: originalName или название документа
  readonly file: UploadResponse | null; // null — метаданные ещё грузятся
}
props: items, onRemove?: (item) => void, removeLabel?: (name) => string
```

Компонент получает уже собранные данные и сам ничего не запрашивает. Документы клиента собирают `file` через `useQueries(uploadInfoQuery)` в `ClientDocumentsSection`. Задачи передают `UploadResponse` как есть. Подтверждение удаления остаётся у вызывающего: `onRemove` для документов клиента открывает `ConfirmDialog`, как сейчас.

*Альтернатива:* компонент принимает `UploadId` и сам вызывает `upload/info`. Отклонено: у задач ответ уже на руках, лишние запросы на каждое вложение.

### 2. Классификация по `contentType`: явный список

`previewKind` приводит MIME-тип к нижнему регистру, отбрасывает параметры после `;` и сверяет со списками:

| kind  | типы |
|-------|------|
| image | `image/jpeg`, `image/png`, `image/gif`, `image/webp`, `image/avif`, `image/svg+xml`, `image/bmp` |
| pdf   | `application/pdf` |
| video | `video/mp4`, `video/webm`, `video/ogg` |
| audio | `audio/*` |
| file  | всё остальное |

Явный список вместо `image/*` нужен, чтобы HEIC/TIFF сразу шли карточкой, а не через ошибку загрузки. Разметка — строго `<img>`/`<video>`/`<audio>`/`<iframe>` только для этих типов. SVG показывается только через `<img>`, где скрипты не выполняются. HTML и прочее никогда не встраиваются в `<iframe>`.

Для `pdf` дополнительно проверяется `navigator.pdfViewerEnabled`: при `false` (Android Chrome) показывается карточка файла. Свойство читается в просмотрщике, а не в `previewKind`, чтобы функция осталась чистой.

### 3. Плитки: единая сетка в исходном порядке

```
+--------+ +--------+ +--------+
|  img   | |  img   | |  [PDF] |
|        | |      x | | 240 KB |
+--------+ +--------+ +--------+
 photo1     photo2     contract.pdf
```

Сетка `grid-cols-[repeat(auto-fill,minmax(6rem,1fr))]`, плитки квадратные: изображение — `object-cover`, файл — иконка и размер. Подпись с именем под плиткой, `truncate` и `title` с полным именем. Порядок вложений не меняется: изображения не группируются отдельно, чтобы позиция «2 из 5» в просмотрщике совпадала с сеткой.

Плитка — `<button>` с `aria-label` «Открыть <имя>». Кнопка удаления — соседний элемент в углу плитки, а не вложенный в кнопку: вложенные интерактивные элементы недопустимы. Поэтому нажатие на ✕ не открывает просмотрщик без `stopPropagation`.

Миниатюра — `<img loading="lazy" decoding="async">`. При `onError` плитка переключается на карточку файла. Состояние ошибки хранится по `key` в `AttachmentList`, чтобы просмотрщик тоже сразу показывал карточку. При `file === null` показывается `Skeleton`, плитка не нажимается.

*Альтернатива:* список-строки с маленькой иконкой слева, как сейчас. Отклонено: по строкам не видно содержимое изображений, ради чего изменение и затевается.

### 4. Просмотрщик: Radix Dialog на весь экран

`DialogContent` с переопределёнными классами: почти весь экран (`h-[100dvh] max-w-none` на телефоне, отступы на десктопе), тёмный фон под содержимым.

```
+-----------------------------------------------------+
| photo2.jpg            2 из 5   [Открыть в вкладке] [x] |
+-----------------------------------------------------+
|  [<]                                           [>]  |
|               +-------------------+                 |
|               |   object-contain  |                 |
|               +-------------------+                 |
+-----------------------------------------------------+
```

- Открытое вложение — `index: number | null` в `AttachmentList`. Если список изменился, пока просмотрщик открыт (вложение удалили), индекс ограничивается длиной списка; пустой список закрывает просмотрщик.
- Контент рендерится с `key={item.key}`, поэтому при переходе `<video>`/`<audio>` размонтируются и воспроизведение останавливается само.
- ←/→ — обработчик `keydown` на `window`, пока просмотрщик открыт. Обработчик на `DialogContent` не подходит: на краю списка нажатая кнопка «Следующее» становится `disabled`, фокус уходит на `body`, и стрелки перестают доходить до диалога. Событие игнорируется, если `target` — `<video>`/`<audio>`: там стрелки перематывают. Внутри `<iframe>` с PDF события до документа не доходят; переход остаётся кнопками.
- Esc, клик по оверлею и ✕ закрывают только Dialog. Radix ведёт стек слоёв, `EditSheet` под ним Esc не получает, его `guard` не срабатывает. Это проверяется тестом из спеки («Esc в форме создания»). Фокус после закрытия Radix возвращает на триггер. Так как Dialog управляемый, `AttachmentList` сохраняет ссылку на нажатую плитку и фокусирует её в `onCloseAutoFocus`.
- «Открыть в новой вкладке» — `<a href target="_blank" rel="noreferrer">`.
- Медиа: `<video controls preload="metadata">`, `<audio controls>`, без `autoplay`. Ошибка `onError` → карточка файла.
- PDF — `<iframe src title>` на всю высоту контента.

*Альтернатива:* отдельная библиотека лайтбокса (yet-another-react-lightbox и т.п.). Отклонено: нужны только изображения без зума, а PDF и медиа она не покрывает. Свой компонент на существующем Dialog проще согласовать со строгими правилами типизации.

### 5. Размер файла — число по локали, единицы из словаря

`ui/attachments/fileSize.ts`: `fileSize(t, bytes)` делит на 1024, пока число не меньше 1024, округляет до одного знака и подставляет его в `attachments.size.b|kb|mb|gb` («{size} КБ»). Число форматирует переводчик по правилам языка: «5,5 МБ» / «5.5 MB».

*Альтернатива:* `Intl.NumberFormat` с `style: "unit"`. Отклонено при реализации: ICU даёт «240 кБ» для `ru` и «512 byte» для `en`, а не «240 КБ» / «512 B», как требует спека.

### 6. Встраивание в экраны

- `TaskSheet`: `items = task.attachments.map(a => ({ key: a.id, name: a.originalName, file: a }))`, `onRemove` → существующий `detach`.
- `TaskCreateSheet` (`NewAttachments`): то же из значения поля формы, `onRemove` убирает элемент из массива.
- `ClientDocumentsSection`: `DocRow` удаляется. `useQueries` по `docs` → `items` с `name: doc.name`, `file: query.data ?? null`. `onRemove` → `setDocToDelete`.
- Кнопки «Прикрепить файл» / «Загрузить документ» и их `<input type="file">` остаются в экранах без изменений.

Новые строки i18n: `attachments.size.*` (§5), `attachments.open` («Открыть {name}»), `attachments.position` («{index} из {total}»), `attachments.previous`, `attachments.next`, `attachments.openInNewTab`, `attachments.viewerTitle` (скрытый заголовок Dialog для скринридеров). Подписи удаления остаются у экранов (`tasks.removeAttachment`, `clients.detail.deleteDoc`).

## Risks / Trade-offs

- [Миниатюры грузят оригиналы, фото с телефона — 3–8 МБ] → `loading="lazy"`, у задач обычно 1–3 вложения. Серверные превью — отдельное изменение, когда это станет заметно.
- [Подпись ссылки в панели создания живёт 1 час] → при истечении сработает `onError`, и вместо миниатюры будет карточка. После создания задачи ссылки уже 7-дневные. Отдельной обработки не делаем.
- [iOS Safari в `<iframe>` показывает только первую страницу PDF] → в просмотрщике всегда есть «Открыть в новой вкладке». `pdfViewerEnabled` на iOS — `true`, поэтому карточку там не показываем.
- [`contentType` от клиента может не совпадать с содержимым] → неверный тип даёт только ошибку загрузки, а та ведёт к карточке. Встраивание ограничено безопасными тегами из решения 2.
- [Стрелки не работают, пока фокус внутри PDF-iframe] → кнопки «Предыдущее»/«Следующее» видны всегда.
- [В jsdom нет `pdfViewerEnabled` и загрузки изображений] → в тестах `load`/`error` вызываются через `fireEvent`, а `navigator.pdfViewerEnabled` подменяется в конкретном тесте.
