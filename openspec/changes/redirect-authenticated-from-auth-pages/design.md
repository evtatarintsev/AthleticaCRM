# Design

## Context

Мотивация — в proposal.md, требования — в `specs/web-client/app-shell/spec.md`.

Текущее устройство веб-клиента (`web/src/app/router.tsx`):

- `appRoute.beforeLoad` проверяет сессию: сначала смотрит в кэш TanStack Query (`sessionQuery`, ключ `["session", "auth/me"]`), иначе вызывает `auth/me`; при `unauthenticated` делает `redirect` на `/login?redirect=<location.href>`.
- `loginRoute` и `signUpRoute` сессию не проверяют.
- `api/client.ts` на 401 вызывает `auth/refresh-token` (кроме эндпоинтов из `WITHOUT_REFRESH`). Если сервер отверг refresh-токен, вызывается `onSessionExpired`: `main.tsx` очищает `queryClient` и вызывает `routing.redirectToLogin()`. Тот переходит на `/login?redirect=<текущий адрес>`, если текущий путь не `/login`.
- Адрес возврата (`redirect`) — путь относительно `basepath` роутера, его проверяет `LoginSearchSchema` (`auth/redirect.ts`): чужой origin сбрасывается в `undefined`.
- Сервер при выходе удаляет обе cookie (access и refresh), поэтому после выхода `auth/me` получает 401, а обновить сессию не выходит.

## Goals / Non-Goals

**Goals:**

- Проверка сессии до отрисовки формы, без мигания формы перед переходом.
- Ни при каком состоянии кэша и cookie переходы не идут по кругу.

**Non-Goals:**

- Проверка на стороне сервера (Ktor) при отдаче `index.html`.
- Изменение API, контрактов и `api/client.ts`.

## Decisions

### 1. Проверка в `beforeLoad` маршрутов `/login` и `/sign-up`

`beforeLoad` выполняется до отрисовки, поэтому форма не мелькает, а `redirect` из него — штатный способ роутера.
Альтернативы:
- `useEffect` в компоненте страницы: форма успевает показаться, и переход виден.
- Редирект на сервере по cookie: сервер отдаёт SPA как статику и не знает её маршрутов. Пришлось бы дублировать проверку токена и логику адреса возврата.

Общий код обеих проверок — функция в `router.tsx` (например `redirectIfAuthenticated(context, target)`). Она вызывает `auth/me` и при успехе бросает `redirect`. Отдельный модуль не нужен.

### 2. Свежий `auth/me` без кэша, результат кладётся в кэш

Проверка всегда вызывает `api.call("auth/me")`, не глядя в `queryClient`. Если сессия на сервере закончилась, а данные в кэше остались, проверка по кэшу отправила бы пользователя в приложение. Там первый же запрос получил бы 401, и пользователь вернулся бы на вход: цикл.
При успехе ответ кладётся в кэш (`queryClient.setQueryData(sessionQuery(api).queryKey, value)`), как в `appRoute`. Тогда `appRoute.beforeLoad` после перехода не делает второй запрос.

Обновление токена при 401 остаётся включённым. Сценарий «истёк только access-токен» должен вести в приложение, а именно это и делает refresh.
Отвергнутая альтернатива — флаг «без refresh» для этого вызова: он ломает тот же сценарий и требует менять `api/client.ts`.

### 3. Куда вести

- `/login` → `search.redirect ?? "/"`. Значение уже прошло `LoginSearchSchema`, поэтому подмена origin невозможна. Адрес относительный к `basepath` и может содержать query (`/?from=bookmark`), поэтому передаётся как `redirect({ href, replace: true })`, а не `to`: `to` не разбирает строку запроса.
- `/sign-up` → `redirect({ to: "/", replace: true })`.

`postLoginTarget` здесь не подходит: он добавляет `BASE_PATH` для `window.location.assign`, а роутер добавляет `basepath` сам. Полная перезагрузка, которую делает `onAuthenticated` после входа, при проверке не нужна: состояние клиента и так от этой же сессии.

### 4. Ошибки проверки показывают форму

Любая неудача (`unauthenticated`, `unavailable`, `contract`, `business`) → `beforeLoad` просто возвращает управление, и форма показывается. Исключение не бросается: иначе `errorComponent` заменил бы форму входа страницей ошибки, и при недоступном сервере пользователь не смог бы даже попробовать войти. Вид ошибки не разбирается, поэтому `switch` по `result.error.kind` не нужен.

### 5. `redirectToLogin` не срабатывает на гостевых страницах

Гость на `/sign-up` получает от `auth/me` 401, refresh отвергается, и вызывается `onSessionExpired`. Сейчас `redirectToLogin` увёл бы его на `/login?redirect=/sign-up`. На `/login` переход уже подавлен, иначе адрес возврата затёрся бы на `/login?...`.
Решение: множество гостевых путей (`/login`, `/sign-up`), на которых `redirectToLogin` ничего не делает. `queryClient.clear()` в `onSessionExpired` гостю не мешает.
Альтернатива — не вызывать `onSessionExpired` для этого запроса — снова требует опции в `api/client.ts` ради одного места.

## Risks / Trade-offs

- [Гость делает два лишних запроса (`auth/me` и `auth/refresh-token`, оба 401) при каждом открытии входа или регистрации] → Запросы лёгкие, страница открывается редко. Если будет мешать, сервер может отвечать на `auth/me` без cookie сразу, но это вне scope.
- [Медленный сервер задерживает показ формы на время `auth/me`] → Роутер покажет pending-состояние по своим умолчаниям. Ответ `auth/me` обычно занимает десятки миллисекунд, отдельный индикатор не делаем.
- [Если выход перестанет удалять refresh-cookie, проверка вернёт вышедшего пользователя в приложение] → Сейчас `clearJwtCookies` удаляет обе cookie. Сценарий «выход → открывается форма входа» закрепляется тестом маршрутизации.
- [Новая гостевая страница (например восстановление пароля) забудет попасть в множество гостевых путей] → Множество объявляется рядом с маршрутами в `router.tsx`, одним списком.

## Migration Plan

Только фронтенд, без данных и API. Выкатывается обычным деплоем веб-клиента; откат — revert коммита.
