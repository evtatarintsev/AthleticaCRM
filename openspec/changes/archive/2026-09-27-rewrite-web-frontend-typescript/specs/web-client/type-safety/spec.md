## Purpose

Гарантирует, что код веб-клиента проходит максимально строгую статическую проверку типов и что ослабить её можно только явным изменением конфигурации, а не локально в коде.

## ADDED Requirements

### Requirement: Проверка типов в самом строгом режиме

Исходный код веб-клиента SHALL проверяться компилятором TypeScript со всеми флагами строгости, которые не меняют семантику выполнения. В том числе:

- строгий режим целиком;
- доступ по индексу возвращает тип с `undefined`;
- необязательное свойство нельзя явно установить в `undefined`, если это не указано в типе;
- к полям индексной сигнатуры обращаются только через скобки;
- функция с не-`void` результатом возвращает значение на всех путях;
- `switch` без проваливания между ветками;
- переопределение метода помечается явно;
- нет неиспользуемых переменных, параметров, меток и недостижимого кода;
- запрещён синтаксис, который не стирается при компиляции (`enum`, `namespace`, parameter properties);
- проверяются и объявления типов в зависимостях.

Отключение любого из этих флагов SHALL требовать изменения общей конфигурации, а не отдельного файла.

#### Scenario: Индекс массива без проверки

- **WHEN** код берёт элемент массива по индексу и сразу обращается к его полю
- **THEN** проверка типов завершается ошибкой

#### Scenario: Явный undefined в необязательном поле

- **WHEN** код присваивает `undefined` необязательному полю, тип которого не включает `undefined`
- **THEN** проверка типов завершается ошибкой

#### Scenario: Enum

- **WHEN** в коде объявлен `enum`
- **THEN** проверка типов завершается ошибкой

### Requirement: Запрет обходов системы типов

Статический анализ с информацией о типах SHALL отклонять код, в котором:

- используется тип `any`, явно или через небезопасное присваивание, вызов, обращение к полю, аргумент или возврат;
- применяется non-null утверждение `!`;
- применяется утверждение типа `as` или `<T>`, кроме `as const`;
- есть директивы подавления проверки типов (`@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`);
- промис создаётся и не ожидается, не возвращается и не обрабатывается явно;
- промис передаётся туда, где ожидается синхронная функция;
- `switch` по объединению или литеральному типу покрывает не все варианты и не имеет ветки, которая доказывает недостижимость;
- в условии используется значение не булева типа без явного сравнения;
- условие всегда истинно или всегда ложно по типам;
- выбрасывается значение, не являющееся `Error`.

Предупреждения анализатора SHALL считаться ошибками.

#### Scenario: Приведение ответа сервера

- **WHEN** код приводит результат `response.json()` к типу через `as`
- **THEN** проверка отклоняет код

#### Scenario: Неполный switch

- **WHEN** в размеченное объединение ошибок API добавлен новый вариант, а `switch` по нему этот вариант не обрабатывает
- **THEN** проверка отклоняет код и указывает на этот `switch`

#### Scenario: Подавление ошибки

- **WHEN** в коде есть `// @ts-expect-error`
- **THEN** проверка отклоняет код

#### Scenario: Потерянный промис

- **WHEN** обработчик события вызывает асинхронную функцию и не ожидает и не обрабатывает её результат
- **THEN** проверка отклоняет код

### Requirement: Полное покрытие типами

Доля выражений в исходном коде веб-клиента, чей тип выводится как `any`, SHALL быть равна нулю. Сгенерированный код контрактов подчиняется тому же правилу.

#### Scenario: any из нетипизированной зависимости

- **WHEN** значение из зависимости без объявлений типов используется в коде
- **THEN** проверка покрытия типами завершается ошибкой

### Requirement: Проверки обязательны на всех путях сборки

Проверка типов, статический анализ, проверка покрытия типами, проверка форматирования и тесты SHALL выполняться одной командой. Эта же команда SHALL выполняться при сборке Docker-образа веб-клиента и в CI до публикации образа. Если любая проверка не прошла, образ не собирается и не выкатывается.

#### Scenario: Ошибка типов в PR

- **WHEN** в `master` попадает коммит с ошибкой типов в веб-клиенте
- **THEN** сборка образа веб-клиента падает, и деплой не выполняется

#### Scenario: Локальная выкатка на стенд

- **WHEN** разработчик выкатывает веб-клиент на стенд скриптом, а в коде есть нарушение правил анализатора
- **THEN** сборка образа завершается ошибкой, и на стенд ничего не заливается

### Requirement: Исключения из правил только в конфигурации

Точечное ослабление правил в исходных файлах (комментарии-директивы, отключающие правило для строки или файла) SHALL быть запрещено. Исключение допускается только в общей конфигурации анализатора, с шаблоном путей и комментарием о причине.

#### Scenario: Директива отключения правила

- **WHEN** в исходном файле есть комментарий, отключающий правило анализатора
- **THEN** проверка отклоняет код
