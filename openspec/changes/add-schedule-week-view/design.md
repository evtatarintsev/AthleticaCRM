## Context

Мотивация — в [proposal.md](proposal.md), требования — в [specs/schedule/spec.md](specs/schedule/spec.md). Здесь только то, что определяет форму реализации.

Что уже есть в системе:

- `sessions` хранит занятия с `org_id`, `group_id`, датой, временем, `hall_id` и статусом; **колонки филиала нет** — филиал живёт на `groups.branch_id`. `group_id` объявлен `ON DELETE SET NULL`, то есть занятие может остаться без группы.
- Связи «многие ко многим»: `session_employees` (тренеры занятия), `group_employees` (тренеры группы), `group_disciplines` (дисциплины группы). На занятии есть флаг `is_employee_assignment_overridden`.
- `Groups.list()` уже ограничивает выборку филиалом из контекста и умеет фильтровать по `disciplineIds` и `employeeIds`.
- `GET /sessions/list` возвращает занятия за период, предварительно материализуя недостающие через `generateSessions` по всем группам филиала. Фронтом он не используется.
- Экран расписания существует как заглушка: `components/schedule/` с сеткой, ViewModel и локальным генератором данных `ScheduleStubData.kt`.
- Есть образец read-модели под страницу списка: `ClientListView` + `ClientListQuery` — доменный интерфейс проекции с собственным query-объектом, не зависящим от `api.schemas`.

Ограничения, которые нельзя обойти: домен не должен знать про схемы API; ссылки между агрегатами только по идентификатору; сборка ответа — задача слоя routes.

## Goals / Non-Goals

**Goals:**

- Один запрос на видимый период отдаёт всё, что нужно для отрисовки сетки.
- Фильтры вычисляются в БД, а не после выгрузки периода в память.
- Цвет резолвится в одном месте на сервере и переживает появление полей цвета без изменения контракта.
- Ограничение филиалом — в запросе выборки, а не в постобработке.

**Non-Goals:**

- Не переносим генерацию занятий на запись — это отдельное изменение, здесь только ограничиваем окно.
- Не вводим пагинацию: границей объёма служит предельная длина периода.
- Не трогаем `GET /sessions/list` и команды над занятиями.
- Не добавляем колонок цвета в БД: резолвер пишется сразу с тремя ступенями, но сегодня работает только последняя.

## Decisions

### Отдельная read-модель расписания вместо переиспользования `Groups.list` + `Sessions.list`

Вводим доменную проекцию (по образцу `ClientListView`/`ClientListQuery`): интерфейс выборки строк расписания с query-объектом `ScheduleQuery(from, to, hallIds, disciplineIds, employeeIds)`. Реализация — один SQL: `sessions` JOIN `groups` (даёт `branch_id` и название группы), фильтры по `hall_id = ANY(...)`, `EXISTS(session_employees ...)`, `EXISTS(group_disciplines ...)`.

Альтернатива — собрать из существующих методов: `groups.list(disciplineIds=...)` уже даёт группы филиала с нужными дисциплинами, дальше по каждой `sessions.list(groupId, from, to)`. Отклонена по двум причинам:

1. **N+1**: запрос занятий на каждую группу филиала, и это на каждое переключение недели.
2. **Неверная семантика фильтра по тренеру**: `Groups.list(employeeIds)` фильтрует по тренерам *группы*, а спека требует фильтровать по тренерам *занятия* — состав переопределяется на уровне занятия (`is_employee_assignment_overridden`). Группа с тренером A и занятие, где A заменён на B, должны попадать в фильтр по B, а не по A.

Индексы под это есть: `idx_sessions_org_date`, `idx_session_employees_employee`; по `groups.branch_id` при необходимости добавится отдельно.

### Филиал берётся из контекста, а не из параметра запроса

`RequestContext.branchIdOrNull` уже несёт текущий филиал из токена, и `Groups.list` на него опирается. Проекция расписания делает то же самое. Клиент филиал не передаёт — иначе появляется способ запросить чужой филиал в обход переключателя.

Занятия с `group_id IS NULL` (осиротевшие после удаления группы) в выдачу **не попадают**: у них нет ни филиала, ни заголовка карточки. Это осознанная потеря, см. риски.

### Справочники подтягиваются пачками, склейка — в роуте

Проекция возвращает доменные строки с идентификаторами. Роут догружает `halls.list()`, `disciplines.list()`, `employees.list()` — по одному запросу на каталог, независимо от числа занятий — и собирает схемы ответа. Домен остаётся без знания об `api.schemas`, N+1 не возникает: каталоги измеряются десятками записей.

### `POST /api/schedule/list` с телом, а не GET с query

Три фильтра — списки идентификаторов. В query они разворачиваются в повторяющиеся параметры и упираются в длину URL. В проекте уже есть прецедент чтения через POST с телом — `/clients/list`. `GET /sessions/list` остаётся как есть для простых сценариев.

### Форма ответа

```kotlin
ScheduleListRequest(from, to, disciplineIds, hallIds, employeeIds)

ScheduleListResponse(from, to, sessions)

ScheduleSessionSchema(
    id, groupId, title,              // title — имя группы
    date, startTime, endTime,        // продолжительность считает клиент
    hall: ScheduleHallSchema,        // id + name
    coaches: List<ScheduleCoachSchema>,
    disciplines: List<ScheduleDisciplineSchema>,
    status: SessionStatus,           // перечисление, не строка
    colorKey: SessionColorKey,
)
```

Отдельные маленькие схемы на каждое измерение (`ScheduleHallSchema`, `ScheduleCoachSchema`, `ScheduleDisciplineSchema`) вместо одной обобщённой пары id+name — чтобы идентификаторы остались типизированными (`HallId` ≠ `EmployeeId`). Приём уже применён в группах: `GroupEmployee`, `GroupDiscipline`, `GroupClient`.

Продолжительность не передаём: это функция от `startTime`/`endTime`, и её формат («1 ч», «20 мин») — вопрос локали клиента.

`isManual` и `isRescheduled` в ответ не включаем — спека их на карточке не требует. Добавятся, когда появится требование.

### Цвет: ключ палитры, резолв на сервере

Ответ несёт `colorKey` — значение перечисления (`ORANGE`, `PURPLE`, `STEEL`, `CYAN`, `GREEN`, `LIME`, `LILAC`, `GREY`), а не hex. Причины:

- Тёмная тема. Карточке нужна пара цветов (фон карточки и фон бейджа), и обе меняются между темами. Один hex с сервера этого не даёт.
- Контракт не привязан к оформлению: перекраска палитры не требует миграции данных.
- Будущий выбор цвета для дисциплины и группы становится выбором из набора, как в календарных продуктах, а не произвольной пипеткой.

Резолвер — одна функция `colorKeyFor(group, disciplines)` с тремя ступенями: цвет группы → цвет первой дисциплины → запасной. Полей цвета сегодня нет, поэтому реально исполняется только третья ступень; появление колонок меняет эту функцию и ничего больше.

Запасной ключ выводится из младших битов UUID (первой дисциплины, а при её отсутствии — группы) по модулю размера палитры. Именно из битов, а не через `hashCode()`: ключ должен быть одинаковым между рантаймами и версиями, иначе карточки перекрашиваются на ровном месте. Выбор по дисциплине, а не по занятию, даёт требуемое спекой свойство «одинаковая дисциплина — одинаковый цвет».

Неизвестный клиенту ключ (сервер новее клиента) рисуется нейтральным — обычный forward compatibility.

### Ограничение периода — 62 дня

Проверка до всякой работы с БД: `from <= to` и `to - from <= 62 дня`, иначе `CommonDomainError`. 62 дня покрывают месячную сетку с выравниванием по неделям (до 42 дней) с запасом, но не дают запросить год одним вызовом.

### Материализация — в границах запроса, генерация переиспользуется как есть

Порядок сохраняется прежний: транзакция генерации, затем транзакция чтения. Генерация вызывается для групп филиала (`Groups.list()` уже ограничен филиалом) строго на запрошенное окно. Существующий `generateSessions` перезапрашивает группу по идентификатору и её тренеров внутри цикла — при вызове из расписания стоит передавать уже загруженную группу, чтобы не повторять выборку на каждую группу филиала.

### Группировка по дням и часам — на клиенте

Сервер отдаёт плоский список занятий периода. Раскладка по колонкам-дням и строкам-часам зависит от режима отображения (неделя сейчас, день и месяц позже) и меняется без участия бэкенда.

### Фронтенд

`ScheduleStubData.kt` удаляется. Состояние страницы остаётся одной ячейкой: `ScheduleState(weekStart, data: ScheduleLoadState, filters, dictionaries)`, где `ScheduleLoadState` — `Loading | Loaded | Error` по образцу `HomeLoadState`. Фильтры и справочники живут в том же снимке, чтобы переключение недели и смена фильтров не расходились.

`ScheduleEventColor` перестаёт быть источником правды и становится отображением `SessionColorKey` в пару цветов темы.

```
   открытие страницы                  переключение недели / фильтра
          |                                        |
          v                                        v
  halls.list                              schedule.list(from,to,filters)
  disciplines.list   --> справочники              |
  employees.list         фильтров                 v
                                        генерация в окне -> выборка
                                                 |
                                                 v
                                     плоский список занятий
                                                 |
                                     группировка по дням/часам
                                                 |
                                                 v
                                             сетка недели
```

## Risks / Trade-offs

- **Чтение по-прежнему пишет в БД.** Листание недель вперёд материализует занятия, пусть и в пределах окна и филиала. → Ограничение периода удерживает объём; вынос генерации на запись запланирован отдельным изменением и не блокируется этим.
- **Занятия без группы исчезают из расписания.** `group_id` обнуляется при удалении группы. → Сейчас пользователь всё равно не увидел бы у такой карточки ни названия, ни филиала. Если окажется, что группы удаляются в реальной эксплуатации, правильное лечение — запретить удаление группы с занятиями, а не показывать безымянные карточки.
- **Нет пагинации.** На пределе периода и крупном филиале ответ может вырасти до тысяч занятий. → Недельный режим держит объём в десятках-сотнях; предел периода — жёсткая верхняя граница. Замерить на реальном объёме до включения режима «месяц».
- **Фиксированная палитра.** Когда появится выбор цвета для группы, он будет ограничен набором ключей. → Это осознанный обмен на работающие темы; расширять палитру дешевле, чем чинить контраст произвольного hex в тёмной теме.
- **Фильтр по дисциплинам через группу.** Дисциплины принадлежат группе, а не занятию, поэтому смена дисциплин группы задним числом меняет фильтрацию уже прошедших занятий. → Соответствует текущей модели; фиксация дисциплин на занятии — отдельное решение, если оно понадобится.

## Migration Plan

Миграций БД и новых переменных окружения нет. Изменение аддитивно: новый роут и новые схемы, существующие endpoint-ы не трогаются.

Порядок: бэкенд (проекция, роут, схемы) → API-клиент в `shared` → переключение страницы с заглушки. До последнего шага страница продолжает показывать заглушку и не ломается.

Откат — возврат коммита: внешних потребителей у нового endpoint-а нет, данные он не меняет, кроме той же материализации занятий, что уже выполняет `GET /sessions/list`.

- Помечать ли перенесённые занятия (`is_rescheduled`) на карточке. Поле есть в домене, добавляется в ответ без изменения структуры.
