## Why

Раздел «Расписание» есть в навигации, но открывает пустой экран с заголовком: занятия организации сейчас нельзя посмотреть нигде, кроме виджета «Занятия сегодня» на главной. Расписание — основной рабочий экран администратора: по нему проверяют загрузку залов, занятость тренеров и находят занятие, чтобы его перенести или отменить.

Данные для этого уже есть: занятия материализуются из версий слотов расписания групп сверкой на записи, есть залы, тренеры и дисциплины. Не хватает проекции под страницу: существующий `GET /sessions/list` отдаёт идентификаторы вместо названий и не принимает фильтров, поэтому собрать из него карточку без пачки дополнительных запросов нельзя.

## What Changes

- Страница «Расписание» отображает недельную сетку «часы × дни недели» с карточками занятий и переключением недели вперёд/назад.
- Карточка показывает только то, что есть в домене: время начала и окончания, продолжительность, название группы, тренеров, зал, дисциплины.
- Три фильтра: дисциплины, залы, тренеры. Множественный выбор внутри фильтра, пересечение между фильтрами.
- Новый endpoint-проекция для страницы: принимает период и фильтры, возвращает карточки с уже развёрнутыми названиями зала, тренеров и дисциплин — фронт не джойнит справочники сам.
- Цвет карточки приходит с сервера как ключ палитры. Резолв: цвет группы → цвет дисциплины → запасной, выведенный детерминированно. Полей цвета в домене пока нет, поэтому сегодня работает только последняя ступень; контракт от их появления не меняется.
- Расписание ограничено текущим филиалом из токена. Сейчас выборка занятий идёт по всей организации, а залы — по филиалу, из-за чего в сетку попали бы занятия чужих филиалов.
- Период запроса ограничен сверху; запрос ничего не материализует — занятия создаёт сверка расписания на записи.

Вне скоупа, сознательно:

- **Вместимость и свободные места.** В домене нет ни вместимости группы, ни вместимости занятия. Бейдж «Есть 7 мест» остаётся на карточке как визуальная заглушка с фиксированным текстом, рисуется на клиенте и в API не попадает — иначе позже нельзя будет отличить заглушку от настоящих данных.
- **Фильтры «Направления», «Виды занятий», «Уровни»** из макета: таких сущностей в домене нет вовсе.
- **Теги «идет набор», «онлайн», «open air»**: признаков формата и статуса набора в домене нет.
- **Режимы «день» и «месяц»**: контракт задаёт произвольный период и обслужит их без изменений, но UI в этом изменении только недельный.
- **Вынос генерации занятий из запроса чтения.** Сделано изменением `temporal-group-schedule`, которое сливается раньше этого: чтение больше не материализует занятия, горизонт зажат внутри сверки. Здесь остаётся только ограничение периода выборки.
- **Действия над занятием** (перенос, отмена, состав тренеров): только просмотр.
- **Пометка «перенесено» на карточке.** Семантика `is_rescheduled` не определена: флаг ставится при любом переносе, не снимается при возврате и защищает занятие от сверки. Решается в [#73](https://github.com/evtatarintsev/AthleticaCRM/issues/73).
- **Сужение фильтра тренеров.** Пока в фильтре все сотрудники филиала; показывать только тренеров (по роли, флагу или назначениям) — [#74](https://github.com/evtatarintsev/AthleticaCRM/issues/74).
- **Удаление `GET /sessions/list` и `SessionListView`.** Фронтом не используется и после этого изменения дублирует проекцию расписания; удаляется отдельно.

## Capabilities

### New Capabilities

- `schedule`: просмотр расписания занятий организации — недельная сетка, состав карточки занятия, фильтрация по дисциплинам, залам и тренерам, границы выборки по филиалу и периоду.

### Modified Capabilities

Нет. `/sessions/detail` и команды над занятиями не меняются; спецификаций на них сейчас нет.

## Impact

**Backend**

- Новые схемы запроса и ответа в `shared/.../api/schemas/schedule/`, включая перечисления статуса занятия и ключа палитры.
- Новая read-проекция `read/schedule/` (`ScheduleView` + `DbScheduleView`): один SQL по `sessions`, `groups`, `halls`, `session_employees`, `group_disciplines`, возвращает схему ответа напрямую; регистрируется в `ReadViews`.
- Новый роут `POST /api/schedule/list` в `server/.../routes/`: валидация периода, нормализация фильтров, вызов проекции.
- Агрегаты `domain/**` и их репозитории не меняются: ограничение по филиалу живёт в SQL проекции.

**Frontend (composeApp)**

- `components/schedule/`: экран, ViewModel и модели уже существуют как заглушка; заглушечный источник данных `ScheduleStubData.kt` удаляется, состояние переводится на загрузку с сервера.
- Новый API-клиент раздела и его регистрация в `ApiClient`.
- Справочники фильтров берутся существующими `halls.list`, `disciplines.list`, `employees.list`.

**Прочее**

- Новых переменных окружения и миграций БД не требуется; ограничение по филиалу меняет только SQL-выборку.
