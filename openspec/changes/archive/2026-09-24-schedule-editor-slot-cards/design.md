## Context

`ScheduleEditor` используется только в `SetScheduleDialog`. Он редактирует `List<ScheduleSlot>` напрямую: одна строка — один слот. `SetScheduleState` хранит этот список как есть, а `isValid` проверяет только `!isSaving`. Сервер (`DbGroupSchedule`) определяет слот ключом `(день, время начала)`: смена времени окончания или зала даёт новую версию, повторяющийся ключ отклоняется с `DUPLICATE_SCHEDULE_SLOT`. Спецификации `group-schedule` и API этим изменением не затрагиваются, мотивация — в proposal.md.

Сейчас у строки есть два скрытых дефекта, помимо ширины:
- локальное состояние `TimeTextField` (`remember(value)`) привязано к позиции в списке, а не к слоту, поэтому после удаления строки недописанный текст может «переехать» к соседней строке;
- названия дней для UI берутся из `DayOfWeek.displayName` в `shared`. Это захардкоженная русская строка в обход `stringResource`.

## Goals / Non-Goals

**Goals:**
- Модель карточки и её соответствие слотам — чистые функции, покрытые тестами в `commonTest`.
- Проверки считаются из состояния, а не хранятся отдельными флагами.
- Раскладка карточки оставляет место под будущее поле тренера без переделки.

**Non-Goals:**
- Изменения API, `ScheduleSlot`, сервера.
- Замена `AlertDialog` на полноэкранный диалог на COMPACT.
- Отказ от `DayOfWeek.displayName` в остальных экранах (`GroupDetailScreen`, `GroupMobileItem`). Это отдельная уборка, здесь только не используем его в новом коде.

## Decisions

### 1. Карточка — модель только для UI, API остаётся по-слотовым

```
 сервер: List<ScheduleSlot>            UI: List<SlotCard>
 Пн 15-17 A --+
 Ср 15-17 A --+-- groupBy(start,end,hall) --> {Пн,Ср} 15-17 A
 Сб 10-12 B -------------------------------> {Сб}    10-12 B
            <-- flatMap(days) при сохранении ----
```

`SlotCard(id, days: Set<DayOfWeek>, startAt, endAt, hallId: HallId?)` живёт в `components/groups`. `id` — локальный идентификатор карточки внутри диалога (счётчик в состоянии), нужен как `key` в Compose и для привязки ошибок к карточке. `hallId` может быть `null`: так выражается «зал не выбран» (см. решение 4).

Функции:
- `List<ScheduleSlot>.toCards()` группирует по `(startAt, endAt, hallId)`. Порядок карточек — по первому дню недели в карточке, затем по времени начала. Так «Пн–Пт 09:00» стоит выше «Пн–Пт 18:00».
- `List<SlotCard>.toSlots()` разворачивает каждый день карточки в `ScheduleSlot`. Вызывается только при сохранении, а сохранение доступно только при `isValid`, то есть когда у всех карточек выбран зал. Карточки без зала функция пропускает, а не падает.

Разворачивание обратно даёт тот же набор слотов, поэтому сохранение без правок отправляет тот же набор, и сервер не создаёт новых версий.

*Альтернатива:* слот с набором дней в API и БД. Отвергнута: ключ `(день, начало)` и версионирование по дню — осмысленная доменная модель (смена зала в среду не должна трогать понедельник), а группировка — чисто вопрос ввода.

### 2. Состояние хранит карточки, а не слоты

`SetScheduleState.slots` заменяется на `cards: List<SlotCard>` и `nextCardId`. Переходы — чистые методы `withCardAdded(halls)`, `withCardChanged(card)`, `withCardRemoved(id)`. VM по-прежнему только присваивает `state = state.with…()`. `SetScheduleViewModel` принимает `initialSlots` как раньше и сам вызывает `toCards()`, поэтому место вызова диалога не меняется.

`ScheduleEditor` получает `cards` и колбэки на изменение, добавление и удаление карточки вместо `onSlotsChange(List<ScheduleSlot>)`.

### 3. Проверки — производное свойство состояния

```kotlin
sealed interface SlotCardError {
    data object NoDays : SlotCardError
    data object NoHall : SlotCardError
    data object EndNotAfterStart : SlotCardError
    data class Duplicate(val day: DayOfWeek, val startAt: LocalTime) : SlotCardError
}
val cardErrors: Map<SlotCardId, List<SlotCardError>>  // считается из cards
val isValid get() = !isSaving && cardErrors.isEmpty()
```

`Duplicate` вычисляется разворачиванием всех карточек в пары `(день, начало) → id карточки` и выбором пар, где больше одной карточки. Ошибка попадает во все участвующие карточки. Поля времени, в которых сейчас недописанный текст, `LocalTime` не меняют (как и сейчас), поэтому проверяется последнее валидное значение. Поле с ошибкой формата подсвечивается само, как сейчас.

*Альтернатива:* проверять только на сервере. Отвергнута: сервер сообщает только первый дубль и без привязки к карточке, а «нет дней» и «нет зала» выразить в запросе невозможно.

### 4. Новая карточка: без дней, зал только если он единственный

`withCardAdded(halls)` создаёт карточку с `days = emptySet()`, временем по умолчанию и `hallId = halls.singleOrNull()?.id`. Кнопка «Добавить» больше не зависит от наличия залов в момент нажатия: при пустом списке залов остаётся текущая подсказка `schedule_halls_empty`, а карточка не пройдёт проверку `NoHall`.

Время по умолчанию берётся из последней карточки, если она есть: вторая карточка чаще всего — то же занятие в другие дни или соседний час. Иначе 00:00–01:00, как сейчас.

### 5. Раскладка карточки

```
 +----------------------------------+
 | [Пн][Вт][Ср][Чт][Пт][Сб][Вс]     |   ряд 1: дни, каждый weight(1f)
 | [ 15:00  ] - [ 17:00  ]     [x]  |   ряд 2: время weight(1f), удаление
 | [ Зал: Большой              v ]  |   ряд 3: зал fillMaxWidth
 |  ! Выберите дни                  |   ошибки карточки
 +----------------------------------+
   (ряд 4 в будущем: тренер)
```

- Карточка — `OutlinedCard`: рамка однозначно показывает, что удаляет [x].
- Дни — ряд из семи переключателей равной ширины (`weight(1f)`), а не `FilterChip`. У `FilterChip` фиксированные внутренние отступы: семь штук не помещаются в ~250 dp контента на 360 dp вместе с отступами. Переключатель — `Surface` с `toggleable`, выделение цветом `secondaryContainer`, высота 40 dp, семантика `Role.Checkbox`.
- Названия дней — новые строки `weekday_short_monday…sunday` в `strings.xml` (и во всех `values-<lang>`), не `DayOfWeek.displayName`.
- Одна раскладка на все размеры экрана. На широком экране зал рядом со временем сэкономил бы строку, но под залом остаётся место для тренера, а одна раскладка проще тестируется.

### 6. Прокрутка диалога

`Column` в `text` диалога получает `verticalScroll(rememberScrollState())`. `AlertDialog` сам ограничивает высоту `text` и держит кнопки на месте. `LazyColumn` не нужен: карточек единицы.

## Risks / Trade-offs

- [На экране 320 dp контенту остаётся ~230 dp, переключатель дня ~30 dp шириной — меньше рекомендованной тач-цели 48 dp] → высота 40 dp и отсутствие зазоров между переключателями дают приемлемую площадь. Если на практике будут промахи, следующий шаг — полноэкранный диалог на COMPACT. Это отдельное решение, в модель оно не вмешивается.
- [Снятие дня в карточке закрывает слот, и это неочевидно] → поведение совпадает с удалением строки сейчас. Предупреждение о закрытии относится к дате вступления в силу и уже есть на уровне диалога.
- [Пользователь хочет в среду другое время, а меняет время во всей карточке] → это осознанная модель «одна карточка — одно занятие». Для отличающегося дня снимается отметка и добавляется новая карточка.
- [Два поля времени в одном ряду с кнопкой удаления на 320 dp] → поля на `weight(1f)` без фиксированной ширины. Текст `ЧЧ:ММ` bodyMedium помещается в ~80 dp.
