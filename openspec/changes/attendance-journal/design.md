## Context

Занятия уже материализуются из расписания (`session-generation`), у занятия есть статусы
`scheduled` / `completed` / `cancelled` и методы `complete()` / `cancel()`. Состав группы
описывается `Enrollment` — периодом участия клиента с `enrolledAt` / `leftAt`. Абонементы
(`memberships`) append-only, списаний нет. Шина доменных событий существует (outbox-таблица
`domain_events` + `DomainEventWorker`), но ни одного подтипа `DomainEvent` пока не объявлено —
эта задача заводит первые.

Мотивация — см. `proposal.md`. Требования — см. `specs/`.

## Goals / Non-Goals

**Goals:**
- Журнал, у которого состав занятия достоверен и в открытом, и в закрытом состоянии, без
  дублирования данных о членстве в группе.
- Модель отметки, в которой «отсутствие без причины» непредставимо на уровне типов, а не только
  проверкой в сервисе.
- Событие о проведении занятия как единственный контракт для будущего списания абонементов (#104):
  подписчик появится позже и не потребует изменений в журнале.

**Non-Goals:**
- Материализованные проекции посещаемости. Чтение — синхронный SQL по таблицам записи, как во всём
  остальном `read/`.
- Хранение истории правок отметок отдельной таблицей: история восстанавливается из аудита и потока
  событий.
- Разграничение прав — вне скоупа задачи целиком (см. `proposal.md`, Non-goals).

## Decisions

### Строка журнала создаётся лениво, состав закрытого занятия — это набор строк

Таблица отметок хранит строку на пару «занятие + клиент». Строка создаётся в момент первой отметки
или ручного добавления разового участника — не заранее.

Состав занятия читается по-разному в зависимости от статуса:

| Статус | Состав |
|---|---|
| `scheduled` | строки журнала ∪ клиенты с активным `Enrollment` на дату занятия |
| `completed` | только строки журнала |
| `cancelled` | только строки журнала (в отчётах не учитывается) |

Это и есть «фиксация состава снимком» из спеки: закрыть занятие можно только когда отмечены все,
значит к моменту закрытия строка есть у каждого участника, и переход на чтение «только строк»
замораживает состав без копирования данных.

*Альтернатива — материализовать состав при генерации занятия.* Отвергнута: занятия генерируются на
горизонт вперёд, умножение горизонта на размер групп даёт большой объём строк, которые почти все
останутся пустыми, и любое изменение `Enrollment` требовало бы их пересинхронизации — ровно та
задача, от которой ленивое создание избавляет.

*Альтернатива — копировать состав в отдельную таблицу-снимок при закрытии.* Отвергнута как
дублирование: та же информация уже лежит в строках журнала.

### Отметка — sealed-тип, «отсутствие без метки» непредставимо

В домене отметка моделируется тремя состояниями: не отмечен, присутствие (метки необязательны),
отсутствие (набор меток непуст). Требование «отметка „не пришёл“ требует метки» становится
инвариантом конструктора, а не проверкой в usecase — по правилу «Make Illegal States
Unrepresentable» из `CLAUDE.md`.

В БД это `presence` (nullable: `NULL` — не отмечен) плюс таблица связи с метками; непустота меток
при отсутствии держится доменом, не constraint-ом, так как выразить её в PostgreSQL без триггера
нельзя.

### Метки — справочник организации с областью применимости

Метка хранит название, применимость (`present` / `absent` / `any`), порядок и признак архивности.
Применимость нужна не только для UI: без неё метка «болеет» может оказаться на присутствии, и
будущая политика списания (#104) получит бессмысленную комбинацию.

Предустановленный набор (опоздал, ушёл раньше, болеет, предупредил, прогул) создаётся миграцией
для существующих организаций и при регистрации новой. Дальше организация правит справочник сама;
предустановленные метки ничем не отличаются от созданных вручную и могут быть архивированы.

*Альтернатива — фиксированный enum статусов (был / не был / болел / опоздал), как сейчас в моке
веб-клиента.* Отвергнута: набор причин у каждой организации свой, а смешивание присутствия и
причины в одну ось не позволяет отметить «пришёл и опоздал» одновременно.

### Одна отметка допускает несколько меток

Связь «отметка — метка» многие-ко-многим. Конфликт меток с разными финансовыми последствиями
(«болеет» + «прогул») сейчас не возникает, потому что списаний нет; правило разрешения конфликта
принимается в #104 вместе с политикой списания.

### Закрытие журнала — существующий переход занятия, а не новый статус

`Session.complete()` получает предусловие «нет неотмеченных участников» и публикацию события.
Новых статусов занятию не нужно: `scheduled` и есть «журнал открыт».

Переоткрытия нет. Закрытие публикует событие, на которое позже подпишется списание; переоткрытие
означало бы откат уже совершённых списаний с каскадом отменённых уведомлений. Вместо этого правка
отметки в закрытом занятии публикует событие об изменении, и подписчик проводит корректировку —
операция, которую он и так обязан уметь.

Запрет `completed` → `cancelled` — следствие того же: отмена проведённого занятия это
сторнирование, а не смена статуса.

### События — первые подтипы `DomainEvent`, подписчиков нет

Объявляются четыре события: отметка поставлена, отметка изменена (с прежним и новым значением),
занятие проведено (итоговый состав с отметками и метками), занятие отменено. Складываются в
существующий outbox; обработчиков в этой задаче не регистрируется.

Событие об изменении несёт прежнее значение, чтобы подписчик мог посчитать дельту, не читая
историю. Событие о проведении несёт полный состав по той же причине: подписчику не нужно
обращаться к журналу.

### Проекции чтения — три, по экранам

`read/attendance/`: журнал занятия (состав с отметками и метками), сводка по группе за период,
посещаемость клиента за период. Правило «состав открытого занятия — объединение строк и активных
записей в группу» живёт в SQL проекции; `read/` не импортирует `domain/**`, как и остальные
проекции.

Командная сторона считает состав самостоятельно: агрегат занятия не может читать проекцию.
Дублирование логики состава между `domain/` и `read/` — осознанная плата за границу слоёв, та же,
что уже есть в проекте.

### Сверка расписания начинает учитывать отметки

К условию «занятие изменено человеком» добавляется наличие строк журнала. Проверка — `EXISTS` по
`session_id`; индекс по `session_id` нужен в любом случае для чтения журнала.

## Risks / Trade-offs

- **Состав открытого занятия зависит от текущих `Enrollment`** → клиента добавили в группу задним
  числом — он появился в составе прошедшего, но незакрытого занятия. Принято осознанно: до
  закрытия журнал и есть черновик. Закрытие фиксирует состав, дальше изменения записей в группу на
  него не влияют.

- **Два сотрудника отмечают одного участника одновременно** → побеждает последний. Уникальный
  индекс на паре «занятие + клиент» исключает дубли строк, а публикация события только по
  фактически изменившемуся значению не даёт лишних событий. Блокировок не вводим: цена ошибки —
  одна неверная отметка, исправляемая вручную.

- **Отметки остаются у отменённого занятия** → мусорные данные в таблице. Проекции фильтруют по
  статусу занятия; удалять строки при отмене не будем, иначе теряется след того, что журнал
  заполнялся до отмены.

- **Массовая отметка большой группы** → одна транзакция на десятки строк плюс столько же событий в
  outbox. Приемлемо; если станет узким местом, события схлопываются в одно пакетное — контракт
  подписчиков ещё не зафиксирован.

- **Веб-клиент теряет мок-поведение отметок** → карточка занятия начинает зависеть от реального
  API. Остальные её действия (отменить, перенести, сменить зал, сменить тренеров, заметка) остаются
  мок-состоянием, как описано в существующей спеке; расхождение сохраняется до отдельной задачи.

## Migration Plan

Миграции данных нет: отметок в системе не существует, переносить нечего. Схема добавляется тремя
таблицами (журнал, справочник меток, связь) плюс наполнением справочника предустановленными метками
для существующих организаций.

Откат — удаление добавленных таблиц; существующие таблицы не изменяются, `sessions` не трогается,
поэтому откат не затрагивает работающую функциональность расписания.

Веб-клиент и сервер выкатываются вместе: контракты генерируются из Kotlin (`npm run contracts`), и
карточка занятия без серверных маршрутов журнала работать не будет.
