# Design

## Context

- Абонемент хранит `price` и не знает об оплате (`domain/memberships/Membership.kt`). Выдача —
  `MembershipsRoutes` → `Memberships.issue(...)`.
- Лицевой счёт клиента — отдельный журнал `client_balance_journal` с `balance_after`
  (`domain/clientbalance`). Его читают `DbClientListView` (колонка, сортировка, фильтр `hasDebt`),
  `DbGroupRosterView` (признак долга), `DbClientBalanceHistoryView`, карточка клиента в
  `ClientsRoutes`, а пишут корректировка `/clients/balance/adjust` и импорт клиентов.
- `orgbalance` и `payment` — биллинг организации у нас, к деньгам клуба не относятся.
- Существующие данные тестовые; обратная совместимость не требуется (см. proposal.md).
- Правила проекта: агрегаты в `domain/`, чтение в `read/` одним SQL, ошибки через `Raise`,
  нарушения ограничений через `onViolation`, деньги только `Money`, smart constructor для инвариантов.

## Goals / Non-Goals

**Goals:**
- Единый механизм для всех денежных остатков (касса, аванс, долг продажи), проверяемый базой.
- Продажа — общий документ для абонементов и услуг, чтобы товары добавлялись без новой модели.
- Чтение — проекции по главной книге без хранимых остатков.

**Non-Goals:**
- Справочник товаров и склад; скидки и промокоды в позиции продажи.
- Фискализация по 54-ФЗ (чеки, ККТ); онлайн-оплата клиентом; импорт банковской выписки.
- P&L, признание выручки по посещениям, проценты тренерам (модель это допускает, см. ниже).
- Смены кассира, закрытие периода от правок, автоматическая комиссия эквайринга.
- Объединение с `orgbalance`.

## Decisions

### 1. Двойная запись как хранилище, а не производная проекция

Три таблицы: `ledger_accounts`, `ledger_transactions`, `ledger_postings`. Остаток счёта —
`SUM(amount)` по проводкам. Знак: дебет `+`, кредит `−`.

*Альтернатива* — типизированные журналы на каждый вид остатка (как `client_balance_journal`) и
вывод главной книги проекцией. Отклонена: каждый новый вид остатка — новая таблица со своей
блокировкой и `balance_after`, а согласованность «приход в кассу = уменьшение долга» держится на
дисциплине usecase-ов, а не на базе.

### 2. Типизированный владелец счёта вместо обобщённой аналитики

```
ledger_accounts (id, org_id, kind, cash_account_id?, client_id?, sale_id?, article_id?)
  kind = cash        → cash_account_id
       | advance     → client_id
       | receivable  → sale_id, client_id
       | income      → article_id
       | expense     → article_id
       | revenue | adjustment | opening  → без владельца, по одному на организацию
  CHECK: заполнены ровно колонки владельца своего вида
  UNIQUE NULLS NOT DISTINCT (org_id, kind, cash_account_id, client_id, sale_id, article_id)
```

FK на каждую колонку владельца сохраняют ссылочную целостность. `receivable` несёт и `client_id`,
чтобы баланс клиента считался одним `JOIN` без обхода продаж. Счета создаются лениво
(`INSERT … ON CONFLICT DO NOTHING RETURNING` + повторное чтение) в момент первой проводки.

*Альтернатива* — колонки аналитики в проводке без таблицы счетов. Отклонена: негде взять строку для
блокировки (решение 5) и нельзя выразить `CHECK` по виду.

### 3. Транзакция и проводки

```
ledger_transactions (id, org_id, kind, occurred_on, sale_id?, reverses_id? UNIQUE,
                     counterparty_employee_id?, counterparty_text?, comment?, advance_used, created_by?, created_at)
  kind = sale | sale_return | payment | payout | adjustment | income | expense | transfer | opening | reversal
ledger_postings (id, transaction_id, account_id, amount NUMERIC, article_id?)
  CHECK amount <> 0
```

- `article_id` в проводке — статья ДДС, обязательна для проводок по счёту `cash`, кроме видов
  `transfer` и `opening` (проверяется в коде и `CONSTRAINT TRIGGER`, т.к. вид счёта в другой таблице).
- Нулевая сумма по транзакции: в коде — smart constructor `LedgerEntry.of(...)` (сумма = 0, одна
  валюта, ≥ 2 проводки, кассовые проводки со статьёй); в базе — `CONSTRAINT TRIGGER … DEFERRABLE
  INITIALLY DEFERRED` на `ledger_postings`, проверяющий сумму транзакции при коммите.
- Сторно: транзакция вида `reversal` с `reverses_id`; `UNIQUE (reverses_id)` даёт «не более одного
  раза» без гонок; отмена `reversal` запрещена в коде.
- Отмена хранится только как сторно; признак «отменено» в проекциях — существование транзакции с
  `reverses_id = id`. Отдельного флага нет — нет второго источника правды.
- Валюта не хранится в проводке: она всегда валюта организации (`ctx.currency`), как в остальном коде.

### 4. Шаблоны проводок по операциям

| Операция | Проводки |
|---|---|
| Продажа на S | receivable(sale) +S · revenue −S |
| Оплата: кассы Cᵢ, аванс A, долг D | cash(i) +Cᵢ [«Поступления от клиентов»] · advance +A · receivable −min(ΣC+A, D) · advance −(ΣC+A−D)⁺ |
| Пополнение аванса | cash +C [«Поступления от клиентов»] · advance −C |
| Возврат по продаже R | revenue +R · receivable −min(R, D) · advance −(R−D)⁺ |
| Выплата с аванса | advance +X · cash −X [«Возвраты клиентам»] |
| Корректировка | advance ∓X · adjustment ±X |
| Прочий приход/расход | cash ±X [статья] · income/expense(статья) ∓X |
| Перевод | cash(to) +X · cash(from) −X |
| Ввод остатка кассы | cash +X · opening −X |

Две проводки по одному счёту аванса в оплате (+A и −переплата) сворачиваются в одну.
`ledger_transactions.advance_used` сохраняет исходную часть с аванса для истории оплаты: при
кассовой переплате её невозможно восстановить из свёрнутой проводки. Шаблоны живут в
одном месте — доменном модуле главной книги — по функции на операцию, каждая возвращает
`LedgerEntry`.

### 5. Конкурентность — блокировка строки счёта

Оплата, возврат, выплата и отмена продажи сначала блокируют строку клиента, затем счета.
Это сохраняет единый порядок при возврате с выплатой, который вызывает команду выплаты.

Проверки «аванс ≥ списания», «оплата ≤ долг», «возврат ≤ продано − возвращено», «сторно не уводит
аванс в минус» выполняются после `SELECT … FOR UPDATE` строк затронутых счетов `advance` и
`receivable` в порядке `id` (чтобы не было взаимных блокировок). Счета касс не блокируются: минус
в кассе разрешён.

### 6. Продажа — агрегат в `domain/sales`, главная книга — его следствие

```
sales      (id, org_id, client_id, sold_on, created_by, created_at,
            cancelled_at?, cancelled_by?, cancel_reason?)
sale_items (id, sale_id, kind: membership|service, name, quantity, unit_price, amount)
memberships: − price, + sale_item_id NOT NULL UNIQUE REFERENCES sale_items
```

- «Оплачено», «возвращено», «долг» не хранятся — считаются проекцией по проводкам счёта
  `receivable` и транзакциям `sale_return`.
- Отмена продажи — единственное изменение строки `sales` (`cancelled_*`), вместе со сторно всех её
  транзакций и отзывом абонементов (`Membership.revoke`, который уже отклоняет отзыв со списаниями).
- После возврата по продаже отдельная отмена оплаты запрещена: это исправление ошибочной записи,
  а не повторная выплата клиенту. Ограничение проверяется под блокировкой клиента, как и возврат;
  полная отмена продажи по-прежнему сторнирует весь документ атомарно.
- Стоимость абонемента читается из `sale_items.amount`; все проекции абонементов делают `JOIN`.
  *Альтернатива* — оставить `memberships.price` снимком. Отклонена: два источника цены.
- Выдача абонемента: usecase `IssueMembership` в одной транзакции создаёт продажу с позицией,
  абонемент со ссылкой на позицию, транзакцию продажи и необязательную оплату.
  `IssueMembershipRequest` получает `payment: PaymentInput?`.

### 7. Слои и модули

- `domain/ledger` — `LedgerEntry` (smart constructor), `Ledger` (запись, сторно, блокировка счетов),
  шаблоны операций.
- `domain/cashaccounts`, `domain/casharticles`, `domain/sales` — агрегаты справочников и продажи.
- `usecases/finance` — оплата, пополнение, выплата, корректировка, возврат (+ выплата), отмена
  продажи и операций, прочий приход/расход, перевод, выдача абонемента с продажей.
- `read/finance` — `CashJournalView`, `CashFlowReportView`, `CashAccountBalancesView`,
  `SaleDetailView`, `ClientLedgerView` (история баланса клиента с `balance_after` через оконную
  функцию). Баланс клиента в `DbClientListView`/`DbGroupRosterView`/карточке — подзапрос
  `-SUM(p.amount)` по счетам `advance` и `receivable` клиента (через `ledger_accounts.client_id`).
  Отдельно исключать отменённые продажи не нужно: сторно уже обнулило их счёт `receivable`.
- `routes/FinanceRoutes.kt` (+ `SalesRoutes.kt`); маршруты без path-переменных, id в теле/query.

### 8. ДДС — один SQL с группировкой по месяцам

Проводки по `cash` выбранных касс → `date_trunc('month', occurred_on)`, `article_id`; переводы
внутри выборки взаимно гасятся и исключаются по виду транзакции, переводы через границу выборки —
строка «Перемещения», `opening` — строка «Ввод остатков». Остаток на начало — `SUM` по тем же
кассам до начала периода. Группы статей — `LEFT JOIN cash_articles parent`.

Исходная операция и сторно входят в ДДС по собственным датам проводок. Сторно использует
статью и вид исходного движения с обратным знаком: расход октября, отменённый в ноябре,
остаётся расходом октября и уменьшает расходы ноября. Исторические остатки не пересчитываются;
остаток на конец сходится с главной книгой. При отмене внутри периода движения взаимно гасятся.

### 9. Права

`UserPermission`: `CAN_ACCEPT_PAYMENTS`, `CAN_MANAGE_FINANCE`, `CAN_VIEW_FINANCE`. Доступ к кассе:
`cash_accounts.branch_id IS NULL OR branch_id ∈ ctx.employee.availableBranches` — фильтр во всех
проекциях и проверка в usecase-ах. Продажа без оплаты прав не требует (как выдача абонемента сейчас).
`CAN_VIEW_CLIENT_BALANCE` по-прежнему открывает историю баланса клиента.

### 10. Статьи и счета организации

Системные статьи помечаются `system_code` (`client_receipts`, `client_refunds`). Создание
организации (`DbAuth` регистрации) сеет системные и начальные статьи; миграция сеет их для
существующих организаций. Счета `revenue`/`adjustment`/`opening` создаются лениво.

## Risks / Trade-offs

- [Ошибка в шаблоне проводок тихо искажает отчёты] → шаблоны в одном модуле, на каждый —
  тест с проверкой остатков всех затронутых счетов; `CONSTRAINT TRIGGER` ловит несбалансированность.
- [Знаки двойной записи путают разработчиков] → знак переворачивается только в проекциях `read/`;
  в `docs/ledger.md` — таблица шаблонов и правило знаков.
- [Баланс клиента в списке клиентов — агрегат по проводкам на каждой странице] → индекс
  `ledger_accounts (org_id, client_id)` и `ledger_postings (account_id)`; при росте — снимки
  остатков по счёту, интерфейс проекции не меняется.
- [Отмена продажи затрагивает абонемент, кассы и аванс сразу] → одна транзакция БД, блокировки
  счетов до проверок, отказ без частичных изменений.
- [Удаление всех абонементов в миграции] → данные тестовые по решению владельца; миграция
  необратима, откат — восстановление из бэкапа.
- [Оплата отрицательного аванса из корректировки] → корректировка разрешает минус, остальные
  операции требуют неотрицательного аванса; правило проверяется в одном месте `Ledger`.

## Migration Plan

1. Одна Liquibase-миграция: `DELETE FROM memberships` (каскадом история, группы, списания);
   `DROP TABLE client_balance_journal`, `DROP TYPE balance_operation_type`; `ALTER TABLE memberships
   DROP COLUMN price, ADD COLUMN sale_item_id … NOT NULL UNIQUE`; создание финансовых таблиц,
   индексов и `CONSTRAINT TRIGGER`; сев статей для существующих организаций.
2. Удаление `domain/clientbalance`, `DbClientBalanceHistoryView`, `AdjustBalanceRequest` и
   маршрутов `/clients/balance/*` в пользу новых финансовых маршрутов; `docs/client-balance.md` →
   `docs/ledger.md`.
3. Перегенерация `web/src/api/generated/`.
4. Откат: восстановление БД из бэкапа и откат релиза; обратной миграции нет.
